# iOS 版以 Capacitor 包殼，不重寫原生

> **這份的結論已被 `ADR-0017` 推翻（2026-08-24）。** iOS 版改寫成 React Native，為的是 iOS 26 的
> Liquid Glass——WKWebView 拿不到那層折射。**推翻的是結論，不是證據**：本份記載的盲測仍然成立，
> 它回答的是「像不像原生」，而 `ADR-0017` 問的是另一題「跟不跟得上 iOS 26」。本份留著不改寫，
> 是歷史。底下對 React Native 列的三個技術障礙，兩個已有現成解、一個已驗過做得出來，逐條重看見
> `ADR-0017`。

要上架 App Store 的 iOS 版與網頁版共用同一份 `src/`。現有的 web 程式碼原封不動跑在 Capacitor 的 WKWebView 裡，靠 build 參數切出兩個產物（網頁版的 `base` 是 `/va-practice/`，iOS 版是 `/`），不複製第二份設定檔，也不維護第二份畫面碼。

殼裡再補上四項網頁那一層拿不到的東西：每日複習提醒、原生日文語音、評分時的觸覺回饋、雲端備份密碼改存 Keychain；其中朗讀要說準一點——WKWebView 裡 Web Speech 本來就找得到日文語音（票 01 真機實測），走原生換到的是 enhanced 品質的語音，不是「從沒有變成有」；另外在 iOS 上多存一份**保險副本**，防的是系統清掉 WebView 那一層的資料。這四項既是使用者要的功能，也同時是通過審查準則 4.2（Minimum Functionality）的實質內容——一支只把網站裝進殼裡的 app 會被退件。

決策的完整經過見 `.scratch/ios-app/spec.md`，本 ADR 只記錄路線本身。

## 為什麼是包殼，不是重寫

**畫面層沒有框架，所以它是資產，不是包袱。** 畫面碼 2,373 行、畫面測試 1,319 行（2026-08-18 實測，行數的權威出處是 `.scratch/ios-app/spec.md` 決定一），全部是手寫的 DOM 操作。任何換掉 DOM 的路線都得把這兩批一起丟掉，換來的是同一套畫面再做一次。

**`core/lib/cloud-crypto.ts` 是這件事的下限。** 加解密必須與網頁版位元級相容——同一個人用電腦存上去的備份，手機要解得開。重寫這一段等於拿使用者已經在雲端的資料賭一次，而錯了不會當場報錯，會在某天解不開。

## Considered Options

- **Swift + SwiftUI 原生重寫**：唯一能保證每個元件都是系統原生的路，但畫面層無框架，2,373 行畫面碼與 1,319 行畫面測試全數作廢；換掉 TypeScript 之後，純邏輯與其測試也一併作廢。加上 `cloud-crypto.ts` 的位元級相容要求，這條路是資料損毀的高風險來源。

- **Flutter**：真正的從零重寫——Dart 讓純邏輯與其測試也全數作廢，不只畫面。而且它與 WebView 同類：兩者都在一塊空白畫布上自繪，不使用系統原生元件。「畫面要是原生元件」正是想離開 WebView 的動機，按這條判準 Flutter 與現況同罪。

- **React Native**：**不是**從零重寫。RN 同為 TypeScript，純邏輯與其測試可以搬過去，要重寫的只有畫面層。否決的理由不在行數，在三處接不上的地方：`localStorage` 是同步的、`AsyncStorage` 是非同步的，而 `localStorage` 是唯一真相來源（`ADR-0002`），改成非同步會傳染到每一個呼叫端；`crypto.subtle` 在 RN 上沒有對應物，`cloud-crypto.ts` 要換套件重刻並維持位元級相容；**振假名沒有對應物**——`src/ui/reading-html.ts` 現在用瀏覽器內建的 `<ruby>`／`<rt>` 六行解決，RN 的 `<Text>` 不暴露 `CTRubyAnnotation`。此選項後來以實機盲測正式否決，見 Consequences。

- **維持純 PWA，只補強現有體驗**：零風險、零審查。但它給不了上架、推播與原生語音，而這三項正是本次工程的目的。

- **讓 WebView 載入遠端網址**：Capacitor 支援讓 WebView 直接指向線上網址，等於免送審熱更新。但離線會完全失效——通勤時複習不了——而且這是準則 4.2 最典型的退件理由。內容一律打包進 app。

## Consequences

**更新節奏從「push 即上線」變成「每次送審 1–2 天」。** 這是最有感的日常代價。網頁版仍然是 push 完就是最新的；iOS 版每一次修正，哪怕是一個錯字，都要重新出包、上傳、等審查。改動一旦跨兩個平台，兩邊的版本會有幾天不一致。

**準則 4.2 的退件風險不為零。** 提醒、原生語音、Keychain、觸覺是實質內容，不是裝飾，但「夠不夠實質」由審查員裁量。被退件時能做的是補說明與補功能，不是換架構。

**`ADR-0002` 的立場不變。** localStorage 仍是唯一真相來源，所有讀寫路徑一字不改，`StorageLike` 維持同步介面。iOS 上多出來的保險副本是**唯讀的救援管道，不是第二個真相來源**：程式任何時候讀的都是 localStorage，副本只有一個用途——啟動時發現 localStorage 空白而副本有東西，才寫回去並照常啟動。

**`ADR-0003` 的立場不變。** 密碼遺失仍然無法復原。Keychain 加上 iCloud 同步降低了忘記密碼的機率，但沒有消除它——使用者可能沒開 iCloud 鑰匙圈，或整個換掉 Apple ID。因此設定雲端備份的畫面必須明說後果，並指向手動匯出這條後路。

**`ADR-0003` 的額度估算已依「多人使用」重看過一次，但重算的是單筆，不是總量。** 該 ADR 末段寫著「若日後改為多人使用，需重新計算」——公開上架就是那一刻。已經做的是單筆：安全規則的上限放寬到 4 MB（約當 27,000 張卡），客戶端在送出前先量長度、超限直接擋下並顯示人話。**沒有做的是總量**——多人加起來會不會吃爆 1 GB 儲存與 10 GB／月傳輸並未重算，而且單筆上限也擋不住有心人用大量合規的小備份慢慢塞滿。此風險經評估後**接受**，配套是 Firebase 自己那套用量警示（查證結果為本專案預設已開啟）。這個分辨同時記在 `ADR-0003` 末段的訂正裡，兩邊不要各說各話。經過見 `.scratch/ios-app/issues/03-firebase-size-limit-and-alerts.md`。

**React Native 是用實機盲測否決的，不是用推論。** 2026-08-18，維護者把 RN 原型與 Capacitor 版裝在同一支 iPhone 上，兩者的圖示、名稱、啟動畫面、配色、尺寸皆已對齊，用 Spotlight 搜尋開啟（兩列同名同圖示，擲硬幣決定點哪一列），蒙著滑完整張卡——**在做出判斷之前分不出來哪個是原生的**。

而在此之前，同一個人在知道哪台是哪台、並排比較的情況下，指得出字體與版面的差異，而且那些差異後來查出來都是真的。**同一組差異，標示著就看得見，蒙起來就消失。** 這正是「想改原生」那個動機的實測結果：它買到的是知識，不是感知。原文與完整判定見 `.scratch/rn-spike/issues/01-review-screen-spike.md` 的 `## Comments`。

順帶記錄一項這次量出來的代價：RN 的振假名要靠兩層 `<Text>` 疊字，詞條因此被拆成多個 `<Text>`，而 iOS 的長按選取只在單一個 `<Text>` 內成立——整串詞條選起來複製去查字典會做不到。網頁版的 `src/styles.css` 特地寫明不碰 `.term` 與 `.meaning`，保的正是這個功能。
