# iOS 的讀音預填改用維護者的固定金鑰，走 Firebase AI Logic 代理；網頁版維持自備金鑰

從 App Store 下載這支 app 的人，打完詞條就看到假名自己填進來，中間什麼都不必設定。讀音預填在 iOS 上不再需要使用者自備金鑰——資料畫面的「Gemini API（Application Programming Interface，應用程式介面）金鑰」整個區塊在 iOS 產物裡不渲染，也**不留「貼自己的金鑰蓋過去」這條後路**。請求不再由裝置直接打 Google，改走 Firebase AI Logic：金鑰留在 Google 的伺服器上、一個位元組都不進 app，靠 App Check 加 App Attest 證明發請求的是真的那支 app。

**網頁版一個字都不動**，仍然走 `gemini-key.ts` 那條路：使用者自備金鑰、自己貼、存在自己那台裝置、走自己的額度。網頁版掛在公開的 GitHub Pages 上，任何寫進打包產物的字串按 F12 就看得到，用 CI（Continuous Integration，持續整合）的 secret 在打包時注入也一樣——secret 只是沒進 git 歷史，照樣印進那個公開的 JS 檔。

決策的完整經過見 `.scratch/fixed-gemini-key/spec.md`，本 ADR 只記錄決定本身。

## 這份與 `ADR-0005` 的關係

`ADR-0005` 留著不改寫，它是歷史；由這一份指回去。它的前提有些原封不動，有些換掉了。

**還在的：**

- **這個功能永遠是選配的。** 離線、超額、模型掛掉、回覆過不了驗證，一律降級成手動填，**絕不擋住儲存**。這條保底路徑一字未改，而且因為額度改成大家共用，它被踩到的機會比從前多。
- **金鑰刻意不進 `AppData`。** 網頁版照舊存在自己的抽屜裡，不上雲、不進匯出檔；iOS 上則根本沒有金鑰這個東西可以存。因此 `ADR-0003` 那句「若日後要放入任何敏感資料，這個前提必須重新評估」**仍然沒有被觸發**。
- **「端點寫死單一模型而非 `-latest` 別名」的精神。** 見 Consequences 裡 Remote Config 那一段。

**換掉的：**

- 「需要使用者自備的金鑰，沒設定時連請求都不發」——**iOS 上不再成立**。什麼都不設定就會發請求。
- 「代價是金鑰不跨裝置，每台各設定一次」——iOS 上不再是代價，換成一個新的代價：**共用額度**。
- 「不經過任何第三方伺服器」——**iOS 上請求先經過維護者的 Firebase 專案**，才由 Google 加上金鑰轉給模型。
- 「專案對外部服務的依賴又多了一項」——現在是三項：Firebase RTDB（Realtime Database，即時資料庫；雲端備份）、Firebase AI Logic（讀音預填）、Firebase Remote Config（模型名字與提示詞）。三項共用同一個 Firebase 專案。

## Considered Options

- **硬把金鑰塞進 ipa**：最省事，但那只是換個地方公開——ipa 拆包就找得到，金鑰照樣會被拿去打光額度；而且要換一把金鑰得重新打包送審，等一到兩天。它連「藏起來」這件事都沒做到，只做到「藏得比較不明顯」。

- **自己寫一支 Cloud Function 當代理**：打包產物不會胖，控制權也最完整。否決的理由是 Cloud Functions 需要 Blaze 方案，**等於現在就得綁卡**，直接牴觸「不開計費」那條決定；此外 App Check 的驗證要自己寫、伺服器要自己維護。用 Firebase AI Logic 換到的正是這些都不必做。

- **網頁版也吃固定金鑰**：兩個平台一套程式碼，最乾淨。做不到的原因是網頁版是公開的靜態網站，沒有「伺服器端」可以藏東西；改走 Firebase AI Logic 也擋不住——web 的 App Check 只有 reCAPTCHA 可選，而 reCAPTCHA 擋機器人、擋不住看得到原始碼的人照著發請求。Google 還會主動掃 GitHub 上外洩的 API 金鑰並停用，那會連帶把 iOS 那條路一起弄壞。

- **維持現狀，iOS 也要使用者自備金鑰**：零工程、零額度風險。否決的理由是它讓這個功能對絕大多數人等於不存在——一個從 App Store 下載 app 的人，不會為了幫漢字標假名跑去 Google AI Studio 申請一把 API 金鑰。`ADR-0005` 寫的「每台裝置各設定一次」在手機上尤其麻煩，要在小鍵盤上貼一串長字元。

## 這條路是用真機驗過的，不是推論

App Attest 是 Apple 的原生 API，模擬器一律回「不支援」，因此整條路能不能走通只有 TestFlight 加一支真 iPhone 答得出來。2026-08-20 驗完：原生層跟 Apple 換到的權杖，經 `CustomProvider` 交給 WebView 裡的 JS SDK（JavaScript Software Development Kit，JavaScript 軟體開發套件），Google 那端認得也接受（App Check 指標「已驗證的要求」不是零；沒帶權杖的對照組被 401 擋下）。經過見 `.scratch/fixed-gemini-key/issues/01-app-attest-spike.md`。

過程中量到的一件事值得記在決策層：**provider factory 必須搶在 `FirebaseApp.configure()` 之前指定**，否則 App Check 會用出廠預設的 DeviceCheck 把自己建好，之後再指定也換不回來。`ios/App/App/AppDelegate.swift` 那十行 Swift 因此不是探路程式碼，是這條路成立的前提。

## Consequences

**app 越受歡迎，讀音預填越常罷工。** 免費額度是**按專案**算的一桶共用的水（Google 官方文件：「Rate limits are applied per project, not per API key」），不是每人一桶。一百個人同時新增卡片那天，一百個人一起沒讀音，而且誰都沒辦法自救——因為 iOS 上不留自備金鑰的後路，也不開計費。這是「給任何人用」「不留自備金鑰的後路」「不綁卡」三者相乘的必然結果，**是知情選擇，不是疏漏**。見底時畫面上是一句不需要任何背景知識的話——「自動填讀音失敗：暫時無法使用，稍後再試」，其中後半截是 `gemini.quotaExhausted` 代進去的成因；程式裡誠實記錄，畫面上刻意不提額度也不提狀態碼。儲存照常。

**`ADR-0005` 那個沒有第二道防線的風險被放大了。** 「整串讀音幻覺」——模型很有自信地說 `吹雪` 唸 `すいせつ`——不會報錯，要等複習翻面才發現，還會一路存進雲端備份。原本這只會發生在自己申請金鑰、知道自己開了什麼的人身上；現在**每個下載的人第一張卡就可能中**。防線仍然只有三道：填進格子而非直接存檔、一行「讀音由 AI 填入，請確認」的提示、預覽。本次一道都沒有加強，連那行提示的文字都沒改，因此這個放大了的風險是**原樣接受**的，不是被緩解過的。下次要動它，起點是「AI 可能填錯」與「儲存前」這兩句話從來沒有寫進 `editor.noteFilled`。

**本決定不沿用「密碼跟著走，同意不跟著走」那條判例。** `.scratch/ios-app/issues/14` 立過那條規矩，理由是掌控感。讀音預填**不問使用者、不加開關**，第一次打完詞條就發請求。連帶兩個後果：不在乎這個功能的人也會消耗共用額度；而 `ADR-0005` 那句「送出去的內容是日文單字，可接受」的正當性換了主體——原本是使用者自己申請金鑰、自己接受 Google 的條款，現在是維護者替他決定的。這一點寫進了隱私權政策。理由與代價見 `.scratch/fixed-gemini-key/spec.md` 決定十。

**Remote Config 不牴觸「拒絕 `-latest` 別名」那條。** `ADR-0005` 那句話的重點在「**無預警**」——它寫的是「端點寫死單一模型而非 `-latest` 別名，是為了讓『模型換人』以錯誤的形式暴露出來，而不是讓同一個詞的讀音無預警改答案」。它拒絕的是無預警，不是不能換。差別在方向盤在誰手上：`-latest` 是 Google 想換就換、你不知道；Remote Config 是維護者自己按按鈕才換。之所以非搬上去不可，是因為固定金鑰把「模型下架」的修復成本從幾分鐘拉到幾天：`ADR-0005` 記錄過 `gemini-2.5-flash` 對新金鑰關閉、且型錄查不出來的事故，在自備金鑰下那是零星使用者踩到、改個字串 push 上去；在固定金鑰加 iOS 下，那是所有人同時停擺、等一輪送審，而使用者沒有自救途徑。兩個代價據實記錄。**一、不是「立刻生效」**：發布在 Google 那端是即時的，但裝置要等下一次抓取才看得到，本專案把間隔設成一小時（SDK 預設 12 小時，太久）——實務上仍是「幾小時」對「一到兩天」。**二、程式碼裡的 `gemini-3.6-flash` 這個字串不會消失**，只是身分從「唯一答案」變成「連不上時的後備」。

**App Check 拿不到憑證時完全靜默，讀音格留空。** 與網頁版「沒設金鑰就什麼都不發生」一致。不出錯誤提示——那條錯誤使用者一點辦法都沒有，看了只會焦慮。**代價是維護者收不到任何回報**：外掛載不起來、`GoogleService-Info.plist` 沒被打包這類問題，會安靜地什麼都不發生。這與「額度見底要給一句交代」不衝突，兩者的差別在使用者知不知道有這個功能：App Check 失敗時他從頭到尾沒看過讀音自己填好，靜默不會讓他困惑；額度見底時他看過，這次沒填就得給一句話。

**Firebase 專案沿用雲端備份那一個，不新開。** 理由不是省事：一支 iOS app 的原生層只吃一份 `GoogleService-Info.plist`，接第二個專案要手動開第二個 app instance，Capacitor 外掛不一定支援。代價據實記錄——**日後若升級 Blaze，是整個專案一起升**，雲端備份那個 RTDB 也會從免費額度變成按用量計費。另外，`GoogleService-Info.plist` 進版控：裡面那把 Firebase 金鑰**設計上就是公開的**，靠 App Check 與安全規則擋、不靠保密，跟本決定在保護的 Gemini 金鑰是完全不同的東西。

**升級 Blaze 是一條隨時可走、不必送審的退路，但那是單向門。** 在主控台按一下就生效，客戶端一行程式碼都不用改。走之前要知道四件事：免費層**整個消失**，每個呼叫從第一個 token 起計費；**帳單沒有上限，而且無法設上限**——Google Cloud 的預算警示只寄信、不停服務，唯一的硬性封頂是自己寫一支 Cloud Function 監聽預算通知去關掉計費；整個 Firebase 專案一起升；App Check 的價值會從「省額度」變成「省錢」，被濫用直接等於帳單。因此那是一張未來的票，不是隨手按的開關。

**更新節奏的代價比 `ADR-0015` 記的又深一層。** 那份寫的是「每次送審 1–2 天」；固定金鑰讓這件事從「維護者的麻煩」變成「所有使用者一起停擺」，因為 iOS 使用者沒有任何自救途徑。Remote Config 就是為了把最可能發生的那兩種停擺（模型換人、判準出包）搬出送審流程之外，但它只蓋得住這兩種。
