# 畫面測試不上真瀏覽器：jsdom 只寫非 DOM 不可的行為

畫面**不做真瀏覽器的端對端測試**（Playwright、Cypress 那一類）。

畫面**可以在 jsdom 上測，但只寫那些非 DOM 不可的行為**：焦點落在誰身上、鍵盤與指標事件的接線、元素的先後順序、事件接上了沒有。**不斷言版面、不斷言 class 名、不做 DOM 快照。**

開 jsdom 的方式是檔頭一行 `// @vitest-environment jsdom`，`vite.config.ts` 的 `environment: 'node'` 維持預設值。`src/ui/` 之中不碰 DOM 的純函式照常在 node 環境直接跑。

## 為什麼

**這條界線是翻案來的。** 這一節原本明文禁止畫面的自動化測試，理由是「以此工具的規模，瀏覽器層級測試的維護成本高於其所能攔截的缺陷」，而且點名了 jsdom 這類假瀏覽器。

翻案的起點是 `editor-view.ts` 的失焦換欄（`.scratch/focus-target-tests/issues/01-jsdom-focus-target.md`）。那段邏輯把「焦點落到誰身上」翻成「要不要把使用者搶回空的必填格」，而 `relatedTarget` 是一個 DOM 物件，翻不成序號，也搬不進模組——它非 DOM 不可。它擋下的是使用者看得見的壞掉：新增卡片時釋義必定是空的，一碰讀音區就被彈走，讀音永遠改不成。

實作那張票時撞到的一件事，說明這類測試不是把 `if` 用另一種語法再抄一遍。驗收原本寫「焦點停在讀音格」，照字面用 `document.activeElement` 斷言；把 production 的兩個 `if` 都拔掉重跑，七條測試**全部照樣綠**。原因是 `focus()` 的順序——先發 blur、等處理器跑完，才把新目標設成 `activeElement`，中途搶回來的那一下被後面這步蓋掉。改成斷言「這一趟裡拿到 `focus` 事件的元素依序有誰」才真的紅。能踩到這種坑，本身就是「非 DOM 不可」的證據。

後來走上同一條路的還有 `book-filter.ts` 的選單開關（Esc 與點外面收合）、`data-view.ts` 各段的順序與語言選單、`app.ts` 從 `start()` 開機驗一次「換語言之後當前畫面立刻重畫」，以及三語冒煙測試。目前跑在 jsdom 上的檔案有七個。

**否決窄例外的原因就在這個數字。** 原本設想的形狀是「唯一例外：`editor-view.ts`」，在寫進文件之前就已經不只一個。例外清單會長大，而且清單不會告訴你第八個該不該准。規則自己說得出准與不准，才不必養那份清單。

## Considered Options

- **維持原判，畫面一律不測**：省一條 devDependency，那幾個 `if` 全靠註解與真機。否決的原因是落點分類 jsdom 真的抓得住，抓的是使用者看得見的行為，不是實作細節。
- **保留原規則，補一張例外清單**：門檻仍然很高，下一個想寫畫面測試的人得先證明自己也在例外裡。否決的原因見上——例外從一個變成七個檔案。
- **整個專案改成 `environment: 'jsdom'`**：寫測試時不必想檔頭。否決的原因是「模組不得 import DOM」的執法會從「違反了測試就爆」降成「大家要記得」。
- **`vite.config.ts` 加 glob 搭配 `*.dom.test.ts` 命名約定**：達成同樣的隔離。否決的原因是檔頭 docblock 效果相同，少一份設定與一條命名約定，而且「這個檔案要 jsdom」寫在檔案自己頭上，讀 code 的人不必翻設定檔對照。

## Consequences

**測不到的東西沒有變少，只是換了地方講。** iPhone 鍵盤開著時點「取消」（blur 先於 touchend）、桌機的 Tab 順序、版面被撐爆——jsdom 一概演不出來，仍然只能實機驗收。手動驗收清單不會因為這條界線而縮短。

**「非 DOM 不可」需要當場判斷，比「一律不准」難執行。** 寫測試的人得先問一句「這件事離開 DOM 還成不成立」。成立的話它屬於模組，該在 node 環境測，不是把它拖進 jsdom。

**不斷言版面是硬規則，不是建議。** class 名與快照會在每次微調時無辜變紅，然後被人習慣性地改掉——那種測試比沒有測試更糟，因為它訓練人忽略紅燈。版面對不對只有實機看得出來。

**`environment: 'node'` 是預設值這件事有執法作用。** 模組一旦 import DOM，測試立刻爆。改動那個預設值等於拆掉這道自動檢查，不要為了少寫一行檔頭而動它。
