# 雲端備份採用 Firebase Realtime Database 加安全規則，不自建後端

跨裝置的進度搬運需要一個裝置以外的儲存位置。選定 Firebase Realtime Database，以 `fetch` 呼叫其 REST 介面，不安裝 Firebase SDK，也不撰寫任何後端程式碼。存取控制完全交給資料庫的安全規則：路徑上存著一份由密碼派生的指紋，規則要求寫入必須帶對指紋，否則連刪除都不允許。資料本身在上傳前以密碼派生的金鑰加密，因此規則層放行的「任何人可讀」也讀不出內容。

這個組合是唯一同時滿足三個約束的方案：不必維護後端服務、不必綁定信用卡、而且密碼是真的擋得住人的——不是只在前端做做樣子。前兩點是專案體質的要求（單人自用的純前端工具，托管在 GitHub Pages），第三點則是因為原始碼公開，任何「靠地址沒人知道」的保護都不成立。

## Considered Options

- **不做雲端備份，只優化現有的匯出／匯入**：零成本、零風險，也最符合這個工具的體積。但手動搬檔案的摩擦正是要解決的問題，優化它並不能讓進度「自己跟著走」。保留匯出匯入作為後路，但它不能取代本功能。

- **Cloud Run + Cloud Storage**：保護力最強、額度最大，一度定案。放棄的原因是它就是一個要寫、要部署、要維護的後端服務，且必須綁定 GCP 帳單帳戶。對一個單人自用的閃卡工具，維護一個後端服務的長期成本不成比例。

- **Cloud Storage bucket 開放公開寫入**：純前端、零後端程式碼。但專案開源、bucket 名稱寫在公開的原始碼裡，等於把倉庫鑰匙貼在門口——任何人都能塞檔案、覆蓋任何人的進度，而帳單由專案擁有者支付。不是理論風險。

- **Cloudflare Workers + Workers KV**：同樣免信用卡，但仍需撰寫並部署一個 Worker（即後端），且免費額度為每日 1,000 次寫入。本功能採「每答完一張卡就推送一次」，與這個上限距離太近，沒有安全邊際。

- **免註冊的第三方 JSON 儲存服務**：門檻最低，但這類服務隨時可能關站或限流，且多半只回傳隨機識別碼，無法用暱稱直接定位資料，還得再維護一份「暱稱對應識別碼」的目錄——那份目錄本身又會有並發覆寫的問題。

- **Google Drive 的應用程式私有資料夾**：資料存在使用者自己的雲端硬碟，免維運。但需要 OAuth 設定，且未送審前的測試模式登入狀態約七天就要重新授權，與「快速認人」的訴求直接衝突。

## Consequences

**保護的邊界必須說清楚。** 規則擋的是「寫」，不是「讀」——任何人都能讀走任一筆資料，只是讀到的是密文。這在此情境可接受（內容是日文單字的複習進度），但若日後要放入任何敏感資料，這個前提必須重新評估。

**密碼遺失即無法復原。** 沒有伺服器可以重設密碼，密碼同時是解密金鑰。雲端那份會永久無法讀取，本機那份與手動匯出的 JSON 是僅有的後路。

**換密碼會使其他裝置立即失效。** 密碼身兼指紋與金鑰，換過之後，仍記著舊密碼的裝置既無法寫入也無法解密，必須各自重新輸入。這是機制的必然結果，只能在介面上說明，無法在設計上消除。

**`ADR-0002` 的立場不變，但邊界要重申。** localStorage 仍是唯一的資料來源；雲端只是備份的搬運帶，不是第二個真相來源。因此雲端備份不放進 `src/lib/storage.ts`——該模組註解中「日後若改接雲端服務，僅需替換此模組內部」所設想的情況並未發生。

**專案不再是完全的純前端。** 沒有自建後端，但已依賴一個外部服務。離線仍可完整複習（決定 13），然而「換裝置能接上進度」這件事從此取決於 Firebase 的可用性與政策。手動匯出備份因此不能移除。

**額度目前有充裕餘裕，但不是無限。** 內建牌組 10.4 KB / 132 張，加密後每次推送約 20 KB；以每日 50 張的複習量估算約 1 MB／日、30 MB／月，遠低於免費方案的 10 GB／月傳輸與 1 GB 儲存。若日後改為多人使用，或牌組大幅成長，需重新計算。

> **訂正（2026-08-18，票 `ios-app/03`）**：「改為多人使用」這個條件已經觸發——iOS 版上架就是那一刻。但**重算的是單筆，不是總量**，兩者不要混為一談。
>
> 已經做的：以本段自己的數字反推出每張卡加密後約 155 bytes，據此把安全規則的單筆上限訂在 `4194304`（4 MB，約當 27,000 張卡），並在 `cloud-backup.ts` 送出前先量長度、超限直接擋下，一個請求都不發。
>
> **沒有做的：多人加總會不會吃爆 1 GB 儲存與 10 GB／月傳輸，並未重算。** 單筆上限防的是單一路徑一次吃掉大量額度與程式異常膨脹，它**不防**有心人建立大量合規的小備份把額度慢慢塞滿——本 ADR 選定的方案在免費方案上沒有速率限制能力。此風險經評估後**接受**，配套是 Firebase 自己那套用量警示（查證結果為本專案預設已開啟）。
>
