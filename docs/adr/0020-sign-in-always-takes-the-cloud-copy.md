# 登入一律以雲端那份為準，不比新舊

`signIn()` 原本與 `begin()` 走同一條規則——比 `updatedAt`，較新的那一份整份勝出。但本機那格時間戳是**上一次推給某個暱稱時，那台伺服器蓋的**，而資料裡沒有任何一格記著那是誰。換一個暱稱登入時，兩個屬於不同人的數字照樣被拿來比，本機贏了就整份 PUT 上去，把對方現有的雲端備份蓋掉且救不回來（`.scratch/cloud-backup/issues/05`）。因此登入不再比新舊：**雲端已經有備份就一律以雲端那份為準，本機那份整份被它取代**；只有在雲端還空著時才寫得進去，而那時沒有東西可以被蓋掉。行為的完整規則與實作範圍在 `.scratch/cloud-backup/issues/06`。

## Considered Options

- **在資料裡記住血統**：`AppData` 多一格「上次推給哪個暱稱」，時間戳只在同一個暱稱之內比較。最貼近病灶，也保住「離線改過、重新登入同暱稱就推上去」那條路。但光有血統不夠——`updatedAt` 只在推成功時才動，離線改的東西不留痕跡，因此還要第二格「推上去之後改過沒有」，加上一段舊資料遷移，以及兩版存檔路徑各接一次。
- **登入時若會覆蓋就跳一次確認**：改動最小。但它的觸發條件（本機比較新、雲端那個暱稱已經有東西）**抓不住跨暱稱**——同一個暱稱離線改過再登入回來，條件一樣成立，確認框會照跳。要只在跨暱稱時跳，仍然得先有上面那格血統。兩條其實是綁在一起的，不是二選一。
- **換暱稱登入時清空本機**：乾淨，不必比任何東西。但它把「這台的資料還在不在」變成登入的副作用，使用者沒有機會反悔。

三條都被同一件事淘汰：它們都在「保住本機那份有機會上雲端」與「不准蓋掉別人那份」之間找平衡，而那個平衡需要程式知道本機這份屬於誰。放棄前者之後，後者不必知道也成立。

## Consequences

**離線改過的東西不能靠重新登入帶上雲端。** 停止備份之後改了卡，再登入回同一個暱稱，雲端那份會蓋掉本機那份。確認框因此必須指出退路：先取消，到資料頁匯出備份檔，登入之後再匯回來。這是本決定唯一真正拿掉的能力。

**平常那條路不受影響。** 登入著的時候每一次改動都會自動推上去（`push()`），開 app 時雲端較新就整份拉下來（`begin()`）。`CONTEXT.md` 的「較新的那一份整份勝出」在這兩條上仍然成立，登入是唯一的例外。

**密碼錯的時候更早被擋下。** 原本只有「雲端較新」那條路會先解密，「本機較新」那條是送出去被安全規則擋在 401。現在一律先解密，兩條路的行為一致。

**`AppData` 一個字不動，沒有資料遷移**，`ADR-0002` 的立場不受影響。
