# 內建牌組退場，第一次打開 app 是空的

原本 `src/data/cards.json` 隨程式一起發佈，首次啟動整份複製進 localStorage，此後每次啟動再做一次單向合併：把 `cards.json` 裡本機尚未存在的詞條補進去，已存在的一律不動（見 ADR-0002）。

引入單字本之後，這個機制沒有安身之處。每張卡都必須剛好屬於一本，那 `cards.json` 裡的卡該進哪一本？如果程式替它建一本，那本的名字是程式取的、使用者刪掉之後下次啟動又會被單向合併重新塞回來——「刪掉」變成一句空話。要讓它不重新塞回來，就得記住「使用者刪過這本」，於是又是一組只為了這件事存在的狀態。

## 決定

**整套拿掉。** 刪除 `src/data/cards.json`、單向合併邏輯、以及記錄「哪些內建卡已經來過」的 `knownBuiltinIds`。資料存取模組不再需要「內建牌組」這個建構參數。第一次打開 app 看到的是零本零卡加上一個「新增單字本」的入口；卡片只有兩種來源——使用者自己新增，或用「匯入單字」把一份備份檔的卡整批帶進指定的一本。

既有使用者的資料不受影響：升級後打開 app，原本的卡會自動被收進一本名為「我的單字」的單字本，進度完整保留，那本可以改名也可以刪掉。

## Considered Options

- **保留為「可選匯入」**：`cards.json` 繼續隨程式發佈，但不自動塞進去，改成資料頁上一顆「匯入內建牌組」按鈕。保住了「新裝置想要那 132 張時拿得到」，也避開了刪不掉的問題。否決的理由是它為了一個一次性的動作，長期背著一份資料檔與一條只有第一天會用到的程式路徑；而同樣的事情用「匯入單字」加一份備份檔就做得到，不需要專屬機制。這副牌組是使用者自己的資料，本來就該待在他自己的備份裡。
- **維持自動塞入**：`cards.json` 照舊，只是額外決定它進哪一本。否決的理由就是上面那個死結——使用者刪不掉程式硬塞的東西，除非再長出一組「刪過了別再塞」的記憶。而這個 app 的內建牌組實際上早就不再更新了，機制留著只剩下維護成本。

## Consequences

**要回頭的成本很高。** 刪掉的不只是一個 JSON 檔——單向合併、`knownBuiltinIds`、以及圍繞它們的那批測試都一併沒了。日後若想恢復「隨程式發佈一批卡」，得連同「它進哪一本」「使用者刪掉之後怎麼辦」一起重新設計，那是新的一輪決策，不是把檔案加回來就好。判斷是不會回頭：這個 app 是單人自用工具，發佈端沒有內容要推給使用者。

**新裝置不再開箱即用。** 換手機打開只會看到空狀態，得先匯入備份或匯入單字。換來的是兩件事：資料模型裡不再有「內建卡」與「使用者的卡」之分（其實 ADR-0002 當初就是為了消滅這個區別而做的，如今連來源都沒了，區別自然消失）；以及**發佈新版本不會再偷改使用者的資料**——過去每次啟動都可能因為 `cards.json` 更新而多出幾張卡，現在只有使用者自己的動作會改變自己的資料。

**ADR-0002 的後半段就此作廢。** 該 ADR 的「localStorage 為唯一來源」仍然成立且仍是現況，但它描述的 `cards.json` 與單向合併已不存在，該檔開頭已標示被本 ADR 取代。
