# 介面多語言：一語一檔、語意 key、語言屬於裝置不屬於資料

介面支援繁體中文、英文、日文三種語言，加一個跟隨裝置的「系統預設」。四項架構決定：

- **翻譯檔一語一檔**（`src/i18n/{zh-Hant,en,ja}.ts`），漏譯由 TypeScript 型別在建置時擋下
- **key 用語意命名**（`books.addButton`），不用中文原文當 key
- **錯誤物件帶 key，不帶文字**（`throw new AppError('book.scopeEmpty')`），畫面層拿到 key 才查表
- **語言選擇存在 `va-practice:lang`，不進備份**，`DATA_VERSION` 維持 3

實作細節與逐條決定見 `.scratch/i18n/spec.md`。

## 界線：這是介面語言，不是學習內容的語言

`CONTEXT.md:22` 定義卡片是「一個**日文**詞條與其中文釋義的配對」，而振假名（讀音標記）是日文獨有的機制。**本 ADR 不動搖這條定義。**

介面多語言改變的只有「app 用什麼語言跟使用者說話」。支援英文或韓文的單字卡是另一回事——那會動到領域模型的根：詞條不再必然是日文、讀音格的概念在非日文語境下不存在、`ADR-0009`（讀音必填）的前提會消失。那件事若真要做，需要它自己的 ADR。

這一段是為了關掉 `.scratch/app-name/issues/02-rename.md` 記下的遺留缺口：「多語言這個方向在 repo 裡沒有 ADR，`CONTEXT.md` 的領域定義至今仍是日文專用」。**定義維持日文專用是對的，因為介面多語言不需要動它。**

## 為什麼語言不進備份

這是本 ADR 最容易被反過來改的一條，所以理由要留下來。

**表面上它跟三組範圍選擇很像。** `CONTEXT.md:18` 說複習範圍／列表範圍／統計範圍「都隨資料備份到雲端」，`:110` 進一步說「在手機上設好的複習範圍，電腦打開也是同一組」。照這個邏輯，語言好像也該跟著走。

**但備份是整份覆蓋，不是逐欄同步。** 語言若進備份，四台裝置就被綁成同一個語言——公司電腦想用英文、家裡 iPad 想用中文，做不到，而且是「誰最後開 app 誰的語言蓋掉其他台」。範圍選擇綁在一起是使用者要的（複習進度本來就該一致），語言不是。

這個 app 的設定**本來就分兩類**，語言歸的是既有的那一類：

| 進備份（`va-practice:data`） | 不進備份（各自獨立的鍵） |
| --- | --- |
| 三組範圍選擇 | `va-practice:reminder` 提醒開關 |
| | `va-practice:reminder-time` 提醒時間 |
| | `va-practice:gemini` Gemini 金鑰 |
| | **`va-practice:lang` 介面語言** ← 本 ADR |

判準是**這是「你的東西」還是「這台機器的東西」**。提醒時間、金鑰、語言都屬後者。

第二層理由是格式債。`DATA_VERSION` 一旦升到 4，這個世界上就開始存在「帶語言欄位的備份檔」，`parseAppData()` 從此得永遠認得那個欄位。而它換到的好處——換裝置不用重選——在預設值是「系統預設」的前提下本來就很小：新裝置一裝上語言通常就已經對了。

**好處是暫時的，格式債是永久的。** 若日後雲端備份真的改成第三方登入，語言的歸宿會是帳號；從獨立 localStorage 搬到帳號是改一處，從備份格式裡搬出來則要再升一次版。

## Considered Options

**一個字串多語並排（單檔約 193 組，每組底下各語）。** 優勢是改文案時各語同時在眼前、哪個格子沒填一目了然。但「沒填」這件事已經被 TypeScript 型別在建置時擋掉，優勢剩一半；代價是單檔數百行，而且 iOS 的 `.strings` 本來就是一語一檔，日後若走 `.scratch/swiftui-spike/` 那條路要先拆開才能搬。

這個選擇後來立刻有了回報：釘規格途中砍掉韓文（見下）時，一語一檔的動作是刪一個檔案、其餘兩支不動；並排那種寫法要逐條刪一欄。

**中文原文當 key（`t('新增單字本')`）。** 讀 code 時畫面上的字直接在眼前，不用跳檔。否決的理由是兩個具體後果：中文改一個字，其餘翻譯檔的 key 加上 code 全要跟著改；以及同一句中文在不同語境被綁死同一個翻譯——「刪除」既是按鈕也是確認對話標題，英文一個要 `Delete` 一個要 `Delete book?`。

**錯誤維持字串，只把來源從寫死改成查表**（`throw new Error(t('book.scopeEmpty'))`，測試斷言 `zhHant['book.scopeEmpty']`）。成本低很多，也一樣解掉「改文案就假紅燈」。否決的理由是錯誤物件本身仍綁著某一個語言的文字——語言在錯誤產生的那一刻就被凍住了，而錯誤可能在切換語言之後才被顯示。帶 key 的物件從頭到尾與語言無關。

**測試固定跑中文、維持斷言中文字面值。** 那 22 處 `toThrow` 一個字都不用改。否決的理由是它與三語冒煙測試直接衝突，而且中文文案改一個字就假紅燈——那是在教人忽略紅燈。

**三語譯名寫回 `CONTEXT.md` 的條目裡。** 沒有第二份檔可以漂移，改定義時譯名就在眼前。選獨立 `docs/glossary.md` 換到的是「三語並排好查、日後原生版可整份搬走」，代價是要靠一支守門測試釘住兩邊條目一致，而那支測試抓不到「譯名寫錯」與「定義改了譯名沒跟」。

**分辨繁簡，簡體中文歸為「不符合」而套英文。** 否決的理由是規則不對稱——中文要額外維護一張白名單（`zh-TW`／`zh-HK`／`zh-Hant`），另外兩語卻只要看主碼。而且繁簡差在字形與部分用詞，簡中使用者讀繁中的門檻遠低於讀英文。

## Consequences

**25 處 `throw new Error` 加上每一個接住錯誤的畫面層都要改。** 這是本 ADR 唯一動到架構的部分。`storage.ts:61` 的註解「壞掉時的訊息可以直接顯示給使用者」在改完之後不再成立——畫面層必須先查表。`toMessage()`（`storage.ts:367`）的角色也要跟著重新定義。

**`CONTEXT.md` 被動到一處：釋義的 `_Avoid_` 拿掉「意思」。** 理由是英文的 `Meaning` 正好等於那個被避開的詞，而「意思」屬於「只是比較鬆散的同義詞」這一類——沒有第二個東西可以混淆、也不會誤導，不值得為它把英文扭成 `Gloss`。逐條理由見 `.scratch/i18n/spec.md` 決定一。**除此之外 29 則的定義段落一個字都沒改。**

順帶記下一個已知缺口：這 29 則的 `_Avoid_` 全是 AI 產生的，維護者不清楚各項在避什麼，因此清單裡可能還有其他多餘或寫錯的項目。整份重審尚未開票。

**`CONTEXT.md` 與 `docs/glossary.md` 之間會有三種漂移，測試只擋得住一種。** 擋得住的是「條目多了或少了」；擋不住的是譯名寫錯、定義改了譯名沒跟、`_Avoid_` 更新了譯名沒跟。後三種只能靠人，而第一種正是最容易發生的那種，所以這支測試仍然值得。

**韓文在釘規格途中被砍掉，需求從四語變三語。** 唯一的理由是**沒有人驗得了韓文**——維護者能驗中英日，韓文沒人看得懂，而 agent 產得出韓文卻沒有任何驗收條件擋得住翻錯（型別只看 key 齊不齊、冒煙測試只看有沒有漏出 key，兩者都不判斷文字對不對）。韓文還多一層風險：敬語階層用錯的觀感傷害比語氣問題大得多，且看不出來。

被否決的是「付費請母語者校對一次」（約 3900 字是有界的一次性支出，最乾淨，只是這輪不走）、「照出不校對、靠回報修」（看到敬語錯亂的人不會回報，只會刪掉）、「標示為機器翻譯」。

**這不是永久決定，恢復成本很小**：加回 `src/i18n/ko.ts`、`glossary.md` 補一欄、主碼比對表加一列、選單加一個選項。韓文譯名初稿留在 `.scratch/i18n/issues/01-glossary.md` 的紀錄裡。**韓國市場沒有跟著砍**——韓國 storefront 照樣上架，韓文裝置的介面落到英文，砍的是介面語言不是市場。

**語言在四台裝置之間不同步，這是刻意的。** 使用者換新裝置若刻意選過非系統語言，要重選一次。日後若有人回報「為什麼我的語言沒跟著同步」，答案是本 ADR，不是 bug。

**`ADR-0012` 的守門範圍要擴張。** `privacy.html` 出中英兩份之後，`app-name.test.ts` 那四條嵌著中文上下文的 regex 對英文版全部失效，要改成用 `data-app-name` 屬性標記、測試抓屬性。這不是換做法，是讓同一套守門也管得到翻譯版；順帶解掉現在「改個換行就紅燈」的脆弱。

**PWA manifest 從此是英文的。** `vite.config.ts` 的 `description` 與 `lang` 改成英文與 `en`。中文使用者在網頁版的「加到主畫面」提示會看到英文描述。iOS 上架版走 `Info.plist` 不受影響。

**`APP_NAME` 仍是單一字串，沒有多語言化。** 這是刻意的，理由見 `.scratch/app-name/issues/02-rename.md`：拉丁字母的名字三語通用，中文名字會讓英文使用者的主畫面出現看不懂的字。若日後決定名稱也要跟著切，`ADR-0012` 與 `app-name.test.ts` 那整套要重做，而且 iOS 端要加 `InfoPlist.strings`。

**日文介面與日文學習內容的視覺衝突尚未解決。** 這是已知的開放項，`.scratch/i18n/issues/08` 是那張驗證票。若英日翻譯完成後沒人執行它，實質結果等於「接受、不處理」。
