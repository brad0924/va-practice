# 複習畫面的標題列放一顆單字本開關，推翻「複習畫面不放任何開關」

複習畫面的標題列中央放一顆單字本下拉，改的是**複習範圍**那一組。資料頁單字本區每一列的勾選框**保留**——同一組設定刻意有兩個入口。

連帶訂下第二條：**佇列重建時保留正在看的那張**。複習範圍內的卡片集合一有變動就重建佇列，但正在看的那張若仍在新集合裡且仍然到期，就留在隊首、答案維持掀開。這條規則對**所有**入口一律適用，不替複習畫面開特例。

## 為什麼

**這件事當初是明文否決的。** `.scratch/vocabulary-books/spec.md:223`：

> **複習畫面上放單字本開關**：被否決。使用者選擇維持複習畫面乾淨，複習範圍改到資料頁設定。

同一份 spec 的第 150 行（「複習畫面：不放任何單字本開關，頂部列維持『剩餘 N 張』與『卡片』」）是這個決定的另一道護欄。那兩行**保留原樣不改**，沿用 `docs/agents/issue-tracker.md:12`（實作完成後檔案保留不刪，決策紀錄與 commit 訊息互為對照）背後的同一條理由：`.scratch/` 底下的東西是「當時這麼決定」的紀錄，改掉就看不出曾經另有判斷。訂正的落點就是這張 ADR。

改主意的理由是那次的代價後來才顯出來：「答題時視線裡不放多餘的東西」換到的乾淨，代價是**每次切本都得離開複習畫面**——資料頁 → 單字本區 → 勾選 → 走回複習畫面，四步。而練到一半想換一本，正是這個 app 最常見的動作之一。

重新衡量之後，兩邊並不對等。開關在**標題列**、不在答題區中央，跟「剩餘 N 張」與「卡片」按鈕排在同一條線上；答題時視線落在畫面中央的詞條上，標題列本來就在視野邊緣。對「視線乾淨」的破壞有限，換回來的是一步到位。

**保留正在看的那張**是這個決定的必要配件。開關就在眼前，切換變成隨手的動作，若每切一次就把手上這張連同已掀開的答案一起洗掉，這顆開關反而變成陷阱。它同時修掉一個既有的小毛病：刪掉一本與正在看的那張無關的單字本，那張卡以前也會跟著飛走。

**兩個入口的行為必須一致**，這是把重建規則抽進 `rebuildQueue()`（`src/lib/review.ts`）、讓 `applyData()`（`src/app.ts`）統一走它的原因。同一個設定從兩個地方改卻得到兩種結果，是比多一個入口更糟的事。

## Considered Options

- **不推翻，改善資料頁那條路徑**（複習畫面加一顆直達單字本區的捷徑，或資料頁改完自動彈回複習畫面）：動的地方少，複習畫面完全乾淨。否決的原因是切本時仍然得離開複習畫面，只是來回快一點——真正的痛點沒有被解掉。
- **只在「今日份完成」畫面放下拉**：複習中完全乾淨，剛好對上「這本練完了，換一本」，而且那時佇列是空的，完全避開重建問題。否決的原因是練到一半想換就沒轍。
- **不合併兩支畫面，勾一本就整頁重建**：程式改動最小。否決的原因是要勾三本得開三次選單，而且同一顆零件在卡片列表、統計頁不會收，只有複習畫面會收——同一個東西三種行為。
- **勾選時不生效，關選單那一刻才一次套用**：不用重構也能連勾。否決的原因是這顆元件多出一種「改了還沒生效」的狀態，三個呼叫端只有這一個這樣。
- **下拉放右側跟「卡片」並排**：空間最充裕。否決的原因是「在練哪幾本」是狀態不是動作，跟導覽按鈕擺一起會讓人以為它也是跳頁鈕。
- **下拉放左側跟「剩餘 N 張」並排**：兩個狀態擺一起。否決的原因是選單從按鈕右緣往左長且有最小寬度，按鈕靠左時選單會溢出畫面左緣，手機上尤其明顯。
- **拿掉資料頁的勾選框，讓每組範圍只有一個入口**：最乾淨，沒有「兩邊會不會不一致」的問題。否決的原因是資料頁那一列是「這本有幾張卡、要不要納入複習」一起看的地方，拿掉之後從單字本管理的角度反而少一塊。兩個入口的代價由「行為一致」這條規則吸收。
- **切換前先跳確認視窗**：避免誤觸。否決的原因是使用者是自己主動去點那顆下拉的，不是意外。
- **只給複習畫面那顆下拉保留正在看的那張，資料頁維持全部重洗**：改動範圍最小。否決的原因見上——同一個設定兩種結果。

## Consequences

**複習畫面不再是「零開關」。** 標題列從兩個東西變成三個。這是刻意付的代價，不是疏漏；下一個想在複習畫面加東西的人不能再引用「這裡什麼都不放」當理由，但也不代表門開了——標題列以外的地方仍然不放。

**複習範圍有兩個入口，兩邊必須行為一致。** 任何改動複習範圍的新路徑都得走 `applyData()`，不能自己重建佇列。這條紀律沒有型別在保護，只靠這份文件與 `rebuildQueue()` 的所在位置。

**`reviewView` 與 `doneView` 合併成同一支函式。** 勾一勾剛好把佇列勾空時，畫面得從「複習中」就地變成「今日份完成」而不弄丟開著的選單，兩支各自畫一整頁做不到這件事。因此之後要替複習畫面加新的畫面狀態，得走它的 `refresh()`，而不是再新增一支 view。零本時的 `noBooksView` 仍然獨立——那時選單是空的，放上去是顆死按鈕。

**保留正在看的那張這條規則會被繼承。** 日後任何「換一批卡」的情境（例如雲端拉下新資料）若走 `applyData()`，就自動有這個行為。這是想要的，但它是隱性的：`rebuildQueue()` 的呼叫端不必知道自己開啟了這條規則。

**這扇門推得回去**——把標題列那顆下拉刪掉、`rebuildQueue()` 換回 `buildQueue()`，兩者都是幾行的事，`reviewView` 的合併留著也無妨。真正難回頭的不是程式，是「複習畫面可以有開關」這個判斷本身。
