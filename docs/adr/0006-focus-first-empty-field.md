# 換欄鍵：填完一格就把游標送到下一個還空著的格子

編輯畫面上，填完一格按鍵盤上的換欄鍵，程式就把游標送到下一個還空著的必填格。順序是**詞條 → 讀音格（左到右）→ 釋義**，從目前這格往下找，到底繞回頭。

起因是手機：iPhone 虛擬鍵盤上「填完一格、換到下一格」得自己用手指點。而使用者會依當下的輸入法決定先打哪一格（中文注音時先打釋義、日文九宮格時先打詞條），所以不能只做單一方向。

**這份決定的範圍被 ADR-0009 擴大過。** 最初只管詞條與釋義兩格——當時讀音可以整串留空，空的讀音格既是合法終點又不能當終點，納進來會讓游標永遠出不去。ADR-0009 把讀音改成必填，「還空著＝還沒填完」才成立，讀音格因此進場。下面〈實測結果〉一節仍是最初那次量測的紀錄，結論一字未改。

## 決定

### 換欄（↵ 與 ✓ 共用同一套）

```
從目前這格往下找下一個還空著的格子，到底繞回頭
順序：詞條 → 讀音格（左到右）→ 釋義
前提一：離開的那一格必須有值
前提二：焦點自己落到別的輸入框、或讀音區裡的任何東西，就不搶
不出錯誤訊息、不儲存
全部有值時 ↵ 放行送出表單（✓ 本來就不送出）
```

**↵ 與 ✓ 是兩顆不同的鍵，落點必須一樣。** 使用者心裡只有一個動作「換到下一個要填的地方」，兩顆鍵到不同的地方沒法解釋。兩者唯一的差別是 iOS 的物理限制，不是規則的差別：↵ 是真按鍵，`focus()` 站在使用者手勢裡，鍵盤留得住；✓ 只發 `blur`，鍵盤一定收掉。理由見〈實測結果〉。

**前提一「離開的那一格必須有值」不是可有可無的修飾。** 少了它，兩格都空時按 ✓ 會在格子之間來回彈，鍵盤永遠收不掉。加上這個前提就沒事，而且它正是「**輸入完**這一格」本來的意思。代價是從一個空格出發按不動，想先填後面的得用手指點——這是刻意的。

**前提二「焦點自己落到別的輸入框或讀音區就不跳」也是不加就會壞掉的前提。** 少了它，你點另一個讀音格、或按讀音區的合併縫 `⊕`／拆開縫 `·`，都會被彈走。桌機按 Tab 也走這條，既有的 Tab 順序因此完全不受影響。

**換欄不出錯誤訊息。** 打完一格按鍵時使用者還沒說要儲存，這時候念他「三個都要填」等於每張卡都被念一次，錯誤訊息會貶值成常態。錯誤訊息只留給真正按下儲存那一刻。

**這件事對 ↵ 得動手擋，不是什麼都不做就會發生。** ↵ 沒被攔下來時瀏覽器會拿它去送出表單，於是使用者收到的不是「沒事發生」而是一行紅字。兩種情況要攔：**從空的格子出發**（前提一沒過），以及**避讓生效但找不到空格**——後者不代表填滿了，讀音格根本沒進候選，空的正是它們。第二種不是邊角：先填釋義再回頭打詞條的人（注音輸入法的典型順序）有設金鑰時每張卡都會走到。只有真正「全部有值」時才放行，那一下 ↵ 才等於按下儲存。

### AI 預填避讓

```
離開詞條時，若正在詢問 AI、或這一下離開會開始詢問
（有金鑰 ＋ 詞條有漢字 ＋ 讀音格全空 ＋ 這個詞還沒問過）
  → 這次輪詢把讀音格整段跳過，游標直接送到釋義
```

沒有這條，有設金鑰的人會這樣：詞條打完按 ↵，游標跳進第一個讀音格、鍵盤留著，你開始打假名——約一秒後 AI 回覆到達，讀音區整個重畫（`ADR-0005` 的預填會依回覆決定每串開幾格），你打的字被蓋掉、游標消失、鍵盤收起來。就算你什麼都沒打，光是重畫就會讓游標和鍵盤一起沒掉，而「鍵盤留得住」正是 ↵ 這條路唯一的價值。

判斷條件寫成「會不會去問」而不只是「正在問」，是因為時序：**按鍵的當下詢問還沒開始**——詢問是詞條失焦才觸發的，而失焦發生在跳轉之後。只看「正在問」的話，第一次按永遠漏掉。

沒設金鑰的人完全不走這條，行為單純。

### 按下儲存（「儲存」／「儲存並繼續」）

```
依 詞條 → 釋義 → 讀音 的順序找第一個空的
  → 錯誤訊息「詞條、讀音與釋義都要填。」＋ 游標送過去，不儲存
讀音填了但不是假名 → 原本的多句列舉，游標不動
```

**三種必填格一視同仁：都是錯誤訊息 ＋ 游標指路。** ADR-0009 之前，讀音驗證失敗是不跳游標的，理由是「讀音的錯可能一次好幾個，跳第一個未必是你要改的」。必填之後讀音的錯幾乎只剩一種——沒填——那條例外跟著「可留空」一起退場。「填了但填錯」（不是假名）仍走原本的多句列舉、游標不動，因為那跟「沒填」是兩回事。

**儲存的順序是詞條 → 釋義 → 讀音，跟換欄的畫面順序不一樣。** 這是使用者明確選的：讀音排最後。代價是同一張卡上兩顆鍵的落點可能不同——詞條填好、讀音空、釋義空時，↵ 帶你去讀音格，儲存鍵帶你去釋義。

**Enter 不算「按下儲存」。** 按鈕是「我要存」，換欄鍵是「我要往下走」，兩者不是同一個意圖，因此錯誤訊息只留給按鈕。這條是實測之後才長出來的，理由見〈實測結果〉。

**錯誤訊息維持單一句**，不改成指名缺哪一格。游標已經指路了，訊息再指一次是重複；維持一句，少一組要維護的措辭。

## Considered Options

- **只在按下儲存時檢查**（最初的方向）：漏掉真正的需求。手機上的換欄鍵不送出表單，使用者要的是填完一格就被帶到下一格，而不是等到按儲存被擋下來才知道。
- **換欄也出錯誤訊息**：一致，但正常填卡流程每張都會閃一次紅字。
- **錯誤訊息改成指名缺哪一格**（「還沒填釋義」）：焦點已經指路，訊息是重複。
- **只做新增、不做編輯**：使用者原話只講新增，但同一支 `editor-view.ts` 兩種模式都管，把釋義刪光按儲存同樣會撞到，要排除反而得多寫條件。
- **只跳單一方向（釋義 → 詞條）**：可以完全避開跟讀音確認打架，但不對稱、難解釋，而且使用者有一半時候先打詞條，那一半就享受不到。
- **詞條含漢字時不跳**（有讀音要確認就別打擾）：同一個動作時而跳時而不跳，比不跳還難預測。
- **一律回到最上面那個空格**（而不是從目前這格往下）：永遠不會跳過空格，順序固定。否決的原因是它會把人往回帶，跟手指往下填表單的方向相反，感覺像倒退。改成往下輪詢後，中間還空的格子會被暫時跳過，但繞完一圈就回來，最後一樣填得滿。
- **✓ 完全不動，只改 ↵**：改動最小，也完全避開 AI 撞車（✓ 不會把你送進讀音格）。否決的原因是同一張卡上 ✓ 跳釋義、↵ 跳讀音格，兩顆看起來都像「下一格」的鍵到不同地方。
- **讀音格按 ✓ 不跳**（最初的決定）：理由是改完假名按 ✓ 通常是想收鍵盤看預覽對不對（ADR-0005 要求預填結果儲存前一律人工確認）。使用者選擇一致性優先，接受「改完假名按 ✓ 會被彈到下一格」這個代價；要看預覽的話，游標落在哪一格預覽都在同一個位置。
- **AI 撞車改成「回覆到了但游標在讀音區就不套用，改出一行『點一下套用』」**：你正在打的字、游標、鍵盤全保得住，也不必判斷「會不會去問」。否決的原因是畫面多一個要點的東西，而且是在你正忙著打字的時候冒出來。改採避讓，代價是同一顆 ↵ 時而跳讀音格、時而跳釋義，看網路快慢。
- **三顆按鈕都防「點空」**：iPhone 上鍵盤還開著時直接點按鈕，`blur` 先發生、焦點跳走、畫面捲動，按鈕在 `touchend` 前就移位，這一下 click 不會觸發。三顆都會中，但兩顆儲存白按的結果（游標跳到該填的格）跟真按到（錯誤訊息＋游標跳到該填的格）差不多，只少一行字；「取消」白按卻是「想離開卻被拉回輸入框、鍵盤又彈出來」，沒有便宜可佔。因此只替取消掛 `pointerdown` 旗子。

## 實測結果

iPhone 上量過了，結論是**手機鍵盤上有兩顆看起來都像「送出」的鍵，性質完全不同**：

- **`✓`**（浮在鍵盤上方那條橫條的右端）是 iOS 的「完了」，純系統 UI。網頁收到的**只有 `blur`**，沒有任何按鍵事件。`focus()` 因此在使用者手勢之外，焦點跳得動、鍵盤叫不回來。這條路無解，只能接受。
- **`↵`**（九宮格鍵盤自己的右下角）是真按鍵，會發 `keydown` Enter。在它的 handler 裡 `focus()` 站在使用者手勢中，**鍵盤留得住**。

原本預期「得改成偵測那顆鍵本身」——結果是那顆鍵（`✓`）根本沒有事件可偵測，反而是另一顆一直沒被注意到的 `↵` 成了答案。因此失焦那條路維持原樣（它負責 `✓`，效果就到「焦點跳了、鍵盤收掉」為止），Enter 那條路則從「按下儲存」裡分出去，成為真正好用的換欄鍵。

## Consequences

畫面多了一個會自己動的東西。代價落在四處：

- **想收鍵盤看畫面時會被拉回來。** 任何一格填好、後面還有空格時按換欄鍵，游標都會被送走。這現在也包含讀音格：改完假名按 ✓ 會被彈到下一格，而不是停在原地看預覽。
- **按 `✓` 時鍵盤仍會收掉，得再點一次。** 見〈實測結果〉，這是 iOS 的規矩，不是可以修的東西。想要鍵盤留著就按 `↵`。
- **同一顆 ↵ 的落點會受網路影響。** 有設金鑰時，詞條打完按 ↵ 跳釋義（避讓）；沒設金鑰時跳第一個讀音格。AI 查完之後又回到一般規則。這是避讓那條的必然結果。
- **換欄鍵與儲存按鈕的落點不一定相同。** 換欄走畫面順序（讀音在中間），儲存走詞條 → 釋義 → 讀音（讀音在最後）。多一組要記的規則。

**已知、這次不處理**：AI 正在查的那一秒，你若用手指自己點進讀音格打字，回覆到達時仍會覆蓋掉你打的字。避讓只擋住「程式把你送進去」，擋不住「你自己走進去」。這在 ADR-0005 落地時就存在，不是這次長出來的。

拿掉這整套只需刪掉 `blur` 與 `keydown` 裡那兩段判斷。真正被鎖住的是「離開的那一格必須有值」與「焦點落到其他輸入框或讀音區就不跳」兩條——它們不是偏好，是不加就會壞掉的前提，日後改寫這段邏輯時不能省。
