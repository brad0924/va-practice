# 詞條與釋義互相帶路：填完一欄就把焦點送到空的那一欄

編輯畫面上，詞條與釋義只要有一欄填好、另一欄還空著，程式就主動把焦點送過去。兩個時機會發生：**離開欄位時**（不出錯誤訊息）與**按下儲存時**（照舊出錯誤訊息）。

起因是手機：iPhone 虛擬鍵盤右下角那顆打勾在本專案的表單裡**只收鍵盤、不送出**，所以「填完一欄、換到下一欄」得自己用手指點。而使用者會依當下的輸入法決定先打哪一欄（中文注音時先打釋義、日文九宮格時先打詞條），兩個方向都得能帶路。

程式看不到「使用者按了打勾」，看得到的只有 `blur`。因此這件事只能掛在失焦上，並由此長出下面幾條約束。

## 決定

**離開的那一欄必須有值，才帶去空的那一欄。**

```
離開詞條：詞條有值 且 釋義空 → 焦點跳釋義
離開釋義：釋義有值 且 詞條空 → 焦點跳詞條
按下儲存：任一欄空 → 錯誤訊息 ＋ 焦點跳到該欄，不儲存
```

「離開的那一欄要有值」不是可有可無的修飾。寫成「有空欄就跳」時，兩欄都空的情況會爆掉：焦點在詞條按打勾 → 釋義空 → 跳釋義 → 再按打勾 → 詞條空 → 跳回詞條，鍵盤永遠收不掉。加上這個前提就沒事，而且它正是「**輸入完**這一欄」本來的意思。

**焦點若是落到其他輸入框，一律不跳**（`blur` 的 `relatedTarget` 是可輸入元素就直接退出）。沒有這條這功能會壞掉：新增卡片時釋義必定是空的，使用者一點進讀音格就會被彈走，讀音格永遠碰不到。桌機按 Tab 也走這條，既有的 Tab 順序因此完全不受影響。

**失焦不出錯誤訊息，按下儲存才出。** 打完一欄按打勾時使用者還沒說要儲存，這時候念他「詞條與釋義都要填」等於每張卡都被念一次，錯誤訊息會貶值成常態。

**範圍只有詞條與釋義兩欄。** 讀音格失焦不跳、讀音格驗證失敗也不跳焦點。

## Considered Options

- **只在按下儲存時檢查**（最初的方向）：漏掉真正的需求。手機上那顆打勾不送出表單，使用者要的是填完一欄就被帶到下一欄，而不是等到按儲存被擋下來才知道。
- **失焦跳轉也出錯誤訊息**：一致，但正常填卡流程每張都會閃一次紅字。
- **錯誤訊息改成指名缺哪一欄**（「還沒填釋義」）：焦點已經指路了，訊息再指一次是重複；維持既有的單一句，少一組要維護的措辭。
- **只做新增、不做編輯**：使用者原話只講新增，但同一支 `editor-view.ts` 兩種模式都管，把釋義刪光按儲存同樣會撞到，要排除反而得多寫條件。
- **只跳單一方向（釋義 → 詞條）**：可以完全避開跟讀音確認打架——從詞條離開時不跳，鍵盤乾淨收起讓人看 AI 填的讀音。但不對稱、難解釋，而且使用者有一半時候先打詞條，那一半就享受不到。改採兩個方向都跳，並接受鍵盤會彈回來；焦點落在釋義時正上方就是預覽區，要**確認**讀音看那行就夠，只有要**改**才需往上捲。
- **詞條含漢字時不跳**（有讀音要確認就別打擾）：同一個動作時而跳時而不跳，比不跳還難預測。
- **讀音格失焦也跳**：改完假名按打勾通常是想收鍵盤看預覽對不對（ADR-0005 要求預填結果儲存前一律人工確認），這時被彈到釋義、鍵盤又擋住畫面。
- **讀音格驗證失敗也跳焦點**：讀音的錯可能一次好幾個，跳第一個未必是使用者要改的；而且錯誤訊息本身已經點名是哪串漢字。
- **三顆按鈕都防「點空」**：iPhone 上鍵盤還開著時直接點按鈕，`blur` 先發生、焦點跳走、畫面捲動，按鈕在 `touchend` 前就移位，這一下 click 不會觸發。三顆都會中，但兩顆儲存白按的結果（焦點跳到該填的欄）跟真按到（錯誤訊息＋焦點跳到該填的欄）差不多，只少一行字；「取消」白按卻是「想離開卻被拉回輸入框、鍵盤又彈出來」，沒有便宜可佔。因此只替取消掛 `pointerdown` 旗子。

## Consequences

畫面多了一個會自己動的東西。代價落在兩處：

- **想收鍵盤看畫面時會被拉回來。** 詞條填好、釋義空著時按打勾，焦點被送去釋義、鍵盤又彈出來。要確認 AI 填的讀音，看預覽那行即可（它就在釋義正上方）；要改讀音得往上捲去點讀音格。
- **iOS 可能不讓程式主動叫出鍵盤。** Safari 限制 `focus()` 只在使用者手勢的呼叫堆疊中才會連帶叫出虛擬鍵盤，而「按虛擬鍵盤的打勾 → 觸發 `blur` → 在 handler 裡 `focus()`」算不算使用者手勢，文件無定論。若實測發現焦點跳了但鍵盤收掉、或整個無效，得改成偵測那顆鍵本身而非偵測失焦——那是另一個決策。

這扇門沒有關死，也很好反轉：拿掉只需刪掉 `blur` 裡那段判斷。真正被鎖住的是「離開的那一欄必須有值」與「落到其他輸入框就不跳」兩條——它們不是偏好，是不加就會壞掉的前提，日後改寫這段邏輯時不能省。
