# 文件與 ADR：讀音預填

Status: ready-for-agent
Type: enhancement

建議在 `01`、`02`、`03` 完成後再落筆，確保文件描述的是真正做出來的東西。

## 需求

本功能改掉了「讀音一律由人輸入」這個前提，而那個前提是 ADR-0004 白紙黑字寫下來的。牽動的文件一起改，並記一份 ADR 說清楚這是走 ADR-0004 預留的門，不是推翻它。

## 決定

### `CONTEXT.md`

1. **新增詞條「讀音預填」**，放在「讀音格」之後（它引用了讀音、讀音格兩個概念，擺後面避免前向引用）。

   定義方向：詞條輸入完畢後，程式代為填入讀音格的動作。填入的內容仍是使用者的草稿——可改、可清空，儲存前一律要人工確認；程式不承擔「讀音一定正確」的責任。需要使用者自備的金鑰，未設定時完全不發生。

   `_Avoid_` 排除會誤導的說法：自動產生、翻譯、辨識（都會讓人以為程式對結果負責）、AI 標音（把手段寫進名字）。

2. **`CONTEXT.md` 只放詞彙，不放實作細節。** 不出現 Gemini、金鑰、localStorage、失焦這些字眼——那些是 issue 與 ADR 的事。

### `docs/spec.md`

3. **User Story 23、24 之後補一條**，方向為：詞條打完後讀音格自動被填好，只需確認或修改，不必逐格打字。措辭沿用既有 User Story 的語氣。

4. **「讀音標記」章節（約 120–124 行）補一段。** 現有內容說「使用者不再手動輸入方括號……儲存時再組回上述方括號字串」，要補上讀音格可由程式預填、但預填結果仍需人工確認，且方括號語法與儲存格式完全沒變。

5. **「模組與接縫」章節（約 85–89 行）的「讀音標記」模組描述補一句**：本模組另負責審核外部來源提供的讀音預填結果，通過才轉成讀音格。維持該模組「純函式，不涉及任何狀態」的描述——`acceptPrefill` 沒有破壞這一點。

6. **測試接縫清單（約 150 行）補一句**：另驗證讀音預填的接受與拒絕條件。

7. **不把網路層寫進模組清單。** 它比照 `cloud-backup.ts` 的地位——存在，但不是測試接縫。

### `docs/adr/0004-no-kanji-reading-dictionary.md`

8. **原檔不改內容，在結尾補一行指向 ADR-0005。** ADR 是決策紀錄不是規格，過去的判斷要留著才看得出脈絡。它的 Consequences 已經寫了「這扇門沒有關死」，ADR-0005 就是那扇門被打開的紀錄。

### `docs/adr/0005-*.md`（新檔）

9. **記一份 ADR**，決定為「讀音預填改用遠端 LLM，作為選配預填，不引入本地字典」。編號 `0005`，沿用 `0001`–`0004` 的體例（標題句、正文、Considered Options、Consequences）。

10. **正文核心：ADR-0004 的四個理由，現在有三個不成立——因為問題本身換了，不是因為鑽漏洞。**

    - **體積**：知識搬到遠端，打包產物維持約 33 KB。原本的「10 倍於整個 app」不再適用。
    - **正確性天花板**：熟字訓（`剃刀[かみそり]`、`吹雪[ふぶき]`）是字典查不到、逐字拆本來就無解的，但 LLM 答得出來。連濁與促音便同理，不必另寫規則。
    - **失敗模式**：這是最關鍵的一項。**分配錯誤不會產生錯卡**——`吹`／`雪` 分反了，卡片正面文字與語音朗讀完全不變，只有振假名標的位置不同，而且預覽當場看得到。ADR-0004 擔心的「安靜的錯卡」在這個形狀下不成立。
    - **仍然成立的那一個**：整串讀音幻覺（AI 說 `吹雪` 唸 `すいせつ`）是真的錯卡，不報錯、要等複習翻面才發現、會存進雲端備份。這一項靠「填進格子＋一行『請確認』提示＋預覽」擋，沒有第二道防線。ADR 要誠實寫出這是本決定唯一沒解決的風險。

11. **Considered Options 至少涵蓋四個被否決的方案**（訪談中逐一評估過）：

    - **kuromoji.js 本地形態素解析**：字典目錄實測 17.0 MB（已 gzip），是現有打包產物的 530 倍，比 ADR-0004 當初寫的「300 KB 起跳」還大 50 倍。而且它**只解決一半**——給的是整個詞的讀音（`吹雪` → `フブキ`），不會告訴你 `吹`＝ふ、`雪`＝ぶき，逐字分配仍得自己做一張單漢字音訓表加連濁、促音便、送假名規則。真實成本是字典加上一整套自寫邏輯。
    - **瀏覽器內建的 Prompt API（Gemini Nano）**：真的免金鑰、免費、離線。但 Android、iOS、ChromeOS 都還不支援，桌機也要約 22 GB 可用磁碟與 4 GB VRAM；而且日文漢字讀音正是超小模型會很有自信講錯的題型。
    - **只做分配、讀音由使用者輸入整串**：只需數十 KB 的音訓表、免金鑰、離線可用、風險最低。否決原因是使用者要的體驗是「打完詞條什麼都不用打」，這個方案仍要打字。
    - **Groq／Cerebras／OpenRouter 的開源模型**：五家免費層的 CORS 預檢實測全部放行瀏覽器直呼，免費額度對「一個詞一個請求」也全都碰不到，所以 CORS 與額度都不是選擇因素；**唯一該比的是日文能力**，而那正是中小型開源模型的弱項。

12. **Consequences 至少寫四條**：

    - **金鑰刻意不進 `AppData`**，因此 ADR-0003 那句「若日後要放入任何敏感資料，這個前提必須重新評估」**沒有被觸發**。這是主動迴避不是忽略：金鑰若進 `AppData` 會同時打開三個出口（Firebase 加密、localStorage 明文、**匯出檔明文**），加密只堵得住第一個。
    - **代價是金鑰不跨裝置，每台各設定一次**，手機上尤其麻煩。已知並接受。
    - **這個功能永遠是選配的。** 沒設金鑰時完全靜默，新增卡片的行為與沒有這個功能時一字不差；離線、超額、AI 掛掉一律降級成手動填，絕不擋住儲存。ADR-0004 的「讀音一律由人輸入」仍是這個 app 的保底路徑。
    - **免費層的內容通常會被供應商拿去改進模型**，且該帳號一旦啟用計費，免費層會整個消失、每個呼叫從第一個 token 起計費。內容是日文單字，前者可接受；後者要在介面上提醒。

## 驗收

- `CONTEXT.md` 有「讀音預填」條，位置在「讀音格」之後，帶 `_Avoid_`，且**不含任何實作細節**（沒有 Gemini、金鑰、localStorage、失焦等字眼）。
- `docs/spec.md` 的 User Story、「讀音標記」章節、模組與接縫、測試接縫四處都已更新，且描述的是 `01`–`03` 實際做出來的東西，沒有描述沒做的功能。
- `docs/adr/0005-*.md` 存在，體例與 `0001`–`0004` 一致；四個理由的存廢逐一交代，**包含誠實寫出仍然成立的那一個**。
- `docs/adr/0004-no-kanji-reading-dictionary.md` 內容未被改寫，只在結尾多一行指向 `0005`。
- 文件之間沒有互相矛盾：ADR-0004 說「不引入字典」，ADR-0005 說「改用遠端 LLM 做選配預填」，兩者讀起來是連續的決策脈絡，不是打架。
