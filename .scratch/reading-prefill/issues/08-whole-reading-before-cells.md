# 08 — 讓模型先寫下整個詞條的假名，再拆格

Status: done
Type: enhancement

## 怎麼發現的

2026-08-21，票 06 把預設模型換成 `gemini-3.5-flash-lite` 之後驗 `吹雪` 這道界線題，網頁版連打五次：**四次 `ふぶき`（對）、一次 `ふくふき`（錯）**。

錯的那次形狀很具體：

| | `splittable` | 格子 | 對不對 |
| --- | --- | --- | --- |
| 應該是 | `true` | `吹`＝ふ、`雪`＝ぶき | — |
| 錯的那次 | `true` | `吹`＝ふく、`雪`＝ふき | 拆對了，讀音錯 |

**它不是拆錯，是拆對了但沒查整串怎麼唸。** 判斷那一層是正確的，兩格也切得對，只是填格子時走了捷徑——把 `吹`＝ふく、`雪`＝ふき 兩個漢字各自單獨的讀音接起來交差，從沒把 `ふぶき` 這個整串讀音寫下來過。

## 為什麼不是「再多寫幾句判準」

`INSTRUCTIONS` 規則 3 **逐字寫著標準答案**：

> `吹雪` 是熟字訓但 `splittable` 為 true：吹=ふ、雪=ぶき 都是各自的讀音。

模型看著同一頁上的答案還抄錯。這跟前兩次事故（`吹雪` 被整串一格、`剃刀` 被硬拆，`ADR-0005` 有紀錄）性質不一樣——那兩次是判準含糊，把話講清楚就修好了；這次判準沒有含糊的空間，加字大概率沒用。

## 想法：用欄位順序逼它先想

`RESPONSE_SCHEMA` 現在的註解自己就寫著這一招：

> `splittable` 排在 `cells` 前面不是隨便放的：模型是一個欄位一個欄位往下生的，先寫下判斷再填格子，格子才會照著那個判斷走。

**同一招沒有用在讀音上。** 沒有任何一格逼它先寫出整串的音，所以它從第一格開始就直接生假名。

作法是在最前面加一格，讓模型先寫下整個詞條的假名，再輪到判斷拆不拆、才輪到填格。填 `吹`＝ふく 的時候，`ふぶき` 已經在它自己剛寫下的上文裡。

**這一格叫 `termKana`，最外層的形狀也跟著改（2026-08-24 triage 拍板，見 Comments）：** 整個詞條的假名不屬於任何一串漢字，現在那個「一串一項」的陣列裝不下它，所以最外層從陣列改成物件 `{ termKana, runs }`。

## 範圍比票 06 大很多

- **`RESPONSE_SCHEMA` 兩條路徑共用**（`fixed-gemini-key` spec 決定十六），改一次動到網頁版與 iOS。
- **一定會牽動 `acceptPrefill`（`reading.ts`）**：不是因為對帳（拍板不對帳），而是因為最外層從陣列變物件，它得多拆一層才拿得到 `runs`。
- **`INSTRUCTIONS` 要跟著調**，講清楚 `termKana` 是什麼、跟 `cells` 的關係。
- **Remote Config 的 `gemini_instructions` 也要同步**，否則 iOS 拿舊判準配新 schema。
- **多一格會多花 token 也多花時間**，而票 06 換模型的全部目的就是變快。這一項要重新量逾時，不能假設 0/10 還在。

## 要決定的事 — 2026-08-24 已拍板

原本兩題，triage 那天連同衍生的十題一起定了。完整清單見 Comments，這裡只留結論：

1. **`termKana` 只當鷹架，不對帳。** 程式收下那一格但完全不讀。要不要加第二道防線，等這輪的數字出來再談。
2. **值不值得由停止線回答，不預先猜。** 網頁版量十五次（`吹雪` 十次、`剃刀` 五次），要求逾時 0 次、兩題全對；iOS 真機量 `吹雪` 十次，要求逾時 0 次。沒過就退回 `needs-triage`，帶著數字重談。

第 2 題的前提沒變，記在這裡免得被 Comments 淹掉：**退步是真的**（對照組 5/5 對 4/5）。而預算有第二個競爭者——票 07 讓 5xx 自動重試，重試沒有自己的碼表、跟第一次共用同一個 `TIMEOUT_MS`。多一格生成再加上一次重試，兩者一起擠那 10 秒。

## 阻擋 — 已解除

原本要等票 06 的對照組。2026-08-21 量到了：**`gemini-3.6-flash` 打五次 `吹雪` 全對，`flash-lite` 錯一次。** 所以那 1/5 確實是換模型換來的退步，這張票的前提站得住——問題就是「小模型在熟字訓上比較弱」，不是「這一招從來就不夠穩」。

維護者選擇保留 `flash-lite`（`0/10` 的逾時值那個價），所以這一格要靠別的辦法贏回來，本票就是那個辦法的候選。

#### 拍板清單

1. **`termKana` 只當鷹架，不對帳。** 程式收下那一格但完全不讀。要不要加第二道防線（各格假名接起來對不對得上 `termKana`），等這輪的數字出來再談。
2. **那一格裝整個詞條的假名**，不是各串漢字各自的音。`取り消し` 寫 `とりけし`，不是 `と` 跟 `け` 兩個。
3. **回答的最外層從陣列改成物件。** 第 2 項的直接後果——整個詞條的假名不屬於任何一串漢字，`items` 裡沒有它的位子。形狀變成 `{ termKana, runs }`，`termKana` 排第一個，鷹架才擋在所有格子前面。
4. **命名 `termKana`，不叫 `wholeReading` 也不叫 `termReading`。** `CONTEXT.md` 對「讀音」的定義是「詞條中各個漢字的假名讀法，以振假名形式標在漢字上方」——專指標在單個漢字頭上的東西。新那一格裝的是整個詞唸起來的音，叫它「詞條讀音」會讓同一個詞在同一份文件裡有兩種意思。`termKana`（詞條假名）避開這個衝突，**因此 `CONTEXT.md` 不動**。陣列沿用程式碼既有的叫法（`KanjiRun`、`scanRuns`），命名 `runs`。
5. **網頁版的停止線：逾時 0/10、`吹雪` 10/10。** 兩條都達標才收。逾時出現一次就退回重談——票 06 花了整張票才把逾時從 3/10 打到 0/10，那個成果不默默讓掉。

7. **iOS 同一張票收，主控台那一步維護者自己按。** 判準文字在 Remote Config 的 `gemini_instructions`，agent 進不去。
8. **順序：先貼主控台，再推程式碼，最後出 build。** 反過來 iOS 會拿新格式配舊判準。
9. **iOS 要一輪 TestFlight 真機驗收**，`吹雪` 十次、逾時 0/10。
10. **iOS 不裝計時探針。** 這張票只需要知道「有沒有超過十秒」，超過了畫面本來就會講。票 06 要探針是因為它要的是分段秒數。
11. **沒過停止線就退回 `needs-triage`。** 程式碼不推，帶著數字重新談。不預先決定下一步是放棄還是回頭調 `TIMEOUT_MS`。

#### 為什麼是 `ready-for-human` 而不是 `ready-for-agent`

跟票 06 同一個體質，那三條理由這張票全中：

- **驗收要真的呼叫模型**，需要維護者自己那把金鑰。`ADR-0005` 決定金鑰只留在使用者裝置上、不進 repo，agent 手上沒有也不該有。
- **`吹雪` 與 `剃刀` 對不對是人眼判斷**，不是斷言擋得住的。
- **主控台那一步在 Firebase 裡**，外加一輪 TestFlight 真機。

程式碼那半邊 agent 做得來，切法見下面那份交付文件。**票不能在驗收之前結案。**

#### 量之前要先確認的兩件事

- **Google 那端沒在塞車。** 票 06 踩過：撞到 503 的時候量，分不出是模型慢、是換模型變快、還是 Google 今天心情不好。連續幾次都沒有 5xx 再開始計數。量到的十五次裡若混進 5xx，單獨記，不要跟逾時算在同一個數字裡。
- **網頁版與 iOS 是不是同一桶額度。** 網頁版走維護者的自備金鑰，iOS 走 Firebase 專案的固定金鑰，多半是分開的兩桶，但 repo 裡查不到這件事。若是同一桶，網頁版十五次加 iOS 十次會爆掉一天的 20 次，要分兩天量。

#### 一件現在不用解、上架之後會變真的事

Remote Config 的判準是全域的，所有已安裝的版本立刻拿到。改判準會讓還沒更新的舊版 app 拿到一句它的回答格式做不到的指示。

**這輪不必處理**：iOS 還沒上架 App Store（`ios-app` 票 11 仍是 `ready-for-agent`），現在只有 TestFlight 內部測試版，裝的人就是維護者本人，舊版直接換掉即可。

上架之後這件事會變真，屆時得靠 Remote Config 的版本條件分流，或把判準寫成新舊都吃得下的措辭。記在這裡，不是這張票要解的。

## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** 讓模型在填讀音格之前，先寫下整個詞條的假名——多一格 `termKana` 當思考鷹架，程式收下但不驗證

**Current behavior:**
結構化輸出的形狀是一個陣列，一串連續漢字一個物件，欄位順序 `splittable` → `cells`。沒有任何欄位要求模型先寫下整個詞條唸起來的音，因此它從第一格就直接生假名。實測 `吹雪` 五次錯一次：錯的那次 `splittable` 判斷正確、格子也切對，但把 `吹`＝ふく、`雪`＝ふき 兩個漢字各自單獨的讀音接起來交差，沒有連濁成 `ふぶき`。判準裡逐字寫著這一題的答案，模型照樣抄錯。

**Desired behavior:**
回答的最外層改成物件，兩個欄位，順序 `termKana` → `runs`。`termKana` 是字串，裝整個詞條唸起來的假名（`取り消し` 是 `とりけし`）。`runs` 是原本那個陣列，每一項的形狀一字不改。

判準要新增一條，要求先填 `termKana`，說明它是整個詞條的假名，並要求各格的假名跟它一致。

收下回覆的驗證只讀 `runs`，**`termKana` 完全不參與驗證**——它是空字串、缺漏、或跟各格接起來對不上，都不影響結果。形狀不對（不是物件、沒有 `runs`、`runs` 不是陣列）一律整批不採用，維持既有的「任一條不過就整批回 `null`」規則。

**Key interfaces:**

- `RESPONSE_SCHEMA` — 最外層從 `type: 'array'` 改成 `type: 'object'`；`properties` 為 `termKana`（string）與 `runs`（原本那個 array，內容原封不動）；`required` 與 `propertyOrdering` 都是 `['termKana', 'runs']`。仍要通過 Firebase AI Logic 的 `SchemaRequest` 型別——那一側比 REST 嚴，過得了它就過得了 REST。
- `acceptPrefill(term, reply)` — 回傳型別不變（`KanjiRun[] | null`）。輸入從陣列變成物件：先確認 `reply` 是物件、`runs` 是陣列，再走原本那套逐串比對。`termKana` 讀都不讀。
- `INSTRUCTIONS` — 新增一條規則。要跟現有那條「依詞條中漢字串出現的順序回答，`cells` 各格的 `kanji` 接起來必須等於原本那串漢字」對得起來，不要互相打架。
- `RESPONSE_SCHEMA` 與 `INSTRUCTIONS` 兩條路徑共用，iOS 那條只是把 `INSTRUCTIONS` 換成 Remote Config 抓來的版本。**這張票不改分岔的方式。**

**Acceptance criteria:**

- [x] `RESPONSE_SCHEMA` 最外層是物件，欄位順序 `termKana` 排在 `runs` 前面
- [x] `acceptPrefill` 收物件；收到舊的陣列形狀回 `null`
- [x] `acceptPrefill` 不讀 `termKana`：`termKana` 是空字串、缺漏、或跟各格假名接起來對不上，回傳值都跟正常情況一樣
- [x] `acceptPrefill` 原有行為一字不變：漢字接起來要與該串一字不差、`splittable` 為 `false` 就併回一格、任一條不過就整批 `null`
- [x] `INSTRUCTIONS` 新增一條，要求先寫 `termKana` 並說明它與各格的關係
- [x] `RESPONSE_SCHEMA` 與 `acceptPrefill` 的註解寫清楚「`termKana` 收下但不驗證」以及為什麼——未來讀程式的人一定會問「為什麼有一格收了卻不用」
- [x] `npm test` 全綠
- [x] `npm run typecheck` 乾淨

**Out of scope:**

- **拿 `termKana` 對帳。** 本輪明確不做，等數字出來再談。
- 調整 `TIMEOUT_MS`。
- iOS 的 5xx 重試（票 09）。
- 新增 `CONTEXT.md` 詞條——`termKana` 刻意避開了詞彙表的「讀音」，不需要動。
- 改 `ADR-0005`——量完之後才補，不在這一段裡。
- 動 Remote Config 主控台——agent 進不去，維護者自己按。
