# 09 — iOS 那條路也要對 5xx 重試

Status: ready-for-agent
Type: enhancement

## 為什麼獨立成一張票

票 07 決定「5xx 自動重試」，但範圍只收網頁版。iOS 被切出來的理由是**測不到**：

重試得寫在 `src/lib/gemini-reading-native.ts` 裡，而那支檔案 import 了 Capacitor 外掛與 firebase 執行期程式碼，**node 底下根本載不起來**。`ai-logic-error.ts` 當初獨立成一支檔案就是為了繞開這件事——它一行執行期 firebase 都不 import，所以測得動。

沒有自動測試守得住，驗收只能上 TestFlight 真機。票 07 若把 iOS 混進來，整張票的狀態就會從 `ready-for-agent` 掉成 `ready-for-human`。

## SDK 不會幫你重試，已查證

`node_modules/@firebase/ai/dist/index.node.mjs:1402` 的 `makeRequest()` 從頭到尾只 `fetch` 一次，非 2xx 直接組 `AIError` 丟出。整份 bundle 唯一的 `retry` 字樣在 1456 行，是一句英文錯誤訊息裡的「then retry」，不是程式邏輯。

## 一個跟網頁版不一樣的地方：碼表的規矩不同

票 07 選了「重試共用同一份 10 秒預算」。**iOS 照抄不會自動成立。**

- **網頁版**：一顆 `setTimeout` 包住整支 `askReading()`，重試自然共用同一份。
- **iOS**：`TIMEOUT_MS` 是交給 SDK 的 `RequestOptions.timeout`（`gemini-reading-native.ts:251`），而 SDK 在**每次** `generateContent()` 裡自己開一顆新計時器。多呼叫一次就是多一份 10 秒。

所以 iOS 要做成「共用一份預算」得自己在外面包一層碼表，**那是額外的工**，不是照抄。也可以決定 iOS 就讓它各給一份——但那樣兩條路的行為會分家，要明講。

## 要決定的事

1. iOS 要不要跟網頁版一樣共用一份預算？還是接受各給一份（最壞等 20 秒以上）？
2. `toReadingError()` 已經把 5xx 收斂成 `gemini.httpError`（`ai-logic-error.ts`），重試的判斷要放在翻譯之前還是之後？放之後就得從 `AppError` 的參數把 status 挖回來。
3. 票 07 的「顯示第幾次」要不要一起在 iOS 上做？畫面那一層是共用的（`editor-view.ts`），所以多半是免費的，但要確認。
4. 沒有自動測試的情況下，驗收怎麼設計才算數。

#### 動筆前查過的三件事

1. **沒做過。** 搜過 `askReadingNative`、`onAttempt`、`retry`：iOS 那條路一行重試都沒有，`editor-view.ts:408` 甚至留了一句註解等這張票。全 `src/` 另一支 `retry()` 在 `cloud-backup.ts`，那是離線後補推備份，跟這條路無關。
2. **沒被否決過。** `.out-of-scope/` 目錄不存在。
3. **票 07 已經 `done`，而且做得比本票面寫的更遠。** 畫面那一層全部落地且兩條路共用：`reading-editor.ts:52` 的 `Note` 有 `retrying`、`reading-editor.ts:126` 的 `awaiting` 抽好了、`editor-view.ts:419` 的 `noteWording` 有那一格、`editor.noteRetrying` 三種語言都在。

#### 票面兩個前提要修正

**一、「共用一份預算是額外的工」——沒那麼貴。**

`getGenerativeModel()` 的 `timeout` 是**建模型時**給的參數（`gemini-reading-native.ts:251`），而這支程式本來就每問一次重建一台模型（第 242 行，理由是要讀得到 `refresh()` 後來才落地的 Remote Config 新值）。重試時把 `timeout` 從 `TIMEOUT_MS` 換成「總預算還剩幾毫秒」就成立了。一個減法，不必包 `Promise.race`、不必自己開 `AbortController`。

**二、「測不到」只在一種寫法下成立。**

票面說重試得寫在 `gemini-reading-native.ts` 裡而那支 node 載不起來。這只在「重試迴圈跟 SDK 呼叫黏在一起」時才對。`ai-logic-error.ts` 開頭那段註解自己講了怎麼繞開；`remoteOrDefault()` 是第二個先例——它只有 iOS 用得到，卻住在 `gemini-reading.ts`，第 149 行寫著理由：**放在這裡是因為這裡測得動**。

重試迴圈只要收一個「做一次事」的 callback，它根本不知道底下是 SDK 還是假貨，node 底下完全跑得動。**這一條把本票從 `ready-for-human` 拉回 `ready-for-agent`。**

### 決定一、重試迴圈抽成 `src/lib/reading-retry.ts`

不 import 任何 firebase 執行期程式碼，因此測得動。檔名是 triage 定的，覺得不好改掉沒關係。

建議形狀（`unknown` 沿用兩條路的慣例：形狀由 schema 保證，內容信不信是 `acceptPrefill` 的事）：

```ts
export async function withRetry(
  attempt: (budgetMs: number) => Promise<unknown>,
  onAttempt?: (n: number) => void,
): Promise<unknown>
```

`attempt` 收到的是「還剩幾毫秒」，拿去建那台模型。`onAttempt` 與網頁版同一份契約：開始第 N 次之前叫一聲，N 從 2 起算。

**不要 inject 時鐘。** 直接用 `Date.now()`，vitest 的 `vi.useFakeTimers()` 預設連 `Date` 一起假造，跟 `gemini-reading.test.ts` 現有那幾條逾時測試同一套手法。多一個參數只是把測試的方便寫進上線的介面。

`TRANSIENT`（`gemini-reading.ts:198`）目前沒 export，改成 export 讓兩條路讀同一份清單。**兩邊各抄一份會漂移，漂移的下場是一邊認得 503、另一邊不認。**

### 決定二、iOS 也封頂 10 秒，與網頁版一致

總預算在**憑證拿到之後**才開始算——`budgeted(appCheckToken())` 那一段自有預算（`gemini-reading-native.ts:286` 的註解寫了非做不可的理由），維持現狀不動。

碼表到期時該講哪句話，規矩與票 07 相同：這一輪撞過 5xx 就丟最後那次的 `gemini.httpError`，一次都沒撞過才丟 `gemini.timeout`。

**iOS 有一條網頁版沒有的分支要處理。** 預算是交給 SDK 的，用完時 SDK 丟 `AbortError`，`toReadingError()` 把它翻成 `gemini.timeout`。那不在 `TRANSIENT` 裡，會被原樣丟出去——但若 `lastTransient` 有東西，該丟的是它。迴圈的 catch 要先擋這一種：

```ts
} catch (error) {
  // 預算是交給 SDK 的，用完時它丟 AbortError → 翻成 gemini.timeout。
  // 撞過 5xx 的話，使用者真正撞到的是 503，講成「等太久」跟事實對不上（票 07）。
  if (lastTransient !== null && isTimeout(error)) throw lastTransient;
  if (!isTransient(error)) throw error;
  lastTransient = error;
}
```

### 決定三、重試的判斷放在 `toReadingError()` 翻譯之後

`toReadingError()` 已經把 5xx 收斂成帶 `status` 參數的 `AppError`（`ai-logic-error.ts:69`），從 `error.params?.status` 讀得回狀態碼。

翻譯之後判斷有兩個好處：`lastTransient` 存的東西跟網頁版的 `lastTransient` 完全同一個形狀；而且不必在 `gemini-reading-native.ts` 裡把「怎麼從 SDK 錯誤挖出 status」抄第二份。

判斷函式（`isTransient`、`isTimeout`）跟迴圈放同一支就好，不必為它們再開一支檔案。

### 決定四、iOS 也顯示第幾次

`editor-view.ts:403` 那條 iOS 分支改成把 `onAttempt` 傳下去，並刪掉第 408 行那句過期的註解。`askReadingNative(term, onAttempt?)` 多收一個參數。畫面那一層全部現成，這一格幾乎是免費的。

### 決定五、真機驗收不是前置條件

比照票 07：離線那一段全過就算完工。真機上實際撞到 5xx 的那一天，再把「重試了幾次、額度剩多少」補進本票的 Comments——5xx 要碰運氣才撞得到，列成前置等於讓這張票無限期卡住。

**票 07 沒裝煞車那個決定在 iOS 上同樣有效**，理由與要量的數字見票 07「不設煞車是刻意的」那一節，不要在本票偷偷裝上去。

**有一件事離線守不住，據實記錄：** 那個「還剩幾毫秒」交給 SDK 之後，它是不是真照辦，只有真機測得出來。假貨測到的是我們自己寫的假貨。

#### 網頁版不要順手改

`askReading()` 裡那套重試已經上線、測試綠著。**不要為了共用而把它改成呼叫 `withRetry`。** 兩邊的碼表機制本來就不同（網頁版是一顆 `AbortController` 包住整支，iOS 是每次把剩餘毫秒交給 SDK），硬併會把一個能動的東西拆開重接。本票只碰非改不可的地方。

#### 驗收

1 到 6 全部離線跑得完，一次網路都不必上、一把金鑰都不必給。

1. `attempt` 第一次丟 503（翻譯過的 `AppError`）、第二次回正常 → `withRetry` 回傳正常那份。
2. 500、502、504 各一條，行為同上。
3. 400、403、404、429 各一條：一次就放棄，**`attempt` 只被呼叫一次**（數呼叫次數）。429 走的是 `gemini.quotaExhausted`、沒有 `status` 參數，這一條順帶釘住「挖不到 status 就不重試」。
4. `gemini.offline`（連不上）、`gemini.notJson`、`gemini.emptyReply`、`SilentError`：一次就放棄。
5. 一直丟 503 直到預算用完 → 丟出的是 `gemini.httpError`（status 503），**不是** `gemini.timeout`。
6. 一次 5xx 都沒撞過就預算用完 → 丟出的仍是 `gemini.timeout`，`{ seconds: 10 }` 那句沒有變樣。
7. 交給 `attempt` 的 `budgetMs` 逐次遞減，加總不超過 `TIMEOUT_MS`。
8. 回報的次數從 2 起算、逐次遞增。
9. `npm test` 全綠、`npm run typecheck` 乾淨。
10. iOS build 打得包（`npm run build` 的 ios 模式），而且**網頁版產物裡沒有 firebase**——新檔案若不小心 import 了執行期 firebase，這一條會抓到。

#### 為什麼是 ready-for-agent 而不是 ready-for-human

票面當初判 `ready-for-human` 的唯一理由是「測不到」。決定一把那個理由拆掉了：重試迴圈不碰 SDK，驗收 1 到 9 全部離線跑得完。剩下那件真機才守得住的事（SDK 收不收我們算的剩餘毫秒）已按決定五降級成上線後補記，不是動工的前置條件。
