# 07 — 503 這種「再試一次就會好」的失敗，現在一次都不重試

Status: needs-triage
Type: enhancement

## 怎麼發現的

2026-08-21，維護者在 dev server 打詞條，讀音預填失敗，畫面出：

```
Gemini 回了 503：This model is currently experiencing high demand.
Spikes in demand are usually temporary. Please try again later.
```

當時用的是 `gemini-3.6-flash`。細節記在 `reading-prefill` 票 06 的 Comments（2026-08-21 那則）。

## 病灶

`gemini-reading.ts` 的 `askReading()` 收到非 2xx 就直接丟出去：

```ts
if (!response.ok) {
  const why = await reason(response);
  throw ...   // ← 不分幾號，一律放棄
}
```

查過 `gemini-reading.ts`、`gemini-reading-native.ts`、`reading-editor.ts`：**整條路徑一行重試都沒有。**

而 503 那句話字面就是「請稍後再試」。這是最該自動重試一次的情況，我們卻直接把錯誤端到使用者臉上，讓他自己填讀音格。

## 為什麼只挑 503，不是全部重試

失敗分兩種。**再送一次會成功的**，跟**再送一百次都一樣的**。

| 狀況 | 哪一種 | 重試的後果 |
| --- | --- | --- |
| 503 那顆模型忙不過來 | 暫時 | **會成功**。Google 自己叫你等一下再試 |
| 連不上（`gemini.offline`） | 暫時 | 可能成功 |
| 400／403 金鑰不對 | 永久 | 一樣失敗。金鑰不會自己變對 |
| 404 型號叫不動 | 永久 | 一樣失敗 |
| 429 額度用完 | 中間 | 馬上重試**更糟**，額度燒更快。Google 會給 `retry in Ns`，要照它退避 |

所以本票的範圍是**只收暫時性那一類**。永久性失敗照舊直接放棄——重試只是讓使用者多等，結果一樣。

## 要決定的事

### 一、重試吃不吃同一份 10 秒預算（最擋路的一題）

`TIMEOUT_MS` 那 10 秒的碼表**包住整支 `askReading()`**：

```ts
const timer = setTimeout(() => controller.abort(), TIMEOUT_MS);
```

碼表一按下去，函式裡做什麼都算在同一份預算裡。所以第一次若花了 8 秒才回 503，**重試只剩 2 秒**，等於沒重試。

兩條路：重試自己一份新預算（總共可能等 20 秒），或共用一份（省事，但常常來不及）。

**這一題與票 06 綁在一起。** 票 06 目前決定不動秒數（維持 10 秒），換模型看能不能解決。本票若選「自己一份預算」，等於繞過那個決定，要一起看。

### 二、哪些狀態碼算暫時性

上面那張表只列了 503。但 500、502、504 是同一家族（都是伺服器那端出事）。**一起收還是只收 503？**

`gemini.offline`（連不上）要不要也重試？它現在是另一條分支，不走狀態碼那一段。

### 三、iOS 那條路要不要一起做

網頁版自己用 `fetch`，iOS 走 Firebase AI Logic 的 SDK，兩條路不同。

**那個 SDK 自己會不會重試，查不到。** 翻過 `node_modules/@firebase/ai` 的型別檔，沒有任何 retry 字樣。這不代表它沒做，只代表沒寫在型別裡。**動工前要先查證**，查完才知道 iOS 那半邊要不要動。

### 四、重試幾次、中間等多久

一次就好，還是兩次？中間要不要等？等固定秒數還是照 Google 給的 `retry in Ns`？

## 實作時會踩到的一件事

程式用 `AbortController` 當煞車。它的規矩是**踩過一次就永遠是踩下的狀態**，放不開。所以重試要開一顆新的，舊那顆怎麼收也要想清楚。

## 與票 05 的連動，要驗

重試代表**回覆更晚回來**。

而票 05 修的正是「回覆太晚回來，蓋掉使用者手打的讀音」。它已經 `done`，`settle()` 現在會先檢查讀音格有沒有字才套用。

**所以應該安全。但要實際驗一次**，不能只用推的。

## 好消息：不必上網就測得出來

`askReading()` 的第三個參數 `doFetch` 是呼叫端遞進來的（`network-seam` 票 02 留的縫）。測試可以餵一個「第一次回 503、第二次回正常」的假 fetch，斷言最後拿到的是正常那份。

`gemini-reading.test.ts` 已經有一整套這種寫法，照著加即可。

## 順序

**票 06 先做。** 換完 `flash-lite` 之後 503 還常不常出現，會直接影響本票值不值得做。若換完幾乎不再撞到，本票可以直接 `wontfix`。

## 驗收（等 triage 拍板上面四題之後再定稿）

- 假 fetch 第一次回 503、第二次回正常時，`askReading()` 回傳的是正常那份，使用者看不到錯誤。
- 假 fetch 兩次都回 503 時，使用者看到的仍是原本那句「Gemini 回了 503：⋯」，訊息沒有變樣。
- 400／403／404 一次就放棄，沒有多送任何一次請求（用假 fetch 數呼叫次數）。
- `npm test` 全綠。
