# 05 — 雲端備份的加解密：寫死標答，兩邊互相對得上

Status: ready-for-human
Type: enhancement
Blocked by: 02, 03

決策背景見 `../spec.md` 的〈雲端備份的加解密〉。

## 為什麼有這張票

雲端備份的內容是加密的。同一個人用電腦存上去的備份，手機必須解得開，反過來也一樣。

網頁版用瀏覽器內建的 `crypto.subtle`。React Native 上沒有，要換成 `react-native-quick-crypto`。**換掉之後加出來的東西，網頁版還解不解得開？**

**這是整條路上風險最高的一塊，而且它錯了不會當場報錯。** 存的時候一切正常，某天想還原才發現打不開，那時資料已經沒了。

這張票排在所有畫面之前，就是要讓這個風險早點曝出來。

## 要做什麼

### 標答檔

用**網頁版現有的** `cloud-crypto.ts` 產生一組固定的加密結果，存成標答檔進版控。

每一筆標答要記：明文、密碼、以及加密的完整輸出。**產生標答的那支腳本也要留著**，日後查得回這些數字怎麼來的。

明文至少要涵蓋：

- 純 ASCII 的短字串
- **日文**（漢字、平假名、片假名都要有）
- **帶讀音標記的詞條**（例如 `焦[こ]がす`）
- **表情符號**（會踩到多位元組邊界）
- **一份接近上限的長備份**（安全規則上限是 4 MB，約當 27,000 張卡）

只手動試一筆碰不到那些只在特定內容下才發作的錯，所以標答要涵蓋這些。

### 對拷測試

兩個方向都要測，而且 CI 每次都跑：

1. **網頁版加密的，React Native 解得開**，解出來與明文完全相同
2. **React Native 加密的，網頁版解得開**——同一組明文、密碼、鹽與初始向量下，兩邊的輸出要**位元級相同**

### 真機實測

自動測試之外，實際做一次：電腦上存一份備份到雲端，手機拉下來，內容對得上。

## 這張票不做的事

- **不改 `cloud-crypto.ts` 的演算法、參數或格式。** 網頁版是標準答案，這裡是讓 React Native 對齊它，不是相反。
- **不碰暱稱、密碼、指紋那套流程。** 只驗加解密本身。
- **不做金鑰搬遷。** Keychain 是另一張票。

## 若對不上

**停下來，不要繞路。** 對不上代表 `../spec.md` 列的最高風險成真了。把差在哪裡（哪一種明文、差在哪個位元組）記進本檔 `## Comments`，那是重新評估路線的依據，不是一個 bug。

## 驗收

- [x] 標答檔在版控裡，涵蓋上列五種明文，產生它的腳本也留著
- [ ] 兩個方向的對拷測試都過，且位元級相同
- [ ] 這組測試進 CI，每次都跑
- [ ] 真機實測做過一次：電腦存、手機拉，內容對得上

## Comments

### 2026-08-25 — 做完了什麼，還缺什麼

先講最要緊的一句：**`react-native-quick-crypto` 到現在一次都還沒真的跑過。** 網頁版那一半
（標答表、對拷、CI）本機驗完了；手機那一半的程式碼與 CI 接線都寫好了，但要跑在 iOS 上，
而維護者這台是 Windows。驗收第 2、3、4 條因此都還開著。

#### 為什麼手機那一半在 CI 的 Linux 機器上驗不到

拆開套件看過：`src/hash.ts` 有個靜態欄位，模組**一被 import 就**去要原生模組
（`NitroModules.createHybridObject('Hash')`）。那層是 C++，Node 裡不存在，當場丟例外。
不是「叫到才爆」，是「載入就爆」，所以任何跑在 Node 上的測試都碰不到它。

四題拍板的結果（2026-08-25，維護者選的）：

| 題目 | 選了 |
| --- | --- |
| 手機那一半在哪驗 | 另建一支 macOS 自動流程，在 iOS 模擬器裡跑 |
| 4 MB 那列怎麼記 | 現場產生明文，只存產生規則與密文的 SHA-256 指紋 |
| CI 怎麼接 | 另開只跑測試的流程，不動 `deploy.yml` |
| 兩支流程的關係 | 同時跑，各自有各自的重跑按鈕 |

#### 標答表

`core/lib/cloud-crypto-vectors.json`，5 KB，六列。由
`scripts/generate-crypto-vectors.mjs` 用**網頁版現有的** `cloud-crypto.ts` 產生，
`cloud-crypto.ts` 一個字沒改。

| 列 | 明文 | 位元組 |
| --- | --- | --- |
| `ascii-short` | 純 ASCII | 35 |
| `japanese-mixed` | 漢字、平假名、片假名 | 76 |
| `reading-markup` | 帶讀音標記的詞條 | 81 |
| `emoji` | 表情符號（含代理對、ZWJ 家庭、國旗、膚色修飾） | 97 |
| `japanese-credentials` | 暱稱與密碼本身是日文 | 62 |
| `huge-backup` | 19,417 張卡的長備份 | 3,145,554 |

第五列是票上沒點名、多加的。票說「至少要涵蓋」，所以不算超出範圍。加它的理由：暱稱是
salt、密碼是金鑰原料，兩者都要先過 UTF-8 編碼，而那一步在兩個執行環境上未必一致——
對不上的話「別人覆寫不了」那道防線就是假的。

`huge-backup` 的明文不存進版控，只存「拿這段重複 19,417 次」與密文的 SHA-256。**位元級
比對照樣成立**：指紋不同就是有位元不同。而「解得開」那一項對這一列改用自己加出來的那份去解，
只有在位元級那一項過了的時候才成立——所以位元級紅燈時這一列直接跳過「解得開」，
不會多印一行綠的讓人誤以為只壞了一半。

初始向量取自每一列名字的 SHA-256 前 12 位元組，不是亂數。標答要重現，這一步就不能隨機。
**正式使用時仍然是真亂數**，換掉的是亂數來源不是 `cloud-crypto.ts`。

#### 對拷測試

`core/lib/cloud-crypto-vectors.test.ts`，一列三項：指紋與路徑、位元級相同、解得開。
故意把一個位元改掉驗過，測試當場紅燈並印出「第 N 個字起不同」。
（第一版寫成四項，多的那一項是空的，見底下的 review 修正。）

比對邏輯抽在 `core/lib/cloud-crypto-vectors.ts`，三個地方跑同一份：vitest、jest、
以及手機上的 `mobile/lib/crypto-self-check.ts`。**只有第三個驗得到真正的風險**，
前兩個守的是「標準答案不准漂」。

#### CI

兩支新流程，`deploy.yml` 與 `ios-testflight.yml` 一行未改。

| 檔 | 跑在哪 | 什麼時候 | 驗什麼 |
| --- | --- | --- | --- |
| `test.yml` | Linux ×2 | 除文件外任何改動 | 網頁版 + 手機版 Node 跑得動的部分 |
| `mobile-crypto.yml` | macOS | 改到 `core/`、`mobile/` | 模擬器裡跑 quick-crypto |

`mobile-crypto.yml` 的做法：`expo prebuild` → Release 設定 `xcodebuild`（JavaScript 打包進
app，不需要 Metro）→ `simctl install` + `launch` → 等 app 把結論寫成
`Documents/crypto-vectors.txt` → 撈出來看有沒有 `PASS`。

不去日誌裡撈那一行，是因為 Release 版對 `console.log` 的處理與 Debug 版不一樣，
日誌串流又會把系統訊息插在中間。檔案沒有這些不確定。

#### 環境補丁

`mobile/lib/install-crypto.ts`，取代原本的 `install-random-uuid.ts`。合成一支是因為
**三件事的順序不能換**：quick-crypto 的 `install()` 是整個換掉 `global.crypto`，
先補的會被它連盤端走。

補三樣：`crypto.subtle`（quick-crypto）、`crypto.randomUUID()`（quick-crypto 自帶，
沒有才退回 `expo-crypto`）、`btoa()`／`atob()`（Hermes 有就用它的，沒有才退回
`react-native-quick-base64`）。第三樣是查不出答案才寫成有條件的——查不到 Hermes 各版本
到底有沒有內建，真機開起來就知道了。

#### 順手發現的：`ITSAppUsesNonExemptEncryption` 現在是錯的

`mobile/app.json` 那個 `false` 從這張票開始不成立了。PBKDF2 加 AES-GCM 鎖使用者資料，
不是只走 HTTPS、也不是只做身分驗證，兩個常見豁免都不適用；OpenSSL 是跟著 app 帶進去的，
「只用作業系統內建加密」那條也走不通。

沒有在這張票改掉——改法牽到出口管制申報，屬於票 `ios-app 11`（送審）。
`mobile/README.md` 已經寫成醒目的警告方塊。**那張票拍板之前不要送審。**

### 2026-08-25 — code review 抓出來的，都改了

#### 一、4 MB 那條線我量錯地方了（最要緊）

第一版把 4 MB 套在**明文**上，做出 4,194,180 位元組的明文。但
`core/lib/cloud-backup.ts:131` 擋的是 `payload.length > CLOUD_PAYLOAD_LIMIT`——
**那條線量的是加密後那串 base64 的字數**。那份明文加密出來是 5,592,280 字，
超過真正的上限 33%。

也就是說那一列驗的是**一份這支 app 根本不會送出去的備份**。看起來有在守，
實際上守的是一個不存在的情況——比沒有這一列更糟。

改成用密文倒推：19,417 張卡、明文 3,145,554 位元組、密文 4,194,112 字，
離上限只差 192 字。腳本現在算完會自己檢查一次，超過就當場停下來；測試也改成
斷言 `payloadChars`，而且從 `cloud-backup.ts` import 那個上限常數，不自己抄一份數字。

**張數與票上寫的 27,000 對不起來，那是對的。** 票上那個數字來自 `ADR-0003` 量到的
「每張卡加密後約 155 位元組」平均值；標答用的那張卡帶著完整的識別碼、讀音標記與表情符號，
加密後是 216 字，比平均重。同一條 4 MB 的線，裝得下的張數自然少一些。

#### 二、「密文裡看不到明文片段」那項檢查是空的

密文是 base64，而每一列明文都含 `{`、`"` 或日文——那些字元不在 base64 的字母表裡，
所以那一項**永遠不會紅燈**。四項檢查實際只有三項，而驗收把它當四項在算。

刪掉了，`checkVector()` 現在明講是三項，並寫明為什麼不需要第四項：密文對得上標答，
就不可能是明文原樣送出去，第 2 項已經涵蓋。

#### 三、其餘五處

- **「解得開」沒照自己寫的邏輯跳過。** 註解說位元級那項沒過就不必看了，程式照跑。
  超大那列會同時印出「密文不同」與「解得開」，讀起來像只壞了一半。改成真的跳過。
- **假的亂數來源會波及別人。** 它換的是全域，而比對在手機上要跑好幾秒，那幾秒內
  畫面沒停住。加了長度判斷：只接管「抽 12 個位元組當初始向量」那一種呼叫，
  其餘原封轉給真的那一份。（查過 quick-crypto 的 `randomUUID` 走的是
  `randomFillSync`、不經過這個全域，所以實際上沒被波及，但這個防呆便宜。）
- **CI 有一處會靜靜失敗。** `ls -d ios/*.xcworkspace | head -1` 的錯誤碼被 `head`
  吃掉（那一步的 shell 沒開 `pipefail`），變數變空字串一路帶到 `xcodebuild`。補了守衛。
- **CI 判定有競態。** 原本等「檔案存在」，但 app 那邊是先開檔再寫內容兩步，
  檔案在開檔當下就存在了。改成等 `[crypto-vectors]` 那一行真的寫進去。
- **兩處小的**：`findMissing()` 的 docblock 掛錯函式；`expand()` 裡
  `repeat === 1` 那個三元多餘（`repeat(1)` 就等於原字串）；產生腳本用張數當
  「要不要存密文」的暗號，改成看配方有沒有設 `fillToPayload`；JSON 裡的
  `iterations` 沒有任何程式讀它，拿掉。

#### 沒改的一項

`test.yml` 順手加了 `npm run typecheck`。Spec 軸點出票上沒要求這個，屬於輕微超出範圍。
留著：兩邊各 20 秒，而型別錯了測試往往還是綠的——這正是這張票在防的那種
「不會當場報錯」的錯。

### 2026-08-25 — CI 第一趟就掛了：`@babel/runtime` 找不到

`test.yml` 的 `mobile` 工作四支測試全部載不進來，錯是
`Cannot find module '@babel/runtime/helpers/interopRequireDefault' from '../core/i18n/index.ts'`。

**本機看不出來，是因為 repo 根自己也有一份 `node_modules` 剛好接住了。** 找套件的規矩是
從用它的那個檔往上層走：`core/` 住在 `mobile/` 外面，所以從 `core/i18n/index.ts` 往上走
會走到 repo 根，永遠走不進 `mobile/node_modules`。CI 上那個工作只在 `mobile/` 裡裝套件，
根目錄是空的。

去叫 `@babel/runtime` 的不是 `core/` 的原始碼——那批一個外部套件都沒 import——
是 **babel 轉譯後產生的程式碼**，每個檔都會帶。

修法兩行：`jest.config.js` 加 `moduleDirectories`，多看一個 `mobile/node_modules`；
`package.json` 把 `@babel/runtime` 明列進去，不靠「剛好有別的套件把它帶進來」。
在本機把根目錄那份藏起來重現過同一個錯，修完在同樣條件下 124 支全過。

**Metro 那條路沒有跟著改。** 它也只裝 `mobile/` 的套件，理論上同一個坑，
但票 `04` 的真機驗收已經證明那條路是通的——探針畫面讀得到 MMKV，走的就是
`core/lib/storage.ts` 轉譯後的程式碼。沒有觀察到問題就去改設定是瞎猜，留著。
真機那一趟若在這裡掛掉，答案就在這一段。
