## 現成的東西

**純邏輯一行都不必改**，`core/lib/` 底下兩支已經在那裡：

- `core/lib/reminders.ts`（61 行）：哪一天會積到幾張到期卡。不取用系統時鐘、不碰原生 API。
- `core/lib/daily-reminder.ts`（304 行）：把預估翻成一批要登記的通知、記住這台有沒有開提醒、
  資料變動時重排。同樣不碰原生 API——**怎麼登記通知由呼叫端遞進來**。

要接的只有 `ReminderNative` 那三支方法（`daily-reminder.ts:65`）：問權限、要權限、整批換掉。
Capacitor 那一端的接線在 `src/lib/daily-reminder-native.ts`，可以照著看，但**實作不能照抄**——
那一支底下是 app 自己寫的 Swift 插件（`ios/App/App/DailyReminderPlugin.swift`）。

畫面那一區的樣子照網頁版 `src/ui/data-view.ts` 的 `reminderSection()`：一個開關加一格時間，
外加權限被拒絕時那句話（`data.reminderDenied`）。**時間格用系統那個滾輪**，
自己做一個只會比它差。

## 已經決定的事

2026-09-02 一輪問完，四條的答案：

1. **原生那一端用 `expo-notifications`，不自己寫 Swift 模組。** 與 Capacitor 版相反，
   理由是那邊的成本估算在這裡不成立：`mobile/.gitignore` 把 `/ios` 排除掉了，原生專案
   每次建置重新產生，所以「自己寫 Swift」除了那支檔還要多寫一支設定檔外掛把它塞進去
   （像 `mobile/plugins/with-app-check-first.js`），再加上新架構的接線。實質是兩份工，
   換掉的只是一條官方套件的依賴。
2. **`FORECAST_DAYS` 維持 7，這張票不動它。** 上限是同時登記 64 則，七則離得很遠，
   而且這個數字正在網頁版與 Capacitor 版上跑，沒有出過問題。
3. **重排接在 `onPersisted`，與雲端推送同一根掛勾**（`mobile/lib/app-context.tsx` 現在
   寫的是 `onPersisted: (data) => cloud.push(data)`）。網頁版 `src/app.ts` 的 `persist()`
   就是把兩件事排在一起，兩邊對齊。另外兩個呼叫點照網頁版補上，見 brief。
4. **開關一列，「提醒時間」另一列，時間格是同一列右邊的膠囊，點下去在原地展開滾輪。**
   對照組是 iOS 內建「提醒事項」設日期時間的樣子。**不是**推入子畫面——為了改一個時刻
   進出兩層太重。

### Agent Brief

**Category:** enhancement

**Summary:** 把 `core/lib/daily-reminder.ts` 的 `ReminderNative` 三支方法接到 `expo-notifications`
上，並在資料頁長出「每日提醒」那一組清單。

**Current behavior:**

純邏輯早就在了，但手機端沒有任何一處呼叫它。`createDailyReminder()` 需要一個 `ReminderNative`
實作（`permission()`、`request()`、`replaceAll()`），React Native 這一側還沒有人提供。
資料頁目前只有介面語言、雲端備份、手動備份三組，沒有提醒那一組。開關與時間都無處可設，
通知一則也不會登記。

Capacitor 版有一份可以對照的接線（`src/lib/daily-reminder-native.ts`），但**底下是 app 自己寫的
Swift 插件，實作不能照抄**——只有「把橋的包裝拆掉、還原成乾淨形狀」那個模式值得借。

**Desired behavior:**

資料頁在「雲端備份」與「手動備份」之間多一組「每日提醒」。關著時只有一列開關；打開後底下
多一列「提醒時間」，右邊是一顆時間膠囊，點下去在原地展開系統滾輪，不換頁。滾輪跟著系統的
12／24 小時制走。

第一次打開開關時請求通知權限。被拒絕時開關彈回關閉，並在群組底下顯示 `data.reminderDenied`。
已經被拒絕過就不再請求第二次——這些判斷全部住在 `createDailyReminder()` 裡，接線層不重寫。

畫出這一組時先照記著的狀態畫，再呼叫 `verify()` 確認權限還在；拿到 false 就把開關彈回去。
使用者可能剛從系統設定把通知關掉，一個亮著卻收不到提醒的開關是 spec 決定二十四明文禁止的。

資料一變就整批重排，三個呼叫點照網頁版 `src/app.ts` 補齊：本機存完一份新資料時、整份資料被
換掉時（匯入單字、整份匯入、雲端拉下來）、以及開機畫面出來之後。第三個是必要的——排的是
未來七天，只靠資料變動觸發的話，一個「開了 app 卻沒複習」的人在第八天之後完全收不到提醒。

**Key interfaces:**

- `ReminderNative`（`core/lib/daily-reminder.ts`）：接線層要提供的就是這三支。`permission()`
  與 `request()` 回 `'granted' | 'denied' | 'prompt'`；`replaceAll()` 收一整批 `ScheduledReminder`，
  語義是「先清光已登記的，再登記這一批」，空陣列即為全部清掉。**不要拆成清空與登記兩支。**
- `ScheduledReminder` 的 `month` 是 1–12，刻意不沿用 `Date` 的 0–11：年月日時分是要交給原生那側

#### 三處與票上寫的不同

**一、`expo-notifications` 的設定檔外掛沒有加進 `app.json`。** 2026-09-02 動工中維護者拍板。

那支外掛在 iOS 上只做三件事：塞一條 `aps-environment` entitlement、搬自訂通知音效檔、
開遠端推播的背景模式。後兩件這支 app 都不做，第一件是**遠端推播**的宣告，而這張票只做本地通知
（〈Out of scope〉第三條）。加了它，建置出來的 app 會帶著推播 entitlement，簽章時 Apple 會回頭查
這個 App ID 有沒有開 Push Notifications 能力，沒開就當場失敗——為了一個一則都不會發的功能。

**不加它，本地通知一件事都不會少**：原生模組是靠 autolinking 進去的
（`node_modules/expo-notifications/expo-module.config.json` 列著十個 module 與一個
AppDelegate subscriber），與設定檔外掛無關。理由的正本寫在
`mobile/lib/daily-reminder-native.ts` 的檔頭。哪天真的要做遠端推播，那時再把它加回來。

`@react-native-community/datetimepicker` 的外掛同樣沒加——它整支只改 Android 的樣式資源。

**二、兩種新的列做成 `SettingsRow` 的兄弟，不是它的參數。** 票上寫「加在既有的那支元件裡」。
三支共用同一份 `styles`，列高、左右內距、分隔線的起算點都是同一套，票要的「不走鐘」成立。
分開的理由是按法不同：`SettingsRow` 整列是一顆按鈕，另兩支整列不能按，按的是右邊那個控制項
本身（iOS 的「設定」也是這樣）。壓成一支會多出「有開關就不要包 Pressable」這種互斥規則，
而那種規則寫錯了編譯器不會攔。

**三、時間膠囊就是系統那個 `UIDatePicker` 本身**（`display="compact"`），不是自己畫一顆膠囊再去
叫滾輪。因此 12／24 小時制、字級、深淺色、展開的動畫全部跟著系統走。這是決定四那句
「時間格是同一列右邊的膠囊，點下去在原地展開滾輪」最直接的走法。

#### 一個差點踩下去的坑

`expo-notifications` 的文件頁把 `CALENDAR`、`MONTHLY`、`YEARLY` 三種觸發排在一起，其中一句
「所有欄位照 JavaScript `Date` 的範圍，一月是 0」讀起來像三種共用。**那句話只掛在後兩種上**：
翻原始碼，只有 `MonthlyTriggerRecord` 與 `YearlyTriggerRecord` 的 Swift 寫著 `month + 1`，
`CalendarTriggerRecord` 是把數字原封塞進 `DateComponents`（1 起算）。

照文件改成 0 起算的話，整批通知會排到前一個月，而且在這台機器上測不出來。
`ScheduledReminder.month` 定成 1–12 剛好直接對得上，一個 `-1` 都不必寫。理由寫在程式碼註解裡。

#### 雙軸審查抓到的四個真缺口，都已修

**一、開關的誠實在 tab 架構下失效（最重的一條）。** 網頁版每次進「資料」畫面都重建整片 DOM，
所以 `verify()` 問一次就夠了。**手機版的四個 tab 底下是 `UITabBarController`**
（`mobile/app/_layout.tsx`），畫面掛上去之後就不卸載——切走再切回來不會重跑 `useEffect`，
從 iOS 設定 app 切回前景更不會。原本的寫法讓驗收第 10 條必掛：開關會一直亮著。

修法是多接一條 `AppState` 的 `active`，與那次 `useEffect` 共用同一支檢查。加了 2 條測試。

**二、開機那次重排掛在「這台要不要接雲端」那一問的 `.then` 裡。** 那一問萬一被拒絕，
提醒就整趟不排。網頁版 `finishBoot()` 是無條件叫它。已搬出 promise 鏈。

**三、同一個閉包裡兩套時鐘。** 複習佇列拿的是遞進去的 `now: () => new Date()`，提醒卻直接
`new Date()`。已收成一支 `now`，兩處共用——通知上的日子與佇列建的日子必須用同一把尺量。

**四、`onPersisted` 上疊了兩塊 JSDoc**（票 `13` 那塊沒清掉）。已併成一塊。

其餘幾處小疵一併修掉：`en.ts`／`ja.ts` 補上指回 `zh-Hant.ts` 的註解、三處 import 排序、
一行貼錯位置的棄用說明、以及「為什麼不跟 `core` 共用那段 `HH:MM` 換算」的說明。

#### 駁回一項

Standards 軸建議把資料頁那四格提醒狀態（開關、時刻、被拒絕、正在問）收成一個 `useReducer`，
理由是它們永遠一起動。**不改**：四個 `useState` 在這裡讀起來比一個 reducer 直接，
而「先叫 `reminder` 再把答案抄回來」那個模式本身就是刻意的——事實住在 `reminder` 那台機器裡，
這四格只是畫面現在顯示什麼。收成 reducer 不會讓那件事更清楚，只是多一層轉譯。
