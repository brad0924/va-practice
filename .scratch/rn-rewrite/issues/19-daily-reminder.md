## 為什麼有這張票

`../spec.md`〈原生功能〉列了四項要在 React Native 上重接，`ADR-0015` 寫明這四項是通過
App Store 審查準則 4.2（Minimum Functionality）的實質內容，少一項就是一支「把網站裝進殼裡」
的 app，會被退件。

| 項目 | 狀態 |
| --- | --- |
| 原生日文語音 | 票 `06` 已收；票 `11` 追一處落差，仍開著 |
| 評分觸覺 | 票 `08`，已收 |
| Keychain 存密碼 | 票 `17` |
| **每日提醒** | **這張票** |

它本來排在資料頁那張票裡。2026-09-01 拍板拆出來，理由是它與資料頁另外三區**沒有任何共用的東西**：
要裝 `expo-notifications`、加設定檔外掛、走一次系統通知權限、排未來七天的通知，
而且資料變動時整批要重排。混在一起的話資料頁那張票的驗收會卡在通知權限這一關。

## 現成的東西

**純邏輯一行都不必改**，`core/lib/` 底下兩支已經在那裡：

- `core/lib/reminders.ts`（61 行）：哪一天會積到幾張到期卡。不取用系統時鐘、不碰原生 API。
- `core/lib/daily-reminder.ts`（304 行）：把預估翻成一批要登記的通知、記住這台有沒有開提醒、
  資料變動時重排。同樣不碰原生 API——**怎麼登記通知由呼叫端遞進來**。

要接的只有 `ReminderNative` 那三支方法（`daily-reminder.ts:65`）：問權限、要權限、整批換掉。
Capacitor 那一端的接線在 `src/lib/daily-reminder-native.ts`，可以照著看，但**實作不能照抄**——
那一支底下是 app 自己寫的 Swift 插件（`ios/App/App/DailyReminderPlugin.swift`）。

畫面那一區的樣子照網頁版 `src/ui/data-view.ts` 的 `reminderSection()`：一個開關加一格時間，
外加權限被拒絕時那句話（`data.reminderDenied`）。**時間格用系統那個滾輪**，
自己做一個只會比它差。

## 已經決定的事

2026-09-02 一輪問完，四條的答案：

1. **原生那一端用 `expo-notifications`，不自己寫 Swift 模組。** 與 Capacitor 版相反，
   理由是那邊的成本估算在這裡不成立：`mobile/.gitignore` 把 `/ios` 排除掉了，原生專案
   每次建置重新產生，所以「自己寫 Swift」除了那支檔還要多寫一支設定檔外掛把它塞進去
   （像 `mobile/plugins/with-app-check-first.js`），再加上新架構的接線。實質是兩份工，
   換掉的只是一條官方套件的依賴。
2. **`FORECAST_DAYS` 維持 7，這張票不動它。** 上限是同時登記 64 則，七則離得很遠，
   而且這個數字正在網頁版與 Capacitor 版上跑，沒有出過問題。
3. **重排接在 `onPersisted`，與雲端推送同一根掛勾**（`mobile/lib/app-context.tsx` 現在
   寫的是 `onPersisted: (data) => cloud.push(data)`）。網頁版 `src/app.ts` 的 `persist()`
   就是把兩件事排在一起，兩邊對齊。另外兩個呼叫點照網頁版補上，見 brief。
4. **開關一列，「提醒時間」另一列，時間格是同一列右邊的膠囊，點下去在原地展開滾輪。**
   對照組是 iOS 內建「提醒事項」設日期時間的樣子。**不是**推入子畫面——為了改一個時刻
   進出兩層太重。

### Agent Brief

**Category:** enhancement

**Summary:** 把 `core/lib/daily-reminder.ts` 的 `ReminderNative` 三支方法接到 `expo-notifications`
上，並在資料頁長出「每日提醒」那一組清單。

**Current behavior:**

純邏輯早就在了，但手機端沒有任何一處呼叫它。`createDailyReminder()` 需要一個 `ReminderNative`
實作（`permission()`、`request()`、`replaceAll()`），React Native 這一側還沒有人提供。
資料頁目前只有介面語言、雲端備份、手動備份三組，沒有提醒那一組。開關與時間都無處可設，
通知一則也不會登記。

Capacitor 版有一份可以對照的接線（`src/lib/daily-reminder-native.ts`），但**底下是 app 自己寫的
Swift 插件，實作不能照抄**——只有「把橋的包裝拆掉、還原成乾淨形狀」那個模式值得借。

**Desired behavior:**

資料頁在「雲端備份」與「手動備份」之間多一組「每日提醒」。關著時只有一列開關；打開後底下
多一列「提醒時間」，右邊是一顆時間膠囊，點下去在原地展開系統滾輪，不換頁。滾輪跟著系統的
12／24 小時制走。

第一次打開開關時請求通知權限。被拒絕時開關彈回關閉，並在群組底下顯示 `data.reminderDenied`。
已經被拒絕過就不再請求第二次——這些判斷全部住在 `createDailyReminder()` 裡，接線層不重寫。

畫出這一組時先照記著的狀態畫，再呼叫 `verify()` 確認權限還在；拿到 false 就把開關彈回去。
使用者可能剛從系統設定把通知關掉，一個亮著卻收不到提醒的開關是 spec 決定二十四明文禁止的。

資料一變就整批重排，三個呼叫點照網頁版 `src/app.ts` 補齊：本機存完一份新資料時、整份資料被
換掉時（匯入單字、整份匯入、雲端拉下來）、以及開機畫面出來之後。第三個是必要的——排的是
未來七天，只靠資料變動觸發的話，一個「開了 app 卻沒複習」的人在第八天之後完全收不到提醒。

**Key interfaces:**

- `ReminderNative`（`core/lib/daily-reminder.ts`）：接線層要提供的就是這三支。`permission()`
  與 `request()` 回 `'granted' | 'denied' | 'prompt'`；`replaceAll()` 收一整批 `ScheduledReminder`，
  語義是「先清光已登記的，再登記這一批」，空陣列即為全部清掉。**不要拆成清空與登記兩支。**
- `ScheduledReminder` 的 `month` 是 1–12，刻意不沿用 `Date` 的 0–11：年月日時分是要交給原生那側
  直接組出當地時間的觸發時刻的，中間不多一層解析。
- `planReminders(cards, now, time)`：接線層遞給 `createDailyReminder()` 的 `plan` 就呼叫它，
  吃的卡必須與 `buildQueue()` 同一批（複習範圍內的），否則通知上的數字與打開 app 看到的對不起來。
  網頁版接線是現成的對照。
- `ReviewSessionHooks` 的 `onPersisted`：重排掛在這裡，與雲端推送並排。
- **`SettingsRow` 目前長不出開關，也長不出時間膠囊。** 它現在只支援「右邊灰字」、「打勾」、
  「`›`」、「紅字」四種右側形狀（票 `18` 建的）。這張票要替它加一種帶開關的列、一種帶時間
  膠囊的列。**加在既有的那支元件裡，不要在資料頁自己畫一列**——三頁共用同一套列高與分隔線，
  各畫各的就會走鐘。列高仍走 `TAP_SIZE`，理由的正本在該檔檔頭（HIG `L-07`）。
- 新依賴兩條，**都要裝在 `mobile/package.json`**，不是 repo 根目錄（票 `12` 的相依守門，
  CI 只在 `mobile/` 裡裝套件）：
  - `expo-notifications`：對上三支方法。它的設定檔外掛要加進 `mobile/app.json` 的 `plugins`。
    iOS 的通知權限**不需要** Info.plist 的用途說明字串，別加一條不存在的需求。
  - 時間滾輪那一支（`@react-native-community/datetimepicker` 或當時 Expo 文件指定的等價套件）。
    **不要自己用 ScrollView 做一個滾輪**，那只會比系統的差。
- **i18n 有一處要處理，不能照搬。** 網頁版把開關與時間讀成一句話：`data.reminderToggle`
  在繁中是「每天提醒我，」（結尾有逗號）、英文是 `Remind me every day`，而 `data.reminderTime`
  繁中是「提醒時間」、**英文只有 `at`**。拆成分組清單的兩列之後，殘留的逗號與孤立的 `at`
  都讀不通。三語各自看過一遍，該補新鍵就補（沿用 `data.reminder*` 的命名）。
  `data.reminderHint` 放群組底下的小字，`data.reminderDenied` 放狀態那一段。
  `reminder.title` 與 `reminder.body` 是通知本身的字，那兩支不動。

**Acceptance criteria:**

- [ ] 資料頁在「雲端備份」與「手動備份」之間出現「每日提醒」那一組
- [ ] 開關關著時只有一列；打開後底下多出「提醒時間」那一列
- [ ] 點時間膠囊，滾輪在原地展開，不推入新頁；跟著系統的 12／24 小時制走
- [ ] 第一次打開開關會跳系統的通知詢問對話框
- [ ] 按「不允許」後開關自己彈回關閉，群組底下出現 `data.reminderDenied` 那段字
- [ ] 允許之後把時間設成兩分鐘後、鎖上螢幕，兩分鐘後鎖定畫面出現通知
- [ ] 通知內文的張數與打開 app 後複習畫面上的張數一致
- [ ] 把今天的卡全部複習完，當天不再收到通知（同樣用「兩分鐘後」驗證）
- [ ] 關掉開關後，先前已排的通知全部不再送達
- [ ] 到「設定 → JP Vocab → 通知」把通知關掉，回到資料頁，開關自己彈回關閉並顯示那段字
- [ ] 隔天打開 app，收到的是依新的一天排出來的一批，數字跟著當天的到期張數走
- [ ] 繁中、英文、日文三種介面語言下那一區的字都完整，沒有殘留的逗號或孤立的 `at`
- [ ] `mobile` 的 `npm test` 與 `tsc --noEmit` 綠燈（票 `12` 的守門，新依賴要進 `mobile/package.json`）

**觀察項（真機驗收時特地看一眼，不是驗收條件）:**

每次評分都會走一趟 `native.permission()`。整批重排本身有節流——`createDailyReminder()` 用
「一份待辦加一個進行中」把連續的變動壓成最新那一批——但**權限查詢不在那道閘門裡**，
連評三十張卡就是三十次查詢。那是讀本機設定、不連網，理論上很便宜，但沒有人在真機上量過。
評分手感真的變頓的話**另開票**，不要在這張票改共用程式碼：`core/lib/daily-reminder.ts`
同時服務網頁版與 Capacitor 版。

**Out of scope:**

- **`core/lib/reminders.ts` 與 `core/lib/daily-reminder.ts` 一行都不改**，包含 `FORECAST_DAYS`（維持 7）
  與上面那條節流觀察
- Capacitor 版那一側（`src/lib/daily-reminder-native.ts`、`ios/App/App/DailyReminderPlugin.swift`）不碰
- 遠端推播（push notification）。這張票只做本地通知
- 通知的動作按鈕、分組摘要、自訂聲音
- 票 `11` 的日文語音落差，那是另一張票
