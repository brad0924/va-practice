# 13 — 標答比對從 app 裡搬出去，CI 另找辦法跑得到

Status: ready-for-agent
Type: enhancement
Blocked by: 14

決策背景見票 `05` 的〈動手前查掉的兩件事〉、`mobile/lib/app-context.tsx` 的開機那一段，
以及 `mobile/lib/crypto-self-check.ts` 的檔頭。

## 為什麼有這張票

**使用者每次開 app 等的那幾秒，是 CI 需求的副作用。**

票 `05` 驗收第 3 條寫的是「這組測試進 CI，每次都跑」——**指的是 CI**。
票 `05` 從來沒有決定過「使用者每次開 app 都要跑一次」。

那是接線的後果。`app-context.tsx` 自己寫著理由：

> **它掛在這裡而不是「資料」那一頁，是刻意的。** CI 只是把 app 開起來然後等結論寫成檔案
> （`.github/workflows/mobile-crypto.yml`），改成進頁才跑的話那支流程會永遠等不到。

`mobile-crypto.yml` 的做法是：在 iOS 模擬器裡開 app → 等 app 把結論寫成
`crypto-vectors.txt` → `grep -q ' PASS ' "$RESULT" || exit 1`。所以比對**必須在開 app 時自動跑**。

而使用者手上的 app 跟 CI 跑的是同一份程式碼，沒有分岔。於是每個人都跟著跑。

## 使用者為此付了三樣代價

| 代價 | 說明 |
| --- | --- |
| 每次開 app 等幾秒 | 表裡最後一筆明文有 4 MB，PBKDF2 又刻意跑得慢 |
| 那六個公開的初始向量每次啟動外洩一次 | `encryptWithFixedIv()` 換掉的是**全域**亂數來源，那幾秒內雲端備份去抽 12 個位元組就中 |
| FAIL 完全沒有作用 | `openGate()`、`cloudReady`、`push()` 三處都不看 `passed` |

第二樣是票 `10` 那道閘門存在的全部理由。**比對搬走，閘門就不必存在。**

第三樣現在只有「資料」tab 上一行紅字看得到，而那行字住在 `probe-screen.tsx`——
那支檔明寫「資料頁一做好，這整支檔案就地被取代」。取代之後 FAIL 會變成完全靜默。

## 這不是票 05 的疏忽

票 `05` 要的是「手機那一半驗得到」，它做到了，而且真機 `PASS 6/6`。
它沒有處理的是**跑的頻率**與**跑的位置**——那時候還沒有導覽列、沒有資料頁，
整支 app 只有一個探針畫面，「掛在開機」是當時唯一的選擇。

## 要做什麼

把「跑比對」從使用者的啟動路徑上拿掉，同時讓 CI 照樣驗得到
**真的 `react-native-quick-crypto`**——那是這條線上唯一驗得到最高風險的地方，不能一起丟掉。

跑在 Node 上的測試取代不了它。票 `05` 拆過套件：`src/hash.ts` 有個靜態欄位，
模組**一被 import 就**去要原生模組（`NitroModules.createHybridObject('Hash')`），
那層是 C++，Node 裡當場丟例外。**不是「叫到才爆」，是「載入就爆」。**

### 一併要收掉的東西

拿掉之後有三處會斷，必須同一張票處理：

- **`gate` 整組刪掉**（`app-context.tsx`）。沒有人鎖亂數來源了，閘門沒有存在的理由。
  留著的話 `openGate()` 沒人叫，`gate.open` 永遠是 `false`，雲端備份整條斷掉。
- **`vectors` 那一格**（`AppShared`、`data.tsx`、`probe-screen.tsx`）。
  它永遠是 `null` 的話，探針畫面的 `cloudReady` 永遠是 `false`，登入按鈕永遠灰著。
- **票 `10` 的接線點**。那張票原本要接在 `openGate()` 裡，閘門沒了就改接在
  `AppProvider` 的 `useEffect`。票 `10` 因此 `Blocked by: 13`。

## 卡住的地方：CI 要怎麼另找辦法

**這一段在 2026-08-27 的 triage 拍板了，見底下的 Comments 與 Agent Brief。**
以下三行是開票當時的紀錄，保留不刪；動工時一律以 Brief 為準。

要的東西是「CI 觸發得到、使用者觸發不到」。想得到的方向，都還沒有查證過：

- 一個只有模擬器吃得到的環境變數或啟動參數
- 一支只在 CI 建置裡才進得去的路由
- 換掉整個做法：不開 app，改用別的方式在模擬器上跑那段程式碼

**動工前要先把這一段 grill 出結論。** 選錯的代價是那支流程失效而沒有人發現——
跟票 `12` 記的「本機綠、CI 紅」是同一類病，只是方向相反。

## 這張票不做的事

- **不動 `core/lib/cloud-crypto.ts`。** 票 `05` 那條規矩照舊：網頁版是標準答案。
- **不動標答表的內容。** 換掉表裡的測試暱稱是票 `14`。
- **不做資料頁。** FAIL 該長什麼樣、該顯示在哪，屬於資料頁那張票。
  這張票只負責「不要讓它靜默地消失」——結論要留在某個看得到的地方，位置由那張票定。
- **不補票 `10` 的接線。** 那張票自己做，只是要等這張。

## 驗收

- [ ] 使用者冷啟動 app，不再跑標答比對，開機那幾秒消失
- [ ] `mobile-crypto.yml` 照樣在 iOS 模擬器裡跑真的 `react-native-quick-crypto`，照樣紅得起來
- [ ] 故意把一列標答改壞，CI 真的紅燈（不能只驗綠燈那一半）
- [ ] `gate` 整組刪掉之後，雲端備份的推送照常運作
- [ ] 探針畫面的登入按鈕沒有因為 `vectors` 變成 `null` 而永遠灰著
- [ ] 比對的結論仍然有一個人看得到的地方，或在票上明確記載「暫時沒有，由資料頁那張票接手」

### 2026-08-27 — Triage：三個代價全部查證屬實，CI 的觸發方式拍板，改 `ready-for-agent`

#### 票上寫的每一句都對照過程式碼了

| 票上的說法 | 查證結果 |
| --- | --- |
| FAIL 完全沒有作用 | **成立。** `mobile/` 底下只有兩處讀 `passed`：`crypto-self-check.ts` 自己算的，與 `probe-screen.tsx` 拿來決定字是紅是白。`openGate()`、`cloudReady`、`push()` 看的都是「跑完了沒」 |

**冗餘檢查**：`mobile/` 底下 `process.env` 與 `EXPO_PUBLIC_*` 零使用，沒有任何現成的
「只有 CI 走得到」的開關。`.out-of-scope/` 不存在，沒有相似的舊否決。

#### 這一輪維護者拍板的

| 題目 | 拍板 |
| --- | --- |
| CI 怎麼觸發比對 | **裝好之後、開起來之前，CI 往 app 的文件夾塞一個觸發檔**。app 開機同步問一句「在不在」，在才跑 |
| FAIL 的去處 | **CI 紅燈就是全部的作用**。app 裡不留任何顯示，`mobile-crypto.yml` 最後那行 `grep -q ' PASS ' \|\| exit 1` 已經在做這件事 |
| 那道閘門 | **整組刪掉**，照票上原本寫的 |
| 票 `14` 的先後 | **票 `14` 先做**，用現在的機制驗。手上有一張剛驗過的綠表當基準，票 `13` 換機制時紅燈才分辨得出是誰造成的 |

#### 為什麼是「塞觸發檔」而不是另外兩條

三條路都查過，差別集中在一句話：**對答案那段程式碼還留不留在使用者的 app 裡。**

- **塞觸發檔**（選定）：CI 開的就是**使用者會拿到的那個 `.app` 檔案，一個位元組不差**。
  `expo-file-system` 的 `File.exists` 是同步布林值，開機問一次幾乎不花時間，
  而且寫結論檔本來就走同一支套件，不必新增任何相依。
  代價是比對那段程式碼仍然打包在使用者的 app 裡，只是永遠不會被叫到。
- **建置時帶 `EXPO_PUBLIC_*` 旗標**：使用者那包在打包階段整段被削掉，固定初始向量那段
  根本不進使用者的 app。代價是 CI 測的不再是使用者拿到的那個檔案，而是一份特製版。
  **另有一個沒查掉的前提**：Metro 在 SDK 57 上死碼削得乾不乾淨沒有實測過。
- **深層連結叫專用路由**：不動建置、不碰檔案系統，但「使用者觸發不到」只算半滿足——
  知道那個網址的人打得開。

維護者拍板時的原話：「程式在 app 存不存在沒有差別」。

#### CI 那一趟不會碰到雲端，這件事查過了

`core/lib/cloud-backup.ts` 的 `begin()` 第一行是 `const saved = recall(); if (saved === null) return;`，
`recall()` 去本機那格儲存翻暱稱密碼。**CI 每一趟都是全新安裝的模擬器，那一格是空的**，
所以 `begin()` 當場返回，一個網路請求都不發。再往後 `push()` 第一行 `if (account === null) return`
還有一層。

因此閘門刪掉之後，CI 那一趟仍然不會在比對期間推任何東西上去。

**但擋住它的從此是「CI 環境剛好沒登入」，不是「程式碼擋著」。** 哪天有人為了驗別的東西
（例如「電腦存、手機拉」）讓 CI 先登入，這道防線會默默消失而沒有人收到通知。
維護者知情並選擇「刪掉就好，風險寫進票的紀錄裡」。**這一段就是那個紀錄。**

#### 順手查出來一個與本票無關的洞，已另開一張票

triage 時攤開三個執行環境的覆蓋率，發現標答表**從來沒有在真的瀏覽器裡跑過**——
`vitest.config.ts` 寫的是 `environment: 'node'`，所以網頁版與上架中的 Capacitor iOS 版
用的 `crypto.subtle`，沒有任何一趟測試碰過。

那不是這張票的事，開在 `.scratch/crypto-vectors-real-browser/issues/01-vectors-never-ran-in-a-real-browser.md`，
狀態 `needs-triage`。**本票的範圍一個字都沒有因此變動。**

## Agent Brief

> *This was generated by AI during triage.*

**類別：** enhancement
**一句話：** 標答比對改成「CI 塞了觸發檔才跑」，使用者的啟動路徑上不再有它

**現在的行為：**
每一個使用者冷啟動 app 都會跑一遍六列標答比對。它佔住 JavaScript 那條執行緒好幾秒——
最後一筆明文有 4 MB，PBKDF2 又刻意跑得慢。那幾秒內**全域**亂數來源被換成標答表裡
一個公開在版控裡的固定初始向量。而比對的結果沒有任何人在看：三個判斷點看的都是
「跑完了沒」，不是「過了沒」。它掛在啟動路徑上的唯一原因，是 CI 只會做「開 app、
等結論寫成檔」這一件事。

**該有的行為：**
app 啟動時先同步問一句「觸發檔在不在」。

- 不在（使用者的每一台裝置）→ 什麼都不做，不跑比對，不寫結論檔，開機那幾秒消失
- 在（只有 CI 會放）→ 照現在的樣子跑一遍，結論照樣寫進結論檔

**關鍵介面：**

- **那支自我檢查模組不要改它的內容。** `runCryptoSelfCheck()` 與 `reportCryptoSelfCheck()`
  現在做的事是對的，包含環境齊不齊的前置檢查、整批中斷時的兜底、以及寫檔失敗不拖垮 app。
  這張票改的是**誰在什麼時候叫它**，不是它做什麼。
- **觸發檔與結論檔放同一個目錄。** CI 已經靠 `xcrun simctl get_app_container … data` 指到
  那裡了，多一個目錄就多一個會對不上的地方。**Documents 在剛安裝完可能還不存在，
  workflow 那一步要先確保目錄在。**
- **`expo-file-system` 的 `File.exists` 是同步的布林值**，不必 `await`，因此這個檢查
  可以擺在比對之前而不必先進 `useEffect` 的非同步區。
- **觸發檔的檔名兩邊必須一致，而且要互相指得到。** 照現有 `RESULT_FILE` 的做法：
  app 那支檔留一句註解指向 workflow，workflow 的 `env` 留一句註解指向 app 那支檔。
  這條線上已經踩穩的做法，照抄，不要自創。

**一併要收掉的三處（漏一處就會斷）：**

1. **`gate` 整組刪掉。** `openGate()`、`gate.open`、`gate.missed`、`push()` 裡那段擋下來
   補推的邏輯，全部拿掉。留著的話 `openGate()` 沒人叫，`gate.open` 永遠是 `false`，
   雲端備份整條斷掉。
2. **`vectors` 那一格從共用那份資料與畫面上拿掉。** 探針畫面的 `cloudReady` 不再看它——
   否則它永遠是 `null`，登入按鈕永遠灰著。畫面上那行「標答比對：⋯」一併拿掉
   （FAIL 的去處已拍板為「CI 紅燈就是全部」）。
3. **workflow 加一步：安裝之後、啟動之前寫入觸發檔。** 順序不能換，寫在 launch 之後
   就會撞上 app 已經問過那一句的空窗。

**驗收：**

**底下六條裡有三條 agent 收不了。** 三條自動的全綠不代表這張票可以收掉。

- [ ] 故意把一列標答改壞，CI 真的紅燈 —— **維護者收尾**。這條是這張票最重要的一條：
