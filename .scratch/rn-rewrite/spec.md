# iOS 版改寫成 React Native，拿到 iOS 26 的 Liquid Glass

Status: ready-for-agent
Type: enhancement

本檔案是整個改寫工程的決策紀錄，不直接實作。實作票見 `issues/`。路線本身另記於 `docs/adr/0017-react-native-rewrite-for-liquid-glass.md`。

**與 `ADR-0015` 相牴觸——那份用實機盲測選定 Capacitor 包殼。** 不是默默覆蓋：`ADR-0017` 明寫它的結論被推翻、它的證據沒有被推翻，兩份並存、由新的指回舊的。牴觸的細節見底下〈這次跟前兩次差在哪〉。

## 問題

iOS 26 換上 Liquid Glass 之後，這支 app 跟別的 app 擺在一起顯得舊。

**問題不在用起來不順。** 這一點在 `.scratch/swiftui-spike/issues/01` 與 `.scratch/rn-spike/issues/01` 兩度釘過，答案兩次都一樣：講不出任何用起來卡的地方。這次也一樣。變的是外部——2026-08-18 做盲測時系統還沒換設計語言，那個差異當時不存在，量不到。

**而 WebView 追不上這個變化。** Liquid Glass 的關鍵是折射，不是模糊。網頁上要做出折射得靠 `backdrop-filter` 吃 SVG 的 `<feDisplacementMap>`，**Safari 與 WKWebView 不支援這個組合**，只會退回單純的毛玻璃。不管 CSS 怎麼寫，這一項都到不了。

## 解法

iOS 版的畫面層以 React Native 重寫，Liquid Glass 用 `expo-glass-effect` 的 `GlassView`——它包的是系統的 `UIVisualEffectView`，是真元件不是模仿。

網頁版留在 GitHub Pages 繼續跑，**不跟進這套外觀**。畫面碼因此變成兩份，各自活。**`src/lib/` 那批純邏輯抽成共用，只有一份。**

## 這次跟前兩次差在哪

同一個維護者，同一支 app，三次動念，前兩次都收在「不做」。差別要講清楚，否則這份 spec 只是第三次的自我說服。

**第一次（`.scratch/swiftui-spike/issues/01`，wontfix）** — 動機釘出來是「我知道它是 WebView，就覺得不對」加「其實是我想寫原生」。判準因此被換成「這是不是好的時間花法」。React Native 在那張票裡出局，理由是它買不到「想寫原生」——寫的還是 TypeScript。

**第二次（`.scratch/rn-spike/issues/01`，wontfix）** — 動機拆細成兩條：想學新語言（React Native 買不到）、畫面要是系統原生元件（React Native 買得到）。維護者要的是第二條，所以改用 React Native 做原型，用實機盲測驗。**結果是蒙著滑分不出來哪個是原生的**，依票上預先寫死的停損條件收在不做。

**第三次（本 spec）** — 動機是 Liquid Glass，問的是「跟不跟得上 iOS 26」。**這是第一次的動機不是關於「原生」這個抽象概念，而是關於一個具體的、可以指著看的外觀差異。** 盲測回答的是「像不像原生」，那個答案還成立，但它回答不了這一題。

**跟著失效的是第一次否決 React Native 的理由。** 那條理由是「它買不到想寫原生」——這次的動機跟寫哪種語言無關，所以不再構成否決。

**沒有變的是：仍然講不出哪裡用起來不順。** 判準也因此不是「改完會不會更好用」，是「並排看起來還舊不舊」。

## 使用者故事

1. 作為一個 iPhone 使用者，我想這支 app 擺在系統 app 旁邊不覺得舊，這樣我不會每次打開就想到它是個網頁。
2. 作為一個複習中的人，我想長按釋義選起來複製，這樣我可以貼去別的地方查。
3. 作為一個複習中的人，我想把日文詞條複製出來貼進字典 app，這樣我不必自己重打一次。
4. 作為一個還在用舊 iPhone 的人，我想這支 app 照樣裝得起來、用得動，就算沒有玻璃質感也沒關係。
5. 作為維護者，我想在 Windows 上完成整個開發與出包流程，這樣我不必等週末回家開那台 Mac。
6. 作為維護者，我想確定手機加密的雲端備份電腦解得開，這樣我不會在某天想還原時才發現資料回不來。

## 實作決定

### 路線

**React Native + Expo，EAS Build 雲端出包。** 整條路在 Windows 上走得完，`.scratch/rn-spike/issues/01` 已經實際走過一次。不選 SwiftUI 的理由就是這個——它要 macOS 與 Xcode，維護者可用的 Mac 只有週末在家那台。

代價：Liquid Glass 要靠第三方套件包系統元件，不是 Apple 第一手的 `.glassEffect()`。

**已定案，不留回頭路。** 沒有停損條件、沒有「做不成就回 Capacitor」。這與前兩張探路票刻意在動工前寫死停損條件的做法相反，是維護者明確的選擇。

**不做 Android。** 每個決定只需要對 iOS 負責——真要寫原生模組時只寫 Swift，不必再寫一份 Kotlin。Liquid Glass 本來也只有 iOS 有。

### 程式碼怎麼擺

**同一個 repo，畫面兩份、邏輯一份。**

`src/lib/` 的純邏輯（排程、儲存、雲端備份、加解密、讀音預填、提醒排程、必填格）抽成共用位置，網頁版與 React Native 各自只留自己的畫面碼。

**邏輯層不准分岔。** 這是這條路上最不能踩的線：雲端備份若有兩套實作在寫同一批資料，哪天解不開會查不出是誰寫壞的。

**程式由 agent 寫，維護者只驗收。** 理由與前兩張票相同：驗收標準是主觀目測，維護者自己寫的話量到的是自己熟不熟 React Native，不是 iOS 26 像不像。

### 儲存

**`react-native-mmkv` 頂替 `localStorage`，第一頁就換、直接讀真的卡。**

MMKV 是完全同步的（走 JSI），因此 `ADR-0002` 的 `StorageLike` 同步介面原封不動，27 處呼叫端一行不改。`AsyncStorage` 不列入考慮——它是非同步的，改下去會傳染到每一個呼叫端。

第一頁就接真資料，是為了讓「同步介面真的頂得上去嗎」這個地基問題第一天就有答案，不要畫面全做完了才發現要大改。

**`ADR-0002` 的立場不變。** localStorage 仍是唯一真相來源，只是換了實作。若發現 MMKV 頂不上去，那不是換個套件的問題，是整個架構要重看。

### 雲端備份的加解密

**`react-native-quick-crypto` 的 `subtle`**，支援 `cloud-crypto.ts` 用到的 PBKDF2 與 AES-GCM。

**位元級相容用寫死的標答擋住。** 先用網頁版加密一組固定資料，把結果存成標答；React Native 那邊要能解開它，也要能加出一模一樣的結果。這組測試 CI 每次都跑。另外真機實際存一次、拉一次。

**這件事錯了不會當場報錯。** 存的時候一切正常，某天想還原才發現打不開，那時資料已經沒了。自動測試存在的意義就是讓它當場報錯。標答要涵蓋日文、表情符號、超長資料——只手動試一筆碰不到那些只在特定內容下才發作的錯。

### 振假名與長按選取

**兩層 `<Text>` 疊字**，做法與量到的位移沿用 `.scratch/rn-spike/issues/01`：假名字身底端貼著漢字字身頂端（真機量到兩版皆為 15 device px），漢字底下補 0.45em 行距。這一題已經驗過，不重做。

**代價是長按選不起整串詞條**，因為詞條被拆成多個 `<Text>`，而 iOS 的長按選取只在單一個 `<Text>` 內成立。

補救分兩邊：

- **釋義**沒有振假名、是完整一段文字，加上可選取就選得起來。
- **詞條**改用一顆「複製詞條」按鈕，複製**去掉讀音標記後的詞條原文**（`焦[こ]がす` → `焦がす`）——那才是貼進字典查得到的東西，也跟判斷詞條全域唯一時用的是同一個基準。

### 外觀與舊版裝置

**最低支援是 iOS 16.4。** 這不是選出來的，是 Expo 給的下限：`expo-modules-core` 的 podspec 把 iOS 16.4 寫死，SDK 57 底下沒有更低的走法（退回 SDK 54 也只到 15.1）。原本這裡寫的是「仍是 iOS 15.0，與現在的 `project.pbxproj` 一致」，票 `03` 動工時發現那個數字兩條路都達不到，2026-08-24 訂正。**實際排除掉的是 iPhone 7 與更舊的機器**，使用者故事四因此縮水了一截。

`GlassView` 在 iOS 26 以下自動退回一般區塊，16.4 到 25 的機器用得到 app，只是沒有玻璃質感。不另外為舊版做一套仿玻璃外觀——那正是想離開的東西。

**驗收因此只在 iOS 26 上成立。**

### 原生功能

**四項全部要在 React Native 上重接**：每日提醒、原生日文語音、評分觸覺、Keychain 存密碼。

`ADR-0015` 寫明這四項是通過 App Store 審查準則 4.2（Minimum Functionality）的實質內容，少一項就是一支「把網站裝進殼裡」的 app，會被退件。

> **保險副本不在名單上，票 `07` 於 2026-08-27 拍板不留。** 它防的是 iOS 清掉 WebView 那一層的網站資料，而 React Native 版沒有 WebView，MMKV 存的是 app 文件夾底下的檔，系統不清那個位置。**這一項本來也不算 4.2 的實質內容**——`ADR-0015` 自己數的就是四項，保險副本是用「另外」帶出來的附加項；把它算成五項之一是這份 spec 與 `ADR-0017` 轉述時多算的，現已訂正。Capacitor 版那一份原封不動，那一版的威脅是真的。

### 上架

**Capacitor 版不先送審，等 React Native 版好了才一起送，而且不設回頭看的時間點。**

票 `ios-app 11`（送審）與 `20`（在地化）都已備妥，維護者明確選擇擋住。**代價已知並接受**：萬一卡在加解密相容那一關，App Store 上就是一直空著。這與 `.scratch/rn-spike/issues/01` 當初「互不阻擋，先上架不吃虧」的做法相反。

## 驗收決定

**兩把尺，並排目測說了算。**

- **Apple 的介面指南（HIG）逐項清單**當施工指引，一頁一頁對著做。Apple 沒有現成的 Liquid Glass 打勾表，清單要自己從材質、版面、導覽、按鈕幾章抽出來，見票 `01`。
- **最終判定是拿它跟 Apple 自家 app 並排目測**（設定、提醒事項、備忘錄那類），維護者說了算。

**這不是盲測。** 前兩張票的盲測是要兩版長得越像越好，才量得到平台差異；這次目的相反，要的是看起來**不一樣**、跟得上 iOS 26。

**沒過的唯一結果是繼續改。** 因為路線已定案，這是驗收線不是停損線。

## 測試決定

**`src/lib/` 的 4,732 行邏輯測試整批搬**，同為 TypeScript，幾乎不用改。它們是這次重寫最大的一筆資產。

**`ADR-0014` 那 1,319 行畫面測試作廢**，jsdom 環境專用，React Native 上跑不了。改用 React Native 自己那套工具重寫重要的幾支，不逐支照抄。

**加解密的標答測試是硬性的**，CI 綠燈的前提，見上面〈雲端備份的加解密〉。

## 實作順序

1. HIG 清單（票 `01`）——每一頁的施工指引，要先有
2. repo 重排，邏輯層抽成共用（票 `02`）
3. Expo 專案骨架，EAS Build 通到真機（票 `03`）
4. MMKV 頂替 `localStorage`（票 `04`）
5. 加解密位元級相容的標答測試（票 `05`）
6. 複習畫面（票 `06`）——第一頁正式程式碼，第一次並排驗收

之後的畫面順序：**卡片列表 → 編輯 → 資料 → 統計**。先把日常最常用的兩頁做完，那時 app 已經能正常複習與維護卡片。資料頁（含雲端備份、金鑰、提醒）最雜但不影響日常使用，排第三。編輯畫面有讀音格、合併切割、必填格、讀音預填，是最難的一頁，排第二是為了讓最大的風險早點曝出來。

這幾頁的票等複習畫面做完再開——HIG 清單要邊做邊長，現在開會寫出用不到的規格。

> **2026-09-01：資料頁那一格拆成三張票，上面那句「含雲端備份、金鑰、提醒」訂正。**
>
> - **票 `17`（Keychain 與同意）** 從資料頁前面切出來。它是一支原生模組加一次共用層介面改造，
>   與畫面工作性質不同，而且擋在雲端備份那一區前面。手法與票 `15` 把單字本管理從資料頁
>   提前拿走一樣：擋在前面的先做。連帶決定見 `docs/adr/0019-react-native-keychain-for-icloud-sync.md`。
> - **票 `18`（資料頁）** 只剩三區：雲端備份、介面語言、手動備份。**單字本已經在票 `15` 搬去卡片列表**，
>   **金鑰在 iOS 上本來就不長**（固定金鑰，`ADR-0016`）——原句把金鑰算進去是轉述時多算的。
> - **票 `19`（每日提醒）** 另開。它要裝 `expo-notifications`、走一次系統通知權限、排未來七天，
>   與另外三區沒有共用的東西；混在一起的話資料頁那張票的驗收會卡在通知權限這一關。
>
> **順序沒有變**，仍是卡片列表 → 編輯 → 資料 → 統計，只是「資料」這一格底下多了兩張票。

## 不在範圍內

- **Android。** 不做，也不為了以後好做而避開只有 iOS 有的東西——那會讓人不敢用 Liquid Glass，而那正是這件事的目的。
- **網頁版的外觀。** 一個字不改，不跟進 Liquid Glass。
- **重新設計功能。** 這次只換畫面的長相與底下的框架，複習流程、排程演算法、單字本結構、讀音預填的行為全部照舊。
- **主畫面 Widget。** 與 `ios-app` spec 一致，仍不在範圍。

## 已知風險

**加解密位元級相容過不了。** 風險最高的一項，而且它擋在整條路中間——雲端備份是跨裝置的唯一管道，網頁版要留著。票 `05` 刻意排在畫面之前，就是要讓它早點曝出來。

> **2026-08-25：沒有發生，這一項退場。** `react-native-quick-crypto` 加出來的東西與網頁版位元級相同——六列標答在 iOS 模擬器與真機上都是 `PASS 6/6`（CI 每次都跑），真機也實際做過一次「網頁版存、手機拉」與反方向。`cloud-crypto.ts` 一個字沒改。細節見票 `05`。
>
> **仍然要守著的是它不准漂。** 標答表與那兩支 CI 流程留著就是為了這個：日後誰動到加解密，當場紅燈。

**上架無限期擋著。** 沒有檢查點，維護者已知並接受。

**驗收沒有客觀停止線。** 「並排不覺得舊」只有維護者能判，而路線已定案，沒過只能繼續改。這是刻意的選擇，記在這裡是為了日後有人問「為什麼這張票拖這麼久」時查得到。
