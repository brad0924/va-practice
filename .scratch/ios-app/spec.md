# 以 Capacitor 把現有網頁包成 iOS app 上架，並加上推播、原生語音、觸覺與 Keychain

Status: ready-for-agent
Type: enhancement

本檔案是整個 iOS 化工程的決策紀錄，不直接實作。實作票見 `issues/`。

**核心立場：現有的 web 程式碼是資產，不是包袱。** 畫面層沒有框架，因此任何「重寫」路線都得丟掉全部 2,480 行畫面碼與 3,642 行測試。Capacitor 包殼是唯一能保住這批資產、又拿得到原生能力的路。網頁版與 iOS 版共用同一份程式碼，~~**網頁版的行為一字不改**~~ — 訂正為**網頁版不出現任何行為回歸**，理由見下。

> **訂正（2026-08-11，票 16）**：硬約束從「網頁版的行為一字不改」改為「**網頁版不出現任何行為回歸**」。
>
> 這條約束存在的目的寫在使用者故事 28 裡——「這樣我不必回頭重測整個網頁版」。它防的是**回歸**：為了 iOS 動了共用程式碼，結果網頁版壞掉。
>
> 票 16 撞到的是另一種情況：連點兩下放大是共用程式碼上的 bug，網頁版與 iOS 版**是同一個毛病**。在 `src/styles.css` 修掉它，網頁版會跟著變好——那是修好，不是弄壞，字面上違反舊約束，卻完全不違反舊約束想達成的事。
>
> 因此改掉前提本身，而不是替它加一個例外（與決定三十三處理「沒有 Mac」時同一個做法）。修訂後的界線很清楚：**不為了 iOS 而改變網頁版的行為；共用程式碼上兩邊都有的 bug，修一次兩邊一起好，不算違反。** 判準仍然可驗證——既有測試必須全數通過且一個都不准改（見〈測試決定〉），那是這條約束的自動化守門員。

## 問題

要在 iPhone 上用這個工具，現在得在 Safari 打開網址、按「加到主畫面」。這條路是通的——PWA 設定完整，離線也能複習——但它給不了四樣東西：

1. **別人找不到它。** 它不在 App Store 上，沒辦法分享給任何不會自己貼網址的人。
2. **不會主動提醒。** 複習這件事完全靠使用者自己想起來。到期的卡在那裡堆著，沒有任何東西會說一聲。
3. **朗讀不可靠。** `src/ui/speech.ts` 走 Web Speech API，日文語音在 iOS 上不保證存在。找不到語音時朗讀按鈕會直接隱藏——使用者不會看到錯誤，只會覺得「這個功能有時候在、有時候不在」。
4. **手感就是個網頁。** 沒有觸覺回饋，不打開 app 就不知道今天還剩幾張。

## 解法

用 Capacitor 把現有的 `dist` 包進原生殼（WKWebView），出成一支可以上架 App Store 的 iOS app。同一個 repo、同一份 web 程式碼，靠 build 參數切出網頁版與 iOS 版兩個產物。

第一版加上三項原生能力——**每日複習提醒、原生日文語音、觸覺回饋**——並把雲端備份的密碼改存 iOS Keychain。這三項既是使用者要的功能，也同時是通過 App Store 審查準則 4.2（Minimum Functionality）的實質內容：一支只把網站裝進殼裡的 app 會被退件，一支會算你的排程、在該提醒時提醒、用系統語音朗讀、把密碼交給 Keychain 保管的 app 不會。

主畫面 Widget 排在第二版，本 spec 不含。

## 實作決定

### 路線

**一、Capacitor 包殼，不重寫。** 現有 web 程式碼原封不動跑在 WKWebView 裡。否決的替代方案：Swift 原生重寫（畫面層無框架，8,700 行含測試全數作廢；且 `src/lib/cloud-crypto.ts` 的加解密必須與網頁版位元級相容，重寫是資料損毀的高風險來源）、React Native／Flutter（同樣從零重寫，卻多背一層跨平台框架，而本專案不需要 Android）。此決定應開 **ADR-0012** 記錄。

**二、同一個 repo、同一份 web 程式碼，兩個 build 產物。** 加入 `ios/` 原生專案目錄（Capacitor 慣例）。網頁版的 `base` 維持 `/va-practice/`（GitHub Pages 子路徑），iOS build 改用 `/`（WebView 從自訂 scheme 載入根路徑），以 build 參數切換，不複製第二份設定檔。

**三、iOS build 關閉 PWA service worker。** 資源本來就打包在 app 內，service worker 在此情境下不提供任何離線能力，只增加一層快取與更新時機的不確定性。網頁版的 PWA 設定完全不動。

**四、iOS build 不載入遠端網址。** Capacitor 支援讓 WebView 直接指向線上網址（等於免送審熱更新），但那會使離線完全失效，且是準則 4.2 最典型的退件理由。內容一律打包進 app，更新走送審。

### 資料層

**五、`ADR-0002` 不推翻：localStorage 仍是唯一真相來源。** 所有讀寫路徑一字不改，`src/lib/storage.ts` 的同步介面 `StorageLike` 保持同步。否決「全面換成 Capacitor Preferences」：該 API 是非同步的，換過去等於把 `storage.ts`、`app.ts` 的 `persist()` 與整批既有測試改寫成等待語意，改動範圍與收益不成比例。

**六、iOS 上另存一份唯讀的保險副本。** `app.ts` 的 `persist()` 在存完 localStorage 之後，額外把同一份資料寫進原生儲存（~~Capacitor Preferences，底層為 iOS UserDefaults~~ — 訂正為 app target 內自寫的一支 Capacitor 插件，底層為 App Group 的 `UserDefaults`，理由見決定九）。這份副本**永遠不被當成資料來源讀取**，只有一個用途：啟動時發現 localStorage 沒有資料、而副本有，才把副本寫回 localStorage 並照常啟動。網頁版沒有這條支線。

**七、保險副本的寫入沿用 `cloud-backup` 的 `pending` / `sending` 模式，不用計時器。** `persist()` 每答一張卡就會跑一次，不可每次都做一趟原生 I/O。做法直接照抄 `cloud-backup.ts` 的 `flush()`：同時只寫一份，寫入期間進來的變動一律覆蓋成「待寫的最新那一份」，上一趟回來後若 `pending` 已換人就再寫一次。因為寫的永遠是整份資料，被合併掉的中間那幾份沒有任何意義。

不採用固定延遲的節流，三個理由：延遲的秒數是個無從論證的魔術數字；計時器會開出一個「資料已改、計時中、app 被滑掉」的破口，而「一次一趟」沒有這個窗口；本 repo 已經有這個模式，照抄勝過新發明一種。原生儲存（UserDefaults）的寫入很快，複習節奏下幾乎排不出隊，真正要擋的是匯入一批單字那種連續湧入——那正是此模式最擅長的情況。

**八、還原判斷發生在 `createStore()` 之前，是啟動流程的一部分。** `store.load()` 在 localStorage 空白時會自行初始化一份新資料，因此還原必須早於它，否則使用者會先看到一個空的 app。這使 iOS 的啟動流程多一個非同步的前置步驟，`src/main.ts` 需要相應調整；網頁版的啟動路徑不變。

**九、這份副本同時是第二版 Widget 的資料來源。** 寫入時即指定 App Group，Widget 才讀得到。本 spec 只負責把資料寫進去，不實作任何讀取端。

**寫入的手段從 `@capacitor/preferences` 換成自寫插件。** 實作票 05 查證官方插件的 iOS 原始碼，發現它的 `group` 參數**做不到 App Group**——那只是加在 key 前面的一段字首，底層一律寫進 `UserDefaults.standard`，也就是 app 私有的那一份，Widget 讀不到。官方文件也從未宣稱它支援 App Group。

因此改為在 `ios/App/App/` 內自寫一支約 30 行、只有 `read` 與 `write` 兩支方法的 Capacitor 插件，直接用 `UserDefaults(suiteName:)`。這是「改掉不成立的前提」而不是「替驗收加例外」：決定九要的是 Widget 讀得到，換一個做得到的手段才叫達成。附帶好處是一個新的 npm 依賴都不必加。

代價據實記錄：多三個原生檔案（插件、註冊用的 `CAPBridgeViewController` 子類、`App.entitlements`）與兩處既有檔案的小改（`Main.storyboard`、`project.pbxproj`），且開發機是 Windows，Swift 編不編得過只能等 CI，連 typo 都不例外。

### 雲端備份的密碼

**十、密碼改存 iOS Keychain，並開啟 iCloud 同步。** 換 Apple 裝置時密碼自動跟著走。iCloud 鑰匙圈為端對端加密，Apple 無法讀取內容。使用者未啟用 iCloud 鑰匙圈時退化為僅存本機，功能不受影響。

**十一、`cloud-backup.ts` 一行不改——用既有的注入接縫。** `CloudBackupHooks.storage` 本來就是外部遞進來的 `StorageLike`，`app.ts` 目前遞 `localStorage`。iOS 版改遞一個 Keychain 支援的實作即可。

**十二、以「啟動時預載」化解同步／非同步的衝突。** Keychain API 是非同步的，`StorageLike` 是同步的。解法是在啟動流程中先非同步讀出憑證，填入一個實作 `StorageLike` 的記憶體物件；此後 `getItem` 由記憶體同步回答，`setItem` 同步更新記憶體、並非同步寫回 Keychain。憑證只有登入、換密碼、登出三個時機會變動，頻率極低，此模型足夠。

**十三、`ADR-0003` 的「密碼遺失即無法復原」不變。** Keychain 降低了忘記密碼的機率，但沒有消除它——使用者可能沒開 iCloud 鑰匙圈，或整個換掉 Apple ID。因此設定雲端備份時的 UI 必須明說後果，並指向手動匯出備份這條後路。

### 朗讀

**十四、不開新接縫，在 `src/ui/speech.ts` 內部分支。** 該模組對外只有 `initSpeech` / `hasJapaneseVoice` / `speak` 三支，`src/ui/review-view.ts` 的呼叫方式一字不改。模組內部先探測原生語音橋接是否存在：有就用原生，沒有就沿用現有的 Web Speech 路徑。

**十五、~~iOS 上朗讀按鈕永遠可用。~~ 訂正為：iOS 上朗讀要取用 enhanced 品質的語音。**

原訂理由是「現行『找不到日文語音就隱藏按鈕』的行為是為 Web Speech 的不確定性而設計的，換原生後 `hasJapaneseVoice()` 恆為真，按鈕不再時有時無」。**實作票 01 的真機實測推翻了這個前提**：iOS WKWebView 裡 `hasJapaneseVoice()` 本來就回 `true`，按鈕正常顯示、也聽得到日文。「按鈕時有時無」在 iOS 上不是真實存在的問題。

真正的問題是音質——接近機械音、重音不對。原因是 iOS 的 Web Speech 雖然底層也是 `AVSpeechSynthesizer`，卻只取得到 compact（壓縮）品質的語音，enhanced／premium 需要使用者自行到系統設定下載。因此決定十四（改用原生）依然成立，但動機從「為了有聲音」換成「為了聲音好聽」：原生實作要明確挑選 enhanced 品質。

`hasJapaneseVoice()` 在 iOS 上恆為真仍然是改用原生後順帶得到的保證，只是不再是動機。網頁版維持原行為。

**重音（高低アクセント）不列入驗收**：那對合成器是難題，原生同樣是從假名推測，換引擎不保證解決。

**十六、朗讀的文字來源不變。** 仍是 `toReadingText()` 轉出的讀音文字，聽到的與卡片教的讀法一致——這是既有決定，原生實作照搬。

### 每日提醒

**十七、新開一支純函式模組 `src/lib/reminders.ts`——這是本工程唯一的新接縫。** 職責是回答「未來各天分別會積到幾張到期卡」。與 `src/lib/review.ts` 同樣不碰時鐘、不碰亂數、不碰任何原生 API，當前時間一律以參數注入。

不放進 `review.ts`：該模組的職責是複習流程本身（排程演算法、抖動、佇列排序、「再次」重排），提醒是它的下游消費者，混進去會稀釋一個目前很乾淨的職責。不重用 `groupByBucket`（在 `src/ui/list-view.ts`）：那支回答的是「六個時間桶各有哪些卡」，形狀與用途都不同，且它住在畫面層。

**十八、到期張數是累積的，不是當天新增的。** 沒複習的卡不會消失——第 N 天的張數是「所有到期日在第 N 天或更早的卡」，加上新卡。新卡沒有到期日，與 `buildQueue()` 一致地視為已到期，因此從第一天起就計入。

**十九、只算複習範圍內的卡。** 與 `buildQueue()` 吃的是同一批（`cardsInBooks(data.cards, data.scopes.review)`），否則通知上的數字與使用者打開 app 看到的對不起來。

**二十、排未來 7 天，張數為 0 的日子不排。** 7 天遠低於 iOS 同時登記 64 則的上限，留有充裕餘裕。今天不排——排程動作發生時當天的提醒時間可能已經過去，且使用者此刻正拿著 app。

> **訂正（2026-08-11，票 09 真機驗收時）**：「今天一律不排」是錯的，已改為**今天也排，但要同時滿足兩個條件**：提醒時間還沒到，且今天還有卡沒複習完。
>
> 原本那條規則有兩個理由，第一個對、第二個錯。「提醒時間可能已經過去」成立——那變成第一個條件。「使用者此刻正拿著 app」不成立：拿著 app 是**排程的那一刻**的事，不是**提醒響的那一刻**的事。使用者早上 5 點打開 app 看一眼就關掉，6 點時他並沒有拿著 app，卻再也不會被叫。
>
> 而「6 點時我正開著 app 就別跳」這件事根本不需要排程去猜——iOS 自己就會處理：Capacitor 的 `NotificationRouter` 是通知代理，本 repo 沒有註冊 local notification handler，因此 `willPresent` 回傳空的呈現選項，**app 在前景時通知會被靜靜丟掉**（`node_modules/@capacitor/ios/.../NotificationRouter.swift`）。用執行當下的真實狀態判斷，永遠勝過在幾小時前預測它。
>
> 這一併修好了決定二十一那條驗收：舊規則下「早上 6 點前開了 app 但沒複習」與「複習完了」都是不響，從外面看一模一樣，那條驗收因此驗不出任何東西。新規則下前者會響、後者不響。

**二十一、資料一變就整批重排。** 先清掉全部已登記的提醒，再依最新資料重新登記。這使「複習完就不再被叫」與「匯入一批卡後數字立刻正確」用同一條路徑實現，不需要個別取消的邏輯。觸發點與 `persist()` 相同，並採用與決定七相同的 `pending` / `sending` 模式——重排的也是「整批」，中間那幾份同樣沒有意義。

各自持有自己的 `pending` / `sending`，不與保險副本共用同一道閘門：兩者寫的是不同的原生 API，共用會讓其中一邊變慢時卡住另一邊。

> **訂正（2026-08-11，票 09 實作時）**：「觸發點與 `persist()` 相同」照字面做會漏掉兩條，實際觸發點是三個：
>
> 1. `persist()`——評分、新增、編輯、刪除、改複習範圍。
> 2. `reload()`——匯入單字、整份匯入、雲端拉下來這三條路都不經過 `persist()`；漏掉的話「匯入一批卡後數字立刻正確」直接不成立。這與決定六遇到的是同一個坑。
> 3. **啟動時一次**。排的是未來 7 天，只靠資料變動觸發的話，一個「開了 app 卻沒複習」的人在第 8 天之後就完全收不到提醒。

**二十二、提醒時間第一版固定為每日 06:00，不做設定畫面。** 不為尚未被要求的需求寫程式。日後若要開放設定，是獨立的一件事。

> **訂正（2026-08-11，票 09 實作時）**：原訂 08:00，由維護者改為 06:00。這只換掉一個常數（`REMINDER_HOUR`），沒有動搖任何架構決定——「今天不排」那條（決定二十）反而更站得住腳：排程動作發生時，早上 6 點更可能已經過去了。
>
> **訂正（2026-08-11，票 18）**：「日後若要開放設定，是獨立的一件事」的那個日後到了。時間改為可設定，預設仍是 06:00，`REMINDER_HOUR` 這個常數因此消失、時間變成 `planReminders()` 的參數。詳見 `issues/18-configurable-reminder-time.md`。
>
> 時間存在 `va-practice:reminder-time`，與開關那一格分開——關掉開關往往只是暫時的，把設好的時間一起洗掉很怪。開關那一格語意一個字沒變，因此票 09 留下的裝置升級後仍在 06:00 被叫，相容處理是零行。
>
> 一個順帶的好處：跟時間有關的手動驗收不必再調系統時鐘，把提醒時間設成「現在的兩分鐘後」就能驗（票 09 的驗收清單已照此改寫）。
>
> **再訂正（2026-08-12，票 18 驗收後）**：預設值由 06:00 **改回 08:00**（本決定最初訂的就是 08:00，票 09 動工時改成 06:00，現在轉回來）。這只動 `DEFAULT_REMINDER_TIME` 一個常數。
>
> 影響範圍就是「時間那一格從來沒被設過」的裝置——**包含票 09 留下的那些**，它們會從 06:00 變成 08:00。時間可設定之後，這個常數不再是「所有人幾點被叫」，只是「還沒表示意見的人幾點被叫」，因此改它的份量比票 09 那次輕得多。設過時間的人一律不受影響。

**二十三、提醒開關放在「資料」畫面，狀態只存本機、不進備份。** 與雲端備份登入同一個畫面。這是「這台裝置要不要叫我」的偏好，不是使用者的資料——與 `src/lib/gemini-key.ts` 的定位一致，因此不進 `AppData`、不上雲端、不進匯出檔。

**二十四、通知權限被拒絕時，開關要誠實。** 不重複請求，且不呈現「提醒已開啟」的假象——關掉開關並指向系統設定。

### 觸覺

**二十五、評分時給一次輕量觸覺回饋，僅此一處。** 不在其他按鈕上加。與朗讀同樣的處理方式：橋接不存在時（網頁版）靜默略過，不需要任何條件判斷散落在畫面層。

### Firebase

**二十六、安全規則的單筆上限放寬到 4 MB。** 這 4 MB（`4194304`）量的是加密後那串 base64 的字數；`ADR-0003` 記錄的每張約 155 bytes（20 KB ÷ 132 張）量的也是推送後的大小，兩者同一把尺，因此約當 27,000 張卡，高於 JLPT 全級數字彙量的兩倍，實際使用者不會觸及。實作時發現規則檔原本就有一道 `2000000`（約 12,900 張）的上限，這次是把它放寬，不是從零加防線。此上限防的是單一路徑一次吃掉大量額度與程式異常膨脹，**不防**有心人建立大量合規小備份——`ADR-0003` 選定的方案在免費方案上沒有速率限制能力，此風險經評估後接受。

**二十七、開啟 Firebase 用量警示。** 這是接受上述風險的配套：補不起洞，至少要第一時間知道。實作時查證：要的不是 Cloud Billing 的預算警示（那要 Blaze 方案加帳單帳戶，且警示的是花費金額，Spark 方案上不會響），而是 Realtime Database 自己那套用量警示——位置在主控台右上角鈴鐺圖示的設定裡，「儲存或下載的資料量即將達到方案上限」本專案預設就已開啟，無需操作。

**二十八、超過上限時顯示人話。** `cloud-backup.ts` 原本對非 401 的失敗一律回「寫入雲端失敗（狀態碼）」。改為在**送出之前**就量加密後的長度，超過就直接顯示人話、一個請求都不發：告知使用者單字量已超過雲端備份上限、請改用檔案備份，並明說本機資料不受影響。不靠狀態碼分辨——安全規則的 `.validate` 失敗回 400 還是 401 無法從官方文件查證，猜錯會把超限說成「暱稱或密碼不對」並讓同步卡死。改由一條測試釘住「客戶端常數與規則檔是同一個數字」，兩邊走鐘時 CI 就紅。

### 上架

**二十九、探路 build 必須是第一張票，其餘票全部 block 在它後面。** 內容是「不加任何功能，把現有 `dist` 包起來裝上真機，從頭到尾操作一遍」。它要回答的是討論無法回答的問題：Web Speech 是否真的失效、`fetch` 對 Firebase 與 Gemini 是否被自訂 scheme 的來源擋下、鍵盤彈出時的版面、安全區域邊距。它的產出（`ios/` 目錄、build 流程）會留在專案裡，因此它是 tracer bullet，不是 `/prototype` 定義下的丟棄品。

**三十、App icon 補一張 1024×1024。** `scripts/generate-icons.mjs` 的 `SIZES` 加一個數字即可，圖案與既有的完全一致。

**三十一、隱私權政策頁面放在既有的 GitHub Pages 站台上。** App Store Connect 的必填欄位。內容須涵蓋雲端備份（端對端加密、伺服器端只有密文、無帳號系統）與 Gemini 讀音預填（使用者自備金鑰、只存本機、不經過任何第三方伺服器）。

**三十二、Gemini 讀音預填維持原狀，一行不改。** 它預設關閉、需使用者自行設定金鑰才啟用，不影響核心功能，也不會成為審查的阻礙。

**三十三、iOS 的 build 與上傳走 GitHub Actions 的 macOS runner，手動觸發。**

原訂「人工在 Mac 上執行，不做 CI」，前提是有一台 Mac 可用。實作票 01 執行時發現前提不成立——維護者的開發機是 Windows，手上沒有 Mac，照原決定執行的結果不是省事，是這張票永遠做不完。因此改掉前提本身，而不是替它加一個例外。

新的做法：`.github/workflows/ios-testflight.yml`，`workflow_dispatch` 手動觸發，在 macOS runner 上跑 `npm run sync:ios` 加 `xcodebuild`，簽章後上傳 TestFlight。三個支撐這個決定的事實：public repo 的標準 macOS runner 不計費；Capacitor 8 改用 Swift Package Manager，不再需要 CocoaPods，因此 `npx cap add ios` 與 `npx cap sync` 在 Windows 上就能跑完；TestFlight 的 Internal Testing 不經任何審查，上傳處理完即可安裝。

「不綁在 push 上」這一點維持原決定的精神：每跑一次就佔用一個 TestFlight build number，自動化沒有價值。既有的網頁版部署 workflow 不動，只在 `paths-ignore` 補上 `ios/**`。

### 文件

**三十四、`CONTEXT.md` 需補進三個新詞彙**：**提醒**（每日推播本身）、**提醒排程**（未來各天要不要提醒、提醒幾張）、**保險副本**（iOS 上那份唯讀的資料副本，明確標示它不是第二個真相來源，`_Avoid_`：同步、快取、備份）。

**三十五、需開 ADR-0012**，記錄「iOS 版以 Capacitor 包殼，不重寫原生」，並在 Consequences 中載明：更新節奏從「push 即上線」變為「每次送審 1–2 天」、準則 4.2 的退件風險不為零、以及 `ADR-0002` 與 `ADR-0003` 的立場在此工程後維持不變。

## 測試決定

**好的測試只驗外部行為。** 沿用本專案既有的做法：純函式吃參數、吐結果，時間與亂數一律注入，不驗內部呼叫順序、不驗私有狀態。

**唯一需要自動測試的新模組是 `src/lib/reminders.ts`。** 它是純函式，測試環境為 node（`vite.config.ts` 已設定），可直接測。要涵蓋的行為：

- 沒有任何卡時，回空
- 全部卡都在未來很遠處時，7 天內回空
- 逾期卡在每一天都被計入（累積語意，決定十八）
- 新卡（`due` 為 `null`）從第一天起就被計入
- 今日到期的卡在第 1 天起被計入
- 第 N 天的張數只增不減
- 張數為 0 的日子不出現在結果裡
- 邊界：恰好第 7 天到期的卡計入，第 8 天到期的不計入
- 跨月、跨年的日期推進正確

**前例**：`src/lib/review.test.ts` 是最接近的範本——同樣是吃 `cards` 與注入的 `now`、驗排程結果的純函式測試；日期邊界的測法可直接參照。

**原生橋接層不寫自動測試。** Capacitor 的 Preferences、Local Notifications、Haptics、Keychain 與原生語音在 node 環境下都不存在，硬要測就得寫一整套假物件，測到的只是自己寫的假貨。這些改為**手動驗收清單**，隨探路 build 與各張實作票一併執行。

**`src/ui/speech.ts` 不新增自動測試。** 它現在也沒有——模組持有全域語音狀態，本來就在測試範圍之外。決定十四刻意不改變它的對外介面，正是為了讓 `review-view` 那一側維持零變動、零新測試。

**既有測試零搬遷、零修改。** 網頁版不出現行為回歸是本工程的硬約束（見本檔開頭）。任何既有測試需要修改，都意味著某處違反了這條約束，應回頭檢視程式碼而不是改測試。這一條在訂正後份量更重：它是「回歸」與「順手修好同一個 bug」之間唯一的自動化判準。

**手動驗收清單（真機執行）**：離線啟動與複習、朗讀在飛航模式下可用、雲端備份登入與跨裝置接續、換手機後 Keychain 帶回密碼、清掉 app 資料後保險副本還原、提醒在有卡／無卡／複習完三種情況下的行為、通知權限被拒絕時的開關狀態、評分觸覺、安全區域與鍵盤彈出時的版面。

## 不在範圍內

- **主畫面／鎖定畫面 Widget**。第二版。本 spec 只把資料寫進 App Group，不實作任何讀取端。
- **Android**。Capacitor 支援，但本專案不需要，且會使每個原生決定都得考慮第二個平台。
- **iOS 的自動送審**。build 與上傳 TestFlight 走 CI 但需手動觸發，送審一律人工（決定三十三）。
- **任何畫面的重寫或視覺改版**。包含捲動手感、轉場動畫、原生元件替換。WebView 的手感就是這一版的手感。
- **為了 iOS 而做的網頁版行為變更**。（原為「網頁版的任何行為變更」，訂正見本檔開頭：共用程式碼上兩邊都有的 bug 修一次兩邊一起好，不在此列）
- ~~**提醒時間的自訂**（決定二十二）~~ — 訂正：已於票 18 做掉，見決定二十二底下那則。
- **Gemini 讀音預填的任何改動**（決定三十二）。
- **雲端備份改為逐張合併的同步**。`CONTEXT.md` 已將「同步」列入 `_Avoid_`，本工程不動這個立場。
- **Firebase 匿名登入或後端改造**。評估後選擇接受風險（決定二十六）。
- **Apple Developer Program 的申請**——需由維護者本人處理，不是實作票。
- ~~**App 名稱、Bundle ID 的決定**~~ — 訂正：走 TestFlight 就必須先在 App Store Connect 建立 app 記錄，而建立時指定的 Bundle ID 之後無法變更，因此已於實作票 01 提前定案為 `io.github.brad0924.vapractice`，主畫面顯示名稱 `JLPT 單字`。App Store 上架用的商品名稱仍可隨時改，留給票 11。

## 補充

### 已知風險

1. **準則 4.2 退件的機率不為零。** 推播、原生語音、Keychain、觸覺是一手紮實的牌，但審查員有裁量權。退件可補件申訴或再加功能重送，不影響已完成的工程。
2. **WKWebView 下有哪些既有行為會失效，目前是未知的。** 最可疑的是 Web Speech（決定十四已備妥退路）、`fetch` 對 Firebase 與 Gemini 的跨來源行為、鍵盤與安全區域。這正是探路 build 先行的理由（決定二十九）。
3. **更新節奏會變慢。** 從「push 後幾分鐘上線」變成「每次送審等 1–2 天」。這是上架的必然代價，寫進 ADR-0012 的 Consequences。

### 工作量估算

第一版約 8–10 個工作天，不含 Apple 審查等待與可能的退件重來。第二版 Widget 另計 2–3 天。

### 建議的實作順序

探路 build（決定二十九）必須最先完成並回報發現；其結果可能會修正後續票的內容，但不會動搖本 spec 的任何架構決定。其後，資料層（保險副本）與 Keychain 因為共用啟動流程的非同步前置步驟，宜相鄰完成；提醒是唯一有實質新邏輯的一項，可獨立進行；觸覺與 icon 是零風險的小票，適合填補空檔；上架素材（隱私權政策、App Store Connect）可與工程並行準備。
