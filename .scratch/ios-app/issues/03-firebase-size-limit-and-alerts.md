## 現況

`ADR-0003` 的最後一條寫著「額度目前有充裕餘裕，但不是無限。若日後改為多人使用，需重新計算」。公開上架就是那一刻。

資料庫網址明碼寫在 `src/lib/cloud-backup.ts` 裡，原始碼公開。安全規則擋得住「覆寫別人已有的備份」，但「建立一份全新的備份」必須放行，否則新使用者第一次備份就會被擋掉。

`cloud-backup.ts` 目前對非 401 的失敗一律回「寫入雲端失敗（狀態碼）」——使用者看到一個數字，不知道發生什麼事、也不知道資料還在不在。

## 決定

### 安全規則加上單筆 4 MB 上限

上限量的是加密後那串 base64 的字數（`4194304`）。`ADR-0003` 記錄的每張約 155 bytes 量的也是同一個東西——那句「內建牌組 10.4 KB / 132 張，加密後每次推送約 20 KB」，155 是 20 KB ÷ 132 得來的，本來就含 base64 的膨脹。兩者同一把尺，直接相除即可：約當 27,000 張卡，高於 JLPT 全級數字彙量的兩倍，實際使用者不會觸及。

實作時發現規則檔原本就有一道 `length <= 2000000`（約 12,900 張）的上限，這張票是把它放寬到 4 MB，不是從零加防線。「省額度」的票淨效果是把單次寫入可吃的量翻倍——接受這件事，理由是 27,000 張才是票面想保障的容量，而 12,900 張離 JLPT 全級數字彙量太近，沒有餘裕。

### 誠實記錄這道防線擋得住什麼

它防的是單一路徑一次吃掉大量額度，以及程式異常膨脹。**它不防**有心人建立大量合規的小備份把 1 GB 慢慢塞滿——`ADR-0003` 選定的方案在免費方案上沒有速率限制能力。此風險經評估後接受，配套是用量警示。

### 開啟 Firebase 用量警示

補不起洞，至少要第一時間知道。

**實際查證：不是 Cloud Billing 的預算警示。** 那套要 Blaze 方案加帳單帳戶，而且警示的是花費金額——Spark 方案上不會有帳單，設了也不會響。Realtime Database 有自己一套用量警示，量的是方案上限的百分比，與帳單無關。

位置在主控台**右上角鈴鐺圖示 → 設定**，不在 Realtime Database 那一頁裡。查證結果：「你的專案已儲存或下載的資料量（以 GB 為單位）**即將達到**方案上限」這一項**本專案預設就已開啟**（控制台與電子郵件兩個管道都開），無需任何操作。門檻百分比不可調，由 Firebase 決定。

順帶記錄：同一區的「你的即時資料庫設有不安全的規則」也開著，而本專案的規則刻意讓 `open` 節點 `.read: true`。**收到那封警示信是預期內的**，不是設定出錯——`ADR-0003` 已寫明任何人都讀得到，只是讀到密文。看到不要改規則。

### 超限時顯示人話

需從一般的寫入失敗中區分出「大小超限」，訊息要講三件事：單字量已超過雲端備份的上限、請改用檔案備份、**本機資料完全不受影響**。第三句最重要——不講的話，使用者會以為自己的卡出事了。

**分辨的位置在客戶端，不在狀態碼。** 原訂做法是看 Firebase 回的狀態碼，但安全規則的 `.validate` 失敗回 400 還是 401，官方文件查不到，實作時也無法驗證。若回的是 401，超限會被現有邏輯當成「指紋不對」——使用者看到「暱稱或密碼不對」，而且 `blocked` 一設就從此不再發任何請求，比原本那個狀態碼還糟。因此改成在 `write()` 裡加密完、送出前先量長度，超過就直接拋出，一個請求都不發。安全規則的上限保留，當作被竄改的客戶端的後門鎖。

代價是同一個數字寫在兩個地方（程式碼與規則檔），走鐘就會漏。用一條測試釘住：直接讀 `firebase-rules.json`，斷言規則裡的數字等於 `CLOUD_PAYLOAD_LIMIT`。

- 不碰任何 iOS 相關的東西——這張票純粹是 web code 與 Firebase 主控台
