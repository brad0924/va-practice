# 03 — Firebase 單筆上限、用量警示，與超限時的人話

Status: ready-for-agent
Type: enhancement
Blocked by: 無，可立即開始

決策背景見 `../spec.md`，本票對應決定二十六、二十七、二十八。

## 現況

`ADR-0003` 的最後一條寫著「額度目前有充裕餘裕，但不是無限。若日後改為多人使用，需重新計算」。公開上架就是那一刻。

資料庫網址明碼寫在 `src/lib/cloud-backup.ts` 裡，原始碼公開。安全規則擋得住「覆寫別人已有的備份」，但「建立一份全新的備份」必須放行，否則新使用者第一次備份就會被擋掉。

`cloud-backup.ts` 目前對非 401 的失敗一律回「寫入雲端失敗（狀態碼）」——使用者看到一個數字，不知道發生什麼事、也不知道資料還在不在。

## 決定

### 安全規則加上單筆 4 MB 上限

依 `ADR-0003` 記錄的每張卡約 155 bytes 推算，4 MB 約當 27,000 張卡，高於 JLPT 全級數單字量的兩倍，實際使用者不會觸及。Firebase 對單筆寫入的硬限制是 16 MB，4 MB 在其規矩之內。

### 誠實記錄這道防線擋得住什麼

它防的是單一路徑一次吃掉大量額度，以及程式異常膨脹。**它不防**有心人建立大量合規的小備份把 1 GB 慢慢塞滿——`ADR-0003` 選定的方案在免費方案上沒有速率限制能力。此風險經評估後接受，配套是用量警示。

### 開啟 Firebase 用量警示

補不起洞，至少要第一時間知道。

### 超限時顯示人話

需從一般的寫入失敗中區分出「大小超限」，訊息要講三件事：單字量已超過雲端備份的上限、請改用檔案備份、**本機資料完全不受影響**。第三句最重要——不講的話，使用者會以為自己的卡出事了。

## 這張票不做的事

- 不加 Firebase 匿名登入、不改造後端（spec「不在範圍內」已排除）
- 不改變雲端備份的加解密、路徑或新舊比較邏輯
- 不碰任何 iOS 相關的東西——這張票純粹是 web code 與 Firebase 主控台

## 驗收

- [ ] Firebase 安全規則加上單筆 4 MB 上限，規則檔一併更新（參考 `.scratch/cloud-backup/firebase-rules.json`）
- [ ] 既有的「指紋對得上才能覆寫」規則不受影響，正常推送照常成功
- [ ] Firebase 主控台開啟用量警示
- [ ] 超過上限時，畫面顯示的是可讀的中文說明，不是狀態碼
- [ ] 該訊息明說本機資料不受影響
- [ ] 超限被拒後，本機資料確實完好，下次啟動仍能正常複習
- [ ] 一般的網路失敗仍走原本的「進度還沒上傳，恢復連線後會自動補上」，沒有被誤判成超限
- [ ] 既有測試全數通過；`cloud-backup.test.ts` 若需新增案例，只加不改
