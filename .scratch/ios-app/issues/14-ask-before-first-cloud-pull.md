# 14 — Keychain 帶回密碼的裝置，第一次接雲端前要先問一句

Status: done
Type: enhancement
Blocked by: 06

決策背景見 `../spec.md` 決定十、十一、十二。**本票訂正決定十的一部分。**

## 要做什麼

在第二台裝置上裝好 app、第一次打開時，**不要默默把整份雲端資料拉下來**——先問一句「這台裝置記得暱稱 xxx，要現在接回來嗎？」

## 為什麼

票 06 真機驗證時發現的：第二台裝置全新安裝、打開，**問都沒問就已經是登入狀態，資料也同步完了**。

機制上完全正確——本機是空的（`updatedAt` 為 0），Keychain 把密碼帶了過來，`cloud.begin()` 比新舊時雲端那份必然勝出，於是整份拉回來。這正是決定十要的「換新 iPhone 時密碼自動跟著走」。

**但它把「不必重新輸入密碼」做成了「不必表示同意」，這兩件事被綁在一起了。** 使用者對第二台裝置沒有任何決定權，資料就出現了。

沒有資料會因此毀掉——全新安裝的本機是空的，拉回來是往空盤子裡放東西。所以這是掌控感的問題，不是安全的問題。唯一具體會讓人不舒服的場景：**家裡共用同一個 Apple ID 的 iPad**，裝了就直接看到你的單字本。

## 決定

### 訂正決定十：密碼自動跟著走，但「要不要接」由每一台裝置各自決定一次

決定十原訂「換 Apple 裝置時密碼自動跟著走」，實作後發現它同時讓「同意同步」也自動跟著走了。訂正為：**密碼跟著走，同意不跟著走**——每一台新裝置各問一次，答過就不再問。

「不必記住一組可能一年沒輸入過的密碼」這個原始目的完全保留：使用者按一下「接回來」，一個字都不必打。

### 問的時機在 `cloud.begin()` 之前，也就是啟動流程裡

拉資料的動作是 `cloud.begin()`，問必須早於它，否則問完資料已經在了。實作上是 `main.ts` 那個非同步前置步驟的下一步。

代價據實記錄：**此時畫面還沒建立，對話框會蓋在空白畫面上**。接受——那一刻本機也真的還沒有任何東西，空白畫面不是假象。

### 「同意過了」記在本機，不進備份、不上雲

與 `src/lib/gemini-key.ts` 及決定二十三（提醒開關）同一個定位：這是「這台裝置要不要接」的偏好，不是使用者的資料，因此不進 `AppData`、不上雲端、不進匯出檔。

**在這台裝置上親手登入成功也算同意**——使用者剛剛才打完密碼，下次開 app 再問一次是在羞辱他。

### 拒絕不刪 Keychain，只記在這台

**`SecItemDelete` 對可同步的項目是全域的**：這台刪掉，iCloud 鑰匙圈會把刪除同步到你所有的裝置。拿「這台不要接」當理由去刪一筆全域的密碼，代價完全不成比例。

因此拒絕只做兩件事：這次不 `begin()`、在本機記下來不再問。

### 拒絕之後要留一條反悔的路

不留的話，使用者想改主意就得重新輸入密碼——那正是這整個功能存在的理由。因此「資料」畫面在「這台拒絕過」的狀態下，雲端備份區塊顯示一顆「接回雲端備份（暱稱 xxx）」的按鈕。

否決「拒絕後每次啟動都再問一次」：共用 iPad 的那個人會被問到天荒地老，而那正是最需要拒絕的使用者。

### `cloud-backup.ts` 仍然一行不改

同意與否是接線層的事，`begin()` 何時被呼叫本來就由呼叫端決定。票 06 建立的接縫在這裡再用一次。

## 這張票不做的事

- 不改雲端備份的加解密、指紋、新舊比較或推拉邏輯
- 不改 `src/lib/cloud-backup.ts`
- 不改 Keychain 的存取方式（票 06 已定案）
- 不做網頁版的任何改動——網頁版沒有 Keychain，密碼不會憑空出現在一台新裝置上，沒有這個問題
- 不做「這台裝置只讀不寫」之類的部分同步模式

## 驗收

- [x] 按「接回來」之後，資料完整拉回來，行為與現在一致（**真機**）
- [x] 同意過的裝置再開 app，不會再被問
- [x] 在這台裝置上親手登入成功後，下次開 app 不會被問

- [x] 拒絕之後重開 app，不會再被問

### 2026-08-11 — 開票背景

票 06 的六條真機驗收全過，這是驗的過程中冒出來的**設計問題，不是缺陷**：功能做到了規格要的事，但規格把兩件事綁在了一起。

提過但沒有採用的三個替代方案：

| 方案 | 為什麼不採用 |
| --- | --- |
| 什麼都不改 | 這正是票 06 要的行為，但使用者對第二台裝置沒有任何決定權這件事站不住 |
| 只加一行告知（拉回來後顯示「已接回 xxx 的雲端備份」） | 改動最小，但它只解決「不知道發生了什麼」，不解決「沒被問過」 |
| 只預填不自動登入 | 換手機後打開看到的是空 app，使用者不會知道要去資料頁按那一下——比現況更糟 |

### 2026-08-18 — 訂正本票的實作位置：那一問在 `app.ts`，不在 `main.ts`

票裡寫「實作上是 `main.ts` 那個非同步前置步驟的下一步」。實作時發現那個位置做不到，改放在 `src/app.ts` 的 `start()` 裡、`app.showReview()` 之前。兩個理由都是硬的：

1. **對話框那句話查不到表。** `t()` 要先 `initI18n()` 才能用，而那一步在 `start()` 的最前面。放 `main.ts` 就得在啟動路徑上多接一次 i18n，或讓對話框講寫死的中文。
2. **暱稱只有 `cloud.nickname()` 拿得到**，而 `cloud` 是 `start()` 裡才建的。`main.ts` 要自己講出「這台記得誰」，就得自己去解 `va-practice:cloud` 那串 JSON——那是 `cloud-backup.ts` 的私事，而本票要求那支一行不改。

票要的兩件事都不受影響：仍然早於 `cloud.begin()`，也仍然早於任何畫面被建立，「對話框蓋在空白畫面上」那個代價照舊成立。

### 2026-08-18 — 補一條票裡沒想到的：升級前就已經在同步的裝置不能問

**這是 code review 抓到的，不補會出事。** 票的前提是「全新安裝、本機是空的，拉回來是往空盤子裡放東西」。但票 06 那台已經登入、已經同步的裝置升級到這一版時，本機**不是**空的，而它同樣沒有「答過」的紀錄——照原設計會被問一次，而且：

- 對話框那句「選『取消』的話這台會從空的開始」對它是假話
- 真的按了取消，那台從此靜默停止備份，使用者不會收到任何提示

因此 `wantsPull()` 多收一個 `syncedBefore`：本機這份資料的 `updatedAt` 非 0（伺服器蓋的時間戳，見 `types.ts`）就代表這台早就在和雲端往返，同意是它自己在更早以前表示過的——不問，直接接，並把 `granted` 記下來。全新安裝的第二台裝置 `updatedAt` 恆為 0，不受這一條影響。

### 2026-08-18 — 據實記錄的三個代價

1. **拒絕的狀態下，「換密碼」與「停止同步」一起被藏起來。** 票只說那個狀態要顯示一顆接回鈕，而那台裝置並沒有在同步，畫成「已登入」會是謊話。後果是：拒絕過的裝置沒有任何入口清掉本機那組憑證，想改用另一個暱稱得先接回來、再停止同步、再登入。若共用 iPad 的人真的想在同一台用自己的帳號，這條路很繞——要不要在拒絕狀態也放一顆「停止同步」是另一張票的事（它會刪掉 Keychain 那一筆，而那是全域的）。
2. **反悔那顆鈕走的是 `cloud.begin()`，因此仍然是「較新的那份整份勝出」。** 拒絕之後在這台累積了一段時間的卡片，按下接回來時若本機比雲端新，被覆蓋的會是雲端那份。這與使用者親手登入的行為完全一致（`signIn()` 同一條規則），且本票明言不改推拉邏輯，因此不在這裡處理。
3. **`CONTEXT.md` 與 `docs/glossary.md` 沒有為這件事新增詞條。** 程式、介面字串與 spec 已經穩定用「接回來／答過一次」這組講法，但詞彙表裡沒有正名。留給 `/domain-modeling` 決定要不要立一則。

### 2026-08-18 — 真機驗證：同意那條路通過

維護者把 app 刪掉、裝上這一版的 TestFlight build，打開後**看到詢問、按「接回來」，卡片與進度完整回來，一個字都沒打**。驗收前兩條（本票唯一非真機不可的那兩條）成立。

刪掉重裝之所以等同「全新的第二台裝置」：刪 app 會把 localStorage 與保險副本一起帶走（票 13 已記錄 iPhone 上沒辦法只清一邊），因此那台重裝後沒有答案、也沒有印章，而密碼從 iCloud 鑰匙圈回來了——正是這張票要處理的情境。**這條路以後就是驗這個功能的標準做法，不必真的找第二台裝置。**

**沒有在真機上驗到的是「取消」那條路**：拒絕之後的初始化、不再被問、以及「資料」畫面那顆反悔的鈕。它們由 `cloud-consent.test.ts` 的 15 條測試與程式碼審查支撐，但**畫面那一段（`data-view.ts` 的拒絕分支）沒有任何自動測試**——它是這張票裡唯一沒被任何一種測試碰到的地方。要驗就得再刪一次 app、在對話框按取消。

### 2026-08-18 — 真機驗證：取消那條路也通過了，空白補上

上一則記著「取消那條路沒在真機上驗到」。維護者接著又刪一次 app、這次在對話框按取消，結果：

- 那台**從空的單字本開始，資料沒有被接回來**——「拒絕之後本機照常初始化成新使用者」成立
- 「資料」畫面認得出這台記著 Keychain 裡那組憑證，**長出了接回來那顆鈕；按一下，資料就回來了，密碼一個字都不必打**

也就是說 `data-view.ts` 那個拒絕分支——這張票裡唯一沒有自動測試覆蓋的地方——已經由真機看過。整張票十二條驗收全數在真機或測試上成立，沒有留下空白。

（唯一沒被明確回報的是「拒絕之後重開 app 不會再被問」，那一條由 `cloud-consent.test.ts` 釘著。）
