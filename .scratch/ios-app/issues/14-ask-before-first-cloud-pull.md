# 14 — Keychain 帶回密碼的裝置，第一次接雲端前要先問一句

Status: ready-for-agent
Type: enhancement
Blocked by: 06

決策背景見 `../spec.md` 決定十、十一、十二。**本票訂正決定十的一部分。**

## 要做什麼

在第二台裝置上裝好 app、第一次打開時，**不要默默把整份雲端資料拉下來**——先問一句「這台裝置記得暱稱 xxx，要現在接回來嗎？」

## 為什麼

票 06 真機驗證時發現的：第二台裝置全新安裝、打開，**問都沒問就已經是登入狀態，資料也同步完了**。

機制上完全正確——本機是空的（`updatedAt` 為 0），Keychain 把密碼帶了過來，`cloud.begin()` 比新舊時雲端那份必然勝出，於是整份拉回來。這正是決定十要的「換新 iPhone 時密碼自動跟著走」。

**但它把「不必重新輸入密碼」做成了「不必表示同意」，這兩件事被綁在一起了。** 使用者對第二台裝置沒有任何決定權，資料就出現了。

沒有資料會因此毀掉——全新安裝的本機是空的，拉回來是往空盤子裡放東西。所以這是掌控感的問題，不是安全的問題。唯一具體會讓人不舒服的場景：**家裡共用同一個 Apple ID 的 iPad**，裝了就直接看到你的單字本。

## 決定

### 訂正決定十：密碼自動跟著走，但「要不要接」由每一台裝置各自決定一次

決定十原訂「換 Apple 裝置時密碼自動跟著走」，實作後發現它同時讓「同意同步」也自動跟著走了。訂正為：**密碼跟著走，同意不跟著走**——每一台新裝置各問一次，答過就不再問。

「不必記住一組可能一年沒輸入過的密碼」這個原始目的完全保留：使用者按一下「接回來」，一個字都不必打。

### 問的時機在 `cloud.begin()` 之前，也就是啟動流程裡

拉資料的動作是 `cloud.begin()`，問必須早於它，否則問完資料已經在了。實作上是 `main.ts` 那個非同步前置步驟的下一步。

代價據實記錄：**此時畫面還沒建立，對話框會蓋在空白畫面上**。接受——那一刻本機也真的還沒有任何東西，空白畫面不是假象。

### 「同意過了」記在本機，不進備份、不上雲

與 `src/lib/gemini-key.ts` 及決定二十三（提醒開關）同一個定位：這是「這台裝置要不要接」的偏好，不是使用者的資料，因此不進 `AppData`、不上雲端、不進匯出檔。

**在這台裝置上親手登入成功也算同意**——使用者剛剛才打完密碼，下次開 app 再問一次是在羞辱他。

### 拒絕不刪 Keychain，只記在這台

**`SecItemDelete` 對可同步的項目是全域的**：這台刪掉，iCloud 鑰匙圈會把刪除同步到你所有的裝置。拿「這台不要接」當理由去刪一筆全域的密碼，代價完全不成比例。

因此拒絕只做兩件事：這次不 `begin()`、在本機記下來不再問。

### 拒絕之後要留一條反悔的路

不留的話，使用者想改主意就得重新輸入密碼——那正是這整個功能存在的理由。因此「資料」畫面在「這台拒絕過」的狀態下，雲端備份區塊顯示一顆「接回雲端備份（暱稱 xxx）」的按鈕。

否決「拒絕後每次啟動都再問一次」：共用 iPad 的那個人會被問到天荒地老，而那正是最需要拒絕的使用者。

### `cloud-backup.ts` 仍然一行不改

同意與否是接線層的事，`begin()` 何時被呼叫本來就由呼叫端決定。票 06 建立的接縫在這裡再用一次。

## 這張票不做的事

- 不改雲端備份的加解密、指紋、新舊比較或推拉邏輯
- 不改 `src/lib/cloud-backup.ts`
- 不改 Keychain 的存取方式（票 06 已定案）
- 不做網頁版的任何改動——網頁版沒有 Keychain，密碼不會憑空出現在一台新裝置上，沒有這個問題
- 不做「這台裝置只讀不寫」之類的部分同步模式

## 驗收

- [ ] 第二台裝置全新安裝後第一次打開，先看到詢問，按「接回來」才同步
- [ ] 按「接回來」之後，資料完整拉回來，行為與現在一致
- [ ] 同意過的裝置再開 app，不會再被問
- [ ] 在這台裝置上親手登入成功後，下次開 app 不會被問
- [ ] 拒絕之後，本機資料照常初始化成新使用者，一個網路請求都不發
- [ ] 拒絕之後重開 app，不會再被問
- [ ] 拒絕之後，Keychain 裡那一筆**仍然在**（其他裝置不受影響）
- [ ] 拒絕之後，「資料」畫面有一條反悔的路，按下去就接回來且不必輸入密碼
- [ ] 網頁版行為零變化
- [ ] `src/lib/cloud-backup.ts` 一行未改
- [ ] 既有測試全數通過，且一個既有測試檔都沒被修改
- [ ] `spec.md` 決定十補上訂正

## Comments

### 2026-08-11 — 開票背景

票 06 的六條真機驗收全過，這是驗的過程中冒出來的**設計問題，不是缺陷**：功能做到了規格要的事，但規格把兩件事綁在了一起。

提過但沒有採用的三個替代方案：

| 方案 | 為什麼不採用 |
| --- | --- |
| 什麼都不改 | 這正是票 06 要的行為，但使用者對第二台裝置沒有任何決定權這件事站不住 |
| 只加一行告知（拉回來後顯示「已接回 xxx 的雲端備份」） | 改動最小，但它只解決「不知道發生了什麼」，不解決「沒被問過」 |
| 只預填不自動登入 | 換手機後打開看到的是空 app，使用者不會知道要去資料頁按那一下——比現況更糟 |
