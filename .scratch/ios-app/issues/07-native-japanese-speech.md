# 07 — 原生日文語音：朗讀按鈕在 iOS 上永遠可用

Status: done
Type: enhancement
Blocked by: 01

決策背景見 `../spec.md`，本票對應決定十四、十五、十六。

## 現況

`src/ui/speech.ts` 走 Web Speech API，找不到日文語音時 `hasJapaneseVoice()` 回 `false`，`src/ui/review-view.ts` 據此把朗讀按鈕整個藏起來。這個設計在網頁上是對的——與其讓使用者聽到外語腔調念日文，不如不要出現這個按鈕。

~~但在 WKWebView 裡，日文語音的存在與否不可靠。結果是使用者不會看到任何錯誤，只會覺得「這個按鈕有時候在、有時候不在」。~~

**訂正（01 實測結果）**：這個前提是錯的。iOS WKWebView 裡 `hasJapaneseVoice()` 回 `true`，**按鈕正常顯示、聽得到日文**。真正的問題是**音質**——接近機械音，重音（高低アクセント）不對。詳見 01 的 `## Comments`。

（01 的災情回報會確認這件事實際發生的程度；**不論結果如何，這張票的做法不變**——這句話成立，下方「決定」一段不受影響。變的只是動機：從「為了讓按鈕不消失」變成「為了聲音好聽」。）

## 決定

### 不開新接縫，在 `speech.ts` 內部分支

該模組對外只有 `initSpeech` / `hasJapaneseVoice` / `speak` 三支，`review-view.ts` 的呼叫方式**一字不改**。模組內部先探測原生語音橋接是否存在：有就用原生（`AVSpeechSynthesizer`），沒有就沿用現有的 Web Speech 路徑。

### iOS 上朗讀按鈕永遠可用

原生語音的日文是系統內建、離線可用，因此 `hasJapaneseVoice()` 在 iOS 上恆為真，按鈕不再時有時無。**網頁版維持原本「沒有日文語音就藏起來」的行為。**

（01 實測後補充：按鈕在 iOS 上本來就永遠顯示，因此這條不是本票的價值所在，只是改用原生後順帶得到的更強保證。）

### 取用 enhanced 品質的語音

這是本票實際要解決的問題。iOS 的 Web Speech 底層雖然也是 `AVSpeechSynthesizer`，但只拿得到 compact（壓縮）品質的語音，那正是 01 實測聽到的機械感來源。原生實作要明確挑選 enhanced／premium 品質的日文語音；系統上沒有安裝時退回預設品質，不要因此讓朗讀失效。

### 朗讀的文字來源不變

仍是 `toReadingText()` 轉出的讀音文字——聽到的與卡片教的讀法一致。這是既有決定，原生實作照搬，不要改成念詞條原文。

### 語速沿用現有設定

現行 Web Speech 路徑用的是 0.9 倍速。原生實作取一個聽感相當的值，不要因為換了引擎就順手調整。

## 這張票不做的事

- 不改 `src/ui/review-view.ts`
- 不改變朗讀的觸發方式——仍然一律由使用者主動點擊，不自動發聲
- 不加語速或語音的設定選項
- 不為 `speech.ts` 補自動測試：它持有全域語音狀態，現在也沒有測試，本票刻意維持對外介面不變正是為了讓這一側零變動

## Comments

### 2026-08-11 — 落地的東西

| 檔案 | 是什麼 |
| --- | --- |
| `src/ui/speech.ts` | 多一條原生分支。對外仍是 `initSpeech`／`hasJapaneseVoice`／`speak` 三支，一支都沒多 |
| `src/lib/speech-native.ts` | 唯一碰 Capacitor 的檔案。網頁版恆回 `null`，呼叫端因此不必判斷平台 |
| `ios/App/App/SpeechPlugin.swift` | 原生那一端，只有 `speak` 一支 |
| `MainViewController.swift`、`project.pbxproj` | 多註冊一支插件、把新的 Swift 檔掛進編譯清單 |

`src/ui/review-view.ts` **一行未改**——這正是決定十四不開新接縫要的效果。

### 為什麼 Capacitor 那一段不寫在 `speech.ts` 裡

沿用 `safety-copy-native.ts`、`keychain-native.ts`、`download-native.ts` 已經立下的分界：碰 Capacitor 的東西一律關在 `src/lib/*-native.ts`，其餘的照常在 vitest 裡跑得動。`speech.ts` 本身不新增測試（票裡明講不補），但讓它繼續維持「不 import 原生東西」這個性質，成本是一個檔案，換來的是這條界線不出現例外。

決定十四說的「在 `speech.ts` 內部分支」仍然成立：**判斷走哪一條的那個 if 就在 `speech.ts` 裡**，`speech-native.ts` 只回答「有沒有原生語音」。

### 原生那一端只做三件原生才做得到的事

念什麼由 TypeScript 決定——`speak()` 先跑 `toReadingText()`，再把讀音文字遞過去（決定十六）。挑語音、選語速、中斷前一次留在 Swift，因為那三件事只有 `AVSpeechSynthesizer` 答得出來。

- **挑語音**：日文語音依 `quality` 取最大值。rawValue 由差到好是 `.default`（compact）、`.enhanced`、`.premium`，因此取最大就是取最好。**沒有寫死 enhanced**：使用者沒下載時清單裡只有 compact，寫死會落到 nil、變成用系統當前語言念日文，比機械音更糟。清單真的空了才退回 `AVSpeechSynthesisVoice(language: "ja-JP")`。
- **語速**：`AVSpeechUtteranceDefaultSpeechRate * 0.9`。兩把尺不同——`AVSpeechUtterance` 的正常速度是 0.5 而不是 1.0，直接填 0.9 會快到聽不清楚。
- **中斷**：`stopSpeaking(at: .immediate)`，連按兩次不會疊在一起念。

### 沒碰音訊類別（AVAudioSession）

因此**靜音鍵切到靜音時聽不到朗讀**。這與改動前的 Web Speech 在同一支 app 裡的行為一致——底層本來就是同一台合成器、同一個預設類別，所以不是這次改動造成的退步。要讓它蓋過靜音鍵得把類別改成 `.playback`，那是票裡沒要求的事，先不做。真機驗收時若覺得該改，開一張新票。

### 2026-08-11 — 真機第一輪：按鈕與朗讀都正常，音質待重驗

出 build 裝上真機後的回報與診斷（診斷細節見票 15）：

| 驗收 | 結果 |
| --- | --- |
| 朗讀按鈕永遠顯示 | ✅ |
| 點朗讀聽得到日文，念的是振假名讀音 | ✅ |
| 音質明顯比 Web Speech 自然 | ⏳ **待重驗**，見下 |
| 網頁版行為零變化 | ✅ |

**「聽起來與網頁版一樣」的原因查清楚了**：本票的規則是「全清單品質最高」，同分時 Swift 的 `max(by:)` 保留先出現的那顆，實際挑到 **Kyoko (Enhanced)**；而網頁版挑的是「清單裡第一顆 `ja`」，在同一支手機上極可能也是 Kyoko (Enhanced)。**兩邊是同一顆語音**，聲音一樣是必然的。

不是這一票做錯了什麼，但它確實沒有帶來預期的音質差別——因為 spec 決定十五假設「iOS 的 Web Speech 只拿得到 compact」，而這支手機的實測顯示網頁那側**也拿得到 enhanced**。

票 15 已把規則改成「跟著系統選的那顆走」，現在挑的是 O-ren (Enhanced)，與網頁版不再是同一顆，A／B 比對要在票 15 的 build 上重做。

### 2026-08-11 — A／B 重比：兩邊念的是不同語音了

票 15 把規則改成「跟著系統選的那顆走」之後，**使用者回報 app 與網頁版聽起來不一樣**——app 念 O-ren，網頁版念 Kyoko，與票 15 的診斷輸出完全對得上。

本票驗收「與改動前 A／B 比對」因此有了執行期的證據：**兩邊確實不再是同一顆語音**。但驗收原文寫的是「音質明顯比 Web Speech 自然」，而實測顯示網頁那側在這支手機上也拿得到 enhanced，兩邊是同級品質的不同語音，不是「差品質對好品質」。**這條驗收的措辭已被實測推翻**，成立的是它的實質目的：使用者現在聽到的是自己選的那顆語音。

仍待真機驗的三條：飛航模式、連按中斷、純假名與外來語詞條。

### 2026-08-11 — 剩下三條真機驗完，本票結案

使用者回報：**飛航模式、連按中斷、純假名與外來語詞條三條全過**，九條驗收因此全數勾完，狀態改為 `done`。

一個新發現不屬於本票：**連按兩次時畫面會被放大**。朗讀的中斷本身是好的，放大是撞上的另一件事——WKWebView 的連點兩下縮放，任何地方連點兩下都會發生，與朗讀無關。已開票 16，並在該票記下查證結果：Capacitor 的 `zoomEnabled` 預設就關著，但它只擋雙指、擋不到連點兩下。
