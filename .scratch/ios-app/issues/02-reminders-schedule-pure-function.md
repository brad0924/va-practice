# 02 — 提醒排程：算出未來各天的累積到期張數

Status: ready-for-agent
Type: enhancement
Blocked by: 無，可立即開始

決策背景見 `../spec.md`，本票對應決定十七、十八、十九、二十。

## 要做什麼

新開 `src/lib/reminders.ts`，回答一個問題：**未來這幾天，每天分別會積到幾張到期卡？**

這是整個 iOS 工程唯一有實質新邏輯的地方，也是唯一開的新接縫。純函式、不碰原生 API、不碰時鐘、不碰畫面——因此完全在 vitest 裡測得到，**不需要等探路 build**。

後續由 09 拿這份結果去登記系統通知，但那是另一張票的事；這張票交付的是一支能單獨測到底的函式。

## 決定

### 為什麼不放進 `review.ts`

`review.ts` 的職責是複習流程本身（排程演算法、抖動、佇列排序、「再次」重排）。提醒是它的下游消費者，混進去會稀釋一個目前很乾淨的職責。

### 為什麼不重用 `groupByBucket`

那支住在畫面層（`src/ui/list-view.ts`），回答的是「六個時間桶各有哪些卡」，形狀與用途都不同。

### 張數是累積的，不是當天新增的

沒複習的卡不會消失。第 N 天的張數是「**所有到期日在第 N 天或更早的卡**」，不是「第 N 天當天才到期的卡」。這使結果天然地只增不減。

### 新卡從第一天起就計入

新卡沒有到期日，與 `buildQueue()` 一致地視為已到期。

### 只算複習範圍內的卡

吃的必須是與 `buildQueue()` 同一批（複習範圍內的卡），否則通知上的數字與使用者打開 app 看到的對不起來。範圍的過濾由呼叫端負責，本模組只吃已經篩好的卡。

### 當前時間一律注入

與 `review.ts` 同樣的紀律：模組內不取用系統時鐘。

### 排未來 7 天，不含今天

今天不排——排程動作發生時當天的提醒時間可能已經過去，且使用者此刻正拿著 app。

### 張數為 0 的日子不出現在結果裡

「今天一張都沒到期就不要吵我」這條規則在這一層就實現，呼叫端不必再過濾。

## 這張票不做的事

- 不碰任何 Capacitor API、不登記任何系統通知（那是 09）
- 不做提醒開關、不請求通知權限（那是 09）
- 不決定提醒的時間點（08:00 是 09 的事，本模組只回答「哪幾天、各幾張」）
