# 09 — 每日提醒：權限、開關，與只在有卡的日子叫人

Status: done
Type: enhancement
Blocked by: 01, 02

決策背景見 `../spec.md`，本票對應決定二十、二十一、二十二、二十三、二十四。

## 要做什麼

讓使用者每天早上收到一則提醒，**上面寫著今天有幾張到期**；今天一張都沒有就不吵他，今天已經複習完了也不再叫。

這同時是 App Store 準則 4.2 的主力論據：一支會算你的複習排程、只在該提醒時提醒的 app，不是「把網站裝進殼裡」。

## 決定

### 排程資料來自 02，不重算

02 已交付的純函式負責回答「未來 7 天各天積到幾張」。這張票只負責把那份結果登記進系統通知，**不要在這裡重寫任何排程計算**。

吃的卡必須與 `buildQueue()` 同一批（複習範圍內的卡），否則通知的數字與打開 app 看到的對不起來。

### 資料一變就整批重排

先清掉全部已登記的提醒，再依最新資料重新登記。這使「複習完就不再被叫」與「匯入一批卡後數字立刻正確」用**同一條路徑**實現，不需要任何個別取消的邏輯。

觸發點與 `persist()` 相同。

### 沿用 `pending` / `sending` 模式，且不與保險副本共用閘門

重排的也是「整批」，中間那幾份同樣沒有意義，因此與 05 採同一個模式。但**各自持有自己的 `pending` / `sending`**——兩者寫的是不同的原生 API，共用一道閘門會讓其中一邊變慢時卡住另一邊。

### 提醒時間第一版固定每日 06:00

不做設定畫面。不為尚未被要求的需求寫程式；日後若要開放設定，是獨立的一件事。

> **訂正（2026-08-11，動工時）**：spec 決定二十二原訂 08:00，維護者改為 06:00。只換一個常數，其餘決定不受影響。

### 開關放在「資料」畫面，狀態只存本機

與雲端備份登入同一個畫面。這是「這台裝置要不要叫我」的偏好，不是使用者的資料——與 `src/lib/gemini-key.ts` 的定位一致，因此**不進 `AppData`、不上雲端、不進匯出檔**。

### 通知權限被拒絕時，開關要誠實

不重複請求，且不呈現「提醒已開啟」的假象——關掉開關並指向系統設定。使用者寧可看到「你關掉了通知權限」，也不要以為提醒在運作卻永遠收不到。

### 7 天遠低於 64 則上限

iOS 同時只能登記 64 則本機通知。排 7 天留有充裕餘裕，不需要額外的裁切邏輯。

## 這張票不做的事

- 不改 `src/lib/reminders.ts` 的計算邏輯（那是 02 的職責）
- 不做提醒時間的自訂
- 不做遠端推播、不架任何伺服器——全部是本機通知
- 不在通知裡放操作按鈕或深層連結到特定卡片

### 三處實作判斷

**一、原生那一端併成一支 `replaceAll`，不是「清空」加「登記」兩支。** 整批重排是一件事；拆成兩支的話，中間那個「已經清空但還沒登記」的狀態就變成 TypeScript 那側要管的東西，而它管不到——那半秒裡 app 被滑掉，提醒就整批消失了。併成一支之後，決定二十一要的「不需要任何個別取消的邏輯」是字面上的真話。

**二、觸發點比 spec 寫的多兩個。** 決定二十一說「觸發點與 `persist()` 相同」，照字面做會漏掉兩條：

- `reload()`——匯入單字、整份匯入、雲端拉下來這三條路都不經過 `persist()`。漏掉的話驗收第七條（匯入後數字立刻正確）直接不成立。這與票 05 遇到的是同一個坑。
- **啟動時一次**。排的是未來 7 天，只靠資料變動觸發的話，一個「開了 app 卻沒複習」的人在第 8 天之後就完全收不到提醒了。這一條 spec 沒寫，但不補上這個功能就是會自己過期。

**三、每次重排前順手問一次權限。** 使用者可能在系統設定裡把通知關掉，此時開關還亮著就是決定二十四說的「假象」。作法是重排前問一次 `permission()`，不是 `granted` 就把開關一起關掉並清空。代價是每次存檔多一次原生呼叫，那是很便宜的本機呼叫。

### 沒有做的一件事：抽出共用的合併閘門

這道 `pending` / `syncing` 閘門與 `safety-copy.ts` 的 `createSafetyCopy()` 形狀幾乎一樣，泛型化成一支共用的並不難。**沒有做**，理由是票 05 那份已經在真機上驗過並結案，為了消掉 15 行重複去動它，風險與收益不成比例（Karpathy 第三條：只碰非改不可的地方）。spec 決定二十一要的是「同一個模式」與「各自持有自己的閘門」，兩者目前都成立。日後真的出現第三個需要它的地方，那時再抽。

### 2026-08-11 — code-review 後的修正

雙軸審查抓到一個真缺口和幾處誠實度問題，都已修掉。

#### 1. 開關的誠實只做了一半（真缺口）

Spec 軸指出：決定二十四要的是「關掉開關**並指向系統設定**」，而權限在系統設定被收回那條路只做了前半——開關會在背後被關掉，但**畫面上已經畫出來的那個勾不會彈回去，也沒有任何一個字說明原因**。使用者要離開再回「資料」畫面才會發現勾不見了，而且看不到為什麼。

修法是把「開關現在是不是真的成立」收成一支 `verify()`：開著、而且權限還在，才回真；發現被收回就就地關掉並清空。重排與畫面兩條路共用它——分開寫的話，兩邊對「現在到底開著沒」會給出不同的答案。「資料」畫面畫出開關後問一次，拿到 false 就把勾彈回去並寫上指向系統設定的那句話。加了 3 條測試。

#### 2. 一句假保證的註解

`DailyReminderPlugin.swift` 原本寫「寫死比較誠實：哪天多出第二種通知時，這裡不會默默把別人的一起清掉」，但清空那一步用的是 `removeAllPendingNotificationRequests()`，`idPrefix` 只用在登記端——**清的就是全部**。目前只有一種通知，行為正確，但那句話是假的。已改成講實話，並寫明哪天多出第二種時該怎麼改。

#### 3. 多要了一項用不到的權限

`requestAuthorization` 原本連 `.badge` 一起要，但這支 app 一個地方都沒設過紅點數字。拿掉，那張對話框不必看起來比實際上更貪心。

#### 4. 命名與重複

- 閘門的旗標原本叫 `syncing`。`CONTEXT.md` 的「雲端備份」條把「同步」列在 `_Avoid_`，而這裡沒有任何東西在同步——做的是整批重排。改成 `scheduling`。
- 「每天早上 6:00 提醒我」原本把時間寫死在畫面上，`REMINDER_HOUR` 就在旁邊卻沒用；改時間要動兩處。已改成從常數組出來。
- 勾選框借用了 `book-check`（那個類別專指單字本那一列）。改成自己的 `toggle-check`。
- Swift 裡 `request(_:)`（請求權限）與 `request(from:)`（造一則通知登記）同名異義，後者改為 `notificationRequest(from:)`。
- 一條恆真的斷言 `expect(REMINDER_HOUR).toBe(6)`——它只是把常數抄一遍，而上一行已經驗過每一則的 `hour` 都是 6。刪掉。

#### 5. 把多出來的觸發點回寫 spec

Spec 軸建議「觸發點比 `persist()` 多兩個」這件事不要只留在票裡。已在 `spec.md` 決定二十一底下補上訂正，列出實際的三個觸發點。

#### 駁回一項

Standards 軸要求把「每日提醒」等新詞彙補進 `CONTEXT.md`。**不在本票動手**——spec 決定三十四已經指名這件事屬於票 10（ADR-0012 與 CONTEXT 詞彙），票 02 當初也是以同一個理由留給票 10 的。這是真實缺口，但它有自己的票。

`cap sync ios` 在 Windows 上會把 `ios/App/CapApp-SPM/Package.swift` 的相依路徑改寫成**反斜線**（`..\..\..\node_modules\@capacitor\filesystem`），那在 macOS 上會解析不到套件。已還原，沒有進 commit。**後續在 Windows 上跑 `cap sync ios` 的人請一律檢查這個檔案**。

### 2026-08-11 — 真機驗收發現「今天一律不排」是錯的

維護者在真機上把時間調到 05:59 等 06:00，沒有收到通知。**行為與程式一致，但規則本身是錯的。**

#### 怎麼發現的

用維護者當天的資料實際算過（複習範圍 `JLPT N2` + `生活用語`，261 張）：

| 日期 | 累積到期 | 舊規則有沒有登記 |
| --- | --- | --- |
| 08-11（當天） | 2 | ❌ 不排 |
| 08-12 | 50 | ✅ |
| 08-13 | 86 | ✅ |

當天那一格從來就不在登記清單裡，所以時間跑過 06:00 什麼都不會發生。**先前寫在維護者待辦裡的那個測試步驟（「調到 05:58 等兩分鐘」）在設計上不可能成功**，那是寫票時沒有把它跟決定二十對起來。

#### 規則錯在哪

決定二十給了兩個理由，第一個對、第二個錯：

- ✅「排程當下今天的提醒時間可能已經過去」——排一個過去的時刻確實沒有意義
- ❌「使用者此刻正拿著 app」——**拿著 app 是排程那一刻的事，不是提醒響的那一刻的事**。使用者早上 5 點開 app 看一眼就關掉，6 點時他並沒有拿著 app，卻再也不會被叫

而且這個洞與驗收「複習完當日的卡之後，當天剩下的提醒不再出現」是同一個機制的正反兩面：

| 早上 5 點做了什麼 | 舊規則 | 對嗎 |
| --- | --- | --- |
| 開了 app 但沒複習 | 不響 | ❌ 漏叫 |
| 把當天的卡複習完 | 不響 | ✅ |

兩者產生**一模一樣的結果**，那條驗收因此驗不出任何東西——程式根本沒問過「你複習完了沒」。

#### 改成什麼

今天也排，但**兩個條件同時成立**才排：提醒時間還沒到，且今天還有卡沒複習完。

第二個條件是免費的：複習完的卡到期日被推到未來，`dueCountToday()` 自然數不到它，而張數為 0 的日子本來就不登記。真正新增的只有第一個條件那一道時間閘門。

#### 「6 點當下我開著 app 就別跳」不必自己實作

維護者提的第三個條件是「而且我沒有開著 app」。**這件事 iOS 已經在做了，一行程式都不必寫。**

Capacitor 的 `NotificationRouter` 是 `UNUserNotificationCenter` 的代理（`handleApplicationNotifications` 預設為 `YES`），而它的 `willPresent` 是這樣寫的：

```swift
presentationOptions = localNotificationHandler?.willPresent(notification: notification)
...
completionHandler(presentationOptions ?? [])
```

本 repo 沒有裝 `@capacitor/local-notifications`，`localNotificationHandler` 因此是 nil → 回傳空的呈現選項 → **app 在前景時通知被靜默丟棄**。背景或關著才會跳。

這也是為什麼舊規則的第二個理由該整條拿掉：**用執行當下的真實狀態判斷，永遠勝過在幾小時前預測它。**

**下次再撞上同一件事的話**：那些憑證的私鑰不在任何一台你摸得到的機器上，後台能下載的只有公開那半，簽不了章，撤掉沒有任何損失。要根治得改成自己握一張固定的 `Apple Distribution` 憑證（用 OpenSSL 在 Windows 上就能產 CSR，不需要 Mac），連同 provisioning profile 存進 GitHub secrets，並拿掉 `-allowProvisioningUpdates`。那不在本票範圍，需要時另開一張。

#### 這張票途中被推翻過兩次前提

兩次都不是實作沒照票做，而是**票本身寫錯了**，記在這裡免得日後只看驗收清單的人以為它一路順利：

1. **提醒時間 08:00 → 06:00**（動工時，維護者決定）。只換一個常數。
2. **「今天一律不排」→ 兩道閘門**（真機驗收時發現）。決定二十的第二個理由把「排程那一刻」與「提醒響的那一刻」混為一談，同時讓一條驗收失去鑑別力。

第二顆是這張票最值得記住的一課：**能用執行當下的真實狀態判斷的事，不要在幾小時前預測它。**「6 點時我開著 app 嗎」正是這種事，而 iOS 本來就會在通知要呈現的那一刻問一次。
