# 22 — 重新設計 app 圖示

Status: ready-for-agent
Type: enhancement
Blocked by: 無，可立即開始

不擋任何票。票 `11`（送審）已不被 `21` 擋著，但這張票會換掉 `11` 要上傳的素材，所以兩張若同時進行要注意順序。

## 這是什麼問題

**現在那張圖示看不出這個 app 是幹嘛的，而且看起來像預設圖。**

票 `21` 換掉了 Capacitor 的藍色叉叉，但它明文寫著「不重新設計圖案。要改設計是另一件事，另開票」。這就是那張票。

現況那張是四個圓角矩形疊出來的一疊閃卡——兩張白卡加兩條橫槓。使用者的原話是兩件事：**看不出來是單字學習 app**、**想要有設計感**。

第二點的原因查出來了：`scripts/generate-icons.mjs` 只認得一種圖形。`inside()` 整個函式就是圓角矩形的數學式，沒有文字、沒有漸層、沒有陰影、沒有曲線。那不是畫得不好，是那台機器只能切方塊。

## 決定

以下每一條都是 2026-08-19 那輪 `/grilling` 談定的，不是實作時的自由選擇。

### 圖案：玻璃格裡的「単語」

一片半透明玻璃板浮在深色底上，板上横排「単語」，頭上標讀音「たんご」。

- **横排，不是直排。**直排是日文正規寫法、大圖也更好看，但兩字上下疊加右側一行假名會變成三欄，小尺寸糊得更快。
- **兩個字，不是一個字。**已知代價是 38 像素時筆畫會黏——使用者看過主畫面模擬的並排對照後接受了。
- **不做大小兩套。**曾經談過「大尺寸放単語、小尺寸放単」，因為 `Contents.json` 只列一張 1024、iOS 沒辦法按尺寸換圖，兩套的實際效果只有 App Store 那一張不同，不值得多維護一份母檔。

### 質感：玻璃

四級質感梯度（平塗／柔光／玻璃／立體）裡選的第三級。具體是：

- 玻璃板用三段白色漸層填充（不透明度 0.34 → 0.10 → 0.05）
- 一圈亮邊描邊，寬度 **14**（不是 8——8 在 38 像素時只剩 0.3 個像素，那圈光會整個消失）
- 左上一道高光弧，右下一道較弱的回光弧
- 底層有徑向光暈與暗角，讓玻璃板浮起來
- 兩組字各有投影：讀音用弱的（dy 9 / blur 13），漢字用強的（dy 18 / blur 26）

### 底色：鉄紺（てつこん）

深藏青。五個沉穩色（靛藍／紺／鉄紺／墨／藍鉄）裡選的。

漸層三段：`#333F73` → `#1B2450` → `#080B24`，方向 `x1=0.12 y1=0 x2=0.88 y2=1`。
光暈色 `#9BA9DC`（不透明度 0.46），暗角色 `#03050F`（不透明度 0.5）。

### 圖案的唯一來源改成 SVG 母檔

**這一條推翻票 `21` 的做法。**票 21 的唯一來源是 `generate-icons.mjs` 裡那份 `SHAPES` 陣列；現在改成一份 SVG 檔案。

理由：使用者要的質感（漸層、光暈、陰影、日文字）那台手刻的繪圖器一樣都做不到。這不是調參數的問題，是換工具的問題。

母檔位置：**`scripts/icon.svg`**。跟讀它的腳本放一起，不新增頂層目錄。（這一條是低風險拍板，不是 grilling 的結論——實作時若有更好的位置可以改，但要一併改測試。）

### 用 sharp 轉檔

**這一條推翻 `generate-icons.mjs` 開頭那句「不引入影像套件」。**

- 加 `sharp` 當 **devDependency**
- `npm run icons` 改成「讀 `scripts/icon.svg` → 輸出四張 PNG」
- 不用 `@resvg/resvg-js`：它對 SVG 濾鏡的支援有缺口，而這個設計的玻璃質感靠的就是 `feDropShadow`

代價是可以接受的，因為 **`npm run icons` 沒有跑在 CI 上**。`.github/workflows/` 只有 `deploy.yml` 與 `ios-testflight.yml`，兩個都不跑它。圖示是本機跑一次、PNG 直接 commit 進 repo。所以「原生二進位在 CI 裝不裝得起來」不是這張票要處理的風險。

### 換的範圍

| 檔案 | 換不換 |
| --- | --- |
| `ios/App/App/Assets.xcassets/AppIcon.appiconset/AppIcon-512@2x.png` | **換** |
| `public/icon-1024.png` | **換** |
| `public/icon-512.png` | **換** |
| `public/icon-192.png` | **換** |
| `ios/.../Splash.imageset` | 不換 |

`public/` 那三張換掉這件事，**直接推翻票 `21` 的第四條驗收**（「三個檔的 md5 與改動前一字不差」）。那條驗收在票 21 的脈絡下是對的——它要保護的是「不順手改不該改的東西」。現在是主動要改，所以那條不再適用。

## 這張票不做的事

- **不碰啟動畫面。**`Splash.imageset` 還是 Capacitor 的範例圖。要處理另開票，理由同票 `21`
- **不補 `Contents.json` 的多尺寸。**維持單一張 1024 的通用圖示
- **不改 app 名稱。**`APP_NAME` 與 ADR-0012 完全不動
- **不做吉祥物。**角色設計談過但沒選，它會長進空狀態與上架截圖，是另一個層級的工作
- **不動 App Store 的文案與截圖。**那是票 `20`
- **不送審。**那是票 `11`

## 技術陷阱

### 一、字必須轉成路徑

母檔裡不能有 `<text>` 元素。

`単語` 用 Noto Serif JP 700，`たんご` 用 Noto Sans JP 700。這兩套字型不在 repo 裡，也不保證每台機器都有——留著 `<text>` 的話，換一台電腦跑出來就是別的字型。

做法：用字型檔把兩組字轉成 `<path>`（Noto 系列是 SIL Open Font License，可自由使用）。轉完形狀完全一樣，只是檔案裡不再有文字。轉完之後 repo 裡不需要留字型檔。

### 二、iOS 那張不能有 alpha 通道

票 `21` 已經踩過這個坑：iOS 的 app 圖示不接受帶 alpha 通道的 PNG，那次是靠 `encodePng()` 多收一個 `{ alpha }` 參數解決的。

換成 sharp 之後這個保護會消失——**sharp 輸出 PNG 預設帶 alpha**。要明確用 `.removeAlpha()` 或 `.flatten()` 才會是 `colorType 2`。

這個錯誤在本機不會有任何徵兆，要等上傳 App Store Connect 被退件才知道。票 21 為此留了兩條讀檔測試，這張票要接手那個保護。

### 三、亮邊在小尺寸會消失

已經從 8 調到 14。但 14 在 38 像素時也只有 0.52 個像素——實機看起來可能還是很弱。這是設計上刻意接受的取捨（再粗會讓大尺寸顯得笨重），不是 bug。

## 驗收

- [ ] `scripts/icon.svg` 存在，且檔案裡**沒有任何 `<text>` 元素**（字都轉成 `<path>` 了）
- [ ] `npm run icons` 產出四張 PNG，圖案是鉄紺底、玻璃板、横排「単語」加上方「たんご」
- [ ] `ios/.../AppIcon-512@2x.png` 是 1024×1024、`colorType 2`（RGB，不帶 alpha 通道）
- [ ] 四張 PNG 的圖案一致（逐像素比對，作法比照票 `21`：同解析度的兩張要求三通道完全相同，不同解析度容許抗鋸齒誤差）
- [ ] `scripts/generate-icons.test.mjs` 重寫，至少守住：SVG 母檔沒有 `<text>`、iOS 那張沒有 alpha、已 commit 的 PNG 沒有意外變動
- [ ] `npm run typecheck` 乾淨、`npm test` 全綠
- [ ] `npm run build` 過，網頁版 favicon 換成新圖
- [ ] **實機確認（要等 CI 打包一次）**：主畫面上是新圖示
- [ ] **實機確認，在深色桌布上**：圖示邊界跟背景分得開。鉄紺是五個候選裡偏深的一個，深色桌布上有黏在一起的風險。若真的分不開，補救方式是加強玻璃亮邊或在四周留一圈亮色——**但那要另開票**，不要在這張票裡順手改設計

## Comments

### 2026-08-19 — 這張票怎麼來的

一輪 `/grill-with-docs`。使用者一開始只說「我想要弄一個新的 app 圖示」，中間推翻過幾次方向，值得記下來的轉折有三個：

**第一次轉折：要不要走日文。** 使用者反問「我不想只走日文這個方向，還是你覺得我的 app 要專心走日文比較好?」查 `docs/adr/0013-interface-localization.md` 與 `.scratch/i18n/spec.md` 之後結論是該走——因為已經走了。`reading.ts`、`reading-editor.ts`、`gemini-reading.ts` 整套是「漢字配假名」的邏輯，ADR-0013 白紙黑字說換學習語言等於動領域模型的根。圖示若為了保留一個程式碼裡不存在的可能性而做成中性的，付了辨識度的代價卻買不到東西。加上票 11 還沒送審、零個使用者，改圖示的成本永遠不會比現在更低。

**第二次轉折：六張候選全被否掉。** 診斷出來不是概念問題，是做工——那六張一個 SVG 濾鏡都沒用，全是平塗色塊。這才有了質感梯度那一輪，也才確定「換工具」是必要的，不是想要而已。

**第三次轉折：兩個字。** 使用者問「単語會不會太擠」。會，但擠的不是字本身——是讀音。「ご」一個假名跟「たんご」三個假名，橫向空間差三倍，而讀音正是這張圖唯一在講「這個 app 會逼你標假名」的部分。畫出主畫面模擬的並排對照之後，使用者看過仍選兩字，接受小尺寸的損失。

過程中的所有候選（六個圖案、四級質感、五個底色、主畫面模擬）都在同一個 artifact 的版本紀錄裡。
