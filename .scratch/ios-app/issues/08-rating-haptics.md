# 08 — 評分時的觸覺回饋

Status: done
Type: enhancement
Blocked by: 01

決策背景見 `../spec.md`，本票對應決定二十五。

## 要做什麼

在 iPhone 上按下評分（再次／困難／好／簡單）時，給一次輕微的震動，讓使用者知道這一下確實被記到了。

整個工程裡最小的一張票，但對「它像一支 app」的體感提升不成比例地大。

## 決定

### 只在評分這一處，不在別的按鈕上加

不對掀答案、切換畫面、儲存卡片等操作加觸覺。到處都震等於沒有回饋。

### 輕量的觸覺，不是警告式的震動

用最輕的那一級，目的是「確認」不是「警示」。

### 四個評分都給同一種回饋

不用觸覺去暗示評分的輕重——那是使用者自己的判斷，程式不該替它加註解。

### 橋接不存在時靜默略過

網頁版沒有這個能力。處理方式與朗讀相同：在接線層吸收掉，**不要讓條件判斷散落到畫面層**。`src/ui/review-view.ts` 不應該知道「觸覺」這個概念存在。

## 這張票不做的事

- 不加開關讓使用者關閉觸覺（系統層級本來就有，不必重造）
- 不在評分以外的任何互動加觸覺
- 不改 `src/ui/review-view.ts` 的結構

## 驗收

- [x] iPhone 上按四個評分鍵，各能感受到一次輕微震動
- [x] 掀開答案、切換畫面、儲存卡片時沒有震動
- [x] 用鍵盤快捷鍵評分時行為一致
- [x] 網頁版沒有任何錯誤，也沒有多餘的判斷散落在畫面層
- [x] 既有測試全數通過，且一個既有測試檔都沒被修改

## Comments

### 2026-08-11 — 自己寫插件而非裝 `@capacitor/haptics`

票裡沒指定走哪條，實作前問過維護者。兩條路打到的是底下同一個 API
（`UIImpactFeedbackGenerator`，`.light` 那一級），**手指摸起來完全一樣**，
差別只在專案負擔。選自己寫的理由不是省那 20 行，而是：往全原生走的路上，
`@capacitor/*` 每多一個就多一條要拔的線；自寫插件是自家檔案，刪掉就沒了。
與 `SpeechPlugin`／`SafetyCopyPlugin`／`KeychainPlugin` 同一個立場。

需要澄清的一點：**今天寫的 Swift 之後搬不過去**。`CAPPlugin`、`jsName`、
`pluginMethods` 那層殼全是為了給 JavaScript 呼叫，真的脫離 WebView 之後
一行都用不到，會留下的只有 `impactOccurred()` 那一兩行。

### 2026-08-11 — 接縫落在 `app.rate()`

滑鼠與鍵盤兩條路都經過 `app.rate()`（`review-view.ts` 的 `submit()` 是
唯一呼叫點），因此接在那裡「鍵盤快捷鍵行為一致」是結構保證的，不是靠兩處
各寫一次。`review-view.ts` 一字未改。網頁版 `createNativeHaptic()` 回傳
空函式，呼叫端零判斷。

### 2026-08-11 — code review 抓到插件沒註冊

Capacitor 6 之後，住在 app 自己 target 裡的插件不會被自動掃描，得在
`MainViewController.swift` 手動註冊。第一版漏了這行，而它的壞法很陰險：
**編得過、不報錯**，JS 那側的失敗又被 `.catch(() => {})` 吞掉，症狀會是
「一切正常但完全沒有觸覺」。已補上。這是本 repo 每加一支自寫插件都要
記得的一步。

### 2026-08-11 — 真機驗收四條全過，本票結案

使用者回報四條真機驗收全過。第五條（測試）由 391 個測試與零測試檔變動
確認。

已知的取捨，不視為缺陷：`generator` 是震完之後才 `prepare()`，因此
**一輪複習裡只有第一下是冷的**（震動馬達尚未喚醒，可能晚幾十毫秒），
第二下起都是熱的。要連第一下都熱，得在「掀開答案」時先暖機——那要多碰
`reveal()`，超出本票範圍。

`CONTEXT.md` 尚無「觸覺回饋」詞條。同一狀況的還有「朗讀」與「保險副本」，
補詞彙是票 10 的工作（spec 決定三十四），本票不動。
