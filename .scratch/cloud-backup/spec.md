# 用暱稱與密碼把進度備份到雲端，換裝置自動接上

拆成兩張實作票，見 `issues/01-cloud-backup-core.md`、`issues/02-cloud-backup-controls.md`。本檔案是兩張票共用的決策紀錄，不直接實作。

## 問題

換裝置時，複習進度只能靠「資料」畫面手動匯出 JSON、再到另一台手動匯入（`src/ui/data-view.ts`）。這條路能走，但每次都要記得做，而且中間隔著一個檔案——手機與電腦之間搬一個檔案本身就是摩擦。實際結果是根本不會去搬，兩台裝置的進度各自漂流。

想要的是：app 認得「這是同一個人」，進度自己跟著走。

## 決定

### 定位

1. **解決的是「一個人多台裝置」，不是「多人共用一台」。** 不引入多帳本切換、不做使用者列表。同一時間一台裝置只服務一個暱稱。

2. **本質是「整份覆蓋的備份」，不是逐張合併的同步。** 兩邊進度不一致時比整份的時間戳，新的贏，舊的整份被蓋掉。不做逐卡比對——那需要在 `Card` 上增加「最後複習時間」並寫合併邏輯與測試，對單人自用的工具不成比例。詞彙表已把「同步」列入 `_Avoid_`，避免日後誤以為存在合併邏輯。

3. **localStorage 仍是唯一資料來源（`ADR-0002` 不變）。** 雲端只是備份的搬運帶，不是第二個真相來源。程式任何時候讀的都是 localStorage；雲端只在「開 app 拉一次」與「答完一張推一次」這兩個時刻被碰到。

### 認人與保護

4. **用「暱稱 + 密碼」認人，密碼必填。** 沒有註冊流程、沒有信箱驗證、沒有第三方登入。

5. **密碼身兼兩職。** 由密碼派生出兩個不同的值：一個**指紋**存在雲端，讓資料庫規則據以擋掉別人的覆寫；一個**金鑰**在上傳前把資料加密，讓拿到密文的人也讀不懂。用瀏覽器內建的 Web Crypto API，不裝任何套件。

6. **雲端有這個暱稱、但密碼對不上時，擋下來，什麼都不寫。** 顯示「暱稱或密碼不對」。程式無法分辨「你打錯密碼」與「這個暱稱已被別人用了」——兩種情況的正確反應都是不要動雲端那份，所以不必分辨。這同時就是「暱稱不可重複」的實現方式：名字被佔用等於你寫不進去。

7. **暱稱與密碼記在本機，之後自動登入。** 這是「快速」的來源。安全上不吃虧：能讀你 localStorage 的人本來就已經能讀你全部的卡片與進度。

8. **提供「停止同步」：忘掉本機記住的暱稱密碼、不再推雲端，但卡片與進度完整留在本機。** 不做完整的換人流程（列出用過的暱稱、點選切換）——那是為不存在的情境寫程式。

9. **提供「換密碼」。已知後果：其他裝置會立刻失效。** 密碼同時是指紋與金鑰，換了之後，還記著舊密碼的裝置既推不上去、也解不開新資料，必須各自手動重新輸入一次新密碼。這是機制決定的，無法避免，UI 上要說明。

### 同步行為

10. **本機資料只要有變動就推一次整份上去，不限於複習評分。** `app.ts` 有三個會改動資料的入口——`advance()`（複習評分）、`upsert()`（新增／編輯卡片）、`remove()`（刪除卡片）——三者都要觸發推送，否則在一台裝置新增的卡片，另一台不會自動收到。實測內建牌組 10.4 KB / 132 張，加密後每次約 20 KB；一天複習 50 張約 1 MB、一個月約 30 MB，離免費額度（10 GB/月傳輸）非常遠，新增／編輯／刪除的頻率遠低於複習評分，不會加重這個估算。因為推的永遠是整份，推送是冪等的——掉一次無所謂，下一次資料變動時會補上。

11. **開 app 時拉一次，兩邊比時間戳，新的贏。** 時間戳用 Firebase 的伺服器時間，不用裝置本機時間——否則某台裝置時鐘偏差就會讓它的資料永遠「比較新」。

12. **首次登入時本機與雲端都有資料，不問，照第 11 條自動判。** 已知風險：這正是兩邊差異最大的時刻，判錯就回不來。經確認接受——手動匯出備份（決定 15）是這個風險的後路。

13. **推送失敗或沒網路時，默默重試，只留一行小狀態。** 複習流程完全不被打斷，離線照常複習，上線後自動追上。不跳錯誤對話框，不擋下一張卡——後者等於放棄 PWA 的離線可用（`vite.config.ts` manifest 寫明「離線可用」）。

14. **登入是選配，入口放「資料」畫面。** 沒登入時 app 完全就是現在的樣子：打開直接進複習。不做「一打開先問你是誰」——那道關卡在離線時無法驗證，會卡住原本能離線複習的情境，而且新裝置不能先用再說。

15. **現有的「匯出備份／匯入備份」保留，不動。** 雲端服務再穩定也可能改政策或出事，手動匯出的 JSON 是唯一不依賴任何人的後路。

### 技術路線

16. **Firebase Realtime Database + 安全規則，用 `fetch` 打 REST 介面。** 不裝 Firebase SDK、不寫後端、不綁信用卡。

    比較過的替代方案見 `docs/adr/0003-firebase-rtdb-cloud-backup.md`。

17. **雲端路徑用暱稱的雜湊，不用暱稱原文。** 兩個理由：Firebase 路徑不接受 `.` `#` `$` `[` `]` `/`，用雜湊就不必限制使用者能取什麼名字；同時別人無法從資料庫列舉出有哪些暱稱存在。

18. **`AppData` 新增 `updatedAt` 欄位，資料格式升到 version 2。** 沒有它就無法比新舊。舊資料（沒有這個欄位）視為最舊。

19. **雲端備份不寫進 `src/lib/storage.ts`。** 該模組的註解說「日後若改接雲端服務，僅需替換此模組內部」，但這裡的情況不是那個情況——storage 仍然是本機的唯一來源，雲端備份是獨立的另一件事。新開一個模組，維持 storage 的職責不變。

20. **雲端的資料形狀分成「可讀」與「不可讀」兩半**（規則見 `.scratch/cloud-backup/firebase-rules.json`）：

    ```
    /backups/<暱稱雜湊>/
        fingerprint   ← 指紋。任何人都讀不到
        prev          ← 寫入者聲稱的現有指紋。任何人都讀不到
        open/
            payload   ← 加密後的整份資料。任何人可讀
            updatedAt ← 伺服器時間戳。任何人可讀
    ```

    指紋必須不可讀，否則保護就破了——任何人只要讀得到指紋，就能照抄一份送上去通過檢查。因此可讀的只有 `open` 這一層。讀取單一路徑時，只要該路徑或其任一祖先開放讀取即可，所以在 `open` 上開放讀取、而 `$key` 不開放，是成立的。

21. **每次寫入都要附上 `prev`，內容是「寫入者認為現在存著的指紋」。** 資料庫規則只看得到「送來什麼」與「現在存著什麼」，沒有別的管道能證明寫入者握有正確的密碼。一般寫入時 `prev` 與 `fingerprint` 相同；換密碼時 `prev` 是舊指紋、`fingerprint` 是新指紋，同一條規則就同時涵蓋兩種情況。刪除也一併被擋住——刪除時送來的資料不存在，`prev` 取不到值，比對必然失敗。

    已知且無法消除的缺口：**尚未被使用的暱稱，任何人都能搶先佔用**。沒有伺服器仲裁就沒有別的辦法。後果僅止於「這個名字被佔走了，換一個」，不會影響已存在的備份。

## 前置（已完成）

Firebase 專案與資料庫已建立，安全規則已發布並以真實 REST 請求驗證通過。

- 資料庫網址：`https://va-practice-default-rtdb.asia-southeast1.firebasedatabase.app`
- 地區：`asia-southeast1`（新加坡，建立後不可變更）
- 規則內容：`.scratch/cloud-backup/firebase-rules.json`

此網址會出現在前端原始碼中（公開）。這在此設計中是預期的——保護來自規則與加密，不來自網址保密。

### 規則驗證結果（十項全過）

以真實 REST 請求驗證，非模擬器。模擬器測不出伺服器時間戳，而該行為是本設計的關鍵之一。

| # | 情境 | 期望 | 結果 |
|---|---|---|---|
| 1 | 讀 `/backups/$key/open` | 允許 | `200` |
| 2 | 讀 `/backups/$key` | 拒絕 | `401` |
| 3 | 讀 `/backups/$key/fingerprint` | 拒絕 | `401` |
| 4 | 讀 `/backups` | 拒絕 | `401` |
| 5 | 新 key 首次寫入 | 允許 | `200` |
| 6 | `prev` 填錯再寫 | 拒絕 | `401` |
| 7 | 直接 DELETE | 拒絕 | `401` |
| 8 | `prev` 填對再寫 | 允許 | `200` |
| 9 | 換密碼（`prev` 舊指紋 + 新 `fingerprint`） | 允許 | `200` |
| 10 | 換密碼後仍用舊指紋寫入 | 拒絕 | `401` |

第 3 項是保護的命脈：指紋若讀得到，任何人都能照抄一份通過檢查。第 9、10 項合起來證明換密碼可行，且其副作用（其他裝置立即失效）與決定 9 描述一致。

**實作必須知道的一點**：`updatedAt` 只能送 `{".sv": "timestamp"}`，規則要求它必須等於伺服器當下時間。客戶端無法自行填入時間戳——這讓「比新舊」不受裝置時鐘偏差影響，是機制保證而非約定。

### 待清理

驗證期間寫入的節點無法用 API 刪除（規則擋刪除，此為預期行為），需在 Firebase Console 的「資料」分頁以管理員身分手動刪除：

- `/backups/__ruletest__`——驗證安全規則十項情境時寫入。
- `/backups/__putecho__`——驗證 `PUT` 回應是否已含解析後的伺服器時間戳時寫入（結論：有，因此推送後不必再 `GET` 一次）。
- `/backups/5f26ef5871a7cafffb5d697fc84f1782e768e06bbc0bda168aa46bf0a54d2f3d`——實作 `01` 後的端對端驗證，暱稱 `e2e-2026-07-24`。

## 驗收

- 未登入時，app 行為與現在完全一致：打開直接進複習，不發任何網路請求。
- 「資料」畫面可輸入暱稱與密碼完成登入；關掉分頁重開後仍是已登入狀態，不需再次輸入。
- 全新暱稱登入 → 本機資料被推上雲端。
- 另一台裝置輸入同一組暱稱密碼 → 拉到第一台的進度。
- 兩台交互複習，各自重開 app 後都拿到對方最新的進度。
- 暱稱正確但密碼錯誤 → 顯示「暱稱或密碼不對」，且雲端該筆資料**未被改動**（以另一台裝置能照常拉到原資料驗證）。
- 斷網情況下仍能正常複習與評分；恢復連線後，進度自動推上雲端。
- 「換密碼」後，另一台仍記著舊密碼的裝置會被擋下並提示重新輸入；輸入新密碼後恢復正常。
- 「停止同步」後不再有任何網路請求，本機卡片與進度完好。
- 「匯出備份／匯入備份」行為與現在一致。
- 直接用瀏覽器查看 Firebase 上那筆資料，內容為無法辨識的密文（不是明文卡片）。
- 既有測試全綠；加密與解密、時間戳比較、密碼指紋比對三處補單元測試（皆為純函式，可測）。
