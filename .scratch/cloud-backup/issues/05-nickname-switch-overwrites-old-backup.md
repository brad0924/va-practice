# 05 — 換一個暱稱登入，會把本機這份推上去蓋掉舊暱稱的雲端備份

Status: needs-triage
Type: bug

決策背景見 `../spec.md`。相關詞彙見 `CONTEXT.md` 的〈雲端備份〉、〈暱稱〉。

## 症狀

2026-09-03 維護者在實機上回報。手順：

1. 在目前的暱稱底下「停止同步」
2. 用另一個暱稱登入
3. 刪掉幾張卡
4. 在新暱稱底下「停止同步」
5. 用原本的暱稱登入

**預期**：第 3 步刪掉的卡只影響新暱稱，回舊暱稱應該還在。
**實際**：舊暱稱的雲端備份裡那幾張卡也不見了。

## 這不是壞掉，是設計的直接後果——但缺一道門

`signIn()` 只做一件事：**比時間戳，誰新誰贏**（`core/lib/cloud-backup.ts:232`）。

```ts
if (remote !== null && isRemoteNewer(remote.updatedAt, local.updatedAt)) {
  // 雲端比較新 → 拉下來
}
// 否則：把本機這份推上去
const updatedAt = await write(keys, local);
```

它不問「本機這份資料本來屬於哪個暱稱」，**因為程式沒有記那件事**。`AppData` 只有
`updatedAt`，沒有任何一格記錄血統。

第 3 步推上去之後，`onPushed()` 把伺服器時間戳寫回本機那份
（`mobile/lib/review-session.ts:296` 的 `noteCloudTimestamp`，網頁版在 `src/app.ts:126`）。
所以第 5 步的比較是：

| | updatedAt | 來源 |
| --- | --- | --- |
| 本機（刪完卡） | 1003 | **新暱稱**那台伺服器蓋的 |
| 舊暱稱的雲端 | 1001 | 舊暱稱那份最後一次推上去時蓋的 |

兩個數字都來自同一台 Firebase 的時鐘，所以比得起來——**比得起來，就被拿來比了**，
即使它們屬於兩個不同人的備份。本機贏，於是被推上去覆蓋。

`CONTEXT.md:133` 定義的模型本身沒有被違反（「整份覆蓋、不合併，較新的那一份整份勝出」），
**缺的是一道門**：登入畫面同一顆按鈕走得到兩個方向（拉下來、或推上去蓋掉別人那份），
而走到覆蓋那一邊時一句都不問（`mobile/ui/cloud-account-screen.tsx:68`）。

## 「停止同步」是假線索

`signOut()` 只忘掉本機記住的暱稱與密碼，**卡片與進度完整留在本機**
（`core/lib/cloud-backup.ts:268`，介面上那行註解也是這樣寫的）。

最小重現把**兩次停止同步都拿掉**，照樣重現。真正的載重條件只有三個：

1. 本機有資料
2. 曾經推上去過任何一個暱稱（本機因此拿到一個較新的時間戳）
3. 接著登入另一個暱稱，而那個暱稱的雲端備份比較舊

## 重現

`core/lib/cloud-backup.test.ts` 的 `describe('換暱稱')`，兩條：

```
npx vitest run core/lib/cloud-backup.test.ts -t '換暱稱'
```

**兩條都是 `it.fails`，不是 `it.skip`。** 斷言寫的是使用者期待的結果，而現況做不到——
所以 bug 還在的時候它們是綠的，**有人修好的那一天會轉紅**，逼修的人回頭把斷言與這張票
一起收掉。`skip` 會安靜地爛在那裡。

第一條裡另有一句機制斷言，釘住「第 5 步發出的是 PUT 不是 GET」——它是寫入，不是讀取。

診斷過程中在假 Firebase 上加了一個 `read(nickname, password)`，讀出雲端現在替某個暱稱
存著什麼。原本只有 `seed()` 放得進去、沒有東西讀得出來。

## 影響範圍

- **兩版都有。** `core/lib/cloud-backup.ts` 是共用的，網頁版與 React Native 版同一支。
- **災情會擴大。** 另一台還留著舊資料的裝置，只要開一次 app 就走 `begin()`
  （`cloud-backup.ts:203`），一樣是比時間戳——雲端那份現在比較新，會整份拉下來蓋掉
  那台的本機資料。**開一次，最後一份就沒了。**
- **救不回來。** 舊暱稱雲端那份已被 PUT 覆蓋，Firebase Realtime Database 預設沒有版本歷史。
  保險副本也幫不上：它只在 localStorage 全空時回填，內容跟本機那份是同一份
  （`core/lib/safety-copy.ts` 檔頭），而且只有 Capacitor 版接了那條支線。

  唯一的退路是匯出過的備份檔，或一台**還沒開過 app** 的裝置（要先斷網再開，匯出備份檔）。

## 待決定

**行為該怎麼改還沒談過。** 底下是幾個方向，一個都還沒選，也不保證這是完整的清單：

- **登入時若會覆蓋，先問一次。** 保留現有的整份覆蓋模型，只在「本機比較新、而雲端那個
  暱稱已經有東西」時跳一次確認。改動最小，但多一個對話框。
- **換暱稱登入時清空本機。** 把「登入」重新定義成「這台裝置從此屬於這個暱稱」。
  乾淨，但「本機新、雲端舊」那條合法的路（手機存、電腦拉）會一起被關掉。
- **本機資料記住血統。** `AppData` 多一格「這份資料上次推給誰」，時間戳只在同一個暱稱
  之內比較。最貼近病灶，但動到資料結構，要考慮既有資料怎麼遷移。
- **停止同步時清空本機。** 讓「停止同步」名副其實。但它會改掉一個已經寫進介面註解的
  承諾（「卡片與進度完整留在本機」），而那個承諾本身有它的用處。

這幾條碰到 `CONTEXT.md` 的〈雲端備份〉定義與 `ADR-0002`（localStorage 是唯一真相來源），
不是改幾行就好。下一步應該是一輪 `/grill-with-docs`。
