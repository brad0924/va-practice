# docs/spec.md 補上雲端備份，並訂正過期的 Out of Scope

Status: ready-for-agent
Type: bug

## 需求

`docs/spec.md` 有兩個關於雲端備份的缺口。

**第一，第 196 行是假的：**

> - **雲端同步**：進度僅存於本機，跨裝置以手動匯出／匯入處理。資料存取模組的介面已預留替換空間，但**本次不實作**。

`src/lib/cloud-backup.ts` 已實作，`src/lib/cloud-backup.test.ts` 有 8 個測試在守，決策見 ADR-0003。另外「資料存取模組的介面已預留替換空間」這句也與事實不符——ADR-0003 的 Consequences 明講雲端備份**不**放進 `src/lib/storage.ts`，該模組註解設想的替換並未發生。

**第二，比那行更麻煩的是結構性的空洞：** Implementation Decisions 完全沒有〈雲端備份〉這一節。第 181、183 行的 Testing Decisions 鉅細靡遺寫了怎麼測它（離線待推、401 之後停手、換密碼送舊指紋⋯⋯），但前面沒有任何一節說它**是什麼、怎麼運作**。這份 spec 裡「怎麼測」有、「是什麼」沒有。

## 決定

1. **第 196 行改寫成真正還在範圍外的東西。** 雲端備份是整份覆蓋、較新的一份勝出；還在範圍外的是「把兩邊進度逐張比對合併」。與第 208 行（匯入備份不合併）平行、不重複——一條講檔案，一條講雲端。

2. **在 Implementation Decisions 新增〈雲端備份〉一節，位置在〈資料模型〉之後、〈技術與部署〉之前。** 材料收攏自 ADR-0003 與 `CONTEXT.md` 的〈雲端備份〉〈暱稱〉〈密碼〉〈指紋〉四個詞條。這一節等於新寫規格文字，因此草稿列在下方，**寫進檔案前先經使用者過目**。

3. **不動 ADR-0003。** ADR 是決策當下的紀錄，即使其中第 33 行仍提到已退場的內建牌組（見 ADR-0008），也不回頭改寫——那是歷史，不是現況說明。

### 〈雲端備份〉草稿

> ### 雲端備份
>
> 備份除了匯出成檔案，也可以自動存放在雲端，讓進度在使用者自己的多台裝置之間搬運（見 ADR-0003）。與備份同樣是整份覆蓋、不合併，差別只在自動且不經過檔案；覆蓋的內容一樣包含單字本與三組範圍選擇，因此在手機上設好的複習範圍，電腦打開也是同一組。兩邊內容不一致時，較新的那一份整份勝出，較舊的被蓋掉。
>
> 認人靠**暱稱**，保護靠**密碼**，兩者皆由使用者自取，不需註冊；已經被別人用掉的暱稱無法佔用。密碼同時決定誰能覆蓋這份備份、以及內容怎麼被加密：由它算出的**指紋**隨備份一起存放，寫入必須帶對指紋才放行；內容則在上傳前以密碼加密，因此即使任何人都讀得到那份資料，讀到的也只是密文。密碼遺失無法補救——沒有伺服器可以重設，本機那份與手動匯出的備份檔是僅有的後路。換密碼會讓仍記著舊密碼的其他裝置立即失去寫入與解密的能力，必須各自重新輸入。
>
> 每答完一張卡推送一次。推不上去時（離線或請求失敗），待推的那一份留著，恢復連線後補送；送出期間又有新的變動，中間那幾份略過，最後送出去的是最新那份。開 app 時比較兩邊新舊：雲端較新就拉下來，本機較新或雲端沒資料就把本機那份推上去。雲端回 401（Unauthorized，未授權）代表指紋不對，之後完全停手、不再發任何請求；未登入與登出之後亦然。
>
> 依 ADR-0002，本機儲存仍是唯一的資料來源，雲端只是備份的搬運帶，不是第二個真相來源。因此雲端備份自成一塊，不放進資料存取模組。離線仍可完整複習，手動匯出的備份檔也因此不能移除——「換裝置能接上進度」這件事從此取決於外部服務的可用性。

## 驗收條件

- 第 196 行不再宣稱雲端備份未實作；改寫後留下的範圍決定是「不做逐張合併」
- Implementation Decisions 底下有〈雲端備份〉一節，位置在〈資料模型〉與〈技術與部署〉之間
- 該節內容經使用者確認後才寫入；與 Testing Decisions 第 183 行所描述的行為逐條對得上
- 用詞通過 `CONTEXT.md` 檢查：使用〈雲端備份〉〈暱稱〉〈密碼〉〈指紋〉四個詞條定義的詞，不使用各自 `_Avoid_` 行列出的同義詞（特別是不得用「同步」指稱雲端備份、不得用「帳號」指稱暱稱、不得用「雜湊」或「token」指稱指紋）
- `docs/adr/0003-firebase-rtdb-cloud-backup.md` 未被修改
- `npm run typecheck` 與 `npm test` 維持全綠（本票不動程式，僅作回歸確認）
