# docs/spec.md 的〈模組與接縫〉仍宣稱資料存取模組「僅需替換內部」即可改接雲端

Status: done
Type: bug

## 需求

`docs/spec.md` 第 98 行（〈模組與接縫〉的「資料存取」那一條）結尾寫著：

> 目前實作為瀏覽器本機儲存；**日後若改接雲端服務，僅需替換此模組內部**，畫面與其他模組不受影響（見 ADR-0002）。

這個設想並未發生。ADR-0003 的 Consequences 第 29 行明講：

> 因此雲端備份不放進 `src/lib/storage.ts`——該模組註解中「日後若改接雲端服務，僅需替換此模組內部」所設想的情況並未發生。

`src/lib/cloud-backup.ts` 的檔頭註解同樣寫明它刻意不寫進 `storage.ts`。而 ADR-0003 所指的那句註解至今仍在 `src/lib/storage.ts` 第 13 行，一字未改——**所以這是文件與程式註解兩處都要修的落差，不只 spec。**

issue 03 已在 Implementation Decisions 新增〈雲端備份〉一節，該節結尾寫的是「雲端備份自成一塊，不放進資料存取模組」。**於是 spec 現在有兩處講反。**

issue 03 的需求段落點名過同一句話，但只提到它出現在 Out of Scope（已隨該票刪除），沒發現〈模組與接縫〉還有一份等價的。本票補這個漏網的。

## 待決定

那句話該改成什麼，還沒談過。至少三種方向：

1. **直接刪掉那半句**，只留「目前實作為瀏覽器本機儲存（見 ADR-0002）」。最小改動，但也丟掉了「這個模組是有接縫的」這項資訊。
2. **改寫成已發生的事實**：說明雲端備份沒有走這條替換路線，理由見 ADR-0003。資訊最完整，但〈模組與接縫〉那一段本來在講模組職責，塞進一段歷史轉折可能離題。
3. **改寫成仍然成立的版本**：本機儲存的**實作**（localStorage 換成別的本機機制）可替換，但「改接雲端服務」這個具體例子換掉。保住原意，只拿掉被推翻的那個例子。

動手前需先與使用者確認方向。**已定案：方向 1，詳見 Comments。**

## 驗收條件

- `docs/spec.md` 第 98 行不再宣稱「改接雲端服務僅需替換此模組內部」
- 改寫後與同檔〈雲端備份〉一節的「不放進資料存取模組」、以及 ADR-0003 第 29 行三者一致
- `src/lib/storage.ts` 第 13 行的檔頭註解一字不差地留著同一句（「目前實作為瀏覽器本機儲存；日後若改接雲端服務，僅需替換此模組內部（見 ADR-0002）。」），與 spec 一併改，兩處講法要一致
- 不修改 `docs/adr/0002-*.md` 與 `docs/adr/0003-firebase-rtdb-cloud-backup.md`——ADR 是決策當下的紀錄
- `npm run typecheck` 與 `npm test` 維持全綠

## Comments

- 來源：issue 03 實作後的 code review（Standards 軸）抓到的落差，非票上原本要求的範圍，故另立本票。
- 待決定已定案：採方向 1（直接刪掉那半句）。兩處都只留「目前實作為瀏覽器本機儲存（見 ADR-0002）」。理由是不再留任何對未來的預言——被推翻的正是這種預言；而「這模組有接縫」這項資訊，同一條前半段列出的對外介面已經說明，並未因此丟失。
