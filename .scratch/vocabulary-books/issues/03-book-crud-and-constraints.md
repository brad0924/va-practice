# 單字本的新增／改名／刪除，與名稱、詞條兩道約束

Status: done
Type: enhancement

決策背景見 `.scratch/vocabulary-books/spec.md`。依賴 `01-book-model-and-migration.md`。本票只做資料存取模組的操作與純函式，不碰畫面。

## 需求

單字本可以新增、改名、刪除。名稱不可重複，詞條在整個 app 裡全域唯一。三組範圍選擇的維護規則一併收在這裡。

## 決定

1. **這些操作全部加在既有的資料存取模組**（`src/lib/storage.ts`），不開新模組。`docs/spec.md` 定義的三個核心接縫裡，「資料存取」就是這一個。

2. **名稱正規化**依序為：Unicode NFKC（`String.prototype.normalize('NFKC')`，統一全形半形）→ 轉小寫 → 去除前後空白 → 中間連續空白收成一個。

   ```
   'JLPT N2'   → 'jlpt n2'
   'JLPT N2 '  → 'jlpt n2'
   'JLPT  N2'  → 'jlpt n2'
   'jlpt n2'   → 'jlpt n2'
   'ＪＬＰＴ　Ｎ２' → 'jlpt n2'
   ```

   **正規化只用於比對。** `Book.name` 存的永遠是使用者原本輸入的字串（僅去除前後空白），畫面顯示的也是它。

3. **名稱規則**：正規化後為空字串則拒絕；與其他本正規化後相同則拒絕。改名時**不與自己比對**——把「JLPT N2」改成「JLPT　N2」應該成功。

4. **不設長度上限。** 過長由畫面截斷顯示。

5. **詞條全域唯一**：比對基準是 `toPlainText(card.text)`（去掉讀音標記後的原文），釋義不參與。新增卡片、編輯卡片改詞條、匯入單字三條路都受此約束。被拒時回報的資訊必須足以讓畫面說出「這個詞已經在『某某本』裡」——也就是要帶出撞到的那張卡所在的 `bookId`。編輯既有卡時**不與自己比對**。

6. **刪除單字本連同該本的卡一起刪除。** 確認對話由畫面負責（見票 04），模組這一層直接刪。

7. **範圍的維護規則收在模組內，不由畫面各自處理**：
   - 新增一本 → 自動加進 `scopes` 的三組。
   - 刪除一本 → 自動從三組移除。
   - 任一組不得為空（`books` 不為空時）。畫面負責在「只剩一本」時把勾選框設為 disabled，模組這一層則拒絕會把某一組清空的變更。

8. **範圍過濾是一支純函式**，供複習、卡片列表、統計三處共用：

   ```ts
   /** 取出屬於這幾本的卡。bookIds 為空時回傳空陣列。 */
   export function cardsInBooks(cards: readonly Card[], bookIds: readonly string[]): Card[];
   ```

   放在資料存取模組（或它旁邊的同一個接縫內），不放在畫面層——三個畫面共用同一支，且要能單獨測試。

9. **錯誤的表達方式沿用既有做法**：模組丟出帶著可直接顯示訊息的 `Error`，由畫面接住（見 `importJson()` 現有的做法與 `toMessage()`）。

## 驗收

- `npm test` 全綠。
- **名稱**：空白被拒；只有空白字元的名字被拒；四種正規化情境（前後空白、中間連續空白、大小寫、全半形）皆判為重名並被拒；改名成自己原本名字的另一種寫法成功；`Book.name` 存的是原輸入而非小寫。
- **詞條全域唯一**：在 A 本已有 `打[う]ち合[あ]わせ` 時，往 B 本新增 `打ち合わせ` 被拒，錯誤資訊帶得出 A 本；編輯 B 本某張卡把詞條改成該詞同樣被拒；把 A 本那張卡的詞條改成它自己不被拒。
- **新增本**：出現在 `books` 末端，且三組 `scopes` 都含它。
- **改名**：`books` 裡的名字變了，該本的卡一張都沒動。
- **刪除本**：該本從 `books` 消失、該本的卡全數消失、三組 `scopes` 都不再含它；刪到剩零本時三組皆為空陣列。
- **範圍不得清空**：`books` 有兩本時，把某一組設成空陣列的操作被拒。
- **`cardsInBooks`**：單本、多本、全選、空 `bookIds`、卡的 `bookId` 不在清單裡，五種情況結果正確。

## Comments

- **形狀由 agent 拍板**：這些操作做成吃一份 `AppData`、吐一份新的**純函式**（`addBook` / `renameBook` / `deleteBook` / `setScope`），不是 `Store` 的方法。理由是 `app.ts` 現行的模式是「記憶體裡持有一份 `data` → 改它 → `persist()` 一次做存檔與推雲端」；若由 `Store` 自己寫檔，會繞過 `cloud.push()`，且 `app.ts` 手上那份會變舊。票 04 的 `importWords()` 因為要吃 JSON 字串並驗證，仍留在 `Store` 上，兩者形狀不同是刻意的。
- **詞條約束開了兩支**：`findTermConflict()`（純查詢，回傳撞到的那張卡，帶得出 `bookId`）與 `assertTermAvailable()`（撞到就丟可直接顯示的例外）。決定 5 要求「帶得出 bookId」、決定 9 要求「丟出可直接顯示的 Error」，兩者無法用同一支滿足；票 04 的批次跳過也只吃得下前者。
- **決定 7 的一個推論**：刪掉某本之後，若某一組範圍被清空（例如統計原本只勾了被刪的那本），該組會**補成全選**。票上只寫「不得為空」沒寫補什麼，這裡沿用載入時 `normalizeScopes()` 既有且已測試的行為（「剔除後為空的那一組補成全選」），三條路才是同一套規則。
- **未加的檢查**：`renameBook` / `deleteBook` 傳到不存在的 `id` 時靜默不動作、`setScope` 不驗證傳入的 id 是否存在。票上皆未要求，且呼叫端（票 05 的畫面）拿的一律是清單上真實的 id；載入時的 `normalizeScopes()` 本來就會剔除指不到的 id。
- 順手把「對三組範圍各做同一件事」抽成 `mapScopes()`，`normalizeScopes()` 與 `addBook()` 共用。
