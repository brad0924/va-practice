## 為什麼有這張票

維護者想把這個 app 改成原生。前一版票把動機釘成「想寫原生」就收工了，**這次拆得更細，結論不同**：

- **想學新語言** → React Native 買不到（還是 TypeScript）
- **畫面要是系統原生元件** → React Native **買得到**（`<Text>` 變成 `UILabel`、`<ScrollView>` 變成 `UIScrollView`，捲動手感、選字放大鏡、動態字級、VoiceOver 全由系統提供）

維護者要的是第二個。所以 SwiftUI 那條退場，Flutter 一併出局——Flutter 用自繪引擎，跟 WebView 同樣不使用原生元件，犯的是同一條。

### 判準沒有變軟

前一版票挖出來的那件事**今天依然成立**：問「哪裡用起來不順」，答案是**講不出來**。而且現在證據更強——`ios-app` 的 16 張票已 `done`（Keychain、原生日語語音、觸覺、每日提醒推播），維護者每天都在用那一版，仍然講不出不順。

所以這張票的判準跟前一版一樣：**不是「改完會不會變好」，是「這是不是好的時間花法」。** 停損條件照樣現在就寫死。

### 為什麼不直接重寫

現有的 app 有 **6,011 行程式碼、6,051 行測試、452 個測試**，網頁版在 GitHub Pages 上跑著，上架流程只差 `ios-app 10` 與 `20` 兩張票。

React Native **不是**從零重寫——純邏輯 3,638 行與其 4,732 行測試同為 TypeScript，可以搬。要重寫的是畫面層 2,373 行，作廢的是畫面測試 1,319 行。

但有三處接不上，而且**都還沒有人驗證過**：

1. **振假名沒有對應物。** `src/ui/reading-html.ts`（29 行）用瀏覽器內建的 `<ruby>`／`<rt>` 六行解決。RN 的 `<Text>` 不暴露 iOS 的 `CTRubyAnnotation`。
2. **`localStorage` 同步，`AsyncStorage` 非同步。** 純邏輯層有 27 處，而它是唯一真相來源（ADR-0002），改動會傳染到每一個呼叫端。
3. **Web Crypto 沒有對應物。** `src/lib/cloud-crypto.ts`（102 行）要換套件重刻，且必須與網頁版**位元級相容**——網頁版要留著，這是硬約束。

**第 1 項是這張票要回答的。** 第 2、3 項留給重寫真的開始之後，這次不碰。

## 要做什麼

用 React Native 做出**複習畫面**，對照 `src/ui/review-view.ts`（175 行）：

| 部位 | 內容 |
| --- | --- |
| 標題列 | 「剩餘 N 張」＋單字本開關（開關可以是死的，不用真的能切） |
| 卡片 | 詞條（**含振假名**，漢字上方標假名）；掀開後顯示釋義 |
| 底部 | 未掀開時一顆「顯示答案」；掀開後換成四顆評分鈕：**再次／困難／好／簡單** |
| 完成狀態 | 三張都答完後顯示「今日份完成」 |

**寫死三張假卡**，其中至少一張要有漢字（才看得到振假名）、一張純假名。按評分鈕就換下一張，不做任何排程計算。

外觀要**盡量對齊現有的網頁版**——這不是美化，是盲測的前提：兩版長得越接近，盲測量到的才越接近「平台差異」而不是「設計差異」。配色抄 `src/styles.css`（`--bg: #141821`）。

### 振假名是這張票的技術核心

RN 沒有 ruby。兩條路，**先試第一條**：

- **兩層 `<Text>` 疊字**：假名一行、漢字一行，用 `lineHeight` 與對齊把假名壓到漢字正上方。純 JavaScript，不寫原生碼。風險是換行、字距、不同字級下會不會跑掉。
- **自寫原生模組包 `CTRubyAnnotation`**：Core Text 原生支援振假名，效果一定對。代價是要寫 Swift（未來還要再寫一份 Kotlin），而且 EAS Build 得改用 development build 流程。

如果第一條做出來在真機上看起來歪掉、或字級一調就爆，**那本身就是一個結論**，寫進 `## Comments`，不要硬撐到第二條——那已經超出探路的範圍。

### 由 agent 寫，不是維護者寫

維護者是 React Native 新手。自己寫的第一版很可能比現有的網頁版還醜——那樣盲測量到的會是熟練度，不是平台差異，判準就被污染了。

維護者在這張票裡**只負責盲測與判定**，不寫程式。

## 這張票不做的事

- **不接排程、不接儲存、不接雲端。** 沒有 SM-2、沒有到期日、沒有 localStorage 對應物、沒有 Firebase。三張卡寫死在程式碼裡
- **不碰 `localStorage` 轉非同步、不碰加密相容。** 那兩項是重寫真的開始之後的事
- **不碰現有的任何程式碼。** `src/`、`ios/`、`vite.config.ts` 一行都不動
- **不承諾重寫。** 這張票結束時唯一的產出是一個決定，不是一個 app
- **不做 Android。** 維護者說 iOS 上架後才要，而且還沒決定 Android 是否也必須是原生元件

## 原型放哪

分支 `prototype/rn-review-screen`，從 `main` 開出去。沿用這個 repo 既有的 `prototype/*`／`throwaway/*` 慣例（見 `prototype/stats-snapshot`、`throwaway/toast-styling-prototype`）。做完砍掉，不進 `main`。

Expo 專案跟純前端 repo 混在一起確實怪，但那是暫時分支，可接受。

## 盲測怎麼做

**這是這張票的核心，不是附註。**

維護者的動機是「我知道它是 WebView，就覺得不對」——**這句話等於承認偏誤確定存在**。如果拿著兩台、心裡清楚哪台是原型，一定會覺得它比較好，那判準就沒有否決能力。所以必須盲測：

1. **原型要編成獨立的 app**，用 **EAS Build**，不能用 Expo Go——Expo Go 有自己的圖示與啟動畫面，一眼就露餡，盲測直接破功
2. **兩版都裝上同一支 iPhone**：RN 原型從 EAS Build 裝；Capacitor 版用已安裝的那一份
3. **網頁版先對齊**：在現有 app 裡手動建一本、加上原型那三張一樣的卡，讓它進到複習畫面時內容相同（不用改任何程式碼）
4. **不標示哪個是哪個**，兩個圖示放在一起、名字都遮掉或排在一起分不出來的位置
5. **隔一天再拿起來滑**，不要當天做——剛做完的印象太強
6. 判定：**分不分得出來哪個是原生的**

## 判定之後

**分得出來** → 這個方向值得投入，才進入下一串問題（`localStorage` 轉非同步怎麼做、加密相容怎麼驗、6,051 行測試怎麼辦、重寫要多久）。**那幾題現在刻意不釘**，沒通過盲測就不需要答案。

**分不出來** → **停。** 這個 app 維持 Capacitor 包殼，把結論寫進 `ios-app 10` 要開的那份 ADR（`docs/adr/0015-capacitor-ios-shell.md`）的 Consequences。想寫原生的欲望另外找小專案滿足，不由這個 app 承擔。

**停損條件現在就寫死，是因為做完當天的維護者已經花了時間，那時候的他不會想承認白做。**

## 這張票與上架的關係

**互不阻擋。** Capacitor 版繼續走完 `ios-app 10`、`20`、`11` 送審上架，這張票同時進行。維護者已明確決定先上架——App Store 上先有東西，之後不論結論如何都不吃虧。
