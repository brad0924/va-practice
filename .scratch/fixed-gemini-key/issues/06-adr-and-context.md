# 06 — 新開 ADR-0016，更新 CONTEXT.md 的「讀音預填」

Status: done
Type: enhancement
Blocked by: 01

決策背景見 `../spec.md`，本票對應決定十七。

## 要做什麼

### 一、新開 `docs/adr/0016-fixed-key-via-firebase-ai-logic.md`

主題：**iOS 的讀音預填改用維護者提供的固定金鑰，走 Firebase AI Logic 代理；網頁版維持自備金鑰。**

**`ADR-0005` 留著不改寫。** 那是歷史，新的這份指回去。0016 裡要講清楚 0005 的哪些前提還在、哪些換掉了：

**還在的**：
- 「這個功能永遠是選配的……離線、超額、模型掛掉、回覆過不了驗證，一律降級成手動填，絕不擋住儲存」——完全保留，而且因為額度共用，這條保底路徑被踩到的機會變多了。
- 「金鑰刻意不進 `AppData`」——網頁版照舊；iOS 上根本沒有金鑰這個東西了，因此 `ADR-0003` 那句「若日後要放入任何敏感資料，這個前提必須重新評估」仍然沒有被觸發。
- 「端點寫死單一模型而非 `-latest` 別名」的精神——見下。

**換掉的**：
- 「需要使用者自備的金鑰，沒設定時連請求都不發」——iOS 上不再成立。
- 「代價是金鑰不跨裝置，每台各設定一次」——iOS 上不再是代價，改成一個新的代價：共用額度。
- 「不經過任何第三方伺服器」——iOS 上請求先經過維護者的 Firebase 專案。
- 「專案對外部服務的依賴又多了一項」——現在是三項：Firebase RTDB（雲端備份）、Firebase AI Logic（讀音預填）、Firebase Remote Config（模型與提示詞）。

**Considered Options 至少要寫進去的三條**（連同否決理由）：
- 硬把金鑰塞進 ipa
- 自己寫一支 Cloud Function 當代理
- 網頁版也吃固定金鑰

**Consequences 必須誠實寫的**：
- **app 越受歡迎，讀音預填越常罷工。** 決定二（不留自備金鑰的後路）、三（給任何人用）、八（不開計費）三者相乘的必然結果。這是知情選擇，不是疏漏。
- `ADR-0005` 那個沒有第二道防線的風險（整串讀音幻覺）被放大了：原本只會發生在自己申請金鑰的人身上，現在每個下載的人第一張卡就可能中。
- 本決定不沿用 `.scratch/ios-app/issues/14` 立下的判例「密碼跟著走，同意不跟著走」——讀音預填不問使用者，理由與代價見 `../spec.md` 決定十。
- Remote Config 為什麼不牴觸「拒絕 `-latest` 別名」：拒絕的是**無預警**改答案，不是不能改。方向盤在維護者手上。
- 升級 Blaze 是一條隨時可走、不必送審的退路，但那是單向門：免費層整個消失、帳單無法設上限、整個 Firebase 專案一起升。

### 二、更新 `CONTEXT.md` 的「讀音預填」詞條

現在寫著：

> 需要使用者另行設定才會啟用，沒設定時完全不發生，讀音格一律留空給人填。

這句話在 iOS 上不再成立。改寫時保留這個詞條原本最重要的那件事——**填進來的仍是使用者的草稿，程式不承擔「讀音一定正確」的責任**——並補上兩邊行為不同的事實。

`_Avoid_` 那一行的既有項目全部保留。

### 三、詞彙表同步

`CONTEXT.md` 與 `docs/glossary.md` 要一起改，否則 `src/lib/glossary.test.ts` 會紅燈。

**評估是否需要新增詞條**，但不要為了湊而加。候選：
- 「固定金鑰」——維護者提供、藏在伺服器端、iOS 使用者看不到也改不了的那把。與網頁版的「自備金鑰」是兩個東西，容易混淆，可能值得各給一條。
- 「共用額度」——所有 iOS 使用者一起舀的那桶水。
- 「說不出口的失敗」——**票 02 實作時冒出來的第三個候選**。程式碼裡叫 `SilentError`（`src/lib/app-error.ts`）：問不成、但畫面上一個字都不出，讀音格單純留空。與「失敗」不同的地方在於它刻意不帶訊息，接住它的地方要做的是**不顯示**。目前只有 iOS 的 App Check 沒過會丟它。

若判斷不需要新增，把判斷理由寫進本檔案的 `## Comments`。

#### ADR-0016 裡多寫的兩段

票裡沒點名、但寫進去了：

- **Considered Options 多了第四條「維持現狀，iOS 也要使用者自備金鑰」。** 三條指定的選項都是「怎麼藏金鑰」，缺了「不藏」那條，讀的人會以為當初沒考慮過什麼都不做。
- **多了一節「這條路是用真機驗過的，不是推論」。** 票 01 冒出來的 `AppDelegate.swift` 順序問題（provider factory 必須搶在 `configure()` 之前指定）屬於決策層而非實作細節——不知道它的人重寫這段會踩同一顆釘子。

#### 詞條：收了「固定金鑰」「自備金鑰」，另外兩條沒收

**收的理由是那條 `_Avoid_` 攔得住一個事實錯誤。** 「固定金鑰」最容易被叫成「內建金鑰」或「打包進 app 的金鑰」，而那正是 `ADR-0016` 明文否決的選項——金鑰一個位元組都不進 app。這種會把決定講反的叫法，正是詞彙表存在的理由。兩條一起收，是因為只定義一邊，另一邊就會被叫成「一般金鑰」「舊做法」，分不出誰是誰。

**「共用額度」沒收。** app 裡沒有這個東西：沒有程式碼、沒有畫面、沒有資料，spec 還明講不在 app 內顯示額度用量。它是 Google 計費規則的一項事實，記在 `ADR-0016` 的 Consequences 就夠了；把它收進詞彙表反而會暗示程式模型裡有這個概念。

**「說不出口的失敗」沒收，但這條最接近邊緣。** 三個理由：

1. **守門的已經是型別，不是名字。** `SilentError` 是一個獨立的類別，接住它的人不可能不小心把它印出來——詞彙表擋不住的東西它擋得住，詞彙表能擋的它已經擋了。
2. **它在介面上永遠是零個字**，三語對照表的三個欄位對它沒有內容可填；`讀音編輯器` 那種同樣不露臉的條目至少指得出一台機器，這一條指的是「什麼都不發生」。
3. **專案自己一直叫它「完全靜默」**（spec 決定十一、十三都是這個講法）。現在另立一個正名，等於製造第二套叫法，與收詞條想解決的問題方向相反。

它已經有一段寫得很完整的說明住在 `src/lib/app-error.ts`。等到第二個地方也需要「說得出口 vs 說不出口」這個分辨時再收進來——目前只有 iOS 的 App Check 這一個用途。

**這三條判斷都便宜到可以反悔**，改的只是兩份 markdown 加一列表格。

### 2026-08-21 — code review 抓到兩處事實失準，已修

Spec 軸的四條驗收全過，但 ADR 內文有兩處與正本對不上，兩處都是「聽起來對、查下去不對」：

1. **把改寫過的句子標成「原話」。** 原本寫「`ADR-0005` 拒絕的原話是『模型在腳下換人的話…』」——`ADR-0005` 沒有這一句。它實際寫的是「端點寫死單一模型而非 `-latest` 別名，是為了讓『模型換人』以錯誤的形式暴露出來，而不是讓同一個詞的讀音無預警改答案」。改成引用真正的那一句。（同一個錯也在 `../spec.md` 決定十五裡，那份是歷史，不改。）
2. **429 的畫面描述漏了前半截。** 原本寫成畫面上只有「暫時無法使用，稍後再試」。票 04 記得很清楚：那條是被代進 `editor.noteFailed`（「自動填讀音失敗：{reason}」）的 `{reason}`，畫面是兩截接起來的。

另外補了三件事：

- **Remote Config 漏掉的那個代價。** `../spec.md` 決定十五要求「據實記錄兩個代價」，原稿只收了後者。補上前者：不是立刻生效，裝置要等下一次抓取，本專案的間隔是一小時（票 03 定的）。
- **「三者相乘」的第二項寫成了它的理由。** 決定二是「不留自備金鑰的後路」，「介面乾淨」是選它的理由。已改回決定本身。
- **縮寫首次出現補上中英文全名**（`CLAUDE.md` 用詞規則）：ADR 裡的 API、CI、RTDB、JS SDK，以及 `CONTEXT.md` 新條目裡的 API。

Standards 軸另外指出 `CONTEXT.md` 的「（見 `ADR-0016`）`」是全檔唯一一處 ADR 交叉引用，且那句共用額度在「讀音預填」條目裡已經講過一次。兩者一併收掉——詞彙表只寫定義，決定的出處不在這裡。
