# iOS app 的讀音預填改用固定金鑰，走 Firebase AI Logic 代理

網頁版維持現狀不動：使用者自備 Gemini 金鑰、自己貼、存在自己那台裝置。

iOS app 改成**使用者什麼都不必做**——下載、打開、新增卡片、打完詞條，讀音就自己填進來。資料畫面上「Gemini API 金鑰」那一整區在 iOS build 消失。請求不再由裝置直接打 Google，改走 Firebase AI Logic：金鑰留在 Google 的伺服器上、一個位元組都不進 app，靠 App Check 加 App Attest 證明發請求的是真的那支 app。

## 問題

`ADR-0005` 把讀音預填做成選配，代價寫得很白：**每台裝置各設定一次金鑰**。在手機上尤其麻煩，要在小鍵盤上貼一串長字元。

更根本的問題是 `.scratch/ios-app/spec.md` 訂下的目標——這支 app 要上架 App Store。一個從 App Store 下載 app 的人，不會為了幫漢字標假名跑去 Google AI Studio 申請一把 API 金鑰。對他來說讀音預填等於不存在。

## 解法

金鑰由維護者提供、藏在伺服器端，iOS 使用者直接用。

**「藏起來」不能靠把金鑰塞進 ipa。** 那只是換個地方公開——拆包就找得到，而且要換金鑰得重新送審。真正的做法是代理：請求先到一台不是使用者的機器上，金鑰在那裡加進去。Firebase AI Logic 就是 Google 提供的這台機器，免費的 Spark 方案就能用，維護者不必自己養伺服器。

代理擋得住「金鑰被挖走」與「假客戶端亂打」，但擋不住第三件事：**真實使用者把共用額度用完**。免費額度是按專案算的一桶水，不是每人一桶。這一項本次不解決，見決定八。

## 使用者故事

### iOS 使用者

1. 作為一個剛從 App Store 下載這支 app 的人，我想打完詞條就看到假名自動填好，這樣我不必知道 API 金鑰是什麼東西。
2. 作為一個看到假名自動出現的人，我想被明確告知這是 AI 猜的，這樣我知道自己要負責檢查。
3. 作為一個在共用額度見底那天新增卡片的人，我想讀音格單純留空、讓我自己填，而不是被一個我無能為力的錯誤擋住。

### 網頁版使用者

4. 作為一個在電腦上用網頁版的人，我想繼續用自己申請的金鑰、走自己的額度，這樣行為與現在一字不差。

### 維護者

5. 作為維護者，我想在 Google 把模型下架的那天，按一下發布就換掉模型，而不是重新打包送審等一到兩天。
6. 作為維護者，我想在讀音判準出包的時候，改一段提示詞就上線，而不是為了幾行文字送一次審。
7. 作為維護者，我想在免費額度撐不住的那天，只在後台綁一張卡就升級，不必動任何程式碼。

## 實作決定

### 範圍

**一、只有 iOS app 改，網頁版一個字都不動。** 網頁版掛在公開的 GitHub Pages 上，任何寫進打包產物的字串都會出現在 `brad0924.github.io/va-practice/assets/*.js` 裡，按 F12 就看得到；用 GitHub Actions 的 secret 在打包時注入也一樣，secret 只是沒進 git 歷史，照樣印進那個公開的 JS 檔。而且 Google 會主動掃 GitHub 上外洩的 API 金鑰並停用。網頁版因此維持 `gemini-key.ts` 那條路。

**二、iOS 上只剩固定金鑰，輸入介面完全移除。** 資料畫面的「Gemini API 金鑰」區塊在 iOS build 不渲染。**不留「貼自己的金鑰蓋過去」這條後路**——維護者明確選擇了介面乾淨，代價見決定八與「已知風險」。

**三、目標是 App Store 上任何人。** 不是只給維護者自己、也不是只給認識的幾個人。這一條是決定八那些代價的來源。

### 金鑰藏在哪裡

**四、走 Firebase AI Logic，不硬塞進 ipa、也不自己寫 Cloud Function。**

- 硬塞進 ipa：金鑰等於公開，被挖走就能拿去亂打，換金鑰要重新送審。
- 自己寫 Cloud Function：打包產物不會胖，但要自己維護、自己驗 App Check，而且 Cloud Functions 需要 Blaze 方案，等於現在就得綁卡——直接牴觸決定八。
- Firebase AI Logic：金鑰留在 Google 的伺服器上，Spark 免費方案可用，不必綁卡，維護者不養伺服器。

**五、App Attest 借道原生層，用 `CustomProvider` 餵給 WebView 裡的 JS SDK。**

App Attest 是 Apple 的原生 API，Firebase 的 JavaScript SDK 拿不到（web 那邊只有 reCAPTCHA 可選）。而這支 app 的畫面全部跑在 Capacitor 的 WebView 裡。走法是裝 `@capacitor-firebase/app-check`，讓原生層去跟 Apple 要憑證，再把換來的權杖交給 JS SDK：

```js
await FirebaseAppCheck.initialize();
const provider = new CustomProvider({ getToken: () => FirebaseAppCheck.getToken() });
await initializeAppCheck(getApp(), { provider });
```

App Check 不是選配：Firebase 對 AI Logic 強制啟用，且 2026 年 11 月 2 日起全面強制。

**六、Firebase 專案沿用現有那個**（雲端備份用的 `va-practice-default-rtdb` 所屬專案），不新開。

理由不是省事：一支 iOS app 的原生層只吃一份 `GoogleService-Info.plist`，要接第二個 Firebase 專案得手動開第二個 app instance，Capacitor 外掛不一定支援。這條路的成本遠大於「兩個功能分開」的好處。App Check 是按服務各別啟用的，開了 AI Logic 不會動到 RTDB。

**代價據實記錄：日後若升級 Blaze，是整個專案一起升**，雲端備份那個 RTDB 也會從免費額度變成按用量計費。

**七、`GoogleService-Info.plist` 進版控。**

那個檔案裡有一把 Firebase 的 API 金鑰，但它**設計上就是公開的**——靠 App Check 與安全規則擋，不靠保密，跟本 spec 在保護的 Gemini 金鑰是完全不同的東西。CI 要用它，不進版控 `ios-testflight.yml` 跑不起來。

### 額度與計費

**八、額度見底就接受「今天沒得用」，不開計費。**

免費額度是**按專案**算的一桶共用的水（Google 官方文件：「Rate limits are applied per project, not per API key」）。iOS 使用者一多，見底是必然。見底時 `ADR-0005` 的保底路徑照常生效：降級成手動填，絕不擋住儲存。

**不開計費的理由沿用 `.scratch/reading-prefill/issues/01` 決定 7**：不綁卡的金鑰即使外洩，代價也只是免費額度被別人用掉，不會產生帳單。

**九、「日後改成綁卡付費」是一條已知的退路，不在本次範圍。**

技術上隨時能走，且**不必重新打包、不必送審**——在 Firebase 主控台升級 Spark 到 Blaze，Gemini 跟著從 Free tier 變 Tier 1，通常立即生效，客戶端一行程式碼都不用改。但走之前要知道四件事：

1. 開了計費，**免費層整個消失**，每個呼叫從第一個 token 起計費（`ADR-0005` 已記錄）。
2. **帳單沒有上限，而且無法設上限。** Google Cloud 的預算警示只寄信通知、不停止服務，且常延遲數小時。唯一的硬性封頂是自己寫一支 Cloud Function 監聽預算通知、呼叫計費 API 關掉計費。
3. 整個 Firebase 專案一起升（見決定六的代價）。
4. App Check 的價值會從「省額度」變成「省錢」——被濫用直接等於帳單。

因此這是一張未來的票，不是隨手按的開關。

### 使用者面

**十、不問使用者、不加開關，直接用。**

第一次打完詞條就發請求，不跳任何框。這一項經過完整評估後確認：

- App Store 審查不會因此退件，Apple 沒有「送資料到伺服器要先徵求同意」這條規定。
- 日文詞條沒有識別性，不是個資，個資法規也咬不到。
- 業界慣例站在「不問」那邊：免費 app 呼叫自家後端的 AI 功能絕大多數不問，會特地問的通常是明顯要花錢、或送的是私密內容。

**但要記錄本決定推翻了什麼。** `.scratch/ios-app/issues/14` 立過一條判例：「密碼跟著走，同意不跟著走」，理由是掌控感。本決定在讀音預填上不沿用那條判例——維護者知情後選擇了介面乾淨。連帶的兩個後果：

- 不在乎這個功能的人也會消耗共用額度。
- `ADR-0005` 那句「送出去的內容是日文單字，可接受」的正當性換了主體：原本是使用者自己申請金鑰、自己接受 Google 的條款；現在是維護者替他決定的。這一點必須寫進隱私權政策（見決定十八）。

**十一、App Check 拿不到憑證時完全靜默，讀音格留空。**

與現在「沒設金鑰就什麼都不發生」一致。不出錯誤提示——那條錯誤使用者一點辦法都沒有，看了只會焦慮。代價是維護者收不到任何回報。

**十二、編輯畫面那行「請確認」提示維持原狀，一個字都不改。**

**本條在票 04 動工前被推翻過一次**，原文是「提示要加強，寫明讀音是 AI 代填的」。推翻的理由不是改變主意，是原本那條決定批評錯了對象。

它的論據來自 `ADR-0005` 對這行提示的簡稱——「一行『請確認』提示」——並據此說它「沒說要確認什麼」。但程式裡真正的字串是 `editor.noteFilled`：「讀音由 AI 填入，請確認」。它有講是 AI 填的。被批評的那個版本從來不存在。

受眾換人（從自己申請金鑰的人變成隨便下載的人）這件事仍然成立，現行字串缺的兩點也仍然成立：沒說 AI 可能填錯、沒說要在儲存前確認。維護者知情後判斷這兩點不值得動這行字。

**因此三道防線一道都沒有加粗**——見「已知風險」那段的修正。

**十三、429 改成一句什麼都不解釋的訊息，不提額度、不提狀態碼。**

現在寫「Gemini 回了 429」是給知道自己有金鑰的人看的。固定金鑰之下那句話對 iOS 使用者沒有意義：他沒有自己的額度，也沒有金鑰設定可看。

**本條的方向在票 04 動工前反轉過。** 原文要求「講清楚不是他做錯什麼、明天會恢復」。維護者選擇不對使用者解釋共用額度這件事。畫面因此顯示「自動填讀音失敗：暫時無法使用，稍後再試」，句子裡不需要任何背景知識。

**新的 key 照「發生了什麼事」命名**（`gemini.quotaExhausted`），與 `gemini.offline`、`gemini.timeout` 一致。程式裡誠實記錄成因，畫面上刻意不講——這是兩件事。

**不走決定十一那種完全靜默。** App Check 失敗時使用者從頭到尾不知道有讀音預填這個功能，靜默不會讓他困惑；額度用完時他已經看過讀音自己填好，這次沒填就得給一句交代。

**網頁版不受影響，且不必另外處理。** 這條分支加在 `ai-logic-error.ts`，那支檔案只有 iOS build 會載入。

### 模型與提示詞

**十四、模型維持 `gemini-3.6-flash`，不趁機換。** Firebase 文件範例已經在用 `gemini-3.7-flash`，但換模型是另一件事、另一張票。

**2026-08-21 後記：那張票開了，也做了。** `reading-prefill` 票 06 把兩個預設值都換成 `gemini-3.5-flash-lite`，理由是「等超過 10 秒沒有回覆」十次有三次。

**本決定的結論被取代，理由沒有被違反。** 結論那半句（模型維持 `gemini-3.6-flash`）不再成立；但它擋的是「趁著別的票順手換」，怕的是兩件事混在一輪驗證裡分不清因果，而票 06 只做換模型這一件事，正好符合那個理由。

**已上線，兩邊都換完了。** 換完實測逾時 3/10 掉到 0/10。代價也量到了：`吹雪` 這道熟字訓界線題，`gemini-3.6-flash` 打五次全對，`flash-lite` 錯一次。維護者知情後選擇保留 `flash-lite`——拿「每五個這種詞錯一個」換「不再有人卡在等 10 秒」。`ADR-0005` 那句「熟字訓 LLM 答得出來」已補上這組數字當註腳。詳情在票 06。

**十五、模型名字與 `INSTRUCTIONS` 都搬上 Firebase Remote Config，程式碼裡留預設值當後備。**

固定金鑰把「模型下架」的修復成本從幾分鐘拉到幾天：`ADR-0005` 記錄過 `gemini-2.5-flash` 對新金鑰關閉、且 ListModels 型錄查不出來的事故。在自備金鑰的設計下那是零星使用者踩到、改個字串 push 上去幾分鐘上線；在固定金鑰加 iOS 的設計下，那是**所有使用者同時停擺、等一到兩天送審**，而使用者沒有自救途徑（決定二）。

`INSTRUCTIONS` 一起搬的邊際成本幾乎是零（同一個 SDK、同一次抓取），而 `ADR-0005` 記錄過那段判準實際改過兩次（吹雪、剃刀）——讀音判準出包也不必送審。

**本決定不牴觸 `ADR-0005` 拒絕 `-latest` 別名那一條。** 該決定拒絕的原話是「模型在腳下換人的話，同一個詞的讀音會**無預警**改答案」。差別在方向盤在誰手上：`-latest` 是 Google 想換就換、你不知道；Remote Config 是你自己按按鈕才換。它拒絕的是無預警，不是可以換。

**據實記錄兩個代價**：不是「立刻生效」——JS SDK 抓取間隔預設 12 小時、Capacitor 外掛預設 1 小時，改完要等下一次抓取（實務上仍是「幾小時」對「一到兩天」）；以及 web 平台的預設值只能寫在程式碼裡，`gemini-3.6-flash` 這個字串不會消失，只是身分從「唯一答案」變成「連不上時的後備」。

### 程式碼

**十六、兩條路徑在打包時切，不在執行期切。**

沿用 `vite.config.ts` 既有的 `mode === 'ios'` 慣例。執行期偵測 Capacitor 會讓網頁版也載入 firebase SDK，白白變胖。

`INSTRUCTIONS`、`RESPONSE_SCHEMA` 的內容、以及 `acceptPrefill`（`reading.ts`）的驗證邏輯**兩邊共用**，只有「請求怎麼送出去」那一段分岔。Firebase AI Logic 支援結構化輸出，schema 的形狀保得住，只是寫法從原始 JSON 物件改成 `Schema.array(...)` 那種建構式。

**體積不是問題**：firebase 套件只進 iOS 那份產物，而那份本來就包在一支好幾 MB 的 app 裡。網頁版走不同 mode，一個位元組都不會胖。

### 文件

**十七、新開 `ADR-0016`，`ADR-0005` 留著不改寫。** 舊決定是歷史，新的那份指回去。

**十八、隱私權政策一頁分兩段講，不多開檔案。** `privacy.html` 與 `privacy-en.html` 已經是按語言分的兩份，再按平台分會變四份。那段「不經過任何第三方伺服器……用的是你自己申請的金鑰、走你自己的額度」對 iOS 版變成假的，必須分岔。

`public/privacy.html` 開頭的註解寫著「這頁寫的每一句都是那幾支程式實際的行為，不是宣示」——這條自我要求不放寬。

## 測試決定

**App Attest 只有真機驗得出來。** 模擬器一律回「不支援」，而維護者的開發機是 Windows，沒有 Mac、沒有模擬器。唯一的驗證管道是跑 `ios-testflight.yml` 送一版、裝到 iPhone 上試。這是票 01 存在的全部理由。

**單元測試涵蓋得到的部分不變。** `gemini-reading.test.ts` 守的是「各種失敗變成一條說得出原因的 key」，那部分邏輯兩條路徑共用。新增的 Firebase 路徑因為靠 SDK 而非 `fetch`，`doFetch` 那個接縫接不上，這一段的正確性靠票 01 的真機驗證，不靠單元測試。

**`keychain.test.ts:159` 用到 `va-practice:gemini`。** 網頁版保留該鍵，該測試不受影響。

## 不在範圍內

- **網頁版的任何改動。**
- **開啟計費**（決定九）。
- **換模型**（決定十四）。
- **Android。** `.scratch/ios-app/spec.md` 提過日後要做，本 spec 不預留。
- **在 app 內顯示額度用量。** Firebase 主控台看得到，不做進畫面。
- **自己蓋帳單保險絲**（決定九第 2 點那支 Cloud Function）。沒開計費就用不到。

## 補充

### 已知風險

**app 越受歡迎，讀音預填越常罷工。** 決定三（給任何人用）、決定二（不留自備金鑰的後路）、決定八（不開計費）三者相乘的必然結果：免費額度是一桶共用的水，一百個人同時新增卡片那天，一百個人一起沒讀音，而且誰都沒辦法自救。**這是知情選擇，不是疏漏。** 真的撐不住時的退路是決定九。

**`ADR-0005` 那個沒有第二道防線的風險被放大了。** 「整串讀音幻覺」原本只會發生在自己申請金鑰、知道自己開了什麼的人身上；現在每個下載的人第一張卡就可能中。防線仍然只有三道：填進格子而非直接存檔、一行確認提示、預覽。

**本次一道都沒有加強，連文字都沒改**（決定十二被推翻的結果）。原本規劃的加粗沒有發生，因此這個放大了的風險是**原樣接受**的，不是被緩解過的。下次要動它，起點是「AI 可能填錯」與「儲存前」這兩句話從來沒有寫進 `editor.noteFilled`。

**票 01 有可能證明整條路走不通。** App Attest 在 Capacitor 的 WebView 裡拿不到、或 `CustomProvider` 這條接法在 Capacitor 8 上卡住，都會讓決定四、五失效。那時要回到「自己寫 Cloud Function」（要 Blaze，牴觸決定八）或「放棄固定金鑰」。這正是票 01 必須排在最前面的理由。

### 建議的實作順序

票 01 必須最先完成並回報發現，其結果可能推翻決定四與五。其後票 02 是主體，票 03（Remote Config）緊接在後——它與票 02 動的是同一段程式碼，分開只是為了讓 01 的驗證範圍最小。票 04（文案）、05（政策與商店申報）、06（ADR 與詞彙）幾乎不碰執行邏輯——**唯一的例外是票 04 要在 `ai-logic-error.ts` 多一條 429 的分支**，那是決定十三的必要成本，寫在這裡以免被當成越權——可與工程並行，但 05 與 06 的內容取決於 01 的結論，宜在 01 之後才定稿。
