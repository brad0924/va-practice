# docs/spec.md 補上時間桶這一段

Status: done
Type: bug

## 需求

issue 02 把卡片列表從「一長串卡片」改成「六個可收合的標頭」，決定 23 交代了 `CONTEXT.md` 要動哪三條詞條，但沒有人提到 `docs/spec.md`。結果是：時間桶這個功能在 spec 裡從來沒有被介紹過。

「時間桶」在 `docs/spec.md` 全文只出現兩次，兩次都是順帶提及：

| 行 | 現在寫的 | 問題 |
|---|---|---|
| 135 | 「範圍過濾發生在排序、時間桶分組與搜尋之前」 | 用了這個詞，但讀者不知道它是什麼 |
| 190 | 「不碰 DOM 的函式…目前屬於這一類的有…卡片列表的時間桶分組」 | 同上 |

只讀 spec 的人會以為卡片列表就是一條由到期日排好的長清單，不知道畫面上其實是六個標頭。連帶的具體後果是：`due-sort-toggle` issue 02 把第 129 行的倒序寫成「整個反過來」，而實際上 `src/ui/list-view.ts:213` 連標頭順序都一起翻——「整個」涵蓋得到，但讀者無從得知它包含標頭，因為標頭在 spec 裡不存在。

另有一句護欄漏了：`CONTEXT.md:92`〈到期排序〉結尾特意寫「只改變列表的呈現，複習佇列的出題順序不受影響」——那正是該詞條 `_Avoid_` 行想擋的誤解。spec 這層沒有這句。

兩點都不影響程式行為。來源是 `due-sort-toggle` issue 02 完工後的 `/code-review`，Standards 與 Spec 兩軸各自獨立指出同一件事。

## 決定

1. **只改敘述，不動程式。** 這張票是文件對齊，`src/` 底下一個字都不碰。

2. **在〈卡片列表〉新增一段描述時間桶**，位置放在狀態文字那段（第 133 行）之後、列表範圍開關那段（第 135 行）之前——先講排序與每張卡怎麼顯示，再講怎麼分組，最後講範圍。內容以 `CONTEXT.md:96`〈時間桶〉詞條為基底，補上詞條沒寫、但屬於 spec 該記的行為。要涵蓋的事實（每一條都請對照程式確認，不要照抄本票）：

   - 六個桶，順序即畫面由上而下：新、現在、`<24小時`、明天、`<1週`、未來（`src/ui/list-view.ts:183`）
   - 分桶依據是逾期天數：新卡、逾期、今日到期、明天、一週內、更遠（`bucketOf()`，`src/ui/list-view.ts:193`）。`<24小時` 是「今日到期」的別名，不是真的用小時算——排程只到日
   - 每個桶一個可點的標頭，標頭上顯示該桶張數，卡片收在標頭底下（`src/ui/list-view.ts:139`）
   - 進入卡片列表時六個桶全部收合；展開狀態只活在這次畫面，離開再回來全部收合，不寫進儲存（`src/ui/list-view.ts:52`、`:57`）
   - 沒搜尋時空桶照樣顯示並標 `0`；搜尋中沒有結果的桶暫時隱藏（`src/ui/list-view.ts:89`）
   - 搜尋框有字時全部展開，清空後還原搜尋前的收合狀態（`src/ui/list-view.ts:98`）
   - 倒序時標頭順序與各桶內的卡片順序一起顛倒（`groupByBucket()`，`src/ui/list-view.ts:213`）

3. **交代模組歸屬。** 第 131 行已寫明「排序與逾期天數的計算歸屬複習流程模組」；時間桶不一樣，它整組住在卡片列表裡（`src/ui/list-view.ts`，見 `due-time-buckets` issue 02 決定 21），spec 應該把這條界線一併寫清楚。第 190 行既有的敘述（時間桶分組屬於 `src/ui/` 的純邏輯測試）是對的，不用改。

4. **補上護欄句**：排序方向與分桶都只改變列表的呈現，複習佇列的出題順序不受影響。放在新段落末尾，一句涵蓋兩者。

5. **第 129 行的「整個反過來」不必重寫。** 新段落把標頭順序講清楚之後，那句話就有了依託。若實作時覺得兩處讀起來仍會打架，可微調 129 行的措辭，但不要把標頭的事重複寫兩遍。

- `src/` 未變動（`git diff --stat` 只有 `docs/spec.md`）
- `npm run typecheck` 與 `npm test` 維持全綠（本票不動程式，僅作回歸確認）
