# 卡片頁時間桶改成可收合的分組

Status: done
Type: enhancement

## 需求

承 issue 01。六個時間桶目前只是每張卡右側的一個彩色標籤，卡片仍然平鋪成一長串。本 issue 把桶從「標籤」升格成「清單的骨架」：每個桶一個可點的標頭，標頭上顯示該桶張數，卡片收在標頭底下。

排程模型一律不動（`due` 仍是 `YYYY-MM-DD`、只到日）；本 issue 只動卡片頁（`src/ui/list-view.ts`、`src/styles.css`）與 `CONTEXT.md` 的三條詞條。

## 決定

### 分組與順序

1. **分組依據就是 issue 01 的六個桶**，不另立第二套分類規則。標頭文字沿用同一組字：新、現在、`<24小時`、明天、`<1週`、未來。

2. **桶順序沿用 `sortByDue()`。** 正序由上而下為 新 → 現在 → `<24小時` → 明天 → `<1週` → 未來。這不是另外挑的順序：桶是 `due` 的連續區間（`overdueDays()` 算的是 `today − due`，單調），`due` 遞增即天數遞減即桶由急到緩，而 `due` 為 `null` 的新卡在 `sortByDue()` 正序時排在最前。因此桶順序與 `CONTEXT.md`「到期排序」詞條所描述的行為完全一致，該詞條的既有內容不需要改寫。

3. **排序方向兩層都翻。** 按下「到期 ↓」時，桶順序顛倒成 未來 → `<1週` → 明天 → `<24小時` → 現在 → 新，同時每個桶內的卡片順序也顛倒。就是「同一份排好的清單整個反過來」的自然結果。

### 收合行為

4. **進入卡片頁時六個桶全部收合。** 第一眼是一張「哪一桶積了多少」的總覽，要看細節自己點開。

5. **展開狀態只活在這次畫面。** 離開卡片頁再回來就全部收合，與 `direction`、搜尋字串的既有行為一致（見 `list-view.ts` 現有註解）。不寫進 localStorage——`storage.ts` 那顆 store 的內容整份會進備份與雲端備份，UI 偏好不該被同步到別台裝置；為此另開一個 localStorage key 不值得。

6. **搜尋框有字時強制全部展開**，清空後回到原本的收合狀態。搜尋的意圖就是看到結果，把結果留在收合的桶裡等於搜尋壞掉。保留分組而非退回平鋪，是為了同時看出「這幾張分別落在哪個桶」。

7. **空桶平時顯示並標 `0`，搜尋中則隱藏。** 沒搜尋時「明天 0」本身是資訊（明天沒事），六個標頭位置固定也養得出肌肉記憶；搜尋只中幾張時，四行「0」會把結果擠下去。這兩件事同屬「搜尋模式」這一條規則。

8. **不加「全部展開／全部收合」。** 尚未發生的需求，六個標頭就在眼前。

### 卡片列

9. **列右側改顯示實際到期日**，不再重複印桶名（展開「未來」後 104 張全印「未來」是純雜訊）。這部分推翻 issue 01 決定 3 的「天數細節捨去」：逾期卡會顯示一個過去的日期，等於把拖了幾天間接還給使用者。這是有意識的改變，不是疏漏。

10. **新卡（`due` 為 `null`）不長出右欄**，不填任何佔位字元。

11. **日期一律 `--muted` 灰。** 桶就是照日期分的，同一桶內每張卡的顏色必然相同，上色不提供新資訊、只是把標頭顏色複製上百次。顏色的職責整個交給標頭。

12. **日期用完整 `YYYY-MM-DD`**，即 `card.due` 原值，零轉換。間隔沒有上限（`good` 每次乘 `ease`，約第 7 次即達 610 天），「未來」桶必然含跨年的卡，省掉年份會讓 `01-15` 分不出哪一年。

13. **上方工具列（`共 N 張` ＋ 排序鈕）原樣不動。** 總數不等於任何單一標頭的數字；搜尋時的「符合 N 張」尤其有用，因為空桶被藏了，光看標頭數不出總數。

### 標頭

14. **標頭用 `<button aria-expanded>`，不用 `<details>/<summary>`。** 兩者外觀做得出完全一致，且**兩者都需要一個 `Set<BucketKey>`** 記住展開狀態（按排序鈕會重畫整段 `rows`，狀態只活在 DOM 裡會被沖掉），所以 `<details>` 的「零 JS 狀態」優勢不成立。剩下的差別很小：`<details>` 多兩行 CSS 拿掉原生三角（含 `-webkit-` 前綴）換來原生語意與 Chrome 頁內搜尋可展開；`<button>` 少那兩行且沿用專案現有的 `button()` helper。手機優先的 PWA 幾乎用不到 Ctrl+F，故選 `<button>`。這題兩邊差距小，日後要換不算翻案。

15. **標頭樣式為「浮在背景上的標題」**：無底色（即頁面底 `--bg`），桶名用該桶顏色且加粗，右側數字 `--muted` 灰。卡片維持 `--surface` 圓角塊。層次是「背景上的標題 + 一疊卡片」。

16. **標頭高度至少 `var(--tap)`（3.25rem）**，指示符號用 `▸`（收合）／`▾`（展開）。

17. **展開後那疊卡片左右各縮 `1.4rem`。** 四周留白一致才有卡片感；右側不縮的話卡片右緣切齊螢幕內距，看起來像被裁掉。左側的層級訊號改由標頭的 `▾`、顏色與粗體承擔。

18. **搜尋時標頭上的數字是符合的張數**，不是「1/52」這種分數，與底下實際列出的卡片數對得上。

### 程式碼結構

19. **`describeSchedule()` 與 `stateModifier()` 收成一個 `bucketOf()` ＋ 一張桶定義表，兩個舊函式刪除。** 現況那兩個函式是兩條平行的 `if` 階梯，分組會需要第三次寫同一條判斷。收斂後同一條階梯只寫一次，桶名與 class 從表查，**表的順序就是畫面由上而下的順序**（決定 2 要的固定桶順序）。兩個舊函式的唯一呼叫點（列上的標籤）已被日期取代，留著是死碼。

    ```ts
    type BucketKey = 'new' | 'now' | 'today' | 'tomorrow' | 'week' | 'future';
    const BUCKETS: readonly { key: BucketKey; label: string }[];  // 順序即畫面順序
    function bucketOf(days: number | null): BucketKey;
    function groupByBucket(cards, now, direction): { key, label, cards }[];
    ```

20. **`groupByBucket()` 永遠回傳完整六個桶**（空的即空陣列），純函式因此沒有分支；「搜尋中藏空桶」是畫面層的一行 `.filter()`。

21. **全部留在 `src/ui/list-view.ts`。** 時間桶是卡片頁專有的概念，沒有別的畫面會用；加上分組後約 160 行，還沒到需要拆檔的體積。**不搬進 `src/lib/review.ts`**——該檔案的檔頭定位是「排程演算法、抖動、佇列排序、『再次』重排全部收在這裡」，而時間桶是顯示層概念，issue 01 已經劃清這條界線。

### 測試與文件

22. **只測純函式，不引入 jsdom／happy-dom。** 會出錯的地方（哪張卡落進哪個桶、六桶順序、倒序怎麼翻、空桶在不在）全在 `bucketOf()` 與 `groupByBucket()` 裡。DOM 那層只剩「點了就換 class」的接線，為它引進整套 DOM 測試環境不划算——專案至今零 DOM 測試相依。

23. **`CONTEXT.md` 動三條詞條**：新增「時間桶」；改寫「逾期」的最後一句（現在寫著「不顯示拖了幾天」，與決定 9 相牴觸）；「到期排序」補一句說明方向同時決定時間桶的順序（既有內容正確，只是沒提標頭也會翻）。

24. **不寫 ADR。** 資料模型一個位元都沒動，全部是 render 邏輯；要撤掉就是刪掉標頭那段回到平鋪清單。與 issue 01 決定 6 同一個判準。

## 驗收

自動（`npm test` 全綠）：

- `bucketOf()` 六個桶的邊界正確：`null`／`1`／`0`／`−1`／`−2`／`−6`／`−7`。
- `groupByBucket()` 正序回傳六個桶，順序為 新、現在、`<24小時`、明天、`<1週`、未來。
- `groupByBucket()` 倒序回傳的桶順序完全顛倒，且桶內卡片順序也顛倒。
- 某個桶沒有任何卡時，`groupByBucket()` 仍然回傳該桶，其 `cards` 為空陣列。
- 每張卡恰好出現在一個桶裡，且各桶張數總和等於輸入張數。

手動：

- 進入卡片頁，六個標頭全部收合，各自顯示張數。
- 點標頭展開該桶、再點收合；展開中的標頭符號為 `▾`、收合為 `▸`。
- 展開後卡片右側顯示 `YYYY-MM-DD` 的到期日，灰色；「新」桶的卡沒有右欄。
- 展開後卡片左右各內縮 `1.4rem`，兩側留白一致。
- 沒搜尋時，空桶仍然顯示並標 `0`。
- 搜尋框輸入字：所有桶自動展開，沒有結果的桶消失；清空搜尋框後回到原本的收合狀態。
- 按「到期 ↓」：標頭順序顛倒，桶內卡片順序也顛倒；展開中的桶維持展開（不因重畫而闔上）。
- 離開卡片頁再回來，六個桶全部收合。
- 複習佇列的出題順序完全沒變。

## Comments

- 決定 9 部分推翻 issue 01 的決定 3。issue 01 那條的理由是「六標籤一對一是接受這點換來的」；分組之後標籤的位置被標頭接手，列右側空出來了，所以原本的取捨前提消失。issue 01 的檔案不改，兩張一起讀才看得出演進。
- 決定 14 的比較過程有做過一個可互動的原型（兩種元素並排、外觀一致），結論是差距很小。若日後為了頁內搜尋想改用 `<details>`，只需替換標頭那段與加兩行 CSS，`bucketOf()` / `groupByBucket()` 完全不受影響。
- 實作時發現決定 6 沒交代「搜尋中點標頭會怎樣」。作法：搜尋框由空變有字時，把當下的收合狀態存一份快照、六桶全設為展開；清空搜尋框時還原快照。因此搜尋中點標頭是真的能收合該桶（畫面立刻有反應），而搜尋期間的展開／收合動作不會帶回搜尋前的狀態。另一個選項是「顯示層強制展開、點擊只改記憶中的狀態」，程式碼少一個變數，但搜尋中點下去畫面完全不動，看起來像按鈕壞了。
- 決定 7 也沒交代空桶能不能點。作法：能點、符號照樣換成 `▾`，但不長出空的卡片容器——否則 `.rows` 的 `gap` 會在標頭之間多留一段空白。
- 決定 3 的字面敘述比實際行為強一點：`sortByDue()` 對同一天到期的卡回傳 `0`，兩個方向下維持同一個相對順序（`CONTEXT.md`「到期排序」刻意保證的行為），所以「桶內順序顛倒」指的是日期反過來，同日到期的幾張不會互換，全是新卡的「新」桶更是完全不動。決定 2 既然明說沿用 `sortByDue()`，這裡不改行為，改補一條測試把它釘住。
- 決定 15 說標頭無底色，實作另加了 `.bucket-head:active` 按下時的底色，沿用 `.row:active`、`.sort-toggle:active` 的既有觸感回饋慣例。靜態外觀仍是無底色。
