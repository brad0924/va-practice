# 讀音改成必填：詞條裡有漢字就一定要填讀音

Status: ready-for-agent
Type: enhancement

## 需求

現在讀音可以整串留空。要改成：詞條裡只要有漢字，**每一個讀音格都要填**才存得下去。

起因是換欄鍵（見 `02`）：使用者要「只要有輸入格還空著，按手機的 ↵ 就把游標送過去」。把讀音格納進來時會死結——空的讀音格既是合法的存檔狀態、又不能當輪詢的終點，游標永遠出不去。必填把矛盾本身拿掉。決策脈絡見 `docs/adr/0009-reading-required.md`。

這張票只做驗證與儲存那一段，換欄留給 `02`。

## 決定

### 驗證規則

`reading.ts` 的 `validateDraft()`：

```
現在：同一串漢字 → 有填的格數 > 0 且 < 總格數 → 「… 要麼全部填、要麼全部留空」
改成：任何一格 reading === '' → 錯
      「填了但不是假名」那條不動
```

「要麼全部填、要麼全部留空」整條退場——它存在的唯一理由是要區分「整串沒填」與「填一半」，現在兩者都是錯，不必再分。

### 「沒填」與「填錯」要分得出來

儲存時兩者的處理不同（沒填要跳游標、填錯不跳），所以 `commit()` 的 `Commit` 型別得分得出來，不能全部混進 `reason: 'invalid'` 的 `errors` 陣列裡。怎麼分由實作決定，觀察得到的行為是下一節那兩條。

### 儲存時的行為

```
檢查順序維持現狀：詞條 → 釋義 → 讀音
  第一個空的 → 錯誤訊息「詞條、讀音與釋義都要填。」＋ 游標送過去，不儲存
讀音填了但不是假名 → 原本的多句列舉，游標不動
```

- 錯誤訊息從「詞條與釋義都要填。」改成「詞條、讀音與釋義都要填。」，**維持單一句**，不指名缺哪一格（游標已經指路）。
- 讀音空著時游標送到**第一個空的讀音格**。這是 ADR-0006 那條「讀音驗證失敗不跳焦點」的例外退場——那條的理由是「錯可能一次好幾個」，必填之後讀音的錯幾乎只剩「沒填」一種。
- 順序刻意**不**改成畫面的由上而下（詞條 → 讀音 → 釋義）。使用者明確選擇讀音排最後。

### 範圍

- **新增與編輯一視同仁。** 手上沒讀音的舊卡，打開來改任何東西都得先補齊讀音才存得回去。
- **匯入單字與匯入備份不檢查，照收。** 必填是編輯畫面的規則，不是資料的規則。`storage.ts` 一行不動。
- 因此「每張卡都有讀音」**不是資料的保證**——渲染、語音朗讀、複習翻面三處對沒讀音的卡的處理一行都不能拿掉。

## 被放棄的替代方案

見 `docs/adr/0009-reading-required.md` 的 Considered Options：維持可留空而在換欄那側加規則（三種）、只擋新增不擋編輯、連匯入一起擋。

## 驗收

`npm test` 全綠。`reading.test.ts` 與 `reading-editor.test.ts` 裡針對「整串留空是合法的」的既有案例要跟著改。

**單元**

- 一串漢字全部留空 → `validateDraft` 回一個錯（現在回空陣列）。
- 一串漢字填一半 → 仍是錯，訊息不必與舊版相同。
- 一串漢字全部填好 → 沒有錯。
- 填了非假名 → 仍回「… 的讀音要填假名」。
- 純假名詞條（「ありがとう」）→ 沒有讀音格，沒有錯。
- 外來語詞條（「テスト」）→ 同上。

**畫面（實測）**

- 新增卡片，詞條「焦がす」、釋義「燒焦」、讀音格留空 → 點「儲存」→ 紅字「詞條、讀音與釋義都要填。」＋游標落在那個讀音格，卡沒被存。
- 承上，填好「こ」再存 → 存得進去。
- 詞條「大丈夫」（三格）、釋義填好、只填第一格 → 點「儲存」→ 紅字＋游標落在第二格。
- 詞條「大丈夫」、釋義**空著**、讀音全空 → 點「儲存」→ 游標落在**釋義**（不是讀音格），因為檢查順序是詞條 → 釋義 → 讀音。
- 讀音格填了漢字或英數（不是假名）→ 紅字「… 的讀音要填假名」，**游標不動**。
- 詞條「ありがとう」、釋義填好 → 存得進去（沒有讀音格）。
- 編輯一張沒讀音的舊卡，只改釋義 → 被擋下來，游標落在第一個空的讀音格。
- 匯入一份含「有漢字沒讀音」的備份檔 → 照樣匯進來，一張都不跳過。
