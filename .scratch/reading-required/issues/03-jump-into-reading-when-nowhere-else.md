# 避讓無處可去時，↵ 改送進第一個空的讀音格

Status: done
Type: bug
Blocked by: 02

## 現況

`02` 上線後在 iPhone 實測（正式站，commit `bed05de`，該裝置有設 Gemini 金鑰）發現：

```
先填釋義 → 按 ↵ → 游標跳到詞條（正確）
填完詞條 → 按 ↵ → 什麼都不發生
```

↵ 變成死鍵。而且因為焦點沒被移走，詞條不會失焦，**AI 連問都沒開始問**（`prefill()` 掛在 `blur` 上）。使用者卡在原地，畫面上沒有任何回饋。

原因是 `editor-view.ts` 的 `jumpOnEnter`：避讓把讀音格整段移出候選後只剩 `[詞條, 釋義]`，兩格都有值 → `nextEmpty()` 回 `null` → 那一段刻意 `preventDefault()` 擋掉表單送出（免得冒出紅字），然後就沒有下文了。

**這是規格本身的死結，不是實作漏了一行。** ADR-0006 的避讓寫的是「跳過讀音格，游標直接送到釋義」，預設釋義是空的；但同一份 ADR 開頭就寫了使用者「中文注音時先打釋義」。兩句話擺在一起，唯一還空著的就是讀音格，而讀音格正是避讓禁止進入的地方。

## 決定

```
避讓照舊：離開詞條時若正在問 AI、或這一下離開會開始問
  → 這一輪把讀音格移出候選
改動只有一條：候選裡找不到空格時（＝釋義已經有值）
  → 送進第一個空的讀音格
     焦點一移動詞條就失焦，prefill() 照常被觸發，AI 開始問
不出錯誤訊息、不儲存（照舊）
全部真的有值時 ↵ 才放行送出表單（照舊）
```

- **範圍是窄的那個，使用者明確選過。** 釋義還空著時仍然走避讓（↵ 送你去釋義），那條路避得開撞車，不要一併拿掉。被放棄的替代方案是「避讓整條拿掉、詞條打完一律進讀音格」——↵ 的落點會變得完全可預測，代價是先打詞條的那一半流程也開始撞車。
- **↵ 與 ✓ 的落點必須維持一致**（ADR-0006）。把退讓做在 `nextEmpty()` 裡（避讓的候選找不到空格就改用完整的一圈再找一次），兩條路自然共用同一個結果；`jumpOnEnter` 裡那段「避讓時攔下送出」也就跟著不需要了——`nextEmpty()` 回 `null` 只剩「真的全部有值」一種意思。

### 已知代價，使用者已被告知並接受

游標進了讀音格之後約一秒，AI 回覆到達 → `renderReading()` 整個 `replaceChildren` → **焦點消失、鍵盤收掉，打到一半的假名被蓋掉**，就算一個字都沒打也會被彈出來。這正是避讓當初存在的理由，這張票不處理它。

真要解得走 ADR-0006 的 Considered Options 裡那條：「回覆到了但游標在讀音區就不套用，改出一行『點一下套用』」。那條解掉之後避讓整條可以退場，這張票也一起失效。**還沒開票，要不要做由使用者決定。**

## 文件

- `docs/adr/0006-focus-first-empty-field.md` 的〈AI 預填避讓〉要補上「無處可去時退讓」這條。
- 同一份 ADR 的〈換欄不出錯誤訊息〉裡，`02` 剛加進去那段「避讓生效但找不到空格 → 攔下送出」要跟著改寫：那個狀態現在有去處了。

## 驗收

`npm test` 全綠。畫面層照 `docs/spec.md` 慣例不寫自動化測試，靠實測。

**iPhone（有設 Gemini 金鑰，主要情境）**

- 先填釋義 → ↵ → 游標到詞條。
- 承上，填完詞條 → ↵ → 游標進**第一個空的讀音格**，讀音區上方出現「詢問中…」。
- 承上約一秒後 AI 回覆 → 讀音格被填好；焦點與鍵盤消失是已知代價，不算失敗。
- 釋義**還空著**時，詞條打完 ↵ → 仍然跳**釋義**（避讓照舊，這條沒被改壞）。
- 同一張卡按 ✓ 與按 ↵ 的落點一致。

**任何裝置**

- 沒設金鑰的人完全不受影響：詞條打完 ↵ → 第一個空的讀音格（`02` 的行為）。
- 全部有值時按 ↵ → 照常送出。
- 桌機在有值的欄位按 Tab → 焦點照既有順序走，不被搶。
