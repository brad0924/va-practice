## 要做什麼

讀音編輯器落地之後，兩份文件會停在已經不成立的敘述上，補回來。**不開 ADR**——本次行為零變化、沒有推翻任何既有決定，ADR-0005 已經記了這個功能為什麼存在與風險在哪。

### 牴觸一：規格說「建立三個模組」

規格的「模組與接縫」段落寫著建立三個模組、各自對應一個測試接縫（複習流程、讀音標記、資料存取）。本次加了第四道。

**不是把數字改成四就好。** 原本那三道是「跟畫面無關的核心」，第四道是「某個畫面的大腦」——性質不同，得寫清楚差別，否則下一個人會以為可以照樣往裡面塞畫面邏輯。

### 牴觸二：規格說「UI 不撰寫自動化測試」

規格的測試段落寫著 UI 不撰寫自動化測試，理由是瀏覽器層級測試的維護成本高於其攔截的缺陷。

字面上與本次直接打架：讀音編輯器住在畫面資料夾，而且有測試。

實質上沒打架——那句擋的是瀏覽器層級測試，本次寫的是不需要瀏覽器的純邏輯測試。而且卡片列表的分桶邏輯早就是這個樣子，只是當初沒回頭改那句話。

改寫成：**畫面本身**不寫自動化測試；畫面資料夾底下不碰 DOM 的邏輯照常測。

### 補一條詞彙

領域文件現有「讀音格」與「讀音預填」，但沒有任何詞在講管著它們的那台機器。補上**讀音編輯器**。

定義要點：編輯畫面背後那台管著讀音格的機器，持有詞條與各格內容，負責決定什麼時候重建格子、什麼時候去預填、預填回來的東西收不收。不碰畫面，因此可獨立測試。
_Avoid_：狀態機（太泛）、控制器、讀音草稿（會與既有的「詞條＋格子」資料結構混淆）
