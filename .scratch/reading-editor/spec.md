# 讀音格的協調邏輯搬出畫面，成為可測的讀音編輯器

Status: ready-for-agent
Type: enhancement

拆成兩張實作票，見 `issues/01-extract-reading-editor.md`、`issues/02-docs.md`。本檔案是兩張票共用的決策紀錄，不直接實作。

**這次行為零變化。** 使用者看到的畫面、文字、錯誤訊息、操作順序一字不改。純粹是把判斷邏輯搬到測得到的地方。

## 問題

`src/lib/reading.ts` 的七支純函式（`toDraft`、`rebuildRuns`、`mergeSeam`、`splitCellAt`、`acceptPrefill`、`validateDraft`、`toMarkup`）各自有測試，共 522 行。

但**「什麼時候呼叫哪一支」的協調邏輯全埋在 `src/ui/editor-view.ts`（249 行）裡，跟 DOM 綁死**。測試跑在 `environment: 'node'`（`vite.config.ts`），沒有 DOM 就進不去。

埋在裡面、目前完全沒有保護的判斷有五類：

1. **搶答檢查**——AI 回覆等待期間使用者改了詞條，這份回覆對的是舊的漢字串，必須整份丟掉。檢查寫成 `termInput.value !== term`，直接讀 DOM 輸入框。
2. **要不要重畫**——`shape()` 把漢字排列壓成指紋比對。排列沒變就不准重建 DOM，否則正在打字的讀音格會失焦、日文輸入法組字會被打斷。這個布林值算出來當場就用掉。
3. **提示字的生死**——ADR-0005 明寫「請確認」那一行是**唯一**擋得住讀音幻覺的防線。它的存亡規則（改詞條時，只要 AI 填的假名還活著就絕不能消失）現在沒有任何東西在保護。
4. **預填守門**——沒金鑰、詞條空白、沒有漢字、已經填過、同一串問過了，任一成立就完全靜默。ADR-0005 承諾「沒設金鑰時一字不多」，靠這五條守著。
5. **`runs` 的就地變動與 `askedTerm`**——狀態散在 `editorView` 的閉包裡。

第 1 與第 3 類壞掉**不會報錯**，只會安靜地把錯讀音填進卡片，一路存進雲端備份，等到複習翻面才發現。

## 解法

抽出一個不碰畫面的模組**讀音編輯器**，把上述五類判斷全部收進去。`editor-view.ts` 只剩畫格子、接事件、照單辦事。

模組不 import 任何 DOM，所以現有的 node 測試環境直接吃得下，不必引進 jsdom。

## 使用者故事

1. 作為使用者，我想在 AI 回覆到達之前改掉詞條時，那份對不上的讀音不要被填進來，以免我沒注意就存下一張錯卡。
2. 作為使用者，我想在詞條尾巴加減假名時（考え込む → 考え込んだ）讀音格不要重建，以免我正在打的假名被輸入法吃掉。
3. 作為使用者，我想在換掉詞條裡的漢字時（考え込む → 考え直す）讀音格立刻跟著換，以免我對著過期的格子填假名。
4. 作為使用者，我想在改動詞條之後「讀音由 AI 填入，請確認」那行提示仍然留著，以便我記得那些假名不是我自己填的、還沒被確認過。
5. 作為使用者，我想在清空所有讀音之後那行提示跟著消失，以免畫面上留著一句已經不成立的話。
6. 作為使用者，我想在沒有設定金鑰時完全不看到任何多出來的字，以便新增卡片的體驗與沒有這個功能時一字不差。
7. 作為使用者，我想在同一個詞條上不要被重複詢問 AI，以免浪費免費額度、也不必看提示字閃來閃去。
8. 作為使用者，我想在讀音格已經填過字時不要被 AI 覆蓋，以便我手動填的內容不會憑空消失。
9. 作為使用者，我想在 AI 回的漢字對不上我的詞條時整批被退掉、讀音格保持原狀留空，以便我直接手動填，不必先清掉一堆錯的。
10. 作為使用者，我想在連不上網路或超時的時候只看到一行失敗訊息、儲存流程完全不受影響，以便我在飛機上也能正常新增卡片。
11. 作為使用者，我想貼上 `焦[こ]がす` 這種帶標記的字串時它自動攤回讀音格、詞條框只留純文字，以便我從別處抄卡片時不必手工拆解。
12. 作為使用者，我想在詞條或釋義沒填時看到「詞條與釋義都要填。」這句話，與現在完全一致，以免我得重新學一次錯誤訊息。
13. 作為使用者，我想在同一串漢字混填混空時被擋下來並看到是哪一串，以便我知道該補哪裡。
14. 作為開發者，我想要那五類判斷有測試保護，以便日後改動讀音編輯行為時，壞掉會在 `npm test` 就紅燈，而不是等使用者複習翻面才發現。
15. 作為開發者，我想在測試裡自由控制「AI 什麼時候回、回什麼」，以便演得出搶答、驗證失敗、連不上網路這些真實環境難以重現的情境。
16. 作為開發者，我想要跑測試不會真的打出網路請求，以便測試快、離線可跑、不消耗免費額度。
17. 作為開發者，我想讀 `editor-view.ts` 時只看到畫面的事，以便我一眼分得出哪些是呈現、哪些是規則。

## 實作決定

以下十項是本次 grilling 的結論，依決定順序排列。

### 一、模組持有 `term`，不從 DOM 讀

搶答檢查現在讀 `termInput.value`，那是 term 的唯一真相。要讓這行檢查測得到，模組必須自己存一份。

使用者每打一個字，畫面呼叫 `setTerm(raw)` 通知模組；搶答檢查因此變成模組內部兩個變數比對。

代價是同一份字串有兩個地方存著，畫面漏通知就會不同步。接受——這五類判斷裡搶答檢查是唯一「壞掉不會報錯」的那一個，值得付這個成本。

**不採用受控輸入**（每次 `setTerm` 後把值寫回輸入框）：那會在日文輸入法組字中途重設 `value`，正是現有註解特地避開的事。畫面只在「貼上帶標記字串」那一種情況才寫回。

### 二、「去問 AI」從外面遞進去

模組不認識 Gemini，建立時收一支 `(term: string) => Promise<unknown>` 的函式。上場時畫面把 `askReading` 綁上金鑰塞進去，測試時遞一支手寫的假貨。

**金鑰未設定時遞 `null`**，模組看到 `null` 就全程靜默。ADR-0005 承諾的「沒設金鑰一字不多」因此成為模組內部一條測得到的規則。

金鑰在建立時取一次即可：編輯畫面開著的時候金鑰不可能變（要改金鑰得離開這個畫面到資料畫面，回來時 `editorView` 已整個重建），所以與現行「blur 當下才讀」行為零差異。

**不採用 `vi.mock` 攔截**：這專案現有測試一個 mock 都沒用過，`storage.test.ts` 與 `gemini-key.test.ts` 都是手寫假物件注入。沿用既有寫法，不新開一種。

`gemini-reading.ts` 本身維持沒有測試——該檔案第 7 行已載明理由（比照 `cloud-backup.ts` 直接用全域 `fetch`），本次不動。

### 三、以「變更單」溝通，不用回呼通知

每支指令回一個小物件，列明畫面各處要不要動：

```ts
interface Change {
  term: boolean;   // 詞條框要改寫（只有貼上帶標記字串時為 true）
  runs: boolean;   // 讀音區要重畫
  note: boolean;   // 提示字要換
}
```

`shape()` 那個布林值不再當場用掉，而是遞出去給畫面。測試可以直接斷言「改詞尾這一下，`runs` 欄是 `false`」。

**不採用回呼通知**（建立時給模組一支「該重畫了」的函式）：要測的行為裡有好幾條是否定句（「不該重畫」），用回呼得斷言「某支從頭到尾沒被叫到」，而沒被叫到的原因不只一種——可能真的是判斷不用重畫，也可能是參數傳錯根本沒進到那段。兩種都是綠燈。

**預覽不進變更單**：預覽由 `term` 與 `runs` 組出來，任何改動都要刷。畫面每次呼叫完一律刷一次，不必逐支判斷。

### 四、變更單不夠，另有唯讀的查看窗口

變更單只說「要不要動」，沒說「內容是什麼」。畫面收到「讀音區要重畫」之後仍需取得目前的格子才畫得出來。

模組因此另外提供唯讀的 `term`、`runs`、`note`。這不是第七支指令，是模組讓外界看得見自己的必要出口。

### 五、`prefill` 回兩張單子

`prefill` 一叫下去會發生兩波事，中間隔著一兩秒：立刻掛上「詢問中…」，答案回來才填格子。一張變更單裝不下兩個時間點。

因此 `prefill` **不宣告成 `async`**——先同步跑完守門與掛提示，再把要等的那件事包成 Promise 交出去：

```ts
prefill(): { now: Change; later: Promise<Change> }
```

守門沒過（沒金鑰、詞條空白、沒有漢字、已填過、同一串問過了）時兩張都是空單，畫面照樣走一遍，什麼都不會動。

**不採用「宣告成 `async`、詢問中靠查看窗口讀」**：那能跑，但依賴的是「非同步函式在第一個 `await` 之前是同步執行」這個看程式碼看不出來的性質，只能靠註解撐著。

### 六、提示字只吐狀態代號，中文留在畫面

```ts
type Note =
  | { kind: 'asking' }
  | { kind: 'filled' }
  | { kind: 'failed'; reason: string };
```

`null` 代表沒話講。畫面用一張四行的對照表翻成中文與樣式（`hint` / `error`）。測試斷言代號，改文案錯字不必動測試。

`failed` 帶的 `reason` 是 `askReading` 拋出來的訊息，本來就已經是人話（「等超過 10 秒沒有回覆」「連不上 Gemini」）。前綴「自動填讀音失敗：」與 CSS class 名稱屬於畫面，不進模組。

### 七、`commit` 也檢查詞條空白，但錯誤訊息一字不改

```ts
commit():
  | { ok: true; text: string }
  | { ok: false; reason: 'empty-term' }
  | { ok: false; reason: 'invalid'; errors: string[] }
```

模組不假設外界已經擋過空白，自己站得住。畫面收到 `empty-term` 之後，與「釋義空白」在自己家裡合成同一句「詞條與釋義都要填。」，順序也維持現狀（空白檢查先、讀音驗證後）。使用者看到的字一字不變。

`errors` 是 `validateDraft` 產的中文句子（訊息裡含漢字，內容依賴資料），原封不動經過模組的手——這是模組唯一碰到的中文文案，代號化要傳一堆參數，不划算。

**`commit` 不改動模組狀態**：驗證沒過時使用者還留在畫面上，若 `commit` 順手把 `term` 換成 `trim` 過的版本，模組裡的字串就跟輸入框裡的不一致了。現行程式碼也是如此（算出來的 draft 是丟掉的區域變數），維持原狀。

### 八、命名為「讀音編輯器」，檔案放 `src/ui/`

`reading.ts` 已有一個 `ReadingDraft` 型別，那是一份靜態資料（詞條＋格子）；新模組是一台有狀態、接指令、會發請求的機器。同名不同義會讓往後任何人（包括 agent）看到都得先想一下是哪個，因此改叫**讀音編輯器**，建立函式 `createReadingEditor`。

放 `src/ui/`——它與 `editor-view.ts` 是一對，往後改讀音編輯行為八成兩支一起開。`list-view.ts` 已有前例證明 `ui/` 底下的邏輯測得到。代價是它會是 `ui/` 裡第一個完全不碰 DOM 的檔案，那條分界線變得沒那麼乾脆，靠 `docs/spec.md` 的文字說清楚。

### 九、六支指令的完整介面

```ts
createReadingEditor(options: {
  markup?: string;                                     // 舊卡的標記字串；新卡不傳
  ask: ((term: string) => Promise<unknown>) | null;    // null 代表沒金鑰，全程靜默
})
```

| 指令 | 回傳 | 說明 |
|---|---|---|
| `setTerm(raw)` | `Change` | 貼上帶標記字串走 `toDraft` 攤回格子並回報詞條框要改寫；否則走 `rebuildRuns` 依漢字內容保留已填讀音，只有漢字排列變了才回報要重畫。順帶套用提示字生死規則。 |
| `setReading(ri, ci, value)` | `Change` | 就地改某一格的讀音。**恆為空單**——重畫會打斷輸入法，這一支永遠不准要求重畫。 |
| `mergeAt(ri, seam)` | `Change` | 呼叫 `mergeSeam`，回報要重畫。 |
| `splitAt(ri, ci, at)` | `Change` | 呼叫 `splitCellAt`，回報要重畫。 |
| `prefill()` | `{ now, later }` | 見決定五。 |
| `commit()` | 見決定七 | 對齊 `trim` 後的詞條重算格子、驗證、組出標記字串。 |

行為細節，全部沿用現況：

- **守門**：`ask` 為 `null`、詞條 `trim` 後為空、沒有任何漢字串、已有任一格填了讀音、詞條等於上次問過的那串——任一成立就靜默返回空單。
- **`askedTerm` 記錄的是「問過」而非「問成功」**：失敗之後同一串不會自動重試；使用者把詞條改掉再改回來也不會重問。
- **搶答時 `later` 回空單，不動提示字**：使用者改詞條那一下已經觸發 `setTerm`，提示字的生死由那條規則處理，不需要 `prefill` 再插手。
- **提示字生死規則**：`setTerm` 之後若沒有任何一格填了讀音就清掉提示字；只要還有讀音活著就原封不動保留。
- **AI 回覆過不了 `acceptPrefill`**：掛 `failed`，讀音格保持原狀留空，儲存流程完全不受影響。

### 十、不開 ADR

行為零變化，沒有推翻任何既有決定，也沒有產生新的「回頭要付大代價」的承諾。ADR-0005 已經記了這個功能為什麼存在、風險在哪。

若「協調邏輯抽成無畫面模組、以變更單溝通」這個模式往後被第二次用上，那時再寫 ADR 才有意義。

## 測試決定

**好的測試只驗證外部行為，不碰內部實作**——沿用 `docs/spec.md` 既有的原則。斷言的對象是「給定這串操作，變更單與查看窗口應該長怎樣」，不是「某支純函式被呼叫了幾次」。

### 現有測試零搬遷

`reading.ts` 這次一行都不動（新模組是**呼叫**那七支純函式，不是取代），因此 `reading.test.ts` 全部 522 行原封不動留在原地。包括 `acceptPrefill` 那 16 個測試——它測的是「AI 回覆能不能採用」，與「什麼時候去呼叫它」是兩件事，留在原地才對得上被測的檔案。

### 新增 `src/ui/reading-editor.test.ts`

四組，全做：

**AI 預填**
- 等待期間改了詞條 → 整份丟掉，讀音格不動
- `ask` 為 `null` → 全程靜默，兩張單子都是空的、提示字始終沒出現
- 已有格子填了讀音 → 不問（開舊卡的情境）
- 同一串詞條問第二次 → 不問
- 詞條沒有漢字 → 不問
- AI 回的漢字對不上 → 掛 `failed`，讀音格保持原狀留空
- `ask` 拋錯（連不上、逾時）→ 掛 `failed` 並帶原訊息，不影響後續儲存

**要不要重畫**
- 考え込む → 考え込んだ（改詞尾）：`runs` 為 `false`
- 考え込む → 考え直す（換漢字）：`runs` 為 `true`
- `setReading` 打字：恆為空單
- `mergeAt` / `splitAt`：`runs` 為 `true`

**提示字生死**
- AI 填完後改詞條、讀音還在 → 提示字**必須**留著（ADR-0005 的唯一防線）
- 清空所有讀音後改詞條 → 提示字消失

**進出口**
- 貼上 `焦[こ]がす` → 攤回格子，且回報詞條框要改寫
- `commit` 詞條空白 → `empty-term`
- `commit` 同串混填混空 → `invalid` 加錯誤清單
- `commit` 正常 → 組出標記字串，且**模組狀態未被改動**

### 前例

- **依賴注入的假物件**：`storage.test.ts` 的 `fakeStorage`、`gemini-key.test.ts` 的 `fakeStorage`——手寫假物件注進去，不用 mock 工具。`ask` 照這個寫法做一支可以控制何時兌現、兌現什麼的假貨。
- **`ui/` 底下的純邏輯測試**：`list-view.test.ts`（`bucketOf`、`groupByBucket`）。
- **讀音領域的測試風格**：`reading.test.ts`——測試名稱直接寫日文例子（「漢仮：焦[こ]がす」），新測試沿用。

### 文件牴觸要一併修正

- `docs/spec.md`「建立**三個**模組，各自對應一個測試接縫」——本次加第四道接縫。原本那三道是「跟畫面無關的核心」，第四道是「某個畫面的大腦」，性質不同，spec 得說清楚兩者的差別，而不只是把數字改成四。
- `docs/spec.md`「**UI 不撰寫自動化測試**」——字面上與本次直接打架。實質沒打架：那句擋的是瀏覽器層級測試，本次寫的是純邏輯測試；`list-view.test.ts` 早已是這個樣子，只是當初沒回頭改那句話。改寫為「**畫面本身**不寫自動化測試；`ui/` 底下不碰 DOM 的邏輯照常測」。
- `CONTEXT.md` 補一條詞彙「**讀音編輯器**」。現有詞彙表有「讀音格」與「讀音預填」，但沒有任何詞在講管著它們的那台機器。

## 不在範圍內

- **`editor-view.ts` 剩下的部分不寫測試**。抽完之後它只剩畫格子、接事件、照單辦事，要測得引進 jsdom 這類假瀏覽器。那是另一個決定，本次不碰——這次的目標正是「不必引進假瀏覽器也測得到那些判斷」。
- **`reading.ts` 的七支純函式不動**，介面與行為都不變。
