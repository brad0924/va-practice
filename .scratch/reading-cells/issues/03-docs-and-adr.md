# 文件與 ADR：讀音格取代語法輸入

Status: done
Type: enhancement

決策背景見 `.scratch/reading-cells/spec.md`。建議在 `01`、`02` 完成後再落筆，確保文件描述的是真正做出來的東西。

## 需求

功能改掉了「使用者手打讀音標記語法」這個前提，牽動的文件一起改，並記一份 ADR 把「不引入漢字讀音字典」的決定留檔。

## 決定

### `docs/spec.md`

1. **User Story 23、24 改寫。** 目前是：

   - 23：「我想用標記語法輸入讀音，以便新增的卡與內建卡有一致的振假名顯示。」
   - 24：「我想在新增畫面上看到語法範例，以免每次都要回想格式怎麼寫。」

   兩條都建立在「使用者要認得並手打語法」上，已不成立。改寫方向：23 改成「我想打完漢字後直接在下方填假名，不必輸入括號或切換輸入法」；24 改成看到自動長出的讀音格、能切開或合併連續漢字。實際措辭實作時定，維持既有 User Story 的語氣。

2. **「讀音標記」章節（現況約在 `## 讀音標記`）補上輸入介面。** 現有內容只描述儲存格式（方括號語法），要補一段說明編輯畫面以讀音格輸入、儲存時轉回方括號字串、方括號仍是唯一的儲存與顯示格式。強調語法沒有消失，只是不再需要人工輸入。

3. **不改「讀音標記」模組的測試接縫描述**（`docs/spec.md` 約 148 行），但可補一句本模組新增了讀音格的雙向轉換與往返測試。

### `CONTEXT.md`

4. **新增詞條「讀音格」**，放在「讀音標記」條之後（它引用了讀音、讀音標記兩個概念，擺後面避免前向引用）。定義方向：漢字串在編輯畫面上對應的輸入格，一格對一段連續漢字；使用者可把連續漢字的格切開或合併，決定假名怎麼分配到哪些漢字上。`_Avoid_` 排除會誤導的說法（例如「欄位」「輸入框」太泛、「切割」聽起來像破壞資料）。實際措辭沿用 `CONTEXT.md` 既有條目的體例。

### `docs/adr/0004-no-kanji-reading-dictionary.md`（新檔）

5. **記一份 ADR**，決定為「讀音格逐字開格、由使用者填假名，不引入漢字讀音字典自動推測」。編號 `0004`，沿用 `0001`–`0003` 的體例（標題句、正文、Considered Options、Consequences）。核心論點：

   - **體積**：現有打包產物 33 KB，一份精簡漢字讀音字典約 300 KB 起跳，10 倍於整個 app，與「純前端、可離線、加入主畫面」的定位不成比例。
   - **正確性天花板本來就到不了 100%**：連濁（`円高`→`えん`+`だか`）、促音便（`昨今`→`さっ`+`こん`）要另外寫規則；熟字訓（`剃刀[かみそり]`、`吹雪[ふぶき]`）字典本來就無法逐字拆。
   - **失敗模式最糟**：猜錯時產生的是看起來正常的錯卡，不會報錯，要等複習時才發現——比「請使用者自己填」更危險。
   - **實際負擔很小**：121 個漢字串裡 85 個是單一漢字，根本無從猜起；使用者本來就知道讀音（是自己要加的詞），填假名不是查資料而是打字。

6. **Consequences 寫明這扇門沒關死**：日後若真的想要自動推測，可作為選配的預填（填完仍要人工確認），而非取代手動。但在那之前，讀音一律由人輸入。

## 驗收

- `docs/spec.md` 讀完不再出現「要使用者手打語法／看語法範例」的描述，User Story 23、24 已改寫且與 `02` 實作出的畫面一致。
- `CONTEXT.md` 有「讀音格」條，位置在「讀音標記」之後，帶 `_Avoid_`。
- `docs/adr/0004-no-kanji-reading-dictionary.md` 存在，四個理由俱全，體例與 `0001`–`0003` 一致。
- 文件內所有指向行為的描述，與 `01`、`02` 實際做出來的一致（不描述沒做的東西）。
