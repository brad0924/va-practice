# 新增卡片頁可以存完不離開，接著加下一張

Status: done
Type: enhancement

## 需求

新增卡片頁（`src/ui/editor-view.ts`）目前只有一顆「儲存」，按下去 `app.upsert()` 之後一律 `back()` 回卡片列表。連續建卡時（例如從課本抄下八個生字）每一張都要「新增 → 填 → 儲存 → 被丟回列表 → 再點新增」，畫面整個換掉再換回來。

想要一顆存完留在原地、清空欄位接著填下一張的按鈕，並在存好時給一則看得到的回饋。

## 決定

1. **兩顆按鈕，不是把「儲存」改成永遠不離開。** 「複習到一半想到一個字，加一張就走」仍是最常見的用法，若新增頁一律不離開，單張新增會從一步變兩步。因此「儲存」維持現狀（存完 `back()`），另加「儲存並繼續」。

2. **按鈕文案是「儲存並繼續」。** 使用者原本的講法是「繼續加入下一個字」，兩處要改：`CONTEXT.md` 明訂卡片是複習的最小單位、要避開「單字／詞彙」的叫法（詞條可能是文法句型），所以加的是一張卡不是一個字；而「繼續」單獨出現沒講到會先存，可能被讀成「不存、直接換下一張」。兩顆並排時「儲存」對「儲存並繼續」的對照最清楚：都會存，差別只在離不離開。

3. **只在新增模式長出這顆按鈕**（`card === null`）。編輯既有卡時不出現——「編輯完 A 卡順手加 B 卡」語意混亂，而且把一個編輯中的表單清空，很容易被讀成「這張卡被我洗掉了」。

4. **左右並排、各半等寬，「儲存並繼續」是主要動作。** 右邊、`.primary` 亮底、`type="submit"`；「儲存」在左邊、沿用既有的 `.secondary` 灰底、改為 `type="button"` 自己綁 click。type 的分派不能省：「儲存」排在 DOM 前面，若也是 submit 會把 Enter 搶走。Enter 歸「儲存並繼續」的理由是連加八張可以「打字 → Enter → 打字 → Enter」手不離鍵盤；只加一張的人按 Enter 會留在頁面上，但 toast 已經講明存好了，再按左上離開即可。編輯模式仍是單顆「儲存」滿寬 `.primary` + `type="submit"`，`.form-actions > .primary { width: 100% }` 的現有行為不動。

5. **清空的範圍是整個表單的草稿狀態**：詞條、讀音格、釋義、讀音區上方那行提示（「讀音由 AI 填入，請確認」）、錯誤那行，全部回到剛進新增頁的樣子，焦點回到詞條輸入框。讀音格由讀音編輯器持有，因此清空等於換一台新的空編輯器——`editor` 目前是 `const` 綁在閉包裡，這裡需要讓它可以被換掉。Gemini 金鑰維持只在建立畫面時讀一次的現狀，不隨清空重讀。

6. **toast 只有「儲存並繼續」會跳。** 「儲存」離開、編輯舊卡、刪除都不跳：那些情況回到列表本身就是回饋，看得到結果。留在原地又被清空才是唯一分不出「存進去了」還是「白打一場」的時刻。因此 toast 完全住在編輯畫面裡，不必像 `sync-status` 那樣掛到 `document.body`。

7. **toast 寫「已加入『焦がす』」，帶詞條。** 連加八張時能一眼確認存到的是哪一張，也偵得到「前一張好像漏了」。詞條用 `toPlainText()` 去掉讀音標記後顯示，不要出現 `焦[こ]がす`。措辭不提雲端：`app.upsert()` 是先存本機（一定成功）再推雲端（可能失敗，失敗由 `sync-status` 那行小字負責），這則 toast 只代表本機那一份。比照 `sync-status` 加 `role="status"`。

8. **toast 約 3 秒自動消失，另附一顆 ✕ 可提前關掉。** 不堆疊：連加八張時是同一則被新內容取代，不是疊八則蓋掉半個畫面。畫面被換掉時計時器可能還在跑，需確認它不會去動已經卸下的節點。

9. **驗證沒過時完全維持現狀**：顯示「詞條與釋義都要填。」或讀音的錯誤訊息，不存、不清空、不跳 toast。兩顆按鈕走同一套驗證。

10. **左上「取消」不改字。** 已經存了三張再按「取消」不會撤銷那三張，但表單畫面用「取消」是本 repo 既有慣例（見 `.scratch/backup-screen/issues/01`），而且每存一張都跳過 toast 說「已加入」，誤解風險低。

11. **不影響排程。** `app.upsert()` 把新卡直接推進當日複習佇列是既有行為，連加八張今天的佇列就多八張。這不是新行為，只是連續新增讓它更容易被感覺到，不動。

12. **`CONTEXT.md` 不動、不開 ADR。** 這次沒有引入新的領域概念，只是「新增卡片」多了一條返回路徑；toast 是畫面元件（與 `sync-status` 同類，那個也沒收錄），而 `CONTEXT.md` 只當 glossary。這個決定好反轉、不需要脈絡就看得懂、也沒有真正被犧牲的替代方案，三個條件都不成立。

## 驗收

- `npm test` 全綠。
- 從卡片頁按「新增」，底部是左右並排的兩顆：左「儲存」灰底、右「儲存並繼續」亮底。
- 填好一張按「儲存並繼續」：留在新增頁，詞條／讀音格／釋義都空了，焦點在詞條輸入框，畫面上跳出「已加入『焦がす』」，約 3 秒後自己消失。
- 同一則 toast 還在時再存一張，內容換成新的詞條，不會變成兩則。
- 按 toast 的 ✕，它立刻消失。
- 在釋義欄按 Enter，行為等同「儲存並繼續」。
- 填好一張按「儲存」：回到卡片列表，不跳 toast，列表上看得到剛加的卡。
- 連加三張後按左上「取消」：回到卡片列表，三張都在。
- 詞條或釋義留空按「儲存並繼續」：顯示「詞條與釋義都要填。」，欄位不被清空，不跳 toast，卡片沒有增加。
- 從卡片頁點一張既有的卡進編輯頁：只有一顆滿寬的「儲存」，沒有「儲存並繼續」；儲存後回列表、不跳 toast。
- 帶讀音的詞條（如 `焦[こ]がす`）存下去時，toast 顯示「焦がす」而不是含方括號的原文。
