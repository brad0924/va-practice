# 01 — 匯出不再繞經 load()

Status: done
Type: enhancement

## 需求

`store.exportJson()`（`src/lib/storage.ts:95-97`）是 `JSON.stringify(load(), null, 2)`。而 `load()`（同檔 51-86 行）不是單純的讀取——它會跑單向合併，並且**一律寫回 localStorage**（第 84 行，那個寫回是刻意的：不寫回的話舊格式資料會一直缺少內建卡名單，下次發佈追加卡片時補不進來）。

結果是：按「匯出備份」這個看起來只讀的動作，順手改寫了一次瀏覽器裡存的資料。

**今天無害。** `app.ts:52` 開 app 時已經 `load()` 過一次，匯出時再跑一次補不到任何新卡，寫回去的內容一模一樣，`updatedAt` 也原封不動（`storage.ts:80`）。所以是多做一次白工，不是會出事。

## 方向

不是把 `load()` 裡的寫回拿掉——那條規則必須留著。要改的是**匯出別再繞經 `load()`**：`App` 手上的 `data`（`app.ts:52` 那個變數）本來就是最新的一份，每次評分、新增、刪除、匯入都同步著，直接序列化即可。

```ts
// src/app.ts
exportBackup(): string {
  return JSON.stringify(data, null, 2);
}
```

`store.exportJson()` 從此沒人用，應一併從 `Store` 介面刪除。

## Agent Brief

**Category:** enhancement
**Summary:** 匯出備份不應再透過帶有寫回副作用的載入路徑

**Current behavior:**
匯出備份目前重用「載入」這個操作來產生輸出內容。載入操作會執行一次單向合併（把尚未見過的內建牌組項目補進使用者資料），並且**一律**把結果寫回儲存——這個寫回對載入本身是必要且刻意的行為，但每次使用者匯出備份時都會順帶觸發一次，即使當下並沒有新內容需要合併。畫面層（App）手上其實已經持有一份跟儲存內容同步的當前資料（每次卡片評分、新增、刪除、匯入都會更新並落地），所以匯出時再繞一次載入路徑是多餘的。

**Desired behavior:**
匯出備份應該直接序列化畫面層已經持有的當前資料，不再呼叫載入／合併／寫回這條路徑。目前那個「內部呼叫載入再序列化」的匯出操作，應該整個從資料存取模組的對外介面中移除——移除之後不會再有任何呼叫端需要它。

**Key interfaces:**
- 資料存取模組（`Store`）對外介面上的 `exportJson()` 應該整個拿掉。
- 畫面層（`App`）對外介面上的 `exportBackup()` 維持原本的簽章（回傳備份內容字串），但內部實作改成直接序列化目前持有的資料，不再呼叫資料存取模組。

**Acceptance criteria:**
- [ ] 匯出備份這個動作不再對儲存產生任何寫入副作用。
- [ ] 在資料相同的前提下，匯出出來的內容（版本號、卡片清單、已知內建卡名單、更新時間戳）跟目前實作產生的結果完全一致。
- [ ] 資料存取模組的對外介面已移除匯出操作，且專案內沒有任何地方還在呼叫它。
- [ ] 既有涵蓋「匯出內容為可讀 JSON 且含版本號」與「匯出再匯入回來資料完全一致」這兩項行為的測試持續存在並通過——測試對象隨實作搬遷調整，不必是原本呼叫資料存取模組匯出方法的寫法。
- [ ] 專案內把「匯出與匯入的往返一致性」列為資料存取接縫測試項目的說明文字，更新成反映匯出已經是畫面層的職責，不再屬於資料存取模組。

**Out of scope:**
- 載入操作內部「一律寫回儲存」這個行為本身——這條規則必須留著，不能動（它是舊格式資料能持續補上新發佈內建卡的機制）。
- 匯入操作的行為（整份覆蓋、不合併）——不受影響，不必更動。
- 載入操作單向合併的邏輯本身——不受影響，不必更動。
