# 06 — 英、日兩語的翻譯內容

Status: ready-for-agent
Type: enhancement
Blocked by: 03

決策背景見 `../spec.md` 決定一、二。

## 要做什麼

把 `en.ts`、`ja.ts` 的約 193 條全部填滿。

**這張票是翻譯，不是工程。** 機制在票 02 已經蓋好、字串在票 03 已經搬完，這裡只填內容。

### 原本是三語，韓文被砍掉了

這張票原本叫「英、日、韓三語」。`../spec.md` 決定十四砍掉韓文，**唯一的理由是沒有人驗得了**。

這一點對本票特別關鍵，因為**這是全部十張票裡唯一沒有機器驗收條件的一張**：`tsc --noEmit` 只看 key 齊不齊、票 07 的冒煙測試只看有沒有漏出 key，兩者都不判斷文字對不對。**翻譯品質從頭到尾只能靠人。**

所以本票的隱含前提是：**維護者讀得懂英文與日文**（這本來就是一個 JLPT 工具）。韓文沒有人讀得懂，因此不做。

日後若備妥韓文校對者要恢復，見票 01 的「附錄：被砍掉的韓文初稿」。

## 決定

### 領域概念一律照 `docs/glossary.md`

29 個領域概念的譯名在票 01 已經定案（中英日三欄）。翻譯時**不得自行發揮**，也不得踩「英文避用」那一欄。

這是票 01 存在的唯一理由——同一個概念在按鈕寫 `Vocabulary Book`、在提示寫 `Deck`、在錯誤訊息寫 `Collection`，英文使用者會以為那是三種不同的東西。

### 漏譯不用擔心，型別會擋

票 02 已經用 `const en: typeof zhHant` 釘住。少一條 `npm run typecheck` 就紅燈，不需要另外檢查。

**但型別擋不到「填了但填錯」**——例如把日文那條複製貼上成英文的。這種只能靠人看。

### 帶參數的字串要注意語序

```ts
// zh-Hant
'books.nameTaken': '已經有一本叫「{name}」了',
// en
'books.nameTaken': 'A book named "{name}" already exists',
// ja
'books.nameTaken': '「{name}」という単語帳はすでにあります',
```

參數的位置各語言不同，這正是票 03 規定「不准用字串拼接」的理由。**不要為了對齊而改寫句子結構。**

### 標點符號跟著語言走

中文的全形逗號句號、日文的「、」「。」、英文的半形標點與空格——**照各語言的習慣寫**，不要沿用中文那份的標點。

### 長度會影響版面，但這張票不處理

英文普遍比中文長，日文的假名也會拉長行寬。按鈕被撐爆是真實風險，但 **jsdom 測不出來**，要靠實機看。這張票只管內容正確，版面問題歸票 08 的實機驗證與後續處理。

若翻譯過程中就發現某條明顯過長（例如一顆按鈕要塞三十個字元），在本檔 `## Comments` 記一筆，不要自作主張縮寫到失去原意。

## 這張票不做的事

- **不改 `zh-Hant.ts`**。若翻譯過程發現中文原文有問題，記在 `## Comments`，另開票處理
- **不改任何 key**
- **不動版面、CSS**
- **不做三語冒煙測試**（票 07）
- **不判斷日文介面跟學習內容打不打架**（票 08）
