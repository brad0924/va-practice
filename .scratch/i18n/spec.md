# 介面多語言（i18n）

把整個介面變成可以調整語言。支援三種語言加一個自動選項：

| 選項 | 行為 |
| --- | --- |
| 繁體中文 | 現況 |
| English | |
| 日本語 | |
| 系統預設 | 跟著裝置語言走；不符合上面三種時套英文 |

`handoff.md` 原本寫的是四種語言（含韓文），**韓文在釘規格的過程中被砍掉了**，理由見決定十四。需求背景與量測過程仍見 `handoff.md`，本檔只寫決定。

## 這不是什麼

**這是介面語言（app 用什麼語言跟使用者說話），不是學習內容的語言。**

`CONTEXT.md:22` 現在定義卡片是「一個**日文**詞條與其中文釋義的配對」，而振假名是日文獨有的。支援英文、韓文的單字卡會動到領域模型的根，那是另一件事，不在本規格內。這條界線也寫進 `docs/adr/0013-interface-localization.md`。

## 規模

- **約 193 條介面字串、約 3900 個中文字**，散在 29 個非測試檔案。分佈最重的是 `src/ui/data-view.ts`（43）、`editor-view.ts`（25）、`stats-view.ts`（19）、`review-view.ts`（19）、`list-view.ts`（18）、`books-section.ts`（18）
- 其中 **25 處是 `throw new Error` 帶中文訊息**，而且都是使用者看得到的——`storage.ts:61` 的註解明講「壞掉時的訊息可以直接顯示給使用者」
- **`CONTEXT.md` 有 29 則詞彙條目**，九則已有英文對照（寫在標題括號裡），日文一則都沒有
- 目前**沒有任何 i18n 機制**，字串全是寫死的字面值

### 有 3727 個中文字元不是介面文字，絕對不能翻

`handoff.md` 量到的「約 204 條」把 `gemini-reading.ts:67` 的 `INSTRUCTIONS` 算進去了。那是**送給 Gemini 的作業指示**（「你是日語讀音標注助手…splittable 逐字檢查…」），約 11 條、3727 個字元，佔了原始量測的一半。

它是給模型讀的，不是給使用者看的。**翻了會直接改變 Gemini 的行為**，而 `ADR-0005` 選 Gemini 的唯一理由就是日文能力，那段指示是為此調出來的。

扣掉之後才是上面那個 193 條、3900 字的數字。同一支檔案裡其餘的字串（「讀不懂 Gemini 的回覆」那類錯誤訊息）仍然要翻。

### 測試的實際衝擊比看起來小

449 個測試裡真正要動的**約 30 處**：

- **22 處 `toThrow('中文訊息')`** —— 主要戰場
- **個位數的 label 斷言** —— 例如 `list-view.test.ts:63` 斷言時間桶叫「新、現在、`<24小時`……」。但同一個測試的 `:54` 已經在斷言 `key`（`'new'`、`'now'`），那半段完全不受影響
- 其餘幾百處中文是**測試資料**（單字本名字、卡片內容如 `焦[こ]がす`），與介面語言無關，一條都不用動

## 決定

### 一、三語對照獨立成 `docs/glossary.md`，加註記與守門測試

29 則詞彙條目的三語譯名寫在新檔 `docs/glossary.md`，三欄表格（中／英／日）。`CONTEXT.md` 維持現狀只管中文定義，頂端 `## Language` 之下加一句註記指向 `glossary.md`。

**韓文欄不留。** 決定十四砍掉韓文之後，留一欄沒人驗過、沒人負責的譯名比空著更危險——日後真的要做韓文時，人會直接拿來用，以為它被審核過了。agent 的韓文初稿仍在 `issues/01-glossary.md` 的紀錄裡，要恢復查得到。

另加一支守門測試，抽 `CONTEXT.md` 裡 `^\*\*.+\*\*：` 的條目標題（實測剛好抓到 29 條，沒有例外），與 `glossary.md` 表格第一欄逐項比對，多一條少一條都紅燈。

**被否決的是「寫回 `CONTEXT.md`」。** 那條路沒有第二份檔可以漂移，而且改定義時譯名就在眼前。選獨立檔換到的是「三語並排好查、漏譯的格子一眼看得到、日後原生版可整份搬走」。

**已知殘餘風險，測試抓不到，只能靠人：**

1. 譯名寫錯（把「詞條」翻成 `Word`，名字清單還是對的，照樣綠燈）
2. 定義改了譯名沒跟（改的是標題底下的段落，標題沒動）
3. `_Avoid_` 更新了譯名沒跟（同上）

第 1 點靠 `glossary.md` 的「英文避用」欄補一部分。

**順帶動到 `CONTEXT.md` 一處領域定義：釋義的 `_Avoid_` 拿掉「意思」。**

原因是英文譯名撞上它——`Meaning` 正好等於被避開的「意思」，中文那邊小心避開，換成英文一腳踩回去。裁決是**改前提而不是扭英文**：`CONTEXT.md:31` 改成 `_Avoid_: 翻譯、定義`，英文欄填 `Meaning`。

判準是這份清單裡的項目份量分三類——**甲**「這個詞在本專案指別的東西」（「牌組」真的存在過並依 `ADR-0008` 退場、「標籤」是時間桶的舊叫法），**乙**「這個詞會讓人誤以為某件不成立的事」（「翻譯」「自動產生」「篩選器」），**丙**「只是比較鬆散的同義詞」。甲乙要留，丙份量最輕。「意思」是丙類：沒有第二個東西可以混淆、也不會誤導，唯一的問題是比較口語，不值得為它把英文扭成 `Gloss` 讓使用者天天看到一個不認識的字。

被否決的是 `Gloss`（精準但一般學習者看不懂）與「清單不動、英文加註說明」（中英兩套標準）。

**這是本規格唯一動到 `CONTEXT.md` 領域定義的地方**，依 `docs/agents/domain.md:49` 在此明確點出。29 則的定義段落一個字都不改。

**另記一個已知缺口**：這 29 則的 `_Avoid_` 全是 AI 寫的，維護者不清楚各項在避什麼，因此清單裡可能還有其他丙類甚至寫錯的項目。整份重審是獨立的一件事，本規格不處理、尚未開票。

### 二、翻譯檔一語一檔，漏譯交給 TypeScript 擋

```
src/i18n/
├── zh-Hant.ts   ← 約 193 條
├── en.ts
└── ja.ts
```

兩支翻譯檔用型別釘住要跟 `zh-Hant` 一致：

```ts
import zhHant from './zh-Hant';
const en: typeof zhHant = { ... };   // 少一條就編譯錯
```

`package.json` 的 `build` 與 `typecheck` 都會跑 `tsc --noEmit`，因此**漏譯在建置時就擋下來**，不需要另寫測試。

**被否決的是「一個字串三語並排」**（單檔約 193 組、每組底下三語）。它的優勢是「改文案時三語同時在眼前」與「哪個格子沒填一目了然」，但後者已經被型別擋掉了大半；代價是單檔數百行，而且日後真的重寫成 SwiftUI，iOS 的 `.strings` 本來就是一語一檔，得先拆開才能搬。

**一語一檔還有一個當初沒想到的好處**：決定十四砍掉韓文時，動作就是刪掉一個檔案，其餘兩支一個字都不用碰。並排那種寫法要逐條刪一欄。

### 三、key 用語意命名

`t('books.addButton')`，不是 `t('新增單字本')`。

理由有三：中文文案改字不用動 code；同一句中文在不同語境可以翻成不同的字（「刪除」既是按鈕也是確認對話標題，英文一個要 `Delete` 一個要 `Delete book?`）；而且這個 repo 已經有前例——`list-view.ts:183` 的時間桶就是 `key: 'new'` 與 `label: '新'` 並存。

代價是讀 code 時看不到畫面上實際的字，要跳去 `zh-Hant.ts` 查。收下。

### 四、錯誤改成帶 key 的物件

```ts
throw new AppError('book.scopeEmpty');   // 錯誤本身不再帶文字
```

畫面層拿到 key 之後自己查表變成文字。測試斷言 key，不碰任何語言的文字。

**這是三個選項裡唯一動到架構的。** 現在 25 處 `throw new Error` 的訊息是直接被畫面拿去顯示的，改成物件之後，每一個接住錯誤的地方都要改成「先查表再顯示」。

被否決的兩條：

- **測試改成從翻譯檔取字串斷言**（`toThrow(zhHant['book.scopeEmpty'])`）—— 成本低很多、也解掉假警報，但錯誤物件本身仍綁著某一個語言的文字
- **測試固定跑中文、維持寫死** —— 成本幾乎是零，但中文改一個字就假紅燈，而且與「三語冒煙測試」直接衝突

帶參數的訊息（如 `storage.ts:172` 的「已經有一本叫『${taken.name}』了」）在 `AppError` 上多帶一組參數，查表時代入。

### 五、語言選擇不進備份

存成獨立的 `va-practice:lang`，與 `va-practice:reminder`、`va-practice:reminder-time`、`va-practice:gemini` 同一類。**`DATA_VERSION` 維持 3，備份格式一個字不改。**

這個 app 的設定本來就分兩類：進備份的只有三組範圍選擇（`CONTEXT.md:18`），提醒開關、提醒時間、Gemini 金鑰都在備份之外。語言歸後者。

**主要理由：備份是整份覆蓋**（`CONTEXT.md:110`「較新的那一份整份勝出」）。語言跟著走就等於四台裝置被綁成同一個語言——公司電腦想用英文、家裡 iPad 想用中文，做不到。

**次要理由**：預設值是「系統預設」，新裝置一裝上語言通常就已經對了，真的要重選的只有「刻意選了跟裝置語言不同」的人。

**第三個理由，比較弱但方向一致**：若日後雲端備份真的改成第三方登入，語言的歸宿會是帳號。從獨立 localStorage 搬到帳號是改一處；從 `va-practice:data` 裡搬出來則要再升一次 `DATA_VERSION`，而舊備份裡那個欄位還得繼續認。**好處是暫時的，格式債是永久的。**

（順帶記一筆，實作時會用到：`parseAppData()` 從頭到尾沒讀過 `source.version`。它判斷舊格式靠的是結構特徵——`:264` 看有沒有 `books` 陣列、`:275` 看 `updatedAt` 是不是數字。目前 `version` 是蓋章不是開關。）

### 六、系統預設只看語言主碼

把 `navigator.language` 橫線後面砍掉再比對：

| 拿到的值 | 主碼 | 給 |
| --- | --- | --- |
| `zh-TW`、`zh-HK`、`zh-Hant`、`zh-CN`、`zh-Hans` | `zh` | 繁體中文 |
| `ja-JP` | `ja` | 日本語 |
| 其餘一切（含 `ko-KR`） | | English |

**簡體中文因此算「符合」，給繁體中文。韓文裝置落到英文**——決定十四砍掉韓文之後，`ko` 不再是支援的語言，走「其餘一切」那條。

一條規則管三種語言。被否決的是「分辨繁簡、簡中給英文」——那要為中文額外維護一張白名單，另外兩語卻不用，規則不對稱。而且繁簡差在字形與部分用詞，簡中使用者讀繁中的門檻遠低於讀英文；何況這只是預設值，使用者隨時能自己改成英文。

### 七、日文介面與日文學習內容打架：先不處理，開驗證票

介面切成日文之後，畫面上哪些字是「app 在跟你說話」、哪些是「你要背的卡片」會混在一起。

**現在不決定。** 開一張驗證票（issue 08），`Blocked by` 三語翻譯那張，驗收條件是實機切日文開複習畫面，判定能不能一眼指出哪幾個字是要背的。判定「會混」才開第二張設計票；判定「不會混」就關票、本檔補一行「已實機驗證不需處理」。

理由：這是**紙上判斷不出來的問題**，現在先設計視覺區隔是臆測。而詞條已經有三個很強的區隔特徵——位置在正中央、字級最大、頭上頂著振假名；評分按鈕則在最底部、包在方框裡。

**已知風險**：票開了不代表有人跑。若三語翻譯做完之後沒人執行那張票，實質結果等於「接受、不處理」。

補充兩件事實，供那張票判定時參考：

- **釋義永遠是使用者自己打的字**。日文介面下的畫面不是「全日文」，而是「日文介面 + 日文詞條 + 使用者的釋義」三種混在一起
- **英文介面沒有這個問題**，拉丁字母與日文漢字假名一眼分得開。所以這條完全是日文獨有的，這也是決定十四砍掉韓文之後、剩下三語裡唯一要驗的一種

### 八、`privacy.html` 出中、英兩份

新增 `public/privacy-en.html`。中文版維持現狀，網址不變（`https://brad0924.github.io/va-practice/privacy.html`，票 `ios-app 04` 已定案並上線）。

上架語系的對應：**繁中語系指中文版，日文語系與韓國 storefront 都指英文版。**

日文版隱私政策不做，理由是下一段那個——這頁每一句都跟程式行為綁死，份數越多越容易有某一份過期，而過期的隱私權政策比外語的更糟。介面出日文但隱私政策只有中英，是可接受的落差。

**被否決的是逐語系各出一份。** 這頁的每一句都跟程式行為綁死（票 `ios-app 04` 的工作量有一大半在「把七處與程式碼對不上的地方改掉」），四份同步是長期負債，漏一份就有一份在說謊。而業界慣例是小型 app 只出一份、多半英文；Apple 允許隱私政策網址按上架語系各給一個，但不強制。

**這個 app 幾乎不收集個資**（票 `ios-app 11` 的資料揭露：不收分析數據、無第三方追蹤、端對端加密、無帳號、不收 email），翻譯的實質保護價值因此很低。

**隨之而來的必要工作**：`app-name.test.ts:56-59` 那四條 regex 全都嵌著中文上下文（`<title>隱私權政策 — (.*?)</title>`、`(.*?) · 最後更新` 等），對英文版全部失效。改成用 `data-app-name` 屬性標記那四處，測試抓屬性而不是抓上下文——順便解掉現在「改個換行就紅燈」的脆弱問題。

### 九、`APP_NAME` 不跟著語言切，PWA 描述改英文

`APP_NAME` 維持 `VocabCard` / `Vocabulary Card Practice`，三語通用。票 `app-name 02` 刻意選拉丁字母就是為了這個需求，`ADR-0012` 的單一來源架構完全不用動。

`vite.config.ts:48` 的 PWA 安裝描述從 `'自建單字本，間隔複習，離線可用'` 改成英文，`:49` 的 `lang` 從 `'zh-Hant'` 改成 `'en'`——跟名稱同一國。

**被否決的是「名稱也跟著切」**：`APP_NAME` 要從單一字串改成每語一組，且 iOS 端要加 `InfoPlist.strings` 多語系檔才能讓主畫面圖示跟著變，`ADR-0012` 與 `app-name.test.ts` 那套守門要重做——而票 `app-name 02` 刻意選拉丁字母的理由就消失了。

代價：中文使用者在網頁版的 PWA 安裝提示會看到英文描述。收下，因為那只影響「加到主畫面」那一刻，iOS 上架版走的是 `Info.plist` 不是 manifest。

### 十、語言選單放資料畫面最上面，用 `<select>`

資料畫面新增一段「介面語言」，放在**最上面**（介面語言 → 雲端備份 → Gemini API 金鑰 → 每日提醒 → 手動備份）。理由：語言是「app 用什麼話跟你說」，比其他四段都基礎；而且看不懂畫面的人要找語言選單時，最上面最容易找到。

用 `<select>`。`editor-view.ts:44` 的單字本選擇已經是同一種元件，不是新東西；iPhone 上會叫出系統原生的選取介面，手感不用自己調。

**四個選項用各自的語言寫**：系統預設（跟著當前介面語言變）、繁體中文、English、日本語。

理由很實際：萬一有人手滑切到日文，滿畫面日文的時候他還認得出「繁體中文」那四個字找得回來；用當前介面語言寫的話就變成猜謎。「系統預設」沒有自稱，只能跟著當前介面語言變。

**選了「系統預設」時不顯示目前實際是哪一種**（不做成「系統預設（日本語）」）。那會讓選項文字變成動態的，換到的好處只是省掉使用者自己看畫面判斷。

**被否決的是自製清單**（五行直接列出、選中打勾）。外觀完全可控，但滑動與點擊的手感要自己調到跟原生一樣。若日後想改成自製的彈出面板，落點不在 i18n：純前端做法屬 `.scratch/touch-feel-gaps/`（它會同時影響語言選單與單字本選單，是共用元件問題），呼叫 Capacitor 原生 Action Sheet 才屬 `.scratch/ios-app/`。

### 十一、加一支三語冒煙測試

約 20 行：三語各切一次、主要畫面各渲染一次，只檢查沒有爆炸、畫面上沒有漏出原始 key。

它抓的是**「程式某處拿顯示文字去做判斷」**這類問題——那是 TypeScript 型別擋不到的。其餘的：漏譯已由型別在建置時擋掉；版面被撐爆 jsdom 本來就看不到，那要靠決定七那張實機驗證票。

**不做的是「整套測試跑四遍」**：收益只剩上面那一項，成本卻是測試時間 ×4。

### 十二、`HOME_BOOK_NAME` 產生當下用介面語言，之後屬使用者資料

`storage.ts:23` 的 `'我的單字'` 是**寫進使用者資料**的字串，不是介面字串——它是 `adopt()` 在「匯入沒有歸屬的舊卡」時生出來的那本的名字。

**產生它的當下用當下的介面語言；產生之後它就是使用者資料，切語言不會跟著變**（使用者可以改名，改了名還被程式改回去會很怪）。

影響很小：全新使用者永遠碰不到它（`blank()` 是零本零卡），只有匯入舊格式備份才會長出來。但規格要寫這一行，否則實作時會有人猶豫。

### 十三、資料畫面的名稱不在本輪處理

那個畫面標題叫「資料」（`data-view.ts:54`），但已經裝了 Gemini 金鑰與每日提醒——那兩個都不是資料。加上介面語言之後名實不符會更明顯。

**本輪不改名。** 改名牽動導覽列、測試與使用者習慣，是獨立的一件事。此處記一筆，日後要改是另一張票。

### 十四、砍掉韓文，需求從四語改成三語

`handoff.md` 寫的需求是四種語言（含韓文）。**釘規格的過程中砍掉韓文，改成中／英／日三語。**

**理由只有一個：沒有人驗得了韓文。**

維護者能驗中文與英文，日文也 cover 得了（這本來就是一個 JLPT 工具）。韓文完全沒有人看得懂。而 agent 產得出韓文翻譯，卻**沒有任何驗收條件擋得住翻錯**——`tsc --noEmit` 只看 key 齊不齊，冒煙測試只看有沒有漏出 key，兩者都不判斷文字對不對。原本票 06 的驗收條件「切到每一種語言，五個畫面都沒有未翻譯的中文殘留」只驗「有沒有翻」，不驗「翻得對不對」。

韓文的風險還比一般語言高一層：**敬語階層**。韓文的階層比日文更嚴格，app 對使用者用錯階層的觀感傷害，比英文的語氣問題大得多，而那不是靠「意思對不對」看得出來的。

**被否決的三條：**

- **付費請母語者校對一次。** 約 3900 字是很小的量，而且 UI 字串翻完之後幾乎不會再動，所以這是有界的一次性支出，不是長期訂閱。這條是最乾淨的解法，只是維護者這輪不走
- **照出、不校對，上架後靠使用者回報修。** 成本零，但看到敬語錯亂介面的人通常不會回報，只會直接刪掉
- **標示為機器翻譯或 beta。** 罕見且觀感差

**這不是永久決定。** 日後若備妥了韓文校對者，恢復的成本很小：`src/i18n/ko.ts` 加回來（一語一檔的結構讓它就是新增一個檔）、`glossary.md` 補一欄、主碼比對表加一列、選單加一個選項。agent 的韓文譯名初稿還留在 `issues/01-glossary.md` 的紀錄裡。

**韓國市場沒有跟著砍。** 韓國 storefront 照樣上架，韓文裝置的介面落到英文——砍的是介面語言不是市場，而且英文介面是完整的、不是半成品。App Store 頁面素材因此是繁中、日文兩組，韓國 storefront 用英文（見 `.scratch/ios-app/issues/20`）。

## 這份規格不做的事

- **不做學習內容的多語言**（英文、韓文的單字卡）——見「這不是什麼」
- **不改雲端備份的認證方式**（第三方登入是獨立方向，未開票）
- **不重新設計任何畫面**，除了新增語言選單那一段
- **不改資料畫面的名稱**（決定十三）
- **不動 `CONTEXT.md` 的中文定義**，只在頂端加一句註記
