## 為什麼有這張票

維護者想把這個 app 改成原生。**但釘下去之後發現，動機不是體驗有問題。**

問「『不夠原生』這個判斷怎麼來的」時，答案是兩個：**「我知道它是 WebView，就覺得不對」**，加上**「其實是我想寫原生」**。從頭到尾**沒有列出任何用起來不順的地方**。

這件事本身就是最重要的發現，它把判準換掉了：不是「改完 app 會不會變好」，而是「這是不是好的時間花法」。這張票的所有設計都建立在這個認知上。

### 為什麼不直接重寫

現有的 app 不是玩具：**4,929 行程式碼、5,072 行測試、449 個測試**，網頁版在 GitHub Pages 上跑著，上架流程已走到票 `ios-app 11`。而維護者要學的是全新語言加全新 UI 框架，可用時間只有週末在家那台 Mac。

**把「學新技術」和「重寫五千行正式專案」疊在一起是兩個困難相乘。** 所以先花一個週末問清楚值不值得，而不是押上幾個月。

### ~~為什麼是 Swift／SwiftUI，不是 React Native~~ — 已推翻，見 `## Comments`

React Native 能在 Windows 上天天開發（Expo Go 即時預覽），一度是最合適的路。**但它買不到動機——RN 寫的是 JavaScript**，維護者白天已經在寫 TypeScript，換個框架而已，語言、型別系統、思考方式都沒變。

它能滿足「不再是 WebView」，滿足不了「想寫原生」。所以出局，Windows 上天天開發這條路也跟著出局。

## 要做什麼

用 SwiftUI 做出**複習畫面**，對照 `src/ui/review-view.ts`（166 行）：

| 部位 | 內容 |
| --- | --- |
| 標題列 | 「剩餘 N 張」＋單字本開關（開關可以是死的，不用真的能切） |
| 卡片 | 詞條（**含振假名**，漢字上方標假名）；掀開後顯示釋義 |
| 底部 | 未掀開時一顆「顯示答案」；掀開後換成四顆評分鈕：**再次／困難／好／簡單** |
| 完成狀態 | 三張都答完後顯示「今日份完成」 |

**寫死三張假卡**，其中至少一張要有漢字（才看得到振假名）、一張純假名。按評分鈕就換下一張，不做任何排程計算。

外觀要**盡量對齊現有的網頁版**——這不是美化，是盲測的前提：兩版長得越接近，盲測量到的才越接近「平台差異」而不是「設計差異」。配色抄 `src/styles.css`（背景 `#141821`）。

### 由 agent 寫，不是維護者寫

維護者是 SwiftUI 新手。**自己寫的第一版很可能比現有的 WebView 版還醜**——不是因為 SwiftUI 不好，是因為還不熟。那樣盲測量到的會是熟練度，不是平台差異，判準就被污染了。

維護者在這張票裡**只負責盲測與判定**，不寫程式。代價要講清楚：這一輪他不會知道自己喜不喜歡寫 SwiftUI，那是另一個問題，留給停損之後的小專案。

## 這張票不做的事

- **不接排程、不接儲存、不接雲端。** 沒有 SM-2、沒有到期日、沒有 localStorage 對應物、沒有 Firebase。三張卡寫死在程式碼裡
- **不碰現有的任何程式碼。** `src/`、`ios/`、`vite.config.ts` 一行都不動
- **不承諾重寫。** 這張票結束時唯一的產出是一個決定，不是一個 app
- **不解決 Mac 長期取得的問題。** 這次就在家裡那台上做。遠端連線是「要持續開發」才需要的基礎建設，探路只需要一次；萬一結論是不做，那份工就白做了

## 原型放哪

分支 `prototype/swiftui-review-screen`，從 `feature/ios-app` 開出去。沿用這個 repo 既有的 `prototype/*`／`throwaway/*` 慣例（見 `prototype/stats-snapshot`、`throwaway/toast-styling-prototype`）。做完砍掉，不進 `main`。

Xcode 專案跟純前端 repo 混在一起確實怪，但那是暫時分支，可接受。

## 盲測怎麼做

**這是這張票的核心，不是附註。**

維護者的動機之一是「我知道它是 WebView 就覺得不對」——**這句話等於承認偏誤確定存在**。如果拿著兩台、心裡清楚哪台是親手寫的原生版，一定會覺得它比較好，那判準就沒有否決能力。所以必須盲測：

1. **兩版都裝上同一支 iPhone**：SwiftUI 原型從 Xcode 裝；網頁版用已安裝的 PWA 或 TestFlight
2. **網頁版先對齊**：在現有 app 裡手動建一本、加上原型那三張一樣的卡，讓它進到複習畫面時內容相同（不用改任何程式碼）
3. **不標示哪個是哪個**，把兩個圖示放在一起、名字都遮掉或排在一起分不出來的位置
4. **隔一天再拿起來滑**，不要當天做——剛寫完的印象太強
5. 判定：**分不分得出來哪個是原生的**

## 判定之後

**分得出來** → 這個方向值得投入，才進入下一串問題（Mac 長期怎麼取得、網頁版留不留、重寫要多久）。**那三題現在刻意不釘**，沒通過盲測就不需要答案。

**分不出來** → **停。** 這個 app 維持 WebView，把結論寫成 ADR——順便補上 `docs/adr/` 現在缺的那份「為什麼選 WebView」（目前 12 份 ADR 裡一份都沒記載這個決定）。想寫原生的欲望另外找小專案滿足，不由這個 app 承擔。

**停損條件現在就寫死，是因為做完當天的維護者已經花了一個週末，那時候的他不會想承認白做。**

## Comments

### 2026-08-18 — 轉 `wontfix`，改做 React Native 原型

一場 `/grill-with-docs` 把本票「為什麼是 SwiftUI，不是 React Native」那段推翻了。推翻的是**理由**，不是方法——本票的探路加盲測結構原封不動搬去新票。

**本票當初的推理錯在哪。** 它寫「RN 買不到動機，因為 RN 寫的是 JavaScript」，把動機當成單一的一件事。實際問下去，動機是兩件可以拆開的東西：

- **想學新語言** → RN 買不到（還是 TypeScript），Flutter 買得到（Dart），SwiftUI 買得到
- **畫面要是系統原生元件** → RN 買得到（`<Text>` 變 `UILabel`），**Flutter 買不到**（自繪引擎，與 WebView 同類），SwiftUI 買得到

維護者選的是第二個。本票沒有做這個分辨，所以把 RN 誤判出局。

**連帶三件事：**

1. **Flutter 出局**，而且理由跟本票寫的不同——不是「多背一層框架」，是它與 WebView 同樣不使用原生元件，犯的是同一條。
2. **RN 不是從零重寫。** 本票與 `ios-app/spec.md` 都假設任何重寫都得丟掉全部程式碼。RN 同為 TypeScript，純邏輯 3,638 行與其 4,732 行測試可搬，要重寫的是畫面層 2,373 行。訂正見 `../../ios-app/spec.md` 決定一底下那則。
3. **「只能在 macOS 上執行」這個限制在 RN 上消失。** 本票開頭那個警告框的成本（Xcode、Mac、一個週末）是 SwiftUI 才有的。RN 用 EAS Build 在雲端編譯，Windows 上就能做出可裝進 iPhone 的獨立 app——盲測需要獨立 app（用 Expo Go 會露餡），這條路走得通。

**沒有推翻的部分**（新票原樣沿用）：由 agent 寫而非維護者寫、寫死三張假卡、外觀對齊網頁版、盲測隔天判定、停損條件現在就寫死。

**一個 grill 中確認的事實**：維護者每天都在用 Capacitor 版，`ios-app` 的 16 張票（Keychain、原生語音、觸覺、每日提醒）都已 `done`。問他哪裡不順，答案仍然是**講不出來**。本票第 19 行「從頭到尾沒有列出任何用起來不順的地方」在十天後依然成立。停損條件因此比當初更重要，不是更不重要。
