# 「再次」重排回佇列的卡，重整頁面後消失，複習不到

Status: done
Type: bug

## 回報

> 我如果把單字標了「再次」，剩餘 X 張的數字不會減少，繼續學習，該單字也會繼續出現讓我重新練習，但重整頁面，被標為「再次」的單字馬上就會不見，不讓我重新學習。

## 跟 `date-rollover/01-stale-date-on-rollover.md` 的關係

表面上都跟「頁面重整／重建佇列」有關，但根因不同：

- issue 01 講的是**該重建的時候沒重建**（跨午夜後 `now()` 沒被重新讀取，佇列停在前一天）。
- 這張講的是**重建了，但重建依據漏資訊**，跟跨日完全無關，同一天內任何時候重整都會發生。

## 根源

`src/lib/review.ts` 的 `rate()`：

```ts
const rest = queue.slice(1);
return {
  card: updated,
  queue: rating === 'again' ? reinsert(rest, updated, random) : rest,
};
```

按「再次」時，兩件事同時發生，但只有一件被存起來：

1. `updated.due` 被設成**明天**（`interval` 重設為 1 天）——這是長期排程要用的最終狀態，會被 `app.advance()` 存進 `localStorage`。
2. `reinsert()` 把這張卡塞回**記憶體中**目前這份佇列的後半段，讓它「今天稍後」還會再出現一次——這個「今天還要再考一次」的狀態**只存在記憶體裡，沒有進 `localStorage`**。

`剩餘 X 張不會減少、會繼續出現在今天的佇列裡`是刻意的設計（`src/lib/review.test.ts:168` 有測試涵蓋），這部分沒問題。

問題在重整（或任何造成 `src/app.ts` 的 `start()` 重跑的情況，例如關掉分頁再打開）：

```ts
let data = store.load();
let queue = buildQueue(data.cards, now(), random);
```

`store.load()` 讀回的卡片，`due` 已經是明天；`buildQueue()` 只認 `due <= 今天`，於是這張卡直接被濾掉，從今日佇列裡消失。使用者以為「再次」的卡還會再出現，結果永遠等不到。

## 重現步驟

1. 進入複習畫面，任選一張卡標「再次」。
2. 觀察：剩餘張數沒變，這張卡稍後確實會再輪到（記憶體內佇列正常）。
3. 重整頁面（或關閉分頁重開）。
4. 這張卡從今日佇列消失，即使它理論上「今天還要再考一次」。

## 待決定

修法牽涉一個設計決定，不是單純的程式錯誤：

1. **重整後，「再次」的卡該不該繼續留在今天的佇列？**
   - **選項 A**：「再次」時 `due` 改設為今天（不是明天），讓 `buildQueue()` 重整後仍撈得到它，同時滿足「今天再考一次」的需求。需要確認：這樣改會不會影響「今天沒複習完就結束、下次登入」時的長期排程意義（`interval` 重設為 1 天這件事本身要不要跟著調整）。
   - **選項 B**：把「今天還要再考一次」這個暫存狀態額外持久化（例如把當前佇列本身也存進 `localStorage`，重整後還原佇列，`due` 照樣設明天，長期排程不受影響）。

## Agent Brief

**Category:** bug
**Summary:** 「再次」評分的卡在頁面重整後會從當日複習佇列消失

**Current behavior:**
使用者對一張卡按「再次」時，系統會做兩件事：(1) 把卡片的到期日設為明天，做為之後正式排程的依據；(2) 把這張卡插回目前這份記憶體內佇列的後半段，讓它當天稍後還會再出現一次進行複習。第二件事只存在於記憶體中的佇列，不會被持久化。因此重整頁面（或關閉分頁重開）後，系統會根據持久化資料重建佇列，只認到期日「小於等於今天」的卡；由於這張卡的到期日已經是明天，它會被排除在外，即使使用者原本預期今天還會再看到它一次。

**Desired behavior:**
「再次」評分後，這張卡的到期日應設為當天（而非明天），讓頁面重整後重建的佇列仍然包含這張卡，維持「今天還會再出現一次」的預期。用來決定下次正式評分（好／困難／簡單）間隔大小的內部狀態（間隔天數）不應受影響，仍以「再次」原本設定的值作為之後計算的基準——也就是說，只有到期日的計算方式改變，這張卡的長期排程進度不變。

**Key interfaces:**
- 評分函式（目前叫 `rate()`，接收目前佇列、評分、當下時間、亂數，回傳更新後的卡片與佇列）：「再次」評分分支計算到期日的邏輯需要獨立於其他評分（好／困難／簡單）——後者維持「複習日期 + 新間隔天數」不變，只有「再次」改成「複習日期當天」。
- `Card` 型別的 `due` 欄位語意因此在「再次」評分下出現一個刻意的例外：`due` 不再等於「複習日期 + 間隔」，而是複習當天；`interval` 欄位不受影響。這個例外已經記錄在 `CONTEXT.md` 的「到期（Due）」定義裡，可以參考該定義確認語意。

**Acceptance criteria:**
- [x] 對一張卡評「再次」後，回傳的卡片到期日等於評分當下的日期（同一天），不是隔天。
- [x] 對一張卡評「再次」後，回傳的卡片間隔天數維持原本「再次」既有的計算結果（不因這次修改而改變）。
- [x] 用評「再次」後得到的卡片資料，在同一天內以「依到期日篩選、重建佇列」的邏輯重新建立佇列，這張卡仍然會被納入佇列。
- [x] 既有測試中斷言「再次」評分後到期日為隔天的案例，需更新為「複習當天」，其餘既有測試（尤其是驗證間隔天數、成長倍數、佇列重排順序的測試）維持通過不變。
- [x] 「好」「困難」「簡單」三種評分的到期日計算方式不變（仍是複習日期 + 新間隔天數）。

**Out of scope:**
- 不處理「重整後佇列洗牌順序」的落差——重整前「再次」的卡會被安排在記憶體佇列的後半段以避免馬上重複出現；重整後，所有當日到期的卡一律隨機洗牌，不特別為這張卡保留「後半段」的順序保證，這是可接受的行為，不需修正。
- 不改動觸發佇列重建的機制本身（例如頁面重整、匯入資料等呼叫路徑）——這次修法完全發生在卡片資料本身（到期日欄位）的計算方式，不需要調整佇列重建的觸發邏輯。
