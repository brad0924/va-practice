# 跨日之後 App 不會重整，佇列與列表都停在前一天

Status: done
Type: bug

## 問題

這個 App 假設每次使用都是一次全新的頁面載入。時間只在特定時機取一次，之後不再更新，因此跨過午夜後整個 App 仍停留在前一天的判定。

根源在 `src/app.ts`：`now` 本身是每次呼叫都回傳新時間的函式，但呼叫它的地方太少。

同一個根源產生兩個症狀，嚴重度差很多。

### 症狀一：複習佇列不重建（嚴重）

`buildQueue()` 在 `start()` 中只執行一次，此後除了匯入備份會觸發 `reload()` 之外，佇列不再重建。`src/main.ts` 也沒有 `visibilitychange`、`pageshow` 或 `focus` 的處理，頁面回到前景不會重新載入。

發作情境：

> 晚上 11:50 打開 App，今天有 5 張到期，佇列裝了那 5 張。
> 複習 3 張後午夜過去。繼續把剩下 2 張做完，畫面顯示「今日完成」。
> 但新的一天其實有 8 張到期，一張都沒出現——使用者以為收工了，實際上今天還沒開始。

要恢復正常必須讓頁面重新載入。這裡有一個**尚未確認的事實**：此工具以 PWA 形式加入手機主畫面，打開時不一定會重新載入——系統若仍保留該頁面，會直接回到上次離開的畫面，`start()` 不會重跑。手機系統保留多久會因裝置、記憶體壓力與作業系統而異，未經實測。

這決定了嚴重度：若每次打開都是全新載入，此問題僅在「跨午夜當下 App 還開著」時發作；若 PWA 經常跨天存活，則每天都會發作。

### 症狀二：列表頁的 now 過期（輕微）

`listView()` 中的 `const now = app.now()` 在建立畫面時取一次。但 `showList()` 每次都重建整個畫面，因此切換頁面、編輯卡片後返回、匯入資料後，時間都會更新。

唯一過期的情況是「打開列表頁後放著不動，跨過午夜」。症狀是逾期天數少算一天、「今日到期」實為前一天的判定。不會出錯，只是數字舊了。

## 為什麼不能只修症狀二

目前兩處是一致的錯（都停在前一天）。若只更新列表的時間而不重建佇列，會產生新的矛盾：列表顯示 8 張今日到期，點進複習卻只看得到昨天那份佇列，複習完仍顯示「今日完成」。使用者更難理解發生什麼事。

## 待決定

1. **偵測時機**：頁面回到前景時檢查日期是否改變（涵蓋所有情境），或僅在進入複習頁時檢查（較簡單，但停在複習頁不動仍不準）。
2. **複習到一半跨午夜該不該打斷使用者**。佇列重建會讓當前這張卡消失或順序改變。是立即重建、等當前這張評分後再重建、還是提示使用者自行決定，尚未討論。
3. **實測 PWA 的存活行為**再定嚴重度。建議實際使用數日，觀察隔天打開時是否為全新載入。

在第 2 點有答案之前不宜進入實作，否則等於讓 agent 替使用者決定中斷體驗。

## Agent Brief

**Category:** bug
**Summary:** 跨過午夜後，複習佇列與各畫面的日期判定停在前一天

**Current behavior:**

App 啟動時依當下日期建立複習佇列。此後只有三條「整份資料被換掉」的路徑會重建佇列（匯入單字、整份匯入備份、雲端拉下較新的資料）。日期本身的改變不觸發任何重建。

因此跨過午夜之後：

- 複習佇列仍是前一天那份。當日新到期的卡不會出現；做完前一天那份後畫面顯示「今日份完成」。切換畫面救不回來，只有整個 app 重新載入才會恢復。
- 卡片列表的時間桶、統計畫面的數字同樣在建立畫面時取一次時間。停在該畫面不動跨過午夜，兩者都停在前一天的判定。

跨日後直接評分時，評分本身用的是新日期、算出的到期日與間隔都正確；錯的只有複習佇列。

**Desired behavior:**

App 應自行察覺「建立目前這份複習佇列時的日期」與「現在的日期」不同，並在察覺的當下重建複習佇列，然後重畫目前畫面。

檢查發生在兩處：

1. app 回到前景時
2. 使用者評分前，且必須在評分實際作用於佇列之前——使用者評的那一張要是當日佇列裡的那一張

檢查必須冪等：日期沒變時不做任何事，佇列順序不得被重洗。

重建時保住使用者正在看的那張卡（若它仍到期），連同其掀開狀態一併保留。不跳提示、不詢問、不中斷。

訊號來源兩條，都接到同一個檢查：

- 網頁的可見性變化事件
- iPhone 原生端在 app 回到前景時主動送出的訊號

兩條同時到達時的結果，必須與只到一條相同。

**Key interfaces:**

- 建立複習佇列的那支純函式（吃卡片、當下時間、亂數，吐佇列）與「重建但保住正在看的那張」的那支（換複習範圍時已在用）都不需要改。跨日重建應重用後者，不要重寫一份。
- 應用層需要多記一個狀態：**目前這份佇列是依哪一天建立的**。值的形式應與卡片到期日同一種日期字串（只到日、不含時刻），與判定到期用的是同一把尺，避免出現「時間戳說跨了、日期字串說沒跨」的邊界矛盾。所有建立或重建佇列的路徑都必須同步更新它——目前有三處（啟動、整份換掉資料、複習範圍變動）。分散更新容易漏，建議把「重建佇列」與「記下日期」綁成同一個動作。
- **跨日檢查不可重用既有的「整份資料被換掉」那條重整路徑。** 那條會重讀本機儲存、清掉掀開狀態、重排每日提醒；跨日這三件事都不需要，而清掉掀開狀態會直接打斷使用者。兩者語義不同：一個是「資料被換掉了」，一個是「資料沒變但判定基準變了」。
- 可見性事件掛在 `document` 上，不是 `window`。這個監聽器屬於應用層級（全 app 註冊一次、與 app 同生共死），與既有的連線恢復監聽器同一類；ADR-0011 分的是畫面層與元件層，不涵蓋這一類，但其判準（有沒有天然的解除時機）支持這個做法。
- iPhone 原生端需新增一支自訂插件，在 app 回到前景時通知網頁層。沿用專案既有的自訂插件模式：原生實作留在本 repo 的 iOS 專案內，不引入額外 npm 依賴（不使用 `@capacitor/app`）。網頁版應拿到一個什麼都不做的東西，與其餘原生功能同一個立場。

**Acceptance criteria:**

- [ ] 前一天建立的佇列，在跨過午夜後 app 回到前景時會重建，當日新到期的卡出現在佇列中
- [ ] 跨過午夜後不切走 app、直接評分，評分作用在已重建的當日佇列上
- [ ] 日期未改變時，回到前景與評分都不重建佇列，佇列順序不被重洗
- [ ] 重建時使用者正在看的那張卡若仍到期，仍留在最前面，掀開狀態保留
- [ ] 跨日重建不跳任何提示或對話框
- [ ] 停在卡片列表跨過午夜，重建後時間桶反映新的日期
- [ ] 停在統計畫面跨過午夜，重建後統計數字反映新的日期
- [ ] 網頁與 iPhone 兩條訊號來源都接上；兩條同時觸發的結果與觸發一次相同
- [ ] 上述行為有自動測試涵蓋（可用假時鐘推進系統時間，從 app 啟動演起）
- [ ] 既有測試全數通過

**Out of scope:**

- 「一天從幾點開始」的設定（例如凌晨 4 點才換日，Anki 有此設定）。這是獨立的產品決定，要做另開票。
- 任何持續執行的計時器或輪詢：不新增定時器來追蹤日期變化。
- 每日提醒的排程邏輯不變。跨日重建不需要重排提醒。
- 評分本身的到期日與間隔計算不變。
- 「再次」評分的佇列行為不變（見 `.scratch/again-requeue-lost-on-reload/issues/01`，已 done）。

## 實作紀錄

**應用層多記一格日期。** `src/app.ts` 的 `queueDate` 記著「目前這份佇列是依哪一天建的」，值是 `toDateKey()` 的日期字串，與卡片到期日同一把尺。建佇列與記日期綁成同一支 `rebuild()`，四條路徑（啟動、整份換掉資料、複習範圍變動、跨日）全部走它，沒有第二個地方寫得到那一格。

**檢查點兩處，訊號兩條，都打到 `rebuildIfNewDay()`。** 日期相同時它一件事都不做並回傳 false，呼叫端據此決定要不要重畫；因此兩條訊號同時到達與只到一條結果相同。`applyData()` 原本那三行「重建並在隊首換人時蓋回答案」抽成 `rebuildKeepingCurrent()`，跨日與換複習範圍共用同一份。

**沒有重用 `reload()`**，理由照 Agent Brief 寫的那條：語義不同，且它會清掉掀開狀態。

**原生那一支是 `Foreground`**（`ios/App/App/ForegroundPlugin.swift`），一支方法都沒有、只送事件，聽的是 `UIApplication.willEnterForegroundNotification`。網頁層的接線在 `src/lib/foreground-native.ts`，網頁版拿到的是什麼都不做的那一個。

**重畫會洗掉的東西，記在這裡。** 跨日重建之後會重畫目前畫面，而這個 app 的重畫是整片重掛，只活在畫面裡的狀態會回到預設：

- 編輯器打到一半的草稿沒了
- 卡片列表的排序方向、展開的桶、搜尋框的字回到預設（`src/ui/list-view.ts` 那三個 `let`）

兩項都只在「跨過午夜的那一下剛好停在該畫面」時發生。這條路本來就存在——語音清單載入完成（`initSpeech`）與雲端拉到新資料時同樣會重畫（見 ADR-0011 提到的那兩處），跨日只是第三個觸發點，沒有為它另外開例外。

**自動測試** 收在 `src/app.test.ts` 的「跨過午夜」，八條，都從 `start()` 演起、用假時鐘把系統時間推過午夜。

「日期沒變就不重建」（回到前景與評分各一條）是靠「一次亂數都沒抽」驗的：洗牌是建佇列唯一用到亂數的地方，而畫面上分辨不出來——重建會保住手上那張，隊首兩種情況下都一樣。**那個 spy 必須早於 `boot()`**：`start()` 在開機的那一刻就把 `Math.random` 抓進手裡，晚一步接上的話 spy 根本不在路上，斷言會恆真。第一版就是這樣寫的，code review 抓出來；改好之後拿「拿掉日期判斷」驗過，三條會確實轉紅。

## 實機驗收流程（維護者執行）

實作完成、自動測試通過之後，由維護者在 iPhone 上跑這一輪。

### 準備

1. 確認手邊資料同時有「今天到期」與「明天到期」的卡各數張，張數不同才分辨得出來（例如今天 2 張、明天 5 張）
2. 打包上 TestFlight，裝到 iPhone

### 測試 A：回到前景會不會更新（主要）

1. 打開 app，把今日份複習完，畫面顯示「今日份完成」
2. 按 Home 鍵離開 app。**不要從多工把它滑掉**——滑掉等於冷啟動，那條路本來就正常，測不到東西
3. 設定 → 一般 → 日期與時間 → 關掉「自動設定」→ 把日期往前調一天
4. 從主畫面點回 app

**預期：** 剩餘張數立刻變成明天那批的張數，複習畫面出現卡片。

**判讀：**

| 看到的 | 意思 |
| --- | --- |
| 切回來剩餘張數立刻變 | 正常。兩條訊號至少有一條有送 |
| 切回來沒變，但按下評分後變了 | 兩條訊號都沒送，第二個檢查點接住了。要追原生那條為什麼沒送 |
| 兩種都沒變 | 與訊號無關，檢查邏輯本身有問題 |

兩條訊號一起做的代價：這個測試分辨不出是哪一條起了作用。這不影響結論——有一條有效就夠了。

### 測試 B：整晚在前景（選配，只能等自然跨日）

這一項沒辦法用改日期的方式測：改日期必須離開 app，而離開再回來就先觸發了第一個檢查點。

想測的話只能等真的跨午夜：

1. 設定 → 螢幕顯示與亮度 → 自動鎖定 → 永不
2. 睡前打開 app，停在複習畫面，留幾張卡不要做完
3. 隔天早上不要切走 app，直接對畫面上那張卡評分

**預期：** 評分後剩餘張數變成新的一天那批。

測試 A 若通過，這一項是純保險，可以略過。

### 收尾

1. 設定 → 一般 → 日期與時間 → 把「自動設定」打開
2. **把每日提醒的開關關掉再打開一次。** 提醒排在 iOS 系統層、依當時的日期排未來 7 天；改過系統日期之後那批可能排在錯的時間。關掉再開會整批重排。
   （此處為依排程寫法所做的推論，未實測。當成「可能會亂」而非「一定會亂」。）

### 網頁版順帶驗一次

修法涵蓋兩邊，網頁版用同樣的方式驗：桌機開著 app 把今日份做完 → 改系統日期往前一天 → 切到別的分頁再切回來 → 看剩餘張數有沒有變。

**兩個會讓人白追一輪的坑**，實測時各踩到一次：

1. **PWA 第一次打開跑的還是舊程式。** service worker 有一層離線快取，部署完之後的第一次啟動仍是舊的那份，關掉再開一次才換上新的。實測時第一次「沒反應」、第二次就正常，程式一個字都沒改。驗網頁版之前先確定手上跑的是新版——最省事的分辨法是直接按評分：張數會變就表示程式在，只是訊號沒送。
   （快取確切在哪一刻換新的未實測，只確定「再開一次就對了」。）

2. **桌機上「另一個視窗蓋上來」不算離開。** 可見性變化事件只在切分頁與視窗縮到最小時送；被別的程式的視窗蓋住時，瀏覽器仍算「看得見」，事件不送、檢查不跑。因此桌機要驗這件事，只能切分頁，不能靠「開設定改日期再切回來」——那條路在桌機上接不到，得靠第二個檢查點（評分前）。

## 驗收結果（2026-08-17）

iPhone 原生 app：測試 A 通過，切回 app 剩餘張數立刻變。
iPhone PWA：第二次啟動後通過（第一次踩到上面第 1 個坑）。
兩條訊號至少有一條有送，本票的目的已達成；分辨不出是哪一條，也不需要分辨。
