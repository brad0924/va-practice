# 詞條與釋義互相帶路：填完一欄就把游標送到空的那一欄

Status: done
Type: enhancement

## 需求

在 iPhone 上新增卡片時，填完一欄要換到另一欄得自己用手指點。使用者的用法是「看現在輸入法是什麼決定先打哪個」——中文注音時先打釋義、日文九宮格時先打詞條，兩種都會發生，所以兩個方向都得能自動帶路。

觸發的動作是 **iPhone 虛擬鍵盤右下角那顆打勾**。實測確認它在本專案的表單裡**只收鍵盤、不送出表單**（使用者回報：按下去鍵盤收起來，畫面其他都沒動）。程式看不到「使用者按了打勾」這件事，看得到的只有輸入框的 `blur`。

另外，現況按下儲存碰到空欄只會出紅字「詞條與釋義都要填。」，游標留在原地不動，還是得自己去點。這條路一併補上。

## 決定

### 兩條觸發路線

**路線一：失焦（`blur`）——主要需求**

```
離開詞條：詞條有值 且 釋義空 → 焦點跳釋義
離開釋義：釋義有值 且 詞條空 → 焦點跳詞條
其他情況 → 不跳
```

**路線二：儲存（Enter／「儲存」／「儲存並繼續」）**

```
詞條空 → 紅字「詞條與釋義都要填。」＋焦點跳詞條，不存
釋義空 → 紅字「詞條與釋義都要填。」＋焦點跳釋義，不存
都有值 → 照舊往下走（讀音格驗證 → upsert）
```

### 逐條

1. **兩條路都做。** 使用者原始需求是路線一（手機打勾）；路線二是討論中順手補的，現況只出紅字不指路。兩條共存，不是二選一。

2. **失焦跳轉的前提是「離開的那一欄有值」。** 一開始寫成「有空欄就跳」，但兩欄都空時會爆掉：焦點在詞條按打勾 → 釋義空 → 跳釋義 → 再按打勾 → 詞條空 → 跳回詞條 → 鍵盤永遠收不掉，來回彈。加上「離開的那欄要有值」就沒事了，而且這正是使用者原話「**輸入完**解釋，判斷單字欄位是否為空」裡「輸入完」三個字的意思。

3. **失焦跳轉只掛在詞條與釋義兩欄，讀音格失焦不跳。** 改完假名按打勾通常是想收鍵盤看預覽對不對（`ADR-0005` 要求讀音預填的結果儲存前一律人工確認），這時被彈到釋義、鍵盤又擋住畫面很煩。

4. **焦點若落到其他輸入框就不跳**（`blur` 的 `relatedTarget` 是可輸入元素時直接 return）。沒有這條這功能會壞掉：新增卡片時釋義必定是空的，使用者一點進讀音格就會被彈走，讀音格永遠碰不到。桌機按 Tab 也走這條，因此 Tab 的既有順序完全不受影響。

5. **失焦跳轉不出紅字。** 打完一欄按打勾時使用者根本還沒說要儲存，這時候念他「詞條與釋義都要填」等於每張卡都被罵一次，紅字會貶值成常態。紅字只留給真正按下儲存那一刻。

6. **紅字措辭不改**，維持「詞條與釋義都要填。」，不改成指名缺哪一欄。

7. **路線二三個入口一視同仁。** Enter、「儲存」、「儲存並繼續」共用同一套，不分鍵盤滑鼠。「儲存」是 `type="button"` 自己綁 click、另外兩個走 `form` 的 submit，實作上是兩個地方，行為必須一致。
   （**已修訂**——實測後 Enter 從這一套裡分出去了，見下方〈實測結果與修訂〉。）

8. **編輯既有卡也套用。** 使用者原話只講新增，但同一支 `editor-view.ts` 也負責編輯，把釋義刪光按儲存同樣會撞到，沒理由只幫新增帶路；而且要排除反而得多寫條件。實務上編輯時兩欄都有值，路線一幾乎不會觸發。

9. **讀音格驗證（第二道關卡）維持現狀**——出紅字，焦點不動。讀音格的錯可能一次好幾個，跳第一個未必是使用者要改的；而且錯誤訊息本身已經點名是哪串漢字（「大丈夫 這串漢字的讀音要麼全部填、要麼全部留空」），不指路也找得到。

10. **只替左上「取消」防點空。** iPhone 上鍵盤還開著時直接點按鈕，`blur` 先發生、焦點跳走、畫面捲動，按鈕在 `touchend` 前就移位了，這一下 click 不會觸發。三顆按鈕都會中，但兩顆儲存白按的結果（焦點跳到該填的欄）跟真按到（紅字＋焦點跳到該填的欄）差不多，只少一行紅字；「取消」白按卻是「想離開卻被拉回輸入框、鍵盤又彈出來，得再點一次」，沒有便宜可佔。作法是在取消按鈕上掛 `pointerdown` 立旗子，該次 `blur` 不跳。

11. **「空」的定義沿用現況**：`trim()` 後為空字串。只打空白鍵算空。

12. **桌機不另外分。** 桌機點畫面空白處也會觸發跳轉。跟手機同一套規則，不加平台判斷。

### 被放棄的替代方案

- **只在按下儲存時檢查**（最初的方向）——漏掉使用者真正要的手機打勾情境。
- **失焦跳轉也出紅字**——正常填卡流程每張都會閃一次紅字。
- **紅字改成指名缺哪一欄**（「還沒填釋義」）——使用者選擇維持單一句。
- **只做新增、不做編輯**——同一張表單兩套行為。
- **只跳單一方向（釋義 → 詞條）**——可以完全避開跟讀音確認打架，但不對稱、難解釋，而且使用者有一半的時候先打詞條，那一半就享受不到。
- **詞條含漢字時不跳**（有讀音要確認就別打擾）——同一個動作時而跳時而不跳，比不跳還難預測。
- **讀音格失焦也跳／讀音驗證失敗也跳焦點**——見決定 3、9。
- **三顆按鈕都防點空**——見決定 10。

## 已知風險：iOS 可能不讓程式主動叫出鍵盤

iOS Safari 限制 `focus()` 只有在使用者手勢的呼叫堆疊中才會連帶叫出虛擬鍵盤。「按虛擬鍵盤的打勾 → 觸發 `blur` → 在 handler 裡 `focus()` 另一欄」算不算使用者手勢，查文件無定論，只能實測。三種可能：

| 結果 | 現象 | 後續 |
| --- | --- | --- |
| 完全成功 | 焦點跳過去，鍵盤不收，直接接著打 | 收工 |
| 一半 | 焦點跳過去了，鍵盤收掉，要再點一下 | 可接受？由使用者判斷 |
| 無效 | 什麼都沒發生 | 得換做法，另開一張票討論 |

**實作完的第一件事是在 iPhone 上按一次確認落在哪一格。**

（**已實測，落在「一半」。** 但同時發現鍵盤上還有另一顆鍵可以走到「完全成功」，見下方〈實測結果與修訂〉。）

## 驗收

`npm test` 全綠。畫面層照 `docs/spec.md` 慣例不寫自動化測試，其餘靠實測。

**iPhone（主要情境）**

- 新增卡片頁，詞條打「焦がす」、釋義空著，按鍵盤打勾 → 游標跳到釋義，**沒有**紅字。
- 承上，鍵盤沒收掉、可以直接接著打釋義（若鍵盤收掉了 → 落在「一半」，回報）。
- 新增卡片頁，釋義打「燒焦」、詞條空著，按打勾 → 游標跳到詞條，沒有紅字。
- 兩欄都填好後按打勾 → 游標不動，鍵盤收起來。
- **兩欄都空**時連按打勾兩三次 → 游標不動，鍵盤收得掉，不會來回彈。
- 詞條打完、點進讀音格改假名 → 不會被彈到釋義。
- 讀音格改完按打勾 → 游標不動，鍵盤收起來，看得到預覽。
- 詞條打完、鍵盤還開著時直接點左上「取消」→ 一下就離開，不會被拉回輸入框。

**任何裝置**

- ~~只填詞條，按 Enter → 紅字「詞條與釋義都要填。」＋游標落在釋義，卡沒有被存。~~
  **已修訂：**只填詞條，按 Enter → 游標落在釋義，**沒有**紅字，卡沒有被存。
- 只填釋義，點「儲存並繼續」→ 紅字＋游標落在詞條。
- 兩欄都空，點「儲存」→ 紅字＋游標落在詞條。
- 兩欄都填好 → 三個入口的行為與現況完全一致（存卡、toast、返回）。
- 讀音格只填一半按儲存 → 紅字「… 這串漢字的讀音要麼全部填、要麼全部留空」，**游標不動**。
- 編輯既有卡，把釋義刪光按「儲存」→ 紅字＋游標落在釋義，沒有回到列表。
- 桌機在詞條按 Tab → 焦點照既有順序走到下一個元素，不會被搶到釋義。

## 實測結果與修訂

在 iPhone 上裝了一支拋棄式的畫面內事件記錄（Windows 接不到 Safari 除錯器）量出來的。

### 量到什麼

**開票時把兩顆不同的鍵當成同一顆了。** 使用者說的「鍵盤右下角那顆打勾」其實是浮在鍵盤上方那條橫條（`∧ ∨ ✓`）最右邊的**「完了」**，不是九宮格鍵盤本身的鍵。

| 鍵 | 是什麼 | 網頁收到的事件 | 結果 |
| --- | --- | --- | --- |
| `✓`（鍵盤上方橫條右端） | iOS「完了」，純系統 UI | **只有 `blur`**，沒有任何按鍵事件 | 焦點跳了、鍵盤收掉＝「一半」 |
| `↵`（九宮格右下角） | 真按鍵，會送出表單 | `keydown` Enter | 焦點跳了、**鍵盤留著**＝「完全成功」 |

`✓` 的記錄（可視高 664＝沒鍵盤、317＝鍵盤在）：

```
8898 --- 可視高 664        ← 鍵盤收掉
8415 詞條 blur 到=null      ← 網頁只收到這一件
8412 釋義 focus 到=null     ← 跳轉確實有跑
```

因此「把跳轉改掛在那顆鍵上」這個備案**沒有鍵可掛**，`focus()` 叫不回鍵盤這件事在 `✓` 這條路上無解，決定 1～12 全部維持。

順帶驗到：兩欄都空時按 `✓` 只有 `詞條 blur`、沒有 `釋義 focus`，不會來回彈。

### 修訂：Enter 從路線二分出去

`↵` 能達成原始需求，但它照決定 7 走的是路線二，會出紅字——而決定 5 不要紅字的理由（每張卡都被念一次、紅字貶值成常態）在這裡一字不差地適用。開票時以為這條路不存在，才只把那條規矩套在失焦上。

**修訂後：**

```
Enter（含 ↵）在詞條或釋義上：
  有空欄 → 焦點跳到由上而下第一個空欄，不出紅字、不儲存
  都有值 → 照舊送出（讀音格驗證 → upsert）
「儲存」／「儲存並繼續」：完全不變，仍出紅字
讀音格上的 Enter：不攔，仍照舊送出表單
```

分家的理由：**按鈕是「我要存」，Enter 是「我要往下走」**，兩者本來就不是同一個意圖。代價是決定 7 的「三個入口一視同仁」不再成立，換來的是 `↵` 變成手機上真正好用的換欄鍵，桌機連著加卡的流程也一起變順（詞條 → Enter → 釋義 → Enter → 存好）。

組字中的 Enter（`isComposing`）不攔，那是輸入法在確定候選字。

### 追加驗收

- 詞條填好、釋義空著，按 `↵` → 游標跳到釋義、**鍵盤不收**、沒有紅字、卡沒被存。
- 承上，接著打釋義再按 `↵` → 卡存進去，行為與「儲存並繼續」一致。
- 兩欄都空按 `↵` → 游標留在詞條，沒有紅字，鍵盤不收。
- 讀音格上按 `↵` → 照舊送出表單（空欄時仍出紅字）。
- 桌機用注音打釋義，選字時按 Enter → 只是確定候選字，不會跳欄也不會送出。

- 實作時擴大了決定 4 的守門範圍：不跳的條件從「`relatedTarget` 是可輸入元素」改成
  「是可輸入元素**或落在讀音區內**」。原寫法漏掉讀音區的合併縫 `⊕` 與拆開縫 `·`——
  它們是 `button`，排在讀音格輸入框前面，因此「編輯既有卡（多漢字一格）＋釋義清空＋
  在詞條按 Tab」會直接被彈到釋義，違反驗收最後一條。決定 4 給的理由是「一點進讀音格
  就會被彈走」，縫本來就是讀音格的操作，照理由擴大而非照字面實作。

- 仍存在、且屬於決定 10 已接受的同一類代價：iPhone 上焦點在詞條、鍵盤還開著時直接點
  讀音區的縫，`relatedTarget` 會是 `null`（Safari 點按鈕不給焦點），因此該次仍會跳到
  釋義，那一下點縫也白按。再點一次就正常（此時焦點在空的釋義，不符合跳轉前提）。
